# Stage 11 catalog-vs-code conflicts

## S11-009

- **Catalog claim:** Unmodified FakeAdapter. `controller.abort()` immediately after dispatching `POST /v1/requests` so the event-source signal is already aborted around invocation start; `onAbort` fires before/around invoke; ZERO `ai_attempt` rows; `ai_request.state = 'Cancelled'`; one zero `usage_event`.
- **Code behavior:** Aborting immediately after dispatch (and especially aborting during `clinicPost`'s `mintAat` before `new Request`) cancels `SELF.fetch` before admission — no ingress, no `ai_request`. workerd also throws if an already-aborted signal is passed into `Request` / `SELF.fetch` construction (`adapter.ts` aborted-at-entry is a different path that does not INSERT). The zero-attempt profile is `runInvocation`'s pre-attempt `callerSignal?.aborted` check (`invocation/index.ts:526-533` / `:581-583`) **before** `portResolver` / `invokeWithTimeout` / `recordAttempt`. A FakeAdapter `invoke` delay is already past those checks: abort then writes one `terminal_failure`/`cancelled` attempt (S11-008), not zero.
- **Followed code:** Mint the AAT first; start `clinicFetch` with a live signal; wait until `ai_request` exists (Accepted); abort while the fetch promise is still pending. A 60 ms hold after the real `persistRoutingDecision` (`journal/index.ts:289-303`, called from `worker.ts` before `runInvocation` at `:1104`) keeps the abort in the pre-attempt window. Unmodified FakeAdapter is never entered. Assertions unchanged (zero attempts, Cancelled, usage 0/0).
- **File:line:** `ai-platform/src/invocation/index.ts:526-533` (pre-attempt abort, no `recordAttempt`); `ai-platform/src/invocation/index.ts:581-583` (same, before `attemptNo++`); `ai-platform/src/adapter.ts:482` / `:539-543` / `:559-570` (aborted-at-entry vs live `request.signal`); `ai-platform/src/worker.ts:1093-1118` (`onAbort` + `runInvocation` signal); catalog S11-009; `ai-platform/test/e2e/stage-11-completed-failed-cancelled.test.ts` S11-009.

## S11-010 / S11-011

- **Catalog claim:** Client abort after second-invoke / 250-char `text_delta`; SSE shows `regenerating` (S11-010) or one provisional `text_delta` (S11-011) before the stream dies; no `cancelled` frame on the dead connection.
- **Code behavior:** Aborting `SELF.fetch` while the promise is still pending is required for `hangUntilAbort(options.signal)` to reject `AbortError` (`invokeWithTimeout` inner controller). Awaiting the SSE Response and pumping the body first (original writer) lets the 5 s timer resolve as `scriptedSuccess` — S11-010 attempt #2 `success` 10/20, S11-011 `Completed`. After a pending-fetch abort, workerd discards the unread body (`events = []`), so the client cannot observe frames that were already `controller.enqueue`'d.
- **Followed code:** Same abort-while-pending pattern as S10-013 / S11-008 (wait for invokeEntered / invokeCount≥2 / chunkEmitted, then `controller.abort()`, then settle the fetch). SSE assertions read bytes captured from `ReadableStreamDefaultController.prototype.enqueue` (the adapter `sink.push` path in `adapter.ts:503-518`) — the same frames the client would have read had the body not been torn down. Assertions unchanged.
- **File:line:** `ai-platform/src/invocation/index.ts:349-376` (`options.signal` is the inner timeout controller, aborted only via `callerSignal`); `ai-platform/src/adapter.ts:503-532` (SSE enqueue); `ai-platform/src/stream/index.ts:395` / `:414-418` (regenerating / `text_delta` `provisional: true`); catalog S11-010 / S11-011; `ai-platform/test/e2e/stage-10-route-retry-idempotency.test.ts` S10-013.
