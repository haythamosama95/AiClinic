# Stage 00 catalog-vs-code conflicts

## S00-008

- **Catalog claim:** After harness pre-install of `test.echo@9.9.9` and Stage 3/4/6 with `allowed_capabilities: ["test.echo"]`, discovery lists `test.echo@9.9.9` and not `clinic.visit_summary@1.0.0`. `POST /v1/requests` naming `clinic.visit_summary` resolves to taxonomy `capability_unknown` (HTTP 404).
- **Code behavior:** Guard stage 3 (`evaluateEntitlement`) runs before stage 5 (`resolve`). A request for `clinic.visit_summary` that is not in `allowed_capabilities` (and has no matching grant) is rejected at stage 3 as `forbidden_capability` / `capability_not_granted` (HTTP 403). `capability_unknown` is only produced when resolve misses the registry, which requires stage 3 to pass — so the entitlement must allow (and grant) the missing capability id.
- **File:line:** `ai-platform/src/pipeline/index.ts:359-398` (stage 3 then stage 5); `ai-platform/src/entitlement/index.ts:195-197` (`capability_not_granted`); `ai-platform/src/capability/index.ts:566-577` (`capability_unknown` on registry miss).

## S00-011

- **Catalog claim:** After a warm authenticated `GET /v1/capabilities` listing `clinic.visit_summary@1.0.0`, a Stage 4 re-entitle replacing `allowed_capabilities` with `[]` succeeds (HTTP 200), and the immediate re-GET returns HTTP 200 `{"manifests":[]}` because `CONFIG_CACHE_TTL_MS=0` makes every consult miss.
- **Code behavior:** `handleEntitle` is one-shot: `entitlement.status !== "pending"` returns HTTP 409 `not_pending`. The only `UPDATE entitlement … allowed_capabilities` is that pending→active entitle write; enroll inserts `'[]'` on a new pending row. There is no control route that replaces `allowed_capabilities` on an already-active entitlement (Stage 9 catalog notes mid-period allow-list removal is not a control-plane operation). TTL `0` is also unsafe in this pool (Phase 0: `preloadRoutingPolicyForInstallation` then `consult` throws `ConfigCacheMissError` in the same request). The live mutation that discovery honors after entitle is cohort-activate (`POST /control/capabilities/{id}/versions/{ver}/activate`), which updates the installation grant version; `clearConfigCache()` stands in for TTL 0 so the next discovery re-reads D1 immediately.
- **File:line:** `ai-platform/src/control/entitle.ts:199-201` (`not_pending`); `ai-platform/src/control/entitle.ts:219-234` (the only `allowed_capabilities` UPDATE); `ai-platform/src/control/cohort.ts:145-152` (cohort-activate grant version write); `ai-platform/src/capability/index.ts:717-749` (discovery intersects registry, allow-list, and grant version).

## S00-037

- **Catalog claim:** After a warm authenticated `GET /v1/capabilities` listing `clinic.visit_summary@1.0.0`, Stage 4 re-entitle setting `allowed_capabilities: []` succeeds, the immediate re-GET (within 100 ms) still lists the capability (TTL-stale), and after >100 ms GET returns `{"manifests":[]}` with a different ETag.
- **Code behavior:** Same entitle one-shot as S00-011 (`not_pending` 409; no allow-list rewrite on an active row). The live D1 mutation that discovery honors after entitle is cohort-activate, which **replaces** the installation grant version (`UPDATE capability_grant SET capability_version = ?`). Discovery intersects the **live in-memory registry** with cached D1 grants/entitlements (`capability/index.ts` `discover()`). A post-activate restore of a 1.0.0-only registry before the stale GET yields empty manifests on a cache miss (2.0.0 grants ∩ 1.0.0 registry). Harness TTL is `"100"` (Phase 0: do not use `"0"`). Follow code: install 1.0.0 plus an enterprise `2.0.0` **before** the warm GET; between warm and stale, only `controlFetch` activate (no `setCapabilityRegistry`, no `entitleInstallation`, no `clearConfigCache`); leave 2.0.0 registered until after all GETs. Cached grant 1.0.0 still lists; after TTL a fresh read of grant 2.0.0 is filtered by `minimumPlanTier: "enterprise"` vs enroll plan `standard` → `{"manifests":[]}`.
- **File:line:** `ai-platform/src/control/cohort.ts:145-152` (grant version replace); `ai-platform/src/capability/index.ts:710-749` (registry + allow-list + plan tier + grant overlay); `ai-platform/src/config-cache/index.ts:89-115` (`consult`/`remember` TTL); `ai-platform/test/e2e/harness` `CONFIG_CACHE_TTL_MS="100"`.
