# P3.8 escalations

Assumptions chosen by the resolver. Each one is written into the design docs named below.

## 1. Transfer success results, package columns, and the early transferIn detail

**Question:** `beginTransfer` returns `transfer_id` and `deleteInstallation` describes effects only, but neither is in the 04 §1.2 `ok` list and neither output includes a receipt, so the success `result` is not defined. `transferOut` / `transferIn` return "Package; receipt", but 03 §3.2 gives `transfer` and `transfer_step` no columns and no package field list. `transferIn` before `transferOut` is `transient`, and that `detail` is not one of `unavailable`, `unknown_kid`, `awaiting_transfer`, or `transfer_pending`.

**Assumption:** `beginTransfer` and `deleteInstallation` do not record a grant or a reversal, so a successful call is `ok`: `code` is empty and `receipt` is absent. `beginTransfer` `detail` is the JSON text of the `transfer` row, which includes `transfer_id`. The same assertion challenge is `ok` again and does not insert another row or create another binding. `deleteInstallation` `detail` is the JSON text of `{installation, tenant_binding}` for those rows after the call. It is `ok` again when the installation is already `deleted` and the binding is already in the status that call left it in; a repeat does not create a binding and does not raise AL-18 again. `transferOut` and `transferIn` return `applied` or, on a retry of the same `transfer_id`, `already_applied` with the original receipt. `detail` is the JSON text of the package. The receipt is the §1.6 object with `transfer_id` as the id member, `installation_id` the installation that step wrote, `envelope_sha256` the SHA-256 of the RFC 8785 canonical package, `ledger_seq` the `clinic_seq` of the `transfer` coverage event that step wrote, and `term_ids` the terms that step ended (`transferOut`) or created (`transferIn`). `transferIn` before `transferOut` has applied is `transient` with `detail` `awaiting_transfer_out` and changes nothing. `transfer` columns are `transfer_id` (ULID), `org_id`, `from_installation_id`, `to_installation_id`, `reason`, `assertion_sha256`, `package` (JSON, null until `transferOut`), and `created_at`. `beginTransfer` inserts that row with `package` null and `to_installation_id` set to the new binding. The package is a JSON array ordered by `position`, one object per term that has not ended: `{origin_grant_id, position, state, plan_snapshot, allowance, duration_unit, duration_count, grace_days, grace_cap, calendar_start, starts_at, ends_at, grace_ends_at}`. Queued and held objects copy the stored term. An active object's `allowance` is that term's `allowance` minus `hot.used`; a grace object's `allowance` is min(`allowance` − `grace_base_used`, `grace_cap`) − (`hot.used` − `grace_base_used`). Remaining days are the unelapsed time until the stored `ends_at` (active) or `grace_ends_at` (grace). `transfer_step` columns are `transfer_id`, `step` (`transfer_out`, `transfer_in`), `receipt`, and `applied_at`, unique on (`transfer_id`, `step`), inserted only when that step returns `applied`.

**Why:** The result envelope has no key beyond `contract_version`, `result`, `code`, `detail`, and `receipt`, and `receipt` is present only for `applied` or `already_applied`. Methods that do not record a grant or a reversal already succeed as `ok` with the stored row as JSON `detail`. `beginTransfer` records the authorisation and returns `transfer_id`; the saga then retries `transferOut` and `transferIn` until both report `applied` or `already_applied`, so only those two steps carry a receipt. `deleteInstallation` is idempotent by target state, and the effects it already describes are the installation row and the binding row. 03 §5.4 already puts each not-ended term into the package with its `origin_grant_id`, the active term's remaining days and allowance, and queued and held terms as stored. Grace is not ended, and §6.4 already defines the unused grace allowance from `hot.used` and `grace_base_used`. Later steps take only `transfer_id`, so the authorisation row holds `to_installation_id`. `transferIn` before `transferOut` is a state that clears when `transferOut` applies, which is what `transient` is for; the four existing details name other states, so the detail is `awaiting_transfer_out`.
