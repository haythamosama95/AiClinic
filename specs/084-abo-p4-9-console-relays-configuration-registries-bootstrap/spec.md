## 2. User Scenarios & Testing

### 2.1 User Story 1 - Registries and bootstrap (Priority: P1)

An operator uses the console to bootstrap the first operator credential on an empty registry, then registers a second credential approved by the first. The console runs WebAuthn `create` and forwards the attestation. The first registration has no approving assertion. The second includes the approving assertion. The platform verifies the call. Bootstrap raises AL-13 bootstrap. The second credential stays pending for 24 hours. The same console registers, retires, and revokes issuer keys and registers and revokes ABO service keys. A new issuer `kid` is accepted on AI tokens until revoke, which rejects it within the TTL. The operator registers the next ABO service key, switches the ABO secret, and revokes the old key. Grants continue and AL-23 stays clear. Every action writes one `operator_action` with the Access email as actor.

**Why this priority**: Later configuration relays are class HP and need an operator credential. The issuer and service-key drills are the registry this console owns.

**Independent Test**: E2E-P4.9-01, E2E-P4.9-03, and E2E-P4.9-04 in harness H-XW.

**Acceptance Scenarios**:

1. **Given** an empty operator-credential registry, **When** the operator completes console bootstrap registration, **Then** AL-13 bootstrap fires. **When** a second credential is approved by the first, **Then** that credential is pending for 24 hours. (E2E-P4.9-01)
2. **Given** the console, **When** the operator registers a new issuer `kid` and an AI token is presented with it, **Then** the token is accepted. **When** the operator revokes that `kid`, **Then** tokens with it are rejected within the TTL. (E2E-P4.9-03, K-2, SR-11)
3. **Given** the console, **When** the operator registers the next ABO service key and switches the ABO secret, **Then** grants continue. **When** the operator revokes the old key, **Then** AL-23 stays clear. (E2E-P4.9-04, K-4)

### 2.2 User Story 2 - Configuration relays and support lookup (Priority: P2)

An operator publishes and retires plan versions, sets the ceiling policy, and relays kill switches, routing policy (publish, canary, promote, rollback), cohort, capability lifecycle, and token contract from the console. The platform verifies these calls. A plan version published in the console accepts a paid grant on it. Routing policy seeded from the console sends requests to the fake provider. That seed is the console routing-policy action that replaces `ai-platform/scripts/bootstrap-routing-policy.sh`. A kill switch from the console answers `capability_disabled` and raises AL-19. Support lookup by request reference shows the envelope and is audited with the actor email. Every action writes one `operator_action` with the Access email as actor.

**Why this priority**: User Story 1 registers the credentials and keys these relays use.

**Independent Test**: E2E-P4.9-02, E2E-P4.9-05, E2E-P4.9-06, and E2E-P4.9-07 in harness H-XW. Earlier suites stay green, and E2E-P4.9-01, E2E-P4.9-03, and E2E-P4.9-04 still pass.

**Acceptance Scenarios**:

1. **Given** the console, **When** the operator publishes a plan version, **Then** a paid grant on it is accepted. (E2E-P4.9-02, FR-01)
2. **Given** the console, **When** the operator seeds the routing policy, **Then** requests are routed to the fake provider. (E2E-P4.9-05)
3. **Given** the console, **When** the operator sets a kill switch, **Then** the capability answers `capability_disabled` and AL-19 fires. (E2E-P4.9-06)
4. **Given** a request reference, **When** the operator looks it up from the console, **Then** the lookup shows the envelope and the audit records the actor email. (E2E-P4.9-07)

### 2.4 Edge Cases

- Console bootstrap registration on an empty registry has no approving assertion and raises AL-13 bootstrap. A second credential approved by the first stays pending for 24 hours. (E2E-P4.9-01, 04 §1.3 row `registerOperatorCredential`, 02 §6 row K-7)
- When `operator_credential` is not empty and the approving assertion is absent, `registerOperatorCredential` is `rejected` with code `assertion_required`. The same `credential_id` stored with a different `public_key_cose` is `conflict` with code `public_key_cose_mismatch` and `detail` empty. (04 §1.3 row `registerOperatorCredential`)
- `revokeIssuerKey` sets the `kid` to `revoked`. Tokens for that `kid` are rejected within one config-cache TTL (≤ 30 s). A missing `kid` is `rejected` with code `kid_not_found` and `detail` empty. (E2E-P4.9-03, 02 §6 row K-2, 04 §1.3 row `revokeIssuerKey`, SR-11)
- `retireIssuerKey` on a `revoked` row leaves it `revoked` and is `rejected` with code `kid_revoked` and `detail` empty. A missing `kid` is `rejected` with code `kid_not_found` and `detail` empty. (04 §1.3 row `retireIssuerKey`)
- A `public_key` that is not the base64url encoding of the raw 32-byte Ed25519 public key is `rejected` with code `public_key_invalid` and `detail` empty. The same `kid` stored with a different `public_key` is `conflict` with code `public_key_mismatch` and `detail` empty. This applies to `registerIssuerKey` and `registerServiceKey`. (04 §1.3 rows `registerIssuerKey`, `registerServiceKey`)
- `revokeServiceKey` sets `status` to `revoked`. There is no `retiring` status for the ABO grant key. A missing `kid` is `rejected` with code `kid_not_found` and `detail` empty. After the next key is registered and the ABO secret is switched, grants continue and AL-23 stays clear. (E2E-P4.9-04, 02 §6 row K-4, 04 §1.3 row `registerServiceKey`, `revokeServiceKey`)
- `publishPlanVersion` for a stored `(plan_id, version)` whose `display_name`, `capabilities`, `max_cost_class`, `concurrency_limit`, or `max_allowance_per_month` differs is `conflict` with code `plan_version_mismatch` and `detail` empty. `retirePlanVersion` for a missing `(plan_id, version)` is `rejected` with code `plan_version_not_found` and `detail` empty. (04 §1.3 row `publishPlanVersion`, `retirePlanVersion`)
- A kill switch from the console answers `capability_disabled` and raises AL-19. (E2E-P4.9-06)

## 3. Requirements

### 3.1 Functional Requirements

- **FR-001**: The console bootstraps and registers operator credentials. WebAuthn `create` produces the attestation. `registerOperatorCredential` is class HP, or bootstrap. The input beyond `contract_version` is the WebAuthn attestation and an approving assertion. The approving assertion is absent only while `operator_credential` is empty. Each H and HP method takes `access_jwt`. Each HP method also takes `assertion`, except this bootstrap call while the table is empty. `ok` inserts the row, `pending` for 24 hours, and sets `activates_at` 24 hours ahead. The insert does not set `status` to `active`. The same `credential_id` stored with the same `public_key_cose` is `ok` again and does not insert another row. `conflict` when it is stored with a different `public_key_cose`: `code` is `public_key_cose_mismatch` and `detail` is empty. On `ok`, `detail` is the JSON text of the `operator_credential` row, `code` is empty, and `receipt` is absent. When the table is not empty and the approving assertion is absent, the result is `rejected` with code `assertion_required`. A later registration that includes a valid approving assertion is the normal `ok` insert. It is idempotent by `credential_id`. The first run on an empty registry is console bootstrap registration and raises AL-13 bootstrap. A second credential approved by the first stays pending for 24 hours. Adding a credential is approved by an existing one and is active after 24 hours. (Implements, 04 §1.3 opening sentence and row `registerOperatorCredential`, 02 §6 row K-7, E2E-P4.9-01)
- **FR-002**: The console revokes an operator credential. `revokeOperatorCredential` is class HP. The input is `credential_id`. `ok` when the row becomes `revoked`, and `ok` when it is already `revoked`. `detail` is the JSON text of that `operator_credential` row. `code` is empty and `receipt` is absent. It is idempotent by target state. Any active credential revokes another at once. (05 §3.2 row "Register, retire, or revoke an issuer key; register or revoke a service key or operator credential", 04 §1.3 row `revokeOperatorCredential`, 02 §6 row K-7, Implements)
- **FR-003**: The console registers, retires, and revokes issuer keys. `registerIssuerKey` is class HP. The input is `kid`, `public_key`, `not_before`, and `not_after`. `public_key` is the base64url encoding of the raw 32-byte Ed25519 public key. `ok` inserts `status` `active`, stores that `public_key` unchanged, sets `issuer` to the configured issuer id, `registered_by` to the Access email, and `assertion_sha256` to the assertion challenge hash. The same `kid` with the same `public_key` is `ok` again and does not insert another row or change `status`. `conflict` when that `kid` is stored with a different `public_key`: `code` is `public_key_mismatch` and `detail` is empty. A `public_key` that is not that encoding is `rejected` with code `public_key_invalid` and `detail` empty. On `ok`, `detail` is the JSON text of the `issuer_key` row, `code` is empty, and `receipt` is absent. This call does not set `retiring`. It is idempotent by `kid`. `retireIssuerKey` is class HP. The input is `kid`. `ok` sets `status` from `active` to `retiring`, and `ok` when it is already `retiring`. Tokens for that `kid` stay accepted until `not_after`. A missing `kid` is `rejected` with code `kid_not_found` and `detail` empty. A `revoked` row stays `revoked` and the result is `rejected` with code `kid_revoked` and `detail` empty. On `ok`, `detail` is the JSON text of the `issuer_key` row, `code` is empty, and `receipt` is absent. This is the only writer of `retiring`. It is idempotent by target state. Routine rotation generates the next `kid`, adds its public key to the ABO's pinned `ISSUER_KEYS` by config deploy, registers it on the platform, switches signing once both accept it, and after 10 minutes (the longest token life) `retireIssuerKey` sets the old `kid` to `retiring`. That `kid` stays accepted until `not_after`. `revokeIssuerKey` is class HP. The input is `kid`. `ok` sets `status` to `revoked`, and `ok` when it is already `revoked`. It does not set `retiring`. A missing `kid` is `rejected` with code `kid_not_found` and `detail` empty. On `ok`, `detail` is the JSON text of the `issuer_key` row, `code` is empty, and `receipt` is absent. It is idempotent by target state. Emergency revocation sets the `kid` to `revoked`, and that `kid` is rejected within one config-cache TTL (≤ 30 s). The K-2 drill registers a new issuer `kid`, accepts AI tokens with it, then revokes it so those tokens are rejected within the TTL. (Implements, 05 §3.2 row "Register, retire, or revoke an issuer key; register or revoke a service key or operator credential", 04 §1.3 rows `registerIssuerKey`, `retireIssuerKey`, `revokeIssuerKey`, 02 §6 row K-2, E2E-P4.9-03, SR-11)
- **FR-004**: The console registers and revokes ABO service keys. `registerServiceKey` is class HP. The input is `kid`, `public_key`, `not_before`, and `not_after`. Those two timestamps are the validity, UTC ISO-8601. `public_key` is the base64url encoding of the raw 32-byte Ed25519 public key. `ok` inserts `status` `active`, stores that `public_key` unchanged, sets `service` to `abo`, `not_before` and `not_after` to the supplied validity, `registered_by` to the Access email, and `assertion_sha256` to the assertion challenge hash. The same `kid` with the same `public_key` is `ok` again and does not insert another row or change `status` or the stored validity. `conflict` when that `kid` is stored with a different `public_key`: `code` is `public_key_mismatch` and `detail` is empty. A `public_key` that is not that encoding is `rejected` with code `public_key_invalid` and `detail` empty. `revokeServiceKey` is class HP. The input is `kid`. `ok` sets `status` to `revoked`, and `ok` when it is already `revoked`. A missing `kid` is `rejected` with code `kid_not_found` and `detail` empty. On `ok`, `detail` is the JSON text of the `service_key` row, `code` is empty, and `receipt` is absent. `revokeServiceKey` is the only writer of `revoked`. Register is idempotent by `kid`. Revoke is idempotent by target state. Routine rotation registers the next public key on the platform, switches the secret, and revokes the old one. There is no `retiring` status. Each attempt signs with the current key, so pending grants need no rework. The ABO checks at isolate start, and hourly, that its signing `kid` is `active` and not expired. If it is not, the ABO pauses `grant` and `reverse` work and raises AL-23. The K-4 drill registers the next ABO service key, switches the ABO secret, grants continue, revokes the old key, and AL-23 stays clear. (Implements, 05 §3.2 row "Register, retire, or revoke an issuer key; register or revoke a service key or operator credential", 04 §1.3 row `registerServiceKey`, `revokeServiceKey`, 02 §6 row K-4, E2E-P4.9-04)
- **FR-005**: The console publishes and retires plan versions. `publishPlanVersion` and `retirePlanVersion` are class HP, verified by the AI Platform. `publishPlanVersion` input is `plan_id`, `version`, `display_name`, `capabilities`, `max_cost_class`, `concurrency_limit`, and `max_allowance_per_month`. `retirePlanVersion` input is `plan_id` and `version`. `publishPlanVersion` `ok` inserts `status` `published` and sets `published_by` to the Access email and `assertion_sha256` to the assertion challenge hash. The same `(plan_id, version)` with the same `display_name`, `capabilities`, `max_cost_class`, `concurrency_limit`, and `max_allowance_per_month` is `ok` again and does not insert another row or change `status` or those fields. `conflict` when that pair is stored with a different value in any of those fields: `code` is `plan_version_mismatch` and `detail` is empty. `retirePlanVersion` `ok` sets `status` from `published` to `retired`, and `ok` when it is already `retired`. A missing `(plan_id, version)` is `rejected` with code `plan_version_not_found` and `detail` empty. On `ok`, `detail` is the JSON text of the `plan_version` row, `code` is empty, and `receipt` is absent. `retirePlanVersion` is the only writer of `retired`. Publish is idempotent by `(plan_id, version)`. Retire is idempotent by target state. A plan version published in the console accepts a paid grant on it. (05 §3.2 row "Publish or retire a plan version; set the ceiling policy", 04 §1.3 row `publishPlanVersion`, `retirePlanVersion`, Implements, E2E-P4.9-02, FR-01)

## 4. Constitution Alignment

### 4.1 Architecture & Operations Impact

- **Clinic Fit**: An operator publishes the plan a clinic can be granted, sets the ceiling, registers the keys and credentials that admit that clinic, and can stop a capability or look up one request. The unit adds no second clinic product and no clinic-desktop flow.
- **Layer Placement**: Codebase is `abo`. No wiring exception is named. The live entry is `opsFetch` → `SELF.fetch` on the ABO worker for the ops host `/ops/*` (`abo/src/worker.ts` `handleOps`). Relays call the real platform `VendorEntrypoint` over the `PLATFORM` binding (`ai-platform/src/vendor/entrypoint.ts`). AI-token, routing, and kill-switch outcomes are `POST /v1/requests` on that platform worker. The paid grant and the ABO secret switch use the existing grant path and `ABO_GRANT_KEY`. H-XW runs that platform worker from source. `plan.md` re-runs the constitution check in 02 §7 (rule S12).
- **Data Integrity & Security**: These relays are verified by the AI Platform. The console forwards the Access JWT. Each HP method also forwards `assertion`, except bootstrap `registerOperatorCredential` while the credential table is empty. One `operator_action` is written per action. The platform call writes `control_audit` with the Access email as actor. (05 §3.2, 04 §1.3)
- **Failure Handling**: A second credential stays pending for 24 hours (E2E-P4.9-01). A revoked issuer `kid` is rejected within one config-cache TTL (≤ 30 s) (E2E-P4.9-03, 02 §6). A kill switch answers `capability_disabled` and raises AL-19 (E2E-P4.9-06). The service-key drill keeps AL-23 clear (E2E-P4.9-04). Platform refusals on these relays keep the codes in the cited 04 §1.3 rows: `assertion_required`, `public_key_cose_mismatch`, `public_key_invalid`, `public_key_mismatch`, `kid_not_found`, `kid_revoked`, `plan_version_mismatch`, and `plan_version_not_found`.
