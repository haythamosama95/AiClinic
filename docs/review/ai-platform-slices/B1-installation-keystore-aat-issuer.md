# Slice Review Report — B1: Installation Keystore and AAT Issuer

**Spec:** `specs/021-installation-keystore-aat-issuer/spec.md` · **Branch:** `021-b1-installation-keystore-aat-issuer` · **Canonical:** §4.2, §4.2.1, §8.1, §5.6

## Executive Summary

B1 delivers the §4.2 clinic-side pair in three migrations: a restricted `ai_internal` keystore and issuance ledger with grant- and RLS-level denial to `anon`/`authenticated`, additive key rotation with revocation, and a `SECURITY DEFINER` issuer that verifies the session, derives every §5.6 claim — including `scopes` from `roles_permissions` with the caller-supplied `p_scopes` correctly ignored — mints an `alg: EdDSA` JWS via `pgsodium.crypto_sign_detached`, records issuance, and rate-limits itself. The happy paths are tested in the SQL/RLS layer the delivery plan names. The most consequential gap sits outside the tests' view: §8.1 requires enrollment to hand the operator the installation id, `kid`, **and public key (JWK)** for the platform enroll call, but neither `enroll_installation_keypair` nor `rotate_installation_key` returns the public key, and the keystore is unreadable by design — the trust bootstrap dead-ends at exactly the step this slice owns. Underneath that: the issuer rate limiter is a check-then-insert race, rotation key selection can tie on transaction-time `valid_from`, and the clinic verifier throws on malformed tokens instead of rejecting them. Test-wise, the rejection tests (T09, T11) pass on *any* exception and so do not pin the gates they name, the non-negotiable `alg: EdDSA` header is never decoded by any test, four of the issuer's seven error codes and the admin-gating branch of every keypair routine have no case, and the §5.6 deliberate omissions are unasserted.

## Critical Issues

1. **The public key never leaves the database, so §8.1 enrollment cannot be completed** (`backend/supabase/migrations/20260801120100_ai_installation_keypair_routines.sql:57-62` and `:127-132`). §8.1's sequence has the clinic Supabase return "installation id + kid + public key (JWK OKP/Ed25519)" to the operator, who then posts that public key to the gateway's control-plane enroll; contract §7 repeats that the key "is published to the platform during enrollment and on rotation". Both routines return only `kid` and `installation_id`. Because the keystore denies reads to every non-definer role (FR-001, correctly), there is no other path to the public key: a repo-wide search finds `public_key` referenced only at insert time and inside `verify_aat` (`20260801120200_ai_token_issuer_rpc.sql:342`). The operator literally cannot construct the enrollment payload, and rotation — which §8.1 says "repeats these three steps" — cannot deliver the successor key to the platform either. The clinic-side output of the trust bootstrap, the part of §8.1 this slice's own scope statement claims, is missing; the one-directional trust the whole band depends on is never actually established end to end.

## Bugs

1. **Issuer rate limiter is a check-then-insert race** (`20260801120200_ai_token_issuer_rpc.sql:198-207` counts, `:258-273` inserts). Two concurrent calls from the same actor both observe `v_recent_mints < v_rate_ceiling` and both mint; nothing serializes the count against the ledger insert (no advisory lock, no insert-first-then-count, no constraint). A compromised client — the exact threat §4.2 names for "rate-limited itself" — can exceed the ceiling by parallelizing requests. At clinic scale the window is small, but the invariant the ceiling exists to provide is not actually enforced.
2. **Rotation key selection ties on transaction-time `valid_from`** (`20260801120200_ai_token_issuer_rpc.sql:177-183`; rows stamped with `now()` at `20260801120100_ai_installation_keypair_routines.sql:41-42` and `:112-113`). `now()` is transaction-start time, so an enroll + rotate (or two rotations) inside one transaction produce keys with identical `valid_from` — and identical `created_at`, the only other timestamp — leaving `ORDER BY valid_from DESC LIMIT 1` to pick the "current" signing key nondeterministically. The tests themselves enroll and rotate within a single transaction (`ai_keystore_rls.sql:296-303`), and no test asserts which `kid` signs after rotation, so the tie is both real and invisible. There is no monotonic tie-breaker and no single-current-key constraint.
3. **`verify_aat` throws instead of returning `false` on a malformed signature segment** (`20260801120200_ai_token_issuer_rpc.sql:337`). The header decode is wrapped in a guard that returns `false` on garbage (`:311-319`), but the signature's `base64url_decode` sits outside any exception block, and a wrong-length or undecodable signature passed on to `pgsodium.crypto_sign_verify_detached` (`:339-343`) can raise as well. A tampered or truncated token — the routine case for a verifier — produces a SQL error rather than a rejection, and T06-style callers must handle both outcomes.
4. **`verify_aat` never binds the payload `iss` to the key row** (`20260801120200_ai_token_issuer_rpc.sql:321-334`). The verifier loads the key by header `kid` alone and never decodes the payload; a token whose header references a valid `kid` but whose `iss` names a different installation verifies cleanly. Contract §8.3 is explicit that "`iss` plus `kid` together select the verification public key" (exact match on `kid` *against the enrolled key set for payload `iss`*), and §5.6 gives `iss` the purpose "selects the verification key". The clinic self-test implements only half of the frozen selection rule.

## Architectural Deviations

1. **The issuer abandons the repo's structured error contract, inconsistently with its own sibling routines** (`20260801120200_ai_token_issuer_rpc.sql:88`, `:106`, `:148`, `:159`, `:174`, `:186`, `:206`, `:221`). Every issuer failure is a bare `RAISE EXCEPTION 'CODE'`, surfacing through PostgREST as a P0001 whose only payload is the message text, while the keypair routines in the adjacent migration return `public.rpc_error('FORBIDDEN', ...)` through the established `rpc_result` envelope (`20260801120100_ai_installation_keypair_routines.sql:57-69`). The slice therefore ships two error conventions for one component group, and clients must string-match SQLERRM to distinguish `RATE_LIMITED` from `SESSION_EXPIRED`. The keypair routines themselves detect `FORBIDDEN` by `SQLERRM = 'FORBIDDEN'` string comparison (`:65`, `:135`, `:186`) — fragile, but at least they convert to structured errors; the issuer does not convert at all.
2. **Current-key selection is not scoped to an installation, and the one-installation invariant exists only by convention** (`20260801120200_ai_token_issuer_rpc.sql:177-183`). The issuer picks the latest non-revoked key across *all* rows with no `installation_id` filter; enroll reconstructs the installation id from the earliest existing key (`20260801120100_ai_installation_keypair_routines.sql:19-28`), so a second installation can only arise from a direct insert — yet nothing in the schema (no unique constraint, no singleton guard) prevents it, and if it ever happened the issuer would silently sign with whichever installation's key is newest while the ledger attributes issuance to that same row. §4.2 models one installation per clinic; the schema should say so.
3. **The frozen clinic-verifier contract omits any `exp` check, making the "validity window" the done-when names untestable** (`specs/021-installation-keystore-aat-issuer/contracts/aat-token.md:159-167`). B1's done-when requires "a token signed by the previous key still verifies *inside its validity window*", and T05 is named for it, but contract §6.3's verification steps — which the implementation follows exactly — never look at `exp`, so an expired token verifies just as happily. Either the clinic self-test should check `exp` (and the contract should say so) or the validity-window language belongs to B3's gateway verifier; as frozen, the contract and the done-when talk about two different things. Documentation/contract issue: the architecture's §5.6 "short lifetime" intent is not pinned anywhere this slice tests.
4. **Grant hygiene around the new schema drifts from the cited pattern** (`20260801120000_ai_keystore_schema.sql:8`, `:13`). `GRANT USAGE ON SCHEMA ai_internal TO service_role` is justified by no cited section — §8.1's whole point is that the platform has no path into the clinic — and `service_role` bypasses RLS regardless, so the grant only widens direct table reach for a role that should not need it. `GRANT pgsodium_keymaker TO postgres` is a no-op for the superuser (§4.2.1 names the *enrollment role* holding keymaker). And none of the new `auth_internal` functions revokes the default `PUBLIC` EXECUTE grant (`20260801120100_ai_installation_keypair_routines.sql:5-191`, `20260801120200_ai_token_issuer_rpc.sql:5-345`), so the `public` INVOKER wrappers are bypassable by any role with schema usage — the gates inside the functions make this low-risk, but the F4 wrapper pattern exists precisely to make the wrapper the only entry point.

## Missing or Weak Tests

1. **T09 proves nothing about the session gate** (`backend/tests/ai_token_issuer.sql:139-147` and `:153-161`). Both halves treat `WHEN OTHERS` as success, and the block deliberately runs *before* enrollment — so if the session check were deleted outright, the absent-session call would still raise `STAFF_NOT_FOUND` and the expired-session call `INSTALLATION_NOT_ENROLLED`, and the test would still pass. Neither `UNAUTHENTICATED` nor `SESSION_EXPIRED` is asserted. The one test guarding the §4.2 "verify the caller's session" requirement cannot fail when the gate is removed.
2. **T11 has the same vacuous-rejection shape, and per-actor scoping is untested** (`ai_token_issuer.sql:316-320`). Any exception from the third mint — not specifically `RATE_LIMITED` — marks the test green. Nothing asserts a *different* actor remains able to mint while the first is limited, though §5.6's `sub` note ("per-actor rate limits") is the stated semantics of the ceiling.
3. **No test decodes the JWS header.** The contract pins `alg: EdDSA` (non-negotiable — a verifier accepting `none` or HMAC "is accepting a forgery", §5.6) and `kid` "by contract test T07", but T07 decodes only the payload (`ai_token_issuer.sql:196-197`); `pg_temp.decode_jws_payload` reads segment 2 by construction (`:13-30`). The single most security-critical field of the token is never asserted.
4. **Four of the issuer's seven error codes have no test, and the admin gate on every keypair routine is untested.** Untested issuer branches: `STAFF_NOT_FOUND` (`20260801120200_ai_token_issuer_rpc.sql:148`, `:159`), `BRANCH_NOT_FOUND` (`:174`), `INSTALLATION_NOT_ENROLLED` (`:186`), `AI_ACCESS_DENIED` (`:221`). Untested keypair branches: `FORBIDDEN` for a non-administrator on enroll/rotate/revoke — a security branch, not a formality — plus `INVALID_INPUT` and `KEY_NOT_FOUND` on revoke (`20260801120100_ai_installation_keypair_routines.sql:154-166`) and rotate's `INSTALLATION_NOT_ENROLLED` (`:93-98`). The coverage rule requires one case per emittable error code; the suite covers three of eleven.
5. **T05's "within its validity window" is vacuous** (`ai_keystore_rls.sql:295-312`). `verify_aat` has no `exp` logic (Deviation 3), so the test would pass identically for a token minted an hour past expiry. The rotation half of T05 is genuine; the window half tests nothing.
6. **No test asserts post-rotation mints are signed by the new key.** T04 checks row presence and distinct `kid`s (`ai_keystore_rls.sql:212-224`) and T05 verifies an old-key token; neither mints *after* rotation and inspects the header `kid`. Combined with Bug 2's `valid_from` tie, the contract §8.3 signing-selection rule ("non-revoked key with greatest `valid_from`") is unverified — and in the same-transaction test shape, unverifiable as written.
7. **T07 asserts presence, not correctness** (`ai_token_issuer.sql:199-213`). A payload with `aud: "wrong"`, another actor's `sub`, or a fabricated `iss` passes as long as nothing is null. FR-008 (`aud` must be the AI platform audience), FR-009 (`jti` unique — two mints are never compared), and the claim-source mapping in contract §4 are all unverified; T08's scopes assertion is likewise containment-only (`:243-244`), not equality with the RBAC-derived set.
8. **No test asserts the §5.6 deliberate omissions.** Nothing decodes a payload and checks for the absence of patient identifiers, quota state, or provider/model hints — an inherited prohibition the coverage rule explicitly includes, and the cheapest possible regression to introduce (one extra `jsonb_build_object` line in the issuer).
9. **The suites COMMIT mutated global state** (`ai_token_issuer.sql:298-305` sets ceiling 2, `:343-347` restores only the ceiling; `ai_keystore_rls.sql:96-101` and four later blocks `DELETE FROM` every key and issuance row). The ceiling/window the tests leave behind depends on execution order — T11 without T12 strands ceiling 2 — and the wholesale deletes are destructive against any database that is not a disposable test fixture. The fixture transactions should roll back or restore every config key they touch.

## Recommended Improvements

- **Return the public key from enroll and rotate** (`20260801120100_ai_installation_keypair_routines.sql:57-62`, `:127-132`): add the raw 32-byte public key to the `rpc_success` payload, ideally pre-encoded as the contract §7 JWK (`{"kty":"OKP","crv":"Ed25519","x":<base64url>,"kid":...}`) so the operator's enrollment payload is constructed by the same code that owns the encoding rules. Without this the §8.1 sequence cannot run; this is the one change that unblocks the trust bootstrap.
- **Close the rate-limiter race** (`20260801120200_ai_token_issuer_rpc.sql:198-207`): take a `pg_advisory_xact_lock` on the actor id before counting, or insert-then-count-and-rollback, so the ceiling holds under concurrent calls.
- **Make current-key selection deterministic and installation-scoped**: filter by `installation_id`, tie-break `valid_from` with a monotonic column (or store an explicit `is_current`/sequence), and enforce one installation per clinic in the schema (`20260801120200_ai_token_issuer_rpc.sql:177-183`; `20260801120000_ai_keystore_schema.sql:48-63`).
- **Harden `verify_aat`** (`20260801120200_ai_token_issuer_rpc.sql:296-343`): wrap the signature decode and `crypto_sign_verify_detached` so any malformed input returns `false`; decode the payload and require `iss` to equal the key row's `installation_id` per contract §8.3; then resolve with the contract whether the clinic self-test should also evaluate `exp` (Deviation 3).
- **Pick one error convention for the slice**: either route the issuer through `rpc_result` like its sibling routines, or document the bare-exception contract in `contracts/aat-token.md` §9 and have the tests assert specific SQLERRM codes — and replace the `SQLERRM = 'FORBIDDEN'` string matches with `RAISE EXCEPTION ... USING ERRCODE` + SQLSTATE checks (`20260801120100_ai_installation_keypair_routines.sql:65`, `:135`, `:186`).
- **Strengthen the rejection tests**: in T09 and T11 assert the specific error text (`UNAUTHENTICATED`, `SESSION_EXPIRED`, `RATE_LIMITED`) instead of `WHEN OTHERS`; add a second-actor mint to T11; run T09 after enrollment so the session gate is the only thing that can reject (`ai_token_issuer.sql:123-170`, `:289-329`).
- **Add the missing cases**: header decode (`alg = 'EdDSA'`, non-null `kid`); one test per untested error code (`STAFF_NOT_FOUND`, `BRANCH_NOT_FOUND`, `INSTALLATION_NOT_ENROLLED`, `AI_ACCESS_DENIED`, keypair `FORBIDDEN`/`INVALID_INPUT`/`KEY_NOT_FOUND`); a non-administrator denied enroll/rotate/revoke; post-rotation mint signed by the new `kid`; deliberate-omissions assertion on the decoded payload; value assertions in T07 (`aud`, `sub`, `iss`) and `jti` uniqueness across two mints.
- **Tighten grants and test hygiene**: drop the `service_role` schema grant and the no-op keymaker grant (`20260801120000_ai_keystore_schema.sql:8`, `:13`); `REVOKE EXECUTE ... FROM PUBLIC` on the new `auth_internal` functions so the wrappers are the only entry; make both suites restore (or roll back) every config key and fixture row they mutate.
