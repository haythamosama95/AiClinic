# Slice Review Report — E1: Client Architecture Guard in CI

**Spec:** `specs/035-client-arch-guard-ci/spec.md` · **Branch:** `ai/035-e1-client-arch-guard-ci` · **Canonical:** §13.5, §3.4.1, R-12

## Executive Summary

E1 delivers the artifacts its slice names: a standalone Dart guard script (`frontend/tool/architecture_guard/architecture_guard.dart`) that scans client sources for prompt-like strings, provider names, and model identifiers and exits non-zero on matches; three deliberately failing fixtures, one per forbidden category; a dedicated step in `.github/workflows/ci.yml` that runs expect-fail invocations against the fixtures and an expect-success invocation against the clean tree with a coverage assertion; and a hardcoded coverage check that every Dart file under the declared client source roots lies inside a scan root. The clean tree genuinely passes today (no near-miss strings exist under `frontend/lib`), and the fixture strings do trip the patterns. The substantive failures are in placement and proof rather than in the script's core loop. First, the guard is wired into a workflow whose triggers (`push` to `main`/`master`/`001-*`/`feature/*`, `pull_request` to `main`/`master`) never fire on the branch line this guard exists to protect — the current checkout is `ai/master` and every slice branch is `ai/NNN-*` — so the R-12 defence is dormant on exactly the pushes where E2+ client AI code will arrive, contradicting DP-6's "the guard must precede the code it guards." Second, the expect-fail fixture steps accept *any* non-zero exit as proof: a deleted or renamed fixture directory makes the script exit 2 ("scan root not found") and the CI loop records that as a successful proof, so the "proven by a deliberately failing fixture" done-when can silently become vacuous while CI stays green. Third, the detection surface misses the highest-probability real violations: the platform's own integrated provider (DeepSeek, per the D5 slice) and its model identifiers match no pattern, and current Anthropic model naming (`claude-sonnet-4-5`) escapes `\bclaude-\d`. Finally, the T5 "covers every client source path" assertion is tautological — it checks a hardcoded two-entry root list against a hardcoded two-entry default, both limited to Dart files — so non-Dart client sources that ship in or build the desktop client (`windows/runner/*.cpp`, `web/index.html`, `web/*.json`, `linux/`) are outside the guard entirely, and any future source root is invisible to both the scan and the assertion.

## Critical Issues

1. **The guard never runs on the branch line it exists to protect — the R-12 defence is dormant for the entire AI development workflow** (`.github/workflows/ci.yml:3-7`). The workflow triggers on `push` to `[main, master, "001-*", "feature/*"]` and `pull_request` to `[main, master]`. The AI Platform program is developed on `ai/NNN-<slice>` branches (this slice: `ai/035-e1-client-arch-guard-ci`; the integration checkout is `ai/master`, per `AGENTS.md` and `git branch --show-current`). No push to any `ai/*` branch, and no pull request targeting `ai/master`, triggers this workflow — so the architecture-guard step (`ci.yml:33-55`) executes only when work eventually PRs into `main`/`master`. The architecture requires the guard to exist "before any AI code is written in the client, not after" (§13.5, lines 3638-3640) and DP-6 states "the guard must precede the code it guards"; R-12's mitigation is "Architectural test in CI that fails on prompt-like strings, provider names, or model identifiers in client code." A guard that does not execute on the branches where E2+ client AI code will actually be pushed precedes the code in merge order but not in enforcement: a prompt fragment committed on an `ai/*` slice branch under deadline pressure — the exact failure mode §3.4.1 names — passes every check that branch ever runs. FR-006 ("The architecture guard MUST exist in CI before any AI code is written in the client") is satisfied on paper and unsatisfied on the only CI line where client AI code will appear.

2. **The expect-fail fixture steps treat any non-zero exit as proof — a missing or renamed fixture silently turns T1–T3 vacuous while CI stays green** (`.github/workflows/ci.yml:42-48`; `frontend/tool/architecture_guard/architecture_guard.dart:124-127`). The loop runs `dart $guard $fixture` and fails only when `$LASTEXITCODE -eq 0`. But the script has a second non-zero exit path: `_scanDirectory` calls `exit(2)` when a scan root does not exist (`architecture_guard.dart:124-127`). If any fixture directory is deleted, renamed, or moved in a later refactor, the script exits 2, the loop's `-eq 0` check is false, and CI records the "deliberately failing fixture" proof as passed. The done-when — "proven by a deliberately failing fixture" (delivery plan §3.6) and FR-005 ("fixtures … each of which fails the build") — then holds vacuously: nothing is being detected, yet all three named tests report green. The same hole accepts a Dart compilation failure of the guard script on the fixture invocations (any non-zero counts), though that specific case is caught downstream by the clean-tree run. The expected-failure contract must be exit code exactly 1 (violations detected); exit 2 and any other non-zero/non-one code are guard-machinery failures and must fail the step.

## Bugs

1. **The platform's own integrated provider is undetectable — `deepseek` and its model identifiers match no pattern** (`frontend/tool/architecture_guard/architecture_guard.dart:24-30`, `:33-38`). The provider list is `openai`, `anthropic`, `gemini`, `cohere`, `mistral`; the model list is `\bgpt-\d`, `\bclaude-\d`, `\bgemini-\d`, `\bo\d-\w+`. The provider this platform actually integrated first is DeepSeek (D5 slice: `ai-platform/src/provider/deepseek.ts`, `api.deepseek.com`), with wire model identifiers such as `deepseek-chat` / `deepseek-reasoner`. None of these strings matches any pattern: `deepseek` is absent from `_providerPatterns`, and `deepseek-chat` matches none of `_modelPatterns`. R-12 exists to stop "prompt fragments or model names creep[ing] into the Flutter app," and the statistically most likely strings to creep in are the provider and model names the platform itself uses — a client-side constant, debug string, or comment referencing `deepseek-chat` passes the guard clean. The T2/T3 fixtures (`fixtures/provider_name/forbidden.dart:5` uses `'openai'`; `fixtures/model_identifier/forbidden.dart:5` uses `'gpt-4o'`) prove the categories only with providers the platform does not use.

2. **Current Anthropic model naming escapes the model-identifier patterns** (`frontend/tool/architecture_guard/architecture_guard.dart:34-36`). `\bclaude-\d` requires a digit immediately after the hyphen; Anthropic's current identifiers place letters there — `claude-sonnet-4-5`, `claude-opus-4-1`, `claude-haiku-4-5` — so all of them pass. `\bgemini-\d` catches `gemini-2.5-pro` but not `gemini-pro` or `gemini-flash-latest`; bare capability names (`sonnet`, `opus`, `haiku`) match nothing at all. A guard whose model patterns only catch OpenAI-style versioned ids under-detects the category FR-003 names ("model identifiers … anywhere in client code").

3. **Per-line matching against contiguous-phrase patterns is trivially evaded by ordinary Dart string forms** (`frontend/tool/architecture_guard/architecture_guard.dart:138-141`, `:16-21`). The scanner splits content on `'\n'` and matches each line independently, and the prompt patterns require the full phrase on one line. Adjacent string literals (`'You are a helpful ' 'assistant that summarizes clinical notes.'`), explicit concatenation, string interpolation assembling the phrase from parts, and multi-line strings that break the phrase across lines all evade every prompt pattern while producing the identical runtime string. The same applies to provider/model patterns split across tokens (`'open' 'ai'`, `'gpt-' '4o'`). Regex-over-source cannot fully close this, but the current form doesn't even attempt the cheap mitigation (matching against the full file content with whitespace-tolerant patterns), so the most natural way prompt text enters a Dart file — a multi-line `'''` string — is also the least detectable.

4. **`exit(2)` on a missing scan root fires mid-scan and conflates operator error with the guard's detection signal** (`frontend/tool/architecture_guard/architecture_guard.dart:124-127`). `_scanDirectory` terminates the process on the first missing root, so in a multi-root invocation later roots are never scanned and earlier roots' violations are never reported; and because the script's contract distinguishes "clean" (0) from "violations" (1) but callers (per Critical 2) do not distinguish 1 from 2, the operator-error path is indistinguishable from a detection at the CI call site. A guard that is itself an architectural component should fail loudly and distinctly on misconfiguration.

## Architectural Deviations

1. **The guard covers only Dart files under `lib/` and `test/` — non-Dart sources that ship in or build the desktop client are outside the prohibition's enforcement** (`frontend/tool/architecture_guard/architecture_guard.dart:9-12`, `:132-134`). The scan skips every non-`.dart` file (`:132-134`), and `clientSourceRoots` is `['lib', 'test']` (`:12`). Yet the desktop client ships and is built from more than that: `frontend/windows/runner/main.cpp`, `flutter_window.cpp`, and the CMake runner (C++ that builds the desktop executable), `frontend/linux/`, and `frontend/web/index.html`, `manifest.json`, `deployment-profile.json` (verified present on disk). A prompt fragment, provider name, or model identifier placed in any of these reaches the client binary path with no check. The done-when is "anywhere in client code" (delivery plan §3.6), §3.4.1 names "the Flutter codebase," and the spec's own Assumptions define client source as "the Flutter application sources under `frontend/` that ship in or build the desktop client" — the `windows/` runner unambiguously *builds the desktop client*. The spec granted include/exclude latitude only "so long as T5 still proves every client source path is covered"; T5 (see Deviation 2) cannot prove coverage of paths that are not in `clientSourceRoots`, so the latitude does not license the exclusion. This is also a spec-vs-architecture narrowing the spec never flags: the architecture's "Flutter codebase" / "anywhere in client code" is broader than the Dart-only surface the plan froze ("primarily `frontend/lib/`"), and the architecture takes precedence.

2. **The T5 full-coverage assertion is tautological and cannot detect a new or dropped source root** (`frontend/tool/architecture_guard/architecture_guard.dart:9-12`, `:172-209`). `_assertFullCoverage` enumerates Dart files under `clientSourceRoots` (`['lib', 'test']`) and checks each lies under the configured scan roots — which default to `defaultScanRoots` (`['lib', 'test']`), the same two-entry literal. The assertion therefore proves only that two hardcoded lists agree with each other. Two real failure modes are invisible: (a) a new client source root (an `integration_test/` directory, a new Dart package under `frontend/`, generated plugin code outside `.dart_tool`) is in neither list, so nothing scans it and nothing flags it — there is no discovery step that enumerates all client sources and asserts each is scanned or explicitly excluded; (b) dropping `'test'` from *both* constants simultaneously shrinks the scan and passes coverage, the exact "placing forbidden content outside a narrow scan root" bypass FR-004 exists to prevent. SC-005 ("The guard's configured scan covers every client source path") and spec acceptance scenario 5 ("no client source path is omitted") are asserted of a self-referential configuration, not of the tree.

## Missing or Weak Tests

1. **T1–T3 are exit-code-agnostic and category-indistinguishable in CI** (`.github/workflows/ci.yml:42-48`). One loop body serves all three named tests, logs a single generic message ("guard_prompt_like_string_fails_build / provider / model"), and checks only `$LASTEXITCODE -eq 0`. Nothing asserts the exit code is exactly 1 (Critical 2), and nothing asserts the reported violation category matches the fixture under test — a regression that flagged the provider fixture only as a "prompt-like string," or that detected the wrong pattern class in all three fixtures, would leave `guard_provider_name_fails_build` and `guard_model_identifier_fails_build` green. The named tests exist to prove three distinct detection branches (spec Test plan T1/T2/T3, one per forbidden category); the CI step cannot tell them apart. The script emits the category on stderr (`architecture_guard.dart:145-165`) but the workflow never inspects it.

2. **The T5 omission case is never exercised** (`.github/workflows/ci.yml:50-55`; `architecture_guard.dart:58-68`). The spec defines T5 as "omitting a client source path from configured scan roots fails the assertion (non-zero exit)" (plan Test Layout; spec acceptance scenario 5). CI only ever runs the coverage assertion in the configuration where it passes (`dart $guard --assert-coverage` with defaults). No job, fixture, or controlled invocation removes a root (or plants a Dart file outside the roots) and expects failure — so the assertion's only behavioural proof is that it doesn't fire when nothing is wrong; that it *would* fire on an omission is untested, and per Deviation 2 the assertion's reference list is itself hardcoded. Half of the named boundary's behaviour (the failing branch) has no test.

3. **The three fixtures prove only the easiest member of each category, and not the provider the platform uses** (`fixtures/prompt_like_string/forbidden.dart:5-6`; `fixtures/provider_name/forbidden.dart:5`; `fixtures/model_identifier/forbidden.dart:5`). The prompt fixture is the literal pattern string `'You are a helpful assistant…'`; the provider fixture is `'openai'`; the model fixture is `'gpt-4o'` — each is the exact canonical form its regex was written against. There is no fixture for the integrated provider (`deepseek` / `deepseek-chat` — Bug 1), none for current Anthropic naming (`claude-sonnet-4-5` — Bug 2), and none for the evasion shapes Bug 3 names (adjacent literals, multi-line strings, interpolation). Under the coverage rule (delivery plan §3.10: "every branch of every rule … behaviourally"), the three detection branches are each proven at a single point that happens to be the point the implementation was written to pass — the fixtures confirm the patterns compile, not that the categories are detected.

4. **No case proves each configured scan root is actually scanned** (`architecture_guard.dart:9-12`; `.github/workflows/ci.yml:50-55`). The clean-tree run scans `lib` and `test` by default, but no test places a violation under `test/` (or any second root) to prove both roots are live. A regression that silently dropped `test/` from both `defaultScanRoots` and `clientSourceRoots` — shrinking the guarded surface to `lib/` — would leave every CI step green: the scan finds nothing, and the coverage assertion compares the two amended lists in agreement. The guard's own configuration is the one piece of code with no guard.

## Recommended Improvements

1. **Run the guard where the guarded code lands**: add `ai/*` (or `ai/**`) to the `push` branch filter and `ai/master` to the `pull_request` targets in `.github/workflows/ci.yml:3-7`, or move the guard into a workflow triggered on all branches. Without this, Critical 1 stands regardless of any script improvement.
2. **Tighten the expect-fail contract in CI** (`ci.yml:42-48`): require `$LASTEXITCODE -eq 1` per fixture (treat 0, 2, and anything else as step failures), and assert the step's stderr names the expected violation category per fixture, so T1/T2/T3 are distinct behavioural proofs rather than one generic non-zero check. Give the script a distinct, documented exit code for operator error (already 2) and surface it as such.
3. **Sync the detection surface with the platform's real routing configuration**: add `deepseek` to `_providerPatterns` and `deepseek-\w+` to `_modelPatterns` (`architecture_guard.dart:24-38`), broaden the Anthropic patterns (e.g. `\bclaude-[\w.-]+`), and consider deriving or cross-checking the provider/model lists against the AI gateway's routing policy so the guard cannot drift from the providers the platform actually integrates.
4. **Reduce per-line evasion cheaply**: match patterns against whole-file content (or a whitespace-normalized form) instead of individual lines (`architecture_guard.dart:138-141`), so multi-line string literals cannot hide a phrase; document concatenation/interpolation as residual evasion accepted by the representative-catalogue scope, or add a secondary heuristic (e.g. adjacent-literal folding for the prompt patterns).
5. **Make coverage honest**: either extend the scan and `clientSourceRoots` beyond Dart (at minimum `windows/`, `linux/`, `web/`, and other `frontend/` source paths that build or ship the client, with explicit include globs), or enumerate *all* files under `frontend/` (minus `build/`, `.dart_tool/`, and an explicit exclusion list) in `_assertFullCoverage` and assert each is either scanned or named in the exclusion list — turning T5 from a constants-agreement check into a tree-wide discovery assertion. Add the spec's missing negative case: a controlled CI invocation with a root omitted (or a planted out-of-root Dart file) expecting non-zero exit.
6. **Amend the spec/plan documentation to reconcile scope with the architecture**: if the Dart-only scope is deliberate, the spec's Assumptions should say so explicitly and note the narrowing of §3.4.1's "Flutter codebase" / the done-when's "anywhere in client code" (architecture takes precedence, so the mismatch must be recorded even if accepted); if it is not, Deviation 1 is an implementation gap to close per item 5.
