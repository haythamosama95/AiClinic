# Slice Review Report — C3: Journal Writer, Post-Response Detail, and Get-Request Endpoint

**Spec:** `specs/027-journal-writer-get-request/spec.md` · **Branch:** `ai/027-c3-journal-writer-get-request` · **Canonical:** §4.3.11, §6.1 stages 9/15/16, §6.3, §7.4, §7.4.1, §7.6, §5.5

## Executive Summary

C3 delivers the modules its contract names — `src/journal/index.ts` (`createRequestRow`, `journalTransition`, `recordTerminalState`, `writePostResponseDetail`, `getRequest`, plus the frozen types) — and all eighteen named tests are present in a single integration-spy suite backed by real D1/R2 bindings. The core write path matches the frozen contract with high fidelity: the stage-9 insert carries every contracted column with the manifest-pinned prompt hash, the three-milestone timestamp model of §6.3 is implemented exactly (overwrite `state`/`updated_at`, stamp `completed_at` on terminal), guard rejection is counted in `platform_counter` with zero `ai_request` inserts, stage 16 performs exactly one R2 `PutObject` with all four envelope sections, N `ai_attempt` rows, and one `usage_event`, failures inside `waitUntil` are swallowed, and `getRequest` resolves each terminal branch through one indexed lookup with no R2 read for failed/cancelled. The substantive defects cluster on the read path and on drift: the wired `GET /v1/requests/{reference}` endpoint performs no identity check or tenant scoping — anyone holding the 40-bit human-readable reference can read a completed request's validated clinical result, and neither contract §3 nor §5.5 settles whether that is intended; `getRequest` maps the terminal `AwaitingContext` state (and every in-flight state) to `found: false`, so a reference that *is* in the journal resolves as "not found," contrary to the done-when; and a completed request whose envelope is missing or whose stage-16 continuation is still in flight likewise returns not-found rather than its state. Since C3 froze its contract, H3's conversational machinery (`listConversationLegs`, `canReachAwaitingContext`, four guard helpers) and the soft-threshold `routing_tier` column have merged into the module without amending the artifact D3/D4/D6/F3 are bound to consume — the same drift pattern as C1's J1 and C2's H2 merges — and the guard-rejection tally the contract's own T5 test exercises is dead code, reimplemented independently in `rate-limit/` and `admission/`. Coverage meets the named-test floor but never tests the one error code the slice can emit (stage-9 insert failure), never exercises `journalTransition`'s terminal branch, and pins none of the read-path edge states.

## Critical Issues

None. At the library level this slice scopes itself to, the done-when criteria are met and spy-proven: the row exists before the provider spy runs, each terminal state is recorded, guard rejection produces no row, exactly one R2 object / N attempt rows / one usage event are written after the terminal marker, a stage-16 failure leaves the terminal state intact, and each get-request branch costs exactly one indexed query. As with C1/C2, the write-path stages (9/15/16) have no caller in `src/` — only `getRequest` is wired (`ai-platform/src/worker.ts:105`) — consistent with the contract deferring pipeline consumption to D-slices, an observation rather than a defect here. The unauthenticated get-request endpoint (Bug 1) is the most consequential finding, but because contract §3 and §5.5 are both silent on whether this surface requires a token, it is classified as a bug demanding a deliberate ruling rather than an unambiguous critical violation.

## Bugs

1. **The wired get-request endpoint performs no identity check, authorization, or tenant scoping — a 40-bit human-readable reference is the sole bearer credential for validated clinical results** (`ai-platform/src/worker.ts:95-126`). The route reads the path segment, normalizes it, and returns the terminal state plus the full validated `result` for completed requests without inspecting an `Authorization` header, minting a `Principal`, or checking that the caller's installation matches the row's `installation_id`. Every other surface on the platform sits behind the §5.6 token contract and the §6.1 guard; this route bypasses all of it. The reference is deliberately short and human-readable (eight Crockford-base32 symbols ≈ 40 bits, `ai-platform/src/reference.ts:3-17`; §8.9's "read aloud" rationale) — guessable in principle and routinely shared with support staff — so reference-as-capability is a weak footing for returning clinical content. Contract §3.1 freezes the lookup mechanics but says nothing about authentication; §5.5's surface table is equally silent. Architecture wins by omission here only if that silence is deliberate — it needs an explicit ruling, and if the answer is "authenticated like every other surface," the endpoint as wired leaks results cross-tenant.

2. **`getRequest` resolves the terminal `AwaitingContext` state — and every in-flight state — to `found: false`, so a journaled request reports as "not found"** (`ai-platform/src/journal/index.ts:383-387`). The final `return { found: false }` catches `Accepted`, `Composing`, `Invoking`, `Streaming`, `Validating`, `Repairing`, and `AwaitingContext`. §6.3 names `AwaitingContext` terminal and immutable — a conversational request that ended in it *has* a terminal state, yet the done-when ("a request reference resolves to its terminal state") yields a 404, indistinguishable from an unknown reference. The frozen `GetRequestResult` union (contracts/journal.md §5.2) simply omits the branch — the contract under-covers §6.3 and the code inherits the gap. The in-flight states are a lesser sin (§5.5 scopes the endpoint to "after the stream is gone"), but conflating "known, still running" with "unknown reference" invites client retry loops against a valid reference; at minimum the distinction should be pinned deliberately.

3. **A completed request whose envelope is missing returns `found: false` — platform data loss is reported as "unknown reference"** (`ai-platform/src/journal/index.ts:361-367`). If stage 16's continuation failed after stage 15 (a failure mode FR-009 explicitly tolerates), or the envelope was purged by F3 retention while the `journal`-class row persists (§7.7's classes expire on different horizons), or the R2 read simply races the still-pending `waitUntil` continuation, `r2.get` returns null and the endpoint answers 404 for a request the journal says completed. The honest responses are state-without-result or a taxonomy error; "not found" is the one answer that is false. The unguarded `JSON.parse(await object.text())` (`:367`) compounds this: a truncated or corrupt envelope throws out of `getRequest` and surfaces as an unhandled 500 from `worker.ts`, not a typed response.

4. **The `payload_pointer ?? envelopeKey(request_id)` fallback deviates from the contract and masks stage-16 partial failure** (`ai-platform/src/journal/index.ts:362`). Contract §3.3 freezes "one `GetObject` on `payload_pointer`" — a pointer dereference, per §7.4 ("a support lookup is a pointer dereference rather than a search"). Deriving the key when the pointer is NULL papers over the exact state where stage 16 wrote the R2 object but not the pointer update (`index.ts:317-323` runs them as separate statements), and it makes the pointer-update half of stage 16 unobservable: no test can distinguish "pointer was set" from "fallback derived the same key," and indeed no test asserts `payload_pointer` is non-null after stage 16.

5. **Terminal-state immutability is nowhere enforced — and the guard that exists is never called** (`ai-platform/src/journal/index.ts:106-114`, `:213-266`). §6.3 is explicit: `Completed`, `Failed`, `Cancelled`, and `AwaitingContext` "are terminal and immutable." `recordTerminalState` and `journalTransition` issue unconditional `UPDATE`s keyed on `request_id`; a second terminal write (a D6 retry bug, a late cancel racing a completion) silently overwrites state, `completed_at`, and `terminal_error_code`. `isJournalTransitionAllowed` encodes exactly the from-terminal prohibition but has no caller anywhere in `src/` — the writers do not consult it. The immutability invariant currently rests on every future caller behaving.

6. **`Failed` can be journaled with a NULL `terminal_error_code`, and `getRequest` then casts the null into the typed response** (`ai-platform/src/journal/index.ts:253`, `:379`). `recordTerminalState` accepts `terminalErrorCode: TaxonomyCode | undefined` and binds `terminalErrorCode ?? null` even on the `Failed` branch; contract §4.4 requires the taxonomy code on `Failed` (recorded from D3/D4/D6). A caller omitting it produces a row whose get-request response carries `terminal_error_code: null` — the `as TaxonomyCode` cast at `:379` hides the violation from the type system, and the client-facing contract ("state plus the terminal error code") is broken silently.

7. **The guard-rejection tally the contract's own test exercises is dead code, duplicated by two live implementations** (`ai-platform/src/journal/index.ts:122-150`, `:414-452`). Nothing in `src/` calls `recordGuardRejection` or `flushGuardRejectionCounters`; the actual rejection counting lives in `rate-limit/index.ts:122-145` (a near line-for-line copy of the same tally/`ON CONFLICT` flush) and `admission/index.ts:313`. T-C3-05 (`test/journal.test.ts:596-620`) therefore proves the invariant against machinery the pipeline never runs, while the machinery the pipeline does run is tested elsewhere against a different code path. Three writers for one table is also a drift hazard: the bucket keying and dimension-set shape can diverge silently.

8. **Stage-16 writes are neither atomic nor idempotent, so a mid-sequence failure leaves permanently partial detail** (`ai-platform/src/journal/index.ts:268-324`). The continuation runs four sequential, unbatched writes — N `ai_attempt` inserts, one `usage_event` insert, one R2 put, one pointer update — and the `.catch(() => undefined)` at `:330-334` swallows a failure at any point. An attempt-insert failure leaves zero attempt rows but no signal; a usage_event failure leaves attempts without the ledger row SC-005 counts on; an R2 failure leaves D1 detail with no envelope. Because each retry would mint fresh ULID `attempt_id`s with no upsert or idempotency key (`:282`), any future retry logic would double-write attempts. FR-009 tolerates the failure; nothing requires the partial state to be detectable, and today it is not — there is no flag, log, or reconciliation hook.

9. **Stage-16 failures are swallowed with no logging, against the contract's own wording** (`ai-platform/src/journal/index.ts:330-334`). Contract §4.5 freezes "swallowed (logged internally if the runtime supports it)"; the implementation discards the error entirely. Workers supports `console.error` in `waitUntil` continuations, so the qualifier does not apply — the one diagnostic for Bug 8's partial states is dropped.

10. **The stage-9 failure return omits the diagnostic fields contract §4.2.2 describes** (`ai-platform/src/journal/index.ts:208-210`). §4.2.2 says the failure is "built via A2 `buildErrorBody` (carrying `request_reference` and `trace_id`)"; the implementation returns the bare `{ ok: false, code: "internal_error" }` of §5.3. The contract is internally inconsistent (§4.2.2 vs §5.3), and the code followed the terser half — the request reference and trace id, the two fields §5.4 puts on every error response, must be re-attached by a caller that has not been written yet.

## Architectural Deviations

1. **H3's conversational machinery and the soft-threshold column are merged into `journal/index.ts` without amending the frozen contract — the same drift pattern as C1's J1 and C2's H2 merges.** (a) `listConversationLegs` and `ConversationLegRow` (`ai-platform/src/journal/index.ts:390-412`) are H3's conversation read path, exported though contract §5's surface omits them. (b) `canReachAwaitingContext`, `isJournalTerminalState`, `isJournalTransitionAllowed`, and `JOURNAL_TERMINAL_IMMUTABLE_STATES` (`:95-120`) are unlisted exports — and the one with semantic weight, `isJournalTransitionAllowed`, is dead (Bug 5). (c) `RequestRowInput.routingTier` and the `routing_tier` insert column (`:29`, `:185`, `:204`) postdate the freeze; §4.2.1's row shape does not list it. On (c) the architecture itself has since been amended — §7.3's `ai_request` field list now includes `routing_tier` and `routing_decision` (docs/architecture/17-ai-platform.md:2247) — so the code is right and the frozen artifact is stale; what may not stand is D3/D4/D6/F3 consuming a contract whose row shape and export surface misdescribe the module they bind to.

2. **The write-path stages are unwired; only the read path is live** (no reference to `createRequestRow`, `journalTransition`, `recordTerminalState`, or `writePostResponseDetail` in `src/` outside `journal/index.ts`; `getRequest` alone is consumed, at `ai-platform/src/worker.ts:105`). Consistent with the contract deferring pipeline consumption to D3/D4/D6 — but worth restating, as the C1/C2 reports did, because every ordering done-when (row-before-provider, transitions timestamped, stage 16 after terminal) is currently proven only against the test harness's own spies, and the live endpoint can only ever return 404 until a writer exists.

3. **The `GetRequestResult` union under-covers §6.3's terminal set** (contracts/journal.md §5.2 vs docs/architecture/17-ai-platform.md:1944). The union has `Completed`/`Failed`/`Cancelled`/not-found; §6.3 has five terminal states, and `AwaitingContext` — reachable, terminal, and immutable — has no branch (Bug 2). Architecture wins: either the union gains the branch (and the endpoint a response for it) or §6.3 is amended to say conversational legs are unresolvable by reference, which would contradict §8.9's support flow.

4. **Double reference normalization on the read path** (`ai-platform/src/worker.ts:104` and `ai-platform/src/journal/index.ts:348`). `worker.ts` normalizes the path segment and `getRequest` normalizes again per contract §3.1. Idempotent and harmless, but one of the two is redundant, and if the two ever diverge the endpoint's behaviour depends on call order.

## Missing or Weak Tests

1. **No test for the one error code the slice can emit** (spec.md:109, :113). The coverage rule demands one case per emittable code; stage 9's `internal_error` on D1 insert failure (`ai-platform/src/journal/index.ts:208-210`) has no case — no test injects an insert failure into `createRequestRow` or asserts the request fails before the provider spy runs. The fail-before-paid-work guarantee of FR-001 is entirely unasserted.

2. **T-C3-05 proves the invariant against dead code** (`test/journal.test.ts:596-620`; Bug 7). The spy assertions (zero `ai_request` inserts, one `platform_counter` increment) pass against `recordGuardRejection`/`flushGuardRejectionCounters`, which no production path calls; the live rejection counters in `rate-limit/` and `admission/` are different code.

3. **`journalTransition`'s terminal branch is never exercised** (`ai-platform/src/journal/index.ts:219-229`). T-C3-06 routes every terminal state through `recordTerminalState` (`test/journal.test.ts:629-634`), so the branch of `journalTransition` that stamps `completed_at` for terminal states — including the `AwaitingContext` case contract §4.3.2's table omits — could be deleted without turning any test red.

4. **No read-path edge-state tests** (Bugs 2, 3, 6). Nothing pins get-request behaviour for an in-flight row, an `AwaitingContext` row, a completed row with a missing envelope or NULL `payload_pointer`, a corrupt envelope (the unguarded `JSON.parse`), or a `Failed` row with NULL `terminal_error_code` — every one of these currently returns either `found: false` or an unhandled throw, and the suite is silent on all of them.

5. **No terminal-immutability test** (Bug 5). §6.3's "terminal and immutable" is a named inherited invariant; no test attempts a second terminal write (or a non-terminal transition after a terminal one) and asserts the row is unchanged — and such a test would fail today, which is exactly why it should exist.

6. **T-C3-01's provider spy observes nothing** (`test/journal.test.ts:531-549`). The named test requires "a provider-call spy observes the `ai_request` row is present before the provider is called"; the test reads the row itself, then invokes the spy, then re-counts. The ordering is constructed by the test's own sequencing rather than observed inside the provider call — a regression that deferred the insert to after invocation within the same function would not be caught by the spy assertion as named.

7. **T-C3-13's "terminal event" is a bare `vi.fn` the test calls itself** (`test/journal.test.ts:797-839`). No SSE terminal event (A6) is involved; the test proves `writePostResponseDetail` does not run before it is called, which is trivially true of a `waitUntil` scheduling wrapper, and proves nothing about stage 14 preceding stage 16 in a real pipeline. The named ordering invariant will only be genuinely tested when D-slices wire the stages.

8. **No assertion that the envelope contains *exactly* four top-level keys** (contracts/journal.md §2.2: "No other top-level keys are permitted on the wire"). T-C3-09 (`test/journal.test.ts:687-715`) uses `toHaveProperty` for the four sections but never asserts the absence of extras — a fifth section added to `buildEnvelope` would pass.

9. **No stage-16 partial-failure or write-ordering assertions** (Bug 8). T-C3-12 injects a failure at the *first* write (attempt insert), so the swallowed-failure path is proven only for the all-or-nothing case; nothing tests a failure after some writes have landed, asserts the write order (attempts → ledger → envelope → pointer), or checks that `payload_pointer` is set on success.

## Recommended Improvements

- **Rule on get-request authentication deliberately** (Bug 1): either wire the route through the §5.6 token check with an installation-scope match against the row, or amend §5.5/contract §3 to state explicitly that the reference is a bearer capability — and if the latter, consider whether 40 bits of entropy is sufficient for a credential that returns clinical content.
- **Close the read-path gaps** (Bugs 2, 3, 4, 6): add an `AwaitingContext` branch to `GetRequestResult` and the endpoint; return state-without-result (or a typed error) when a completed row's envelope is missing rather than `found: false`; drop the `payload_pointer` fallback so the pointer update is observable, or assert it in tests; guard the `JSON.parse`; reject `Failed` terminal writes that arrive without a taxonomy code.
- **Enforce terminal immutability in the writers** (Bug 5): make `recordTerminalState`/`journalTransition` conditional (`WHERE request_id = ? AND state NOT IN (<terminal>)`) or have them consult `isJournalTransitionAllowed`, and add the overwrite tests.
- **Delete or adopt the dead tally** (Bug 7): either route `rate-limit/` and `admission/` through the journal's counter functions (single-sourcing the bucket keying) or remove `recordGuardRejection`/`flushGuardRejectionCounters` from the module and re-point T-C3-05 at the live path.
- **Make stage 16 observable and order-safe** (Bugs 8, 9): log swallowed failures (`console.error` with request id and trace id), consider `db.batch()` for the D1 writes so attempts-plus-ledger fail together, and document the accepted partial states.
- **Amend the frozen contract for the merged reality** (Deviation 1): add the H3 exports, the guard helpers, and the `routing_tier` column to §4.2.1/§5, exactly as C1's and C2's contracts owe their amendments.
- **Add the missing cases**: stage-9 insert failure → `internal_error` before the provider spy; `journalTransition` terminal branch; in-flight/`AwaitingContext`/missing-envelope/corrupt-envelope/NULL-error-code get-request cases; terminal-overwrite rejection; exact-four-keys envelope assertion; `payload_pointer` set after stage 16; stage-16 mid-sequence failure.
