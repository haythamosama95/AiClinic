# Slice Review Report — C1: Capability Registry, Resolver Stage, and Discovery Endpoint

**Spec:** `specs/025-capability-resolver-discovery/spec.md` · **Branch:** `ai/025-c1-capability-resolver-discovery` · **Canonical:** §4.3.4, §5.1, §6.1 stage 5, §5.5, §5.2

## Executive Summary

C1 delivers the module the plan names — `src/capability/` with the `CapabilityRegistry`, `resolve()`, `discover()`, `computeDiscoveryEtag()`, and `buildDiscoveryResponse()` — and all ten named tests are present, split correctly across the Node and Miniflare-D1 pools. The core resolver logic matches the frozen contract: exact-pin lookup with no "compatible version" fallback, retired-before-kill-switch ordering, the four kill-switch scopes (including provider resolution through `active_routing_policy`), `deprecated` served, and the manifest deep-frozen at the registry boundary with the immutability test actually attempting writes. Discovery's entitlement/plan/grant filtering, sorted-set etag over A4's `hashManifest`, and the `If-None-Match` → `304` rule (with a no-reserialisation assertion) are all implemented and tested. Since C1 froze its contract, J1 has merged the §5.1 lifecycle-overlay machinery into the same module (`effectiveLifecycle`, `loadLifecycleOverlay`, `OVERLAP_WINDOW_MS`, `getGrantedCapabilityVersion`) — the code now matches the architecture (§5.1, §5.7, §12.4: deprecated versions announced through discovery with a successor), but the frozen contract was never amended and now misdescribes `discover()`'s lifecycle filter, `resolve()`'s return identity, the etag input, and the export surface that C2/D1/E3 are bound to consume. The substantive defects are bounded but real: the resolver honours no plan-level allowance at all despite §4.3.4 and FR-002 saying it must, and nobody on the submit path enforces the grant's `capability_version` — an installation granted only v1.0.0 can pin and be served v2.0.0; the etag is emitted unquoted on the wire, which RFC-7232-compliant clients will not round-trip, quietly defeating the "revalidated by etag" done-when; kill-switch reads have no miss handling (inconsistent with the module's own overlay/grant reads), so a reader that reports a missing row throws out of `resolve()`; and `JSON.parse` on `allowed_capabilities` is unguarded, the same crash class B3 shipped. Coverage meets the named-test floor but leaves the global/installation/provider kill-switch scopes, the revoked-grant and granted-version-mismatch filters, all three empty-entitlement branches, discovery-caller immutability, and etag order-independence unasserted, and the unit-test reader fabricates rows for unknown keys so a miss can never occur in seven of the ten tests.

## Critical Issues

None. The two done-when criteria are met at the library level this slice scopes itself to (contract §12 defers live route wiring to a later slice, and `worker.ts` accordingly has no discovery route or stage-5 call — an observation, not a defect here). The defects below are real but none disables a criterion outright the way B4's did.

## Bugs

1. **The grant's `capability_version` is enforced in discovery but nowhere on the submit path — an installation can pin and resolve a version it was never granted** (`ai-platform/src/capability/index.ts:300-324`; consumed check at `ai-platform/src/entitlement/index.ts:133-149`; the version filter exists only in discovery at `src/capability/index.ts:401-413`). §7.3 defines `capability_grant` as "which capability versions a plan or installation may use" — version-scoped (`docs/architecture/17-ai-platform.md:2244`). `resolve()` never reads the grant row at all, and B3's stage-3 entitlement check verifies only that *a* grant row for the capability exists and is unrevoked — it never compares `grant.capability_version` against the request's pin. End to end: an installation granted `clinic.x@1.0.0` discovers only 1.0.0, but can submit a pin for any other registered version (say a newer 2.0.0 its plan does not cover) and be served. `getGrantedCapabilityVersion` (`src/capability/index.ts:442-467`) computes exactly the value needed and is exported, yet nothing on the resolve path calls it — only the cohort-activate test does (`test/cohort-activate-promote.test.ts:512`). Either `resolve()` or stage 3 must compare the granted version against the pin, and a test must pin a version other than the granted one.

2. **The etag is emitted unquoted on the wire, so RFC-7232-compliant clients and intermediaries never round-trip it** (`ai-platform/src/capability/index.ts:474-488`). `ETag` is a quoted-string header (`ETag: "9f3a…"`), but `buildDiscoveryResponse` sets the bare hash on both the 200 and 304, and `If-None-Match` comparison is strict string equality against the bare hash. A compliant HTTP stack that normalises the entity-tag to its quoted form (or a cache that rewrites it) will send `If-None-Match: "<etag>"`, never match, and receive a full 200 on every revalidation — the discovery endpoint is then effectively uncacheable, which is the second half of the slice's done-when ("cacheable and revalidated by version or etag"). T-C1-08 pins the non-compliant shape: the matching case sends the raw unquoted value and the mismatch case is itself a *quoted* string (`test/capability.test.ts:716-733`), so the suite proves the bug cannot be observed. The contract froze "strict string equality on the full etag value" (contracts/capability-registry.md:174) without specifying the wire quoting; both must be amended together, with weak (`W/`), list-valued, and `*` forms decided explicitly.

3. **Kill-switch reads have no miss handling, inconsistent with the module's own overlay, policy, and grant reads — a missing row throws out of `resolve()`** (`ai-platform/src/capability/index.ts:163-174`, `:222-227`). `loadConfig` throws `ConfigCacheMissError` when the reader reports `"miss"` (`src/config-cache/index.ts:98-101`), and every other read in the module guards that (`loadLifecycleOverlay` `:95-100`, `resolveProviderId` `:195-200`, discovery's grant read `:404-409`, entitlement read `:348-354`) — the four kill-switch reads do not. Whether a missing kill-switch row means "inactive" (as both test harnesses fabricate: `test/capability.test.ts:396-399`) or "fail closed," throwing an unhandled error out of stage 5 is neither: it surfaces as a 500 `internal_error` for a routine control-plane state. B3's entitlement stage has the identical unguarded pattern (`src/entitlement/index.ts:91-97`, `:151-181`), so the reader contract ("absent switch ⇒ `{active:false}` row" vs "miss") is currently defined only by test fixtures and must be pinned in one place — A5's config-cache contract or the C1 contract's §4.3 — and honoured by both consumers.

4. **Unguarded `JSON.parse` on `allowed_capabilities` crashes `discover()` on a malformed D1 string** (`ai-platform/src/capability/index.ts:137-146`). The same crash class the B3 and B4 reports flagged in entitlement/admission: a non-JSON string in `entitlement.allowed_capabilities` throws a bare `SyntaxError` out of discovery, turning a data problem into a 500. A malformed entitlement should fail closed (empty set) with a logged signal, not crash the surface.

5. **`createCapabilityRegistry` silently skips manifests with non-string identity fields instead of failing the build** (`ai-platform/src/capability/index.ts:283-294`). A4's frozen invariant is a *build failure* on a malformed manifest (spec.md:43-45); a registry that silently drops one turns a build-time defect into a runtime `capability_unknown` for a capability that was supposed to exist — the least diagnosable of the three resolver codes. The registry builder should reject (throw on) any manifest whose `capabilityId`/`version` is not a string, and the skip branch (`:288-290`) should not exist.

6. **Published-`deprecated` manifests are invisible in discovery unless an overlay row happens to exist — two deprecated versions with identical effective state are filtered differently** (`ai-platform/src/capability/index.ts:422-433`). The gate is `overlayAnnounced || publishedActive` followed by an effective-state check: a manifest *published* `deprecated` with no overlay row is excluded (`:423-426`), while the same version *published* `active` and overlay-deprecated is included — though both have effective state `deprecated` and both are served by `resolve()` (T-C1-05). Discovery visibility of a deprecated version should be a function of the effective lifecycle (§5.1: "manifest value, overridden by overlay if one exists"), not of whether an operator row exists; as written, a version published deprecated is announced to nobody. The symmetric edge also holds: an overlay can resurrect a published-`retired` version into discovery and past `resolve()`'s retired check — sanctioned by §5.1's "overlay wins," but worth an explicit test either way.

7. **The unit-test reader fabricates a row for any unknown key, so no unit test can ever produce a miss** (`test/capability.test.ts:156-168`). `makeReader` returns the *entire source object* as the row when the key is absent (`return source as D1Row`), which is why `resolveProviderId` silently sees a bogus policy row (no `provider_id` field → `undefined`) and why the kill-switch miss path of Bug 3 is unreachable in T-C1-01/02/03/05/06. The fallback should be `"miss"`, with named rows for everything the test intends to exist.

## Architectural Deviations

1. **The resolver honours no plan-level allowance, contradicting §4.3.4 and the spec's own FR-002 — the frozen contract silently re-scoped this away** (`ai-platform/src/capability/index.ts:300-324`; contracts/capability-registry.md:65-68). §4.3.4 states the resolver resolves "honouring the client's version pin *and the installation's plan-level allowances* (a capability may be entitlement-gated)" (`docs/architecture/17-ai-platform.md:1223-1227`), and FR-002 repeats it as a MUST (spec.md:162-163). The contract instead declares entitlement "discovery-only" and has `resolve()` return `{ok:true}` to an ineligible installation — and the implementation follows the contract. Architecture wins: either `resolve()` gains the allowance check (the §4.3.4 reading) or the architecture text and FR-002 are amended deliberately; what may not stand is the current three-way disagreement. The practical exposure is Bug 1: with stage 3 not checking grant versions either, the plan-level allowance the section promises is not fully enforced anywhere.

2. **The frozen contract misdescribes the merged module in at least five places — J1 extended the module without amending the artifact C2/D1/E3 consume.** (a) §6's filter table says discovery includes only `active` ("`deprecated` and `retired` are excluded," contracts/capability-registry.md:134); the code includes effective-`deprecated` manifests with successor identity (`src/capability/index.ts:428-435`) — which is what §5.7 and §12.4 require ("retirement is announced through discovery before it is enforced," `:1805`, `:3492-3498`), so the code is right and the contract stale. (b) §6's grant rule is "row exists, `revoked_at` null"; the code additionally filters on `grant.capability_version` (`:401-413`). (c) §9 promises "`resolve()` returns the registry's frozen `Manifest` reference — not a copy"; with an overlay, `resolve()` returns a derived, re-frozen copy (`:103-123`, `:323`). (d) §7's etag is computed over the published manifests; the code hashes the overlay-derived manifests (`:435-439`) — behaviourally better (an overlay flip changes the etag, so clients revalidate), but not what the contract freezes. (e) §10's export surface omits `effectiveLifecycle`, `LifecycleOverlay`, `EffectiveLifecycle`, `OVERLAP_WINDOW_MS` (consumed by `src/control/index.ts:416`), and `getGrantedCapabilityVersion` (consumed by `test/cohort-activate-promote.test.ts:512`), all now exported (`src/capability/index.ts:32-48`, `:442`). The contract's own header binds later slices to it ("extend, never rewrite," contracts/capability-registry.md:5-7); the amendment is overdue in the same way B4's `period_end` drift was.

3. **Process-global mutable registry installed by an unconstrained setter** (`ai-platform/src/capability/index.ts:46`, `:296-298`). `capabilityRegistry` is module-level mutable state swap-able by any importer at any time, and the `Map` itself is never frozen — a holder of the reference returned by `createCapabilityRegistry` can `set`/`delete` entries after installation, bypassing the manifest freeze the contract §9 guarantees. Only tests call the setter today (and every test file mutates shared global state to run, `test/capability.test.ts:130-135`), but the production bootstrap shape is undefined: there is no "install once at startup" discipline, no guard against re-installation, and no production reader/route wired at all (`worker.ts` has no discovery route or stage-5 call — consistent with contract §12 deferring wiring, but worth restating because C2/D1 will import this module next). The slice's own inherited prohibition on per-request server-side state is not violated (the registry is build-time data), but a frozen `Map` facade plus an install-once guard would make the immutability storey coherent end to end.

4. **Kill-switch state is invisible to discovery, so a killed capability is still advertised** (`ai-platform/src/capability/index.ts:333-440` — no kill-switch read in `discover()`). The contract's filter table deliberately omits kill switches, and a kill switch is transient, so advertising is defensible; but §5.5's "active manifests for this installation/plan" reads naturally as "manifests the client can actually use," and an installation-scoped kill means discovery invites submissions that stage 5 will reject with `capability_disabled`. Record the choice in the contract whichever way it lands — and if advertising killed capabilities is intended, note that the etag (correctly) does not change on a kill-switch flip.

## Missing or Weak Tests

1. **Three of the four kill-switch scopes are never tested active** (`test/capability.test.ts:534-570` exercises only `capability:<id>`). `isCapabilityDisabled` evaluates `global`, `capability:`, `installation:`, and `provider:` as independent branches (`src/capability/index.ts:211-220`); the coverage rule's "every branch of every rule" is met for one of four, and `resolveProviderId` — the `active_routing_policy` read, its miss path, and the non-string `routingPolicyRef` early return (`:176-201`) — has no test at all. The retired-then-killed precedence (retired short-circuits before kill switches, `:315-321`) is also unasserted.

2. **Discovery's grant branches are untested: revoked grant and granted-version mismatch** (`src/capability/index.ts:398-413`). T-C1-07 and T-C1-10 seed only live, version-matching grants; the `revoked_at != null` exclusion and the `grantedVersion !== manifest version` exclusion — the latter being the only place the version pin is enforced anywhere (Bug 1) — are dead code as far as the suite is concerned.

3. **All three empty-entitlement branches are untested** (`src/capability/index.ts:341-365`): entitlement row missing (`ConfigCacheMissError` → empty set), `status !== "active"`, and non-string `plan`. The contract promises "an empty `manifests` array and an etag computed over that empty set" for each (contracts/capability-registry.md:141-142); none is asserted, and the empty-set etag's stability (two ineligible installations, or the same installation twice, get the same etag) is likewise unasserted.

4. **Discovery-caller immutability is not tested** (FR-008 covers "a later stage *or to a discovery caller*," spec.md:176-177). T-C1-06 mutates only the `resolve()` result (`test/capability.test.ts:601-649`); the manifests `discover()` returns — including the overlay-derived copies from `manifestWithEffectiveIdentity` (`src/capability/index.ts:103-123`), which are new objects frozen on a separate path — have no mutation test, and the derived-copy freeze is exactly the freeze most likely to regress.

5. **Etag order-independence is untested.** `sortManifests` exists precisely so the same set in any registry-iteration order yields one etag (`src/capability/index.ts:247-253`); T-C1-09 (`test/capability.test.ts:739-763`) asserts change-sensitivity but never that a permuted input order produces the *same* etag — the property client caching actually depends on. A content-only change (same set, one field-group edit, same versions) is also only half-covered: the version-swap case changes the key, not just the content.

6. **`If-None-Match` with no header, a list of etags, a weak etag, and `*` are all unhandled and untested** (`src/capability/index.ts:474-480`). Strict equality covers only the single-exact-value case the unit test pins (in the non-compliant unquoted form — Bug 2); every other grammatically valid conditional request falls through to 200. If that is the intended contract, the contract should say so explicitly and a test should pin at least the absent-header case.

## Recommended Improvements

- **Close the grant-version hole on the submit path** (Bug 1): have `resolve()` (or B3's stage 3) compare the pin against `getGrantedCapabilityVersion`'s value, treating "granted for a different version" as `capability_unknown` or `forbidden_capability` per §4.3.4/§5.4 semantics, and add the test.
- **Fix the etag wire format** (Bug 2): quote the entity-tag on emit and parse `If-None-Match` per RFC 7232 (list, weak comparison, `*`), amend contract §8, and extend T-C1-08 with quoted, list, and absent-header cases. Add an explicit `Cache-Control` (e.g. `private, must-revalidate`) to the 200 and 304 so the "cacheable" promise is visible to intermediaries rather than implicit.
- **Pin the kill-switch row contract in one place** (Bug 3): decide "absent ⇒ inactive" (then catch the miss and treat as inactive) or "reader must always answer" (then A5's reader contract must say so), apply it identically in C1 and B3, and test the miss path with a reader that can actually miss (fix `makeReader`'s fabricating fallback, Bug 7).
- **Fail closed on malformed entitlement data** (Bug 4): guard the `allowed_capabilities` parse and treat unparseable as an empty set, matching the other empty-entitlement outcomes.
- **Reconcile the frozen contract with the merged module** (Deviation 2): amend §6 (deprecated announced with successor, grant-version filter), §7 (etag over effective manifests), §9 (derived frozen copy under overlay), and §10 (the five new exports), so C2/D1/E3 consume an accurate artifact.
- **Harden the registry boundary** (Bugs 5, Deviation 3): throw on malformed manifests at build time, return an unmodifiable `Map` facade from `createCapabilityRegistry`, and make `setCapabilityRegistry` install-once (or replace it with an explicit bootstrap called from the eventual route wiring).
- **Resolve the §4.3.4/FR-002/contract disagreement deliberately** (Deviation 1): either implement the plan-level allowance check in `resolve()` or amend the architecture and spec text — and record which stage owns the grant-version check.
- **Parallelise discovery's per-manifest reads and cut cold-isolate round trips**: the grant and overlay loads per candidate are independent and currently serialised (`src/capability/index.ts:389-416`); `Promise.all` over candidates would halve cold-start latency, and the overlay read can be skipped entirely for manifests already excluded by cheaper filters.
- **Add the missing cases**: active `global`/`installation`/`provider` kill switches; provider-policy present/absent/non-string; retired+killed precedence; revoked grant; granted-version mismatch; all three empty-entitlement branches plus empty-set etag stability; discovery-caller mutation including the overlay-derived manifest; etag order-independence and content-only change; quoted/list/absent `If-None-Match`.
