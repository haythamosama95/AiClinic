# Slice Review Report — D3: Invocation with Bounded Retry and Fallback

**Spec:** `specs/030-invocation-retry-fallback/spec.md` · **Branch:** `030-d3-invocation-retry-fallback` · **Canonical:** §4.3.7, §8.6, §6.6

## Executive Summary

D3 delivers the one module its plan names — `src/invocation/index.ts` (`runInvocation`, the attempt-loop types, and the sink surface) — plus all thirteen named tests in a single integration suite against D2's fake. The sequential walk is structurally faithful to the frozen contract: per-target invokes are bounded by `max_attempts` with an exact spy-verified count, retries follow only the adapter's classification, terminal failures stop the walk, an exhausted or empty chain yields `provider_unavailable`, attempt-level `selection_reason` values are assigned per chain entry, one attempt record is fed per invoke, and the fallback-after-partial-stream path emits `regenerating`. The substantive gaps are in the time dimension and the test proofs: the chain entry's `timeout_ms` — which the D2 contract froze explicitly "so D3 bounds attempts without re-reading policy" — is never read, and the backoff schedule grows without any cap or deadline check, so "bounded" holds only in attempt count; the jitter done-when is unproven because T-D3-03's not-all-identical assertion passes on the deterministic exponential component alone, with `Math.random()` deleted entirely; and T-D3-12's identity assertion is a tautology over a field the implementation never reads. The loop is also built directly on the D2 port's synchronous, streamless shape (`port.invoke(request)` at the heart of the frozen module), which makes the slice's flagship regenerating/no-splice rule unreachable in production — exercisable only through a test harness that calls the sink itself — and guarantees a rewrite of this frozen core when the D2 port is repaired. Two contract-surface drifts recur: a `ProviderHistoryStore` dependency sits on the frozen input type advertising the very §9.14-forbidden mechanism the slice must never use, and the sink's caller-owned object is monkey-patched in place to detect partial streaming.

## Critical Issues

1. **The frozen loop hard-codes the broken D2 port shape, so its signature regenerating/no-splice rule is dead in production and its core must be rewritten when the port is repaired** (`ai-platform/src/invocation/index.ts:186`). `runInvocation` calls `port.invoke(request)` synchronously and reads a single `ProviderInvokeResult` — the exact shape the D2 review's Critical 1 showed a real adapter cannot implement (no async, no chunk surface, no abort signal). The consequences land squarely on this slice's done-when: partial streamed text can never reach `sink.emitStreamText` from any real adapter through this port, so the "stream restarted on a fallback target emits an explicit regenerating event and never splices two providers' text" criterion is exercisable only via the test-only harness that pokes the sink directly (`ai-platform/test/invocation.test.ts:202-216`); and when the port is repaired to async/streaming, the invoke call, the `processInvokeResult` mapping (`index.ts:100-113`), and the monkey-patched partial-stream detection (`index.ts:155-160`) all change together — the artifact D4 and CP3 are told to consume is frozen in a shape that cannot survive the repair its own dependency requires. The frozen contract should either name the repaired port shape it assumes or the repair should land before D4 wires the sink to the stream.

## Bugs

1. **`timeout_ms` on the chain entry is never read — D3 enforces no per-attempt time bound at all** (`ai-platform/src/invocation/index.ts:162-217`). The spec's Consumes section freezes that "each chain entry's `max_attempts` **and `timeout_ms`** … D3 reads those bounds off the chain entry it is walking," and D2's contract §4.2 carries both fields through unchanged explicitly "so D3 bounds attempts without re-reading policy." The loop reads only `entry.max_attempts` (`:181`); `timeout_ms` is dead data end-to-end — no deadline is raced, nothing is passed to the port (which names no timeout option — the D2 port defect), and a hung adapter is never interrupted by the attempt loop. Timeout outcomes arise only when an adapter self-classifies; §4.3.8 does make adapters own timeouts, but then the frozen carry-through of `timeout_ms` to D3 has no consumer anywhere, and one of the two consumed bounds this slice exists to enforce is unenforced.

2. **Backoff is exponential with no cap and no deadline awareness — the time cost of the walk is policy-unbounded** (`ai-platform/src/invocation/index.ts:72-77`, `:210-212`). `computeJitteredBackoff` returns `100·2^i + rand·100·2^i·0.5` with no ceiling, and the sleeper is awaited unconditionally between same-target retries with no check against the request's own `deadline` (carried on the canonical request fixture, `ai-platform/test/invocation.test.ts:76`). Nothing in §4.3.7 clamps `targets[].max_attempts` (the 1–6 clamp covers only `max_parallel_attempts`), so a policy declaring a large `max_attempts` makes the final inter-retry sleep astronomically long — the request sleeps past its deadline while the loop keeps walking. The delivery plan's coverage rule names backoff caps as a boundary this slice must cover; there is no cap to cover.

3. **Mixed timeout/non-timeout exhaustion is journaled as `fallback_after_retryable_error` — including the exact scenario §8.6 diagrams** (`ai-platform/src/invocation/index.ts:176`, `:206-208`, `:215`). The timeout-reason flag requires *every* failure on the prior target to be a timeout (`targetFailuresAllTimeout`). §8.6's own sequence shows P1 failing with a 503 (retryable) and then a timeout before the walk falls back; under this implementation that scenario records `fallback_after_retryable_error`, because the exhaustion was not timeout-only. The frozen contract names `fallback_after_timeout` for "prior target exhausted via timeout-classified retryable failures" without restricting to timeout-*only*, so the one scenario the architecture draws produces a journal reason that hides the timeout. No test drives a mixed script (Weak Tests 5).

4. **The sink's caller-owned object is monkey-patched in place and never restored — reuse stacks wrappers and double-emits stream text** (`ai-platform/src/invocation/index.ts:155-160`). To detect partial streaming the loop reassigns `sink.emitStreamText` with a closure over this run's flag. An `InvocationSink` is an injected dependency owned by the caller; if the same sink instance is ever passed to a second `runInvocation` (a shared collector in CP3 or D4 wiring is the obvious way this happens), the second run wraps the first run's wrapper — every subsequent stream text is forwarded once per stacked wrapper, and the first run's stale flag is set alongside the second's. The detection also fires on *any* sink emission during the run, not just emissions from the current target's invoke, which will matter once the port streams asynchronously.

5. **`idempotencyKey` is a dead field on the frozen input type** (`ai-platform/src/invocation/index.ts:48`). It is accepted, never read, and not fed to the attempt records or the port; the same-request-identity guarantee (FR-009) rests on `requestId` alone. Either the field is load-bearing for the C3/B4 hand-off — in which case the feed is missing it — or it should not be on the frozen surface. T-D3-12 cannot catch this because it asserts the input field against itself (Weak Tests 2).

6. **`processInvokeResult` throws a bare `Error` for any unmapped result kind, and `truncation` is journaled as plain `success`** (`ai-platform/src/invocation/index.ts:100-113`). Today's four-kind union makes the throw unreachable, but the moment the port gains chunk/streaming kinds (Critical 1) an unmapped kind escapes as an untyped throw across the module boundary — the same pattern flagged in D2's router. Meanwhile a truncation outcome loses its signal in the journal feed: the attempt record says `outcome: "success"` with no truncation marker, so C3's `ai_attempt` history cannot distinguish a clean completion from a length-truncated one.

7. **The `provider_unavailable` error's `retryability: false` initializer is dead** (`ai-platform/src/invocation/index.ts:61-69`). `setRetryabilityFromClassification` immediately overwrites it from the taxonomy entry (`provider_unavailable` is retry-safe "Yes" per `ai-platform/src/errors.ts:101-106`), so the literal misstates the emitted error's actual retryability and only survives as misleading reading. Cosmetic, but it obscures what the exhausted-chain outcome actually tells clients.

## Architectural Deviations

1. **A `ProviderHistoryStore` sits on the frozen input surface — the slice advertises the §9.14-forbidden mechanism as an optional dependency** (`ai-platform/src/invocation/index.ts:38-42`, `:52`). Contract §2.1 freezes exactly three injectables (port resolver, event/attempt sink, sleeper); the implementation adds a fourth whose three methods are `getProviderHealth`, `getRecentFailures`, and `isCircuitOpen` — precisely the circuit breaker and shared provider-health state R-20 / §9.14 prohibit and FR-008 forbids the loop to consult. The code never calls it (T-D3-11's spy proves that), but the frozen type now documents the forbidden seam as a supported extension point, inviting exactly the regression the prohibition exists to prevent. The spy test does not require the parameter to exist.

2. **The regenerating/no-splice machinery is unreachable except through the test harness** (`ai-platform/src/invocation/index.ts:163-165`; harness at `ai-platform/test/invocation.test.ts:202-216`). With the synchronous, streamless port, no production adapter can emit partial text through the sink — the only caller of `sink.emitStreamText` in the tree is the test-only double, which stimulates the very condition it exists to test. The done-when's flagship behaviour (regenerating event, discarded text, no splice) is therefore proven only against a self-stimulating fixture, and D4 will be the first slice able to exercise the path for real — against a contract whose trigger condition it cannot yet produce.

3. **The attempt feed drops usage and timing, leaving the C3 hand-off under-specified** (`ai-platform/src/invocation/index.ts:22-30`, `:92-98`). §7.2's `ai_attempt` row carries "latency, tokens in/out, cost, provider request id" alongside outcome; the port's `CanonicalResult` bears usage on success, and the loop discards it — the record carries only identity, reason, outcome, and error code. Contract §6 sanctions this as "optional … not new Freezes," so the code matches the contract; but the contract has quietly deferred the fields that make per-attempt cost attribution (§6.6's stated purpose) possible, and no test joins this feed to C3's `AttemptInput` — the same surfaced-but-unjoined hand-off pattern as D1's prompt version and D2's routing decision.

4. **The module is unwired; nothing in `src/` calls `runInvocation`** (sole definition at `ai-platform/src/invocation/index.ts:134`; no references outside `test/invocation.test.ts`). Consistent with the contract deferring production wiring to CP3 ("production later wires the sink to C3's journal writer and D4's stream path") — restated, as in prior reports, because every done-when criterion is currently proven only against the suite's own fixtures and resolver.

## Missing or Weak Tests

1. **T-D3-03 passes with jitter deleted entirely — the jitter done-when is unproven** (`ai-platform/test/invocation.test.ts:374-377`; `ai-platform/src/invocation/index.ts:72-77`). The assertion is `new Set(delays).size > 1` over two retries whose *deterministic* exponential components already differ (100·2⁰ vs 100·2¹), so the test is green even if `Math.random()` is removed and the backoff is a fixed table. The clarification sanctioned "not all identical" as the assertion, but with an exponential base the identical-interval failure mode the test was meant to catch cannot occur; jitter presence requires either an injectable RNG with recorded samples, a same-retry-index comparison across runs, or an assertion on the jitter component itself (e.g. delay not equal to the pure exponential value).

2. **T-D3-12 is a tautology — it asserts the input fixture against itself and cannot fail** (`ai-platform/test/invocation.test.ts:441-449`). `expect(input.requestId).toBe(requestId)` and `expect(input.idempotencyKey).toBe(idempotencyKey)` compare the local constants to the object the test itself constructed; the implementation could read neither field (it doesn't — Bug 5) and the test stays green. The meaningful half of the case — `attempt.request_id` identical across retries — is covered, but the idempotency-key half of FR-009 ("not a new user-initiated request with a new idempotency key") has no assertion against any emitted artifact.

3. **No empty-chain case** (contract §4: "or the chain has no targets" → `provider_unavailable`; `ai-platform/src/invocation/index.ts:147-149`). The branch exists and is one line, but the coverage rule demands every branch of every rule; no test feeds `chain: []` and asserts `provider_unavailable` with zero attempts journaled.

4. **T-D3-06 asserts presence, not order or count, and has no negative case** (`ai-platform/test/invocation.test.ts:719-726`). `events.some(kind === "regenerating")` passes whether the event arrives before or after the fallback target's output, and whether it fires once or ten times; the contract's trigger ("emit … **before** the fallback target's output is considered") is unasserted. No case covers fallback *without* prior partial text, where `regenerating` must NOT fire — a regression emitting it on every fallback (or on the first target) keeps the suite green. Nor is there a case for partial text followed by a *terminal* failure, where no fallback and no regenerating should occur.

5. **No mixed-failure exhaustion case** (Bug 3): a target failing with a timeout and a non-timeout retryable in the same walk — the exact §8.6 sequence — has no test, so the `fallback_after_timeout` vs `fallback_after_retryable_error` boundary on mixed scripts is unasserted and currently journaled in a way that hides the timeout.

6. **No truncation or malformed outcomes through the loop, and only one terminal taxonomy code is exercised** (`ai-platform/src/invocation/index.ts:100-125`). The fake's scripted set includes `truncation` and `malformed` and eighteen taxonomy codes; the suite drives only `internal_error`, `timeout`, and `provider_rejected`. The truncation-as-success branch (Bug 6), the malformed path, and the terminal classification of the other non-retry-safe codes (`quota_exhausted`, `context_invalid`, `capability_*`, `installation_suspended`, `forbidden_capability`, `request_too_large`, `conversation_budget_exhausted`) are all unexercised — a misclassification in any of them (retrying a terminal failure, or terminating on a retryable one) is invisible to the suite. The coverage rule's "every branch of every rule" and "every error code the slice can emit" are unmet.

7. **No boundary case at `max_attempts = 1`** (`ai-platform/src/invocation/index.ts:179-213`). Every fixture uses 2 or 3; the degenerate target that permits exactly one invoke (no sleeper call, immediate advance) — the floor of the named retry-ceiling boundary — is unasserted, as is the interaction that no backoff should be slept on a target's final attempt.

8. **No assertion that the walk never sleeps past the request deadline or any backoff cap** (Bug 2). The coverage rule names backoff caps as a boundary; the sleeper is recording-capable (`createRecordingSleeper`) but no test asserts a ceiling on requested delays or a deadline check — unsurprisingly, since the implementation has neither.

## Recommended Improvements

- **Sequence the port repair before D4 wires the sink** (Critical 1): amend the frozen contract to state the async/chunked port shape the loop assumes, repair the D2 port, and rework the invoke call, `processInvokeResult`, and partial-stream detection together — rather than letting D4 discover the mismatch mid-wiring.
- **Enforce `timeout_ms` or re-own it explicitly** (Bug 1): race each invoke against the chain entry's `timeout_ms` (classifying the loser as `timeout`), or — if §4.3.8's "adapters own timeouts" is the intended reading — pass the bound into the port's invoke options when the port is repaired, and amend the D2/D3 contracts so the carry-through has a named consumer either way.
- **Cap the backoff and respect the request deadline** (Bugs 2, 8): add a documented ceiling to `computeJitteredBackoff`, skip or truncate sleeps that would exceed the canonical request's `deadline`, and assert both in the suite with the recording sleeper.
- **Fix the timeout-reason rule for mixed scripts** (Bug 3): record `fallback_after_timeout` when the prior target's *exhausting* failure (or any failure in its walk — pick one and amend contract §3 to say which) was timeout-classified, and add the mixed-script test drawn straight from §8.6's diagram.
- **Stop mutating the caller's sink** (Bug 4): wrap the sink in a local delegating object scoped to the run (`const observingSink = { ...sink, emitStreamText: … }`) instead of assigning onto the injected instance, so reuse cannot stack wrappers.
- **Make the jitter proof real** (Weak Test 1): inject the RNG alongside the sleeper, assert the requested delay differs from the pure exponential value across recorded samples, or compare delays at the same retry index across repeated runs — any of these fails under a fixed table; the current assertion cannot.
- **Make T-D3-12 assert against emitted artifacts** (Weak Test 2, Bug 5): drop the tautological input-field assertions; either carry the idempotency key onto the attempt feed and assert it there, or remove the field from `InvocationInput` and the fixtures.
- **Remove `providerHistoryStore` from the frozen input type** (Deviation 1): the spy test can supply the store structurally (an object the module never receives proves non-consultation just as well) without advertising the prohibited seam on the contract surface; amend contract §2.1 if a fourth injectable is genuinely wanted.
- **Add the missing cases**: empty chain → `provider_unavailable` with zero attempts; fallback without prior streaming emits no `regenerating`; partial text then terminal failure emits no `regenerating`; regenerating emitted exactly once and before the fallback target's first output; mixed timeout/non-timeout exhaustion reason; `truncation` and `malformed` through the loop; each remaining terminal taxonomy code not retried; `max_attempts = 1`; no sleeper call on a target's final attempt.
- **Clean up the attempt record fidelity** (Bugs 6–7, Deviation 3): distinguish truncation from clean success in the feed (or amend contract §6's outcome enum), carry usage/timing fields when the port returns them so C3's `ai_attempt` columns have a source, replace the bare throw with a classified outcome, and delete the dead `retryability: false` initializer in `createProviderUnavailableError`.

### 1.3 Fix implemented

- **D3-R1:** Loop awaits async `port.invoke`, relays `text_delta` chunks (including optional error/malformed `chunks`) through a run-scoped observing sink; regenerating fires only after prior partial stream. D2 port result extended with optional failure `chunks` (allowed extension).
- **D3-R2:** Each attempt raced against `entry.timeout_ms` with `AbortSignal`; loser classified as `timeout`.
- **D3-R3:** Backoff capped at 10_000 ms; sleeps truncated to remaining relative `request.deadline` budget; injectable `random`.
- **D3-R4:** `fallback_after_timeout` when the prior target's exhausting failure was timeout-classified (matches §8.6).
- **D3-R5:** Caller sink never mutated; `providerHistoryStore` removed from `InvocationInput`; idempotency key journaled on every attempt.
- **D3-R6:** Distinct `truncation` outcome; optional usage/timing on success/truncation records; unmapped kinds → classified `internal_error`; `createProviderUnavailableError` initializer matches taxonomy retryability.
- **D3-R7:** Empty-chain and `max_attempts = 1` paths covered.
- Spec Kit: `specs/030-invocation-retry-fallback/{spec,plan,tasks,contracts/invocation-attempt-loop}.md` and D2 `provider-port.md` optional-chunks note updated. Architecture docs untouched.
