# Slice Review Report — D2: Provider Port, Fake Adapter, and Routing Policy

**Spec:** `specs/029-provider-port-routing/spec.md` · **Branch:** `029-d2-provider-port-routing` · **Canonical:** §4.3.8, §13.5, §4.3.7, §7.3

## Executive Summary

D2 delivers the four modules its plan names — `src/provider/classify.ts` (`classifyFailure`, `setRetryabilityFromClassification`), `src/provider/port.ts` (`ProviderPort`, `ProviderInvokeResult`, `ScriptedOutcome`), `src/provider/fake.ts` (`FakeAdapter`), and `src/router/index.ts` (`selectCandidateChain`) — plus all twenty-one named tests across two suites. The classification contract is genuinely exhaustive and correctly derived from A2's retryability column via `isRetrySafe`; the fake produces success, every retryable and terminal class, truncation, and malformed through the port; the router implements first-match rule selection, narrow-only installation overrides, the four named feature filters, lowest-of-three cost class with a recorded source, tier matching, and the 1–6 parallelism clamp, all as a pure function of capability, policy, and request. The substantive defect is the port shape itself: `invoke` is synchronous, returns a single result with no `CanonicalStreamChunk` surface, and names no abort-signal option — contradicting the frozen contract's own §2 and §4.3.8's stream-normalization duty — and the already-merged D5/D7 adapters prove the cost, bolting chunks on via an intersection type outside the port and busy-spinning on a promise that can never settle inside a Workers isolate. On the router side, three pieces of policy data are dead: `overrides[].force_cost_class` is never read (the effective class instead trusts a request-side context field the architecture does not name), `rules[].requires` is never enforced, and `defaults.cost_class` has no consumer; the document's `policy_id`/`policy_version`/`schema_version` are never validated against the owning row. The same cross-slice drift pattern as C1/C2/C3/D1 recurs: J3's per-installation preload machinery and F4/D7 consumer suites are merged into the frozen module's file without amending the frozen contracts. Coverage meets the named-test floor but the exhaustiveness test enumerates a hand-copied taxonomy list, the prohibition test inspects only module export names, and the empty-chain edge case, the latency-exclusion reason code, and the chain-entry attempt-bounds carry-through are all unasserted.

## Critical Issues

1. **The frozen port is synchronous and streamless — unusable by the real adapters it exists to type, as the merged D5/D7 code demonstrates** (`ai-platform/src/provider/port.ts:31-33`). `ProviderPort.invoke(request): ProviderInvokeResult` returns synchronously and its result union (`port.ts:24-28`) contains no `CanonicalStreamChunk` — yet the frozen contract §2 binds invoke success to "`CanonicalResult` and/or an ordered sequence of `CanonicalStreamChunk` ending with exactly one terminal chunk," §4.3.8 makes stream-chunk normalization an adapter-owned duty, §4.3.10's cancellation works through an abort signal on the in-flight provider fetch, and contract §2 names "abort signal / deadline" as port-named invoke options. None of that is representable. The merged `DeepSeekAdapter` shows the concrete damage: it intersects `streamChunks` onto the result outside the port type (`ai-platform/src/provider/deepseek.ts:58-60`), so D4 cannot consume chunks through the port; and because `invoke` must return synchronously, `waitForPromiseOutcome` (`deepseek.ts:334-364`) spins `while (!settled && Date.now() < deadline) {}` — a busy loop in which a `fetch` promise can never settle inside a Workers isolate (microtasks and I/O callbacks require returning to the event loop), so every promise-returning transport burns the full timeout in CPU and yields the timeout outcome. The one artifact D2 exists to freeze for D3–D7 and CP3 is shaped so that a real adapter cannot implement it correctly; this must be repaired (async invoke, chunk surface, abort signal) before D3 builds on it, and the contract amended to match.

## Bugs

1. **`force_cost_class` is read from the request context, not from the policy document's override — the document field is dead and an unnamed input channel drives routing** (`ai-platform/src/router/index.ts:211-216`, `:235-289`). §4.3.7 names the third cost-class source as "an installation `force_cost_class` override **in the policy document**," and the document type carries it (`:120`). But `applyInstallationOverride` handles only `exclude_providers` and `pin_target`; `override.force_cost_class` is never read. Instead `resolveEffectiveCostClass` trusts `context.installationForceCostClass` (`:34`) — a request-side input no canonical section names. T-D2-16 (`ai-platform/test/router.test.ts:584-607`) declares the override in the document *and* passes the context field, so the test passes while the document entry is decoration: delete `force_cost_class` from the fixture document and nothing changes.

2. **`rules[].requires` is never read — the rule-level feature floor is dead data** (`ai-platform/src/router/index.ts:107-111`, `:173-201`). Contract §2 and §4.3.7 define `requires` as the "feature floor a target must satisfy," but `ruleMatches` inspects only `match.*` clauses and `filterTargets` compares target features against request requirements; a rule whose `requires` floor exceeds what the capability supplies still matches and its targets enter the chain. Every test fixture sets `requires` to the zero floor (`ai-platform/test/router.test.ts:160-164`), so no test can detect the omission.

3. **`defaults.cost_class` is never read** (`ai-platform/src/router/index.ts:127-130`, `:415-417`). §4.3.7's document table defines `defaults` as `{ cost_class, max_parallel_attempts }` "applied when a rule omits them," but `PolicyRule` has no `cost_class` field and only `defaults.max_parallel_attempts` is consulted. A policy author setting a document-level cost-class default changes nothing.

4. **The document's identity and format version are never validated against the owning row** (`ai-platform/src/router/index.ts:135-139`, `:386-387`, `:421-422`). Contract §2 / §4.3.7: "`policy_id`, `policy_version` — must equal the owning `routing_policy` row." The cache row carries both fields (`ActiveRoutingPolicyRow`), and the router records `document.policy_id` / `document.policy_version` on the decision without ever comparing them to the row's — a mismatched or stale document is journaled as if it were the active version, defeating the auditability that §7.3's full-history retention exists to provide. `schema_version` is likewise never checked; a document in a future format is silently interpreted as the current one.

5. **The no-match path throws a bare `Error`, and the catch-all requirement is unenforced** (`ai-platform/src/router/index.ts:400-404`). §4.3.7 requires a document to end with a catch-all rule; nothing validates this at read time, so a malformed policy surfaces only as an untyped `Error` (with the installation id embedded in the message) thrown across the module boundary — not a classified outcome, not an empty chain. D3, the designated consumer, has no typed signal to catch.

6. **`FakeAdapter.invoke` escapes the port's result union with bare throws, and the scripted-outcome parse is an unchecked cast** (`ai-platform/src/provider/fake.ts:66-68`, `:95`, `:50-55`). An empty queue or unrecognized outcome throws a plain `Error` rather than returning a classified `CanonicalError` — the port's frozen failure shape. `parsePrefixedCode` casts `outcome.slice(...)` to `TaxonomyCode` without validation; a runtime-constructed `retryable:bogus` (the template-literal type constrains compile time only) reaches `getTaxonomyEntry(undefined)` and throws a `TypeError` inside `consumesBudget`/`classifyFailure`. Test-double-only, but D3–D4 and CP3 run against this double.

7. **Latency-class exclusion is recorded as `feature_unsupported`, indistinguishable from a structured-output exclusion** (`ai-platform/src/router/index.ts:337-344`). The `reason_code` enum (contract §4.2, §4.3.7) has no latency-specific value, and the contract's filter table names latency class as its own filter without saying which code it maps to — so the recorded reason for the one filter whose mapping is undocumented collides with another filter's code, and support reading `excluded` cannot tell why the target was dropped. The contract owes a mapping; the code owes whatever the contract says.

## Architectural Deviations

1. **J3's activation machinery is merged into the frozen router module without amending the frozen contract — the same drift pattern as C1's J1, C2's H2, C3's H3, and D1's H2.** `selectCandidateChain` now consults a per-installation cache key `${policyCacheKey}/${installationId}` before the document key (`ai-platform/src/router/index.ts:377-381`), and the module exports `preloadRoutingPolicyForInstallation` — explicitly labeled "(J3)" (`:443-456`) — performing D1 reads through a scoped reader. Contract §2 freezes a single active document "held in the config cache under kind `active_routing_policy`" and states "D2 does not implement R2 policy-document fetch"; the per-installation two-key lookup and the D1-backed preload path are neither in the contract nor in any D2 named test (T-D2-19's spy assertion passes on the *second* consult call, leaving the first lookup unasserted — `ai-platform/test/router.test.ts:691-697`). The merged consumer suites (`routing-policy-canary.test.ts`, `soft-threshold-routing.test.ts`, `second-provider-policy.test.ts`) bind J3/F4/D7 behaviour to a contract whose text does not describe it.

2. **The merged real adapters own logging and journal emission, violating the ownership boundary this slice froze** (`ai-platform/src/provider/deepseek.ts:42-48`, `:299-313`, `:509-518`). §4.3.8 and contract §2.1 are absolute: adapters own "nothing else — no retry decisions, no fallback decisions, **no logging policy**." `DeepSeekAdapter` takes `logger` and `journal` sinks and emits `deepseek.*` log records and `provider.*` journal records on success, error, timeout, and missing credentials. That is D5/D7's code, but the violation is of D2's frozen clause, and D2's own prohibition test is structurally blind to it (Weak Tests 2): the boundary this slice exists to freeze is already eroded in the working tree.

3. **The selection reason is returned on a routing outcome object, not "recorded on the request"** (`ai-platform/src/router/index.ts:75-77`, `:419-432`). The delivery plan's done-when and FR-010 say the router "records the selection reason **on the request**"; the implementation returns a separate `RouterOutcome` and never touches the request. The spec's Edge Cases section sanctions this ("present on the routing outcome"; persistence is C3), so the code matches the spec — but the spec quietly narrowed the done-when, and §4.3.7's `ai_request.routing_decision` persistence now depends on a C3 hand-off that no test joins (as with D1's surfaced prompt version). Documentation mismatch at minimum.

4. **The router and fake are unwired; nothing in `src/` calls `selectCandidateChain` or constructs `FakeAdapter`** (no references outside `src/router`, `src/provider`, and tests). Consistent with the contract deferring pipeline consumption to D3/CP3 — restated, as in prior reports, because every done-when (chain from policy, reason recorded, statelessness) is currently proven only against the suites' own fixtures.

## Missing or Weak Tests

1. **T-D2-06's exhaustiveness rests on a hand-copied taxonomy list, and its expectation is the implementation's own formula** (`ai-platform/test/provider-port.test.ts:21-48`, `:216-233`). `TAXONOMY_CODES` duplicates the eighteen codes from `ai-platform/src/errors.ts:1-19` by hand; `errors.ts` exports no code list, so if A2's taxonomy ever changes, the "exhaustive over the taxonomy" test stays green against the stale copy. Worse, the expected classification is computed as `isRetrySafe(getTaxonomyEntry(code).retryable)` — character-for-character the implementation of `classifyFailure` (`ai-platform/src/provider/classify.ts:10-13`) — so the test can only catch a divergence between two identical expressions, never a wrong mapping. No concrete code-to-class pair is pinned literally (e.g. `provider_rejected` → terminal, `timeout` → retryable).

2. **T-D2-18 inspects only module export names against an anchored prefix pattern** (`ai-platform/test/provider-port.test.ts:53-54`, `:236-243`). `Object.keys(module)` does not enumerate class prototype methods, so a `retry()` or `fallback()` method on `FakeAdapter` — or on the `ProviderPort` interface — is invisible to the assertion; names like `shouldRetry` or `maxRetries` do not match the `^(retry|…)` pattern; and the already-merged real adapters (Deviation 2) are outside the assertion's scope entirely. The one structural prohibition of the slice is guarded by a test that cannot see the places a violation would live.

3. **T-D2-16 cannot catch the `force_cost_class` bug it exists to cover** (Bug 1; `ai-platform/test/router.test.ts:584-607`). The installation-override leg supplies the forced class through the request context while also declaring it in the document; no case puts `force_cost_class` in the document with the context field absent, so the document channel — the only one §4.3.7 names — is unproven.

4. **No empty-chain case** (spec Edge Cases; contract §4.1). "The router may return an empty chain" is a named boundary; no test filters every target out and asserts `chain: []` with all targets in `excluded`. The done-when's chain-depends-only-on-inputs property is likewise unproven for the empty outcome.

5. **T-D2-11 asserts no reason code for the latency filter** (`ai-platform/test/router.test.ts:414-421`) — the one filter whose `reason_code` mapping is undocumented (Bug 7) is the one whose recorded reason is unasserted; the test would pass under any code, including none.

6. **T-D2-14 never asserts the `max_attempts` / `timeout_ms` carry-through the contract freezes for D3** (contract §4.2: carried "unchanged from the matched rule's `targets[]` … so D3 bounds attempts without re-reading policy"). The test file's local `ChainEntry` type omits both fields (`ai-platform/test/router.test.ts:92-96`) and no assertion reads them; a regression dropping the carry-through keeps every test green. The `cost_class_source` tie-break (two sources at the same lowest class — `SOURCE_PRIORITY`, `ai-platform/src/router/index.ts:147-151`, `:225-230`) is likewise unexercised.

7. **No cases for the document-validation and no-match paths** (Bugs 4–5): row/document version mismatch, unknown `schema_version`, a document with no matching rule, and a document violating the catch-all requirement are all unexercised — the router's only failure behaviours have no coverage.

8. **`kill_switch` is a frozen `reason_code` with no emitting code path and no test** (`ai-platform/src/router/index.ts:43`; contract §4.2; §4.3.7). Either the router is missing kill-switch-aware exclusion (B3's guard-stage kill switches are the likely owner, but the frozen enum says the router records this code) or the enum overpromises; as built, one of the six frozen reason codes is dead.

9. **T-D2-20 asserts only the clamped bounds, not the clamp** (`ai-platform/test/router.test.ts:738-743`). With a policy requesting 10 (rule) over 12 (default), the test asserts `≥ 1 && ≤ 6` — it would pass for an effective value of 1, 3, or 6, and does not prove rule-over-default precedence (`ai-platform/src/router/index.ts:415-417`) or that the cap is exactly six.

## Recommended Improvements

- **Repair the port before D3 builds on it** (Critical 1): make `invoke` asynchronous (`Promise<ProviderInvokeResult>` or an async iterable), add a `chunks` surface typed as an ordered `CanonicalStreamChunk` sequence with exactly one terminal chunk (assertable via A3's `assertExactlyOneTerminal`), and name the abort-signal/deadline options on the port; amend contract §2 to the repaired shape and delete `waitForPromiseOutcome` from the merged adapters.
- **Source `force_cost_class` from the document** (Bug 1): read it from the matched installation override inside `selectCandidateChain`, drop `installationForceCostClass` from `RouterContext`, and change T-D2-16 to drive the override through policy data alone.
- **Enforce or remove the dead policy fields** (Bugs 2–3): apply `rules[].requires` as a rule-level floor against the capability requirements during matching, and give `defaults.cost_class` its documented consumer (a rule-level `cost_class`) — or strike both from contract §2 and §4.3.7.
- **Validate the document against the row** (Bugs 4–5): cross-check `policy_id`/`policy_version`, reject unknown `schema_version`, enforce the terminal catch-all rule, and replace the bare no-match `Error` with a typed outcome (or a documented empty chain) that D3 can handle deliberately.
- **Make the exhaustiveness test real** (Weak Test 1): export the taxonomy code list from `errors.ts` (A2-owned) and enumerate from it, and pin several concrete code→class mappings literally so a wrong mapping fails even when the formula and its mirror stay in sync.
- **Strengthen the prohibition test** (Weak Test 2, Deviation 2): enumerate `FakeAdapter` prototype methods and the `ProviderPort` member surface, widen the name pattern, and extend the assertion to every adapter module under `src/provider/` so the merged real adapters' logger/journal ownership is caught.
- **Add the missing cases**: empty chain with full `excluded` list; latency-exclusion reason code (after the contract names it); `max_attempts`/`timeout_ms` carry-through; cost-source tie-break; document/row version mismatch; unknown `schema_version`; no-match behaviour; a `kill_switch` emitting path or a contract amendment removing the code; T-D2-20 asserting the exact clamped value and rule-over-default precedence.
- **Amend the frozen contracts for the merged reality** (Deviations 1–3): add the per-installation policy-key lookup and `preloadRoutingPolicyForInstallation` to `contracts/routing-decision.md`, resolve the adapters-and-logging clause against what D5/D7 actually merged, and reconcile "recorded on the request" with the returned `RouterOutcome` — exactly as the C-slice and D1 contracts owe their amendments.
