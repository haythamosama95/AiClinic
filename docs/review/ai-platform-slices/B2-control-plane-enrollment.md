# Slice Review Report — B2: Control-Plane Enrollment and Installation Lifecycle

**Spec:** `specs/022-control-plane-enrollment/spec.md` · **Branch:** `ai/022-b2-control-plane-enrollment` · **Canonical:** §4.5, §8.1

## Executive Summary

B2 delivers the §4.5 installation-lifecycle surface: five operator-gated handlers under `/control/installations/{id}/{action}` that write the A5-frozen `installation`, `installation_key`, `entitlement`, and `control_audit` rows, with the enroll entitlement correctly frozen at `pending` with zeroed economics and a closed empty period, rotation correctly additive (new `kid`, previous row kept), and every mutation journaled with an operator identity in the same D1 batch as its write. All seven named tests exist and assert real D1 rows. The most consequential gap is the operator gate itself: the spec assumed B2 would *consume* an existing operator-auth mechanism and define none, but none existed — so the slice invented `defaultOperatorAuth`, which accepts **any non-empty bearer token** as a fully-authorized operator and records the raw token as the journaled `operator_id`. As wired in production, the control plane authenticates nothing and its audit trail persists credential material. Underneath that: the lifecycle state machine is unconstrained (suspend resurrects a `deleted` installation; resume on an active installation journals a phantom transition), the one-time enrollment invariant is a check-then-insert race against a schema with no `org_id` uniqueness, and no payload validation or D1-error handling stands between malformed input and an unhandled 500. Test-wise, three of the five emittable rejection codes have no case, the two tested ones are pinned only to "status ≥ 400", the route wiring the plan promised to cover end-to-end is never exercised, and no test touches the terminal-status rules.

## Critical Issues

1. **The production control plane authenticates nothing, and the audit journal stores the credential** (`ai-platform/src/control/index.ts:11-23`, `:989`; wired at `ai-platform/src/worker.ts:85-93`). The spec's Assumptions state "B2 consumes an existing operator-auth mechanism and defines none" (`specs/022-control-plane-enrollment/spec.md:270-272`) and the plan repeats "the real scheme is not implemented here and none is invented (R-20)" (`plan.md:47-51`) — but no mechanism existed to consume, so the slice shipped `defaultOperatorAuth`, which returns `{ operatorId: token }` for *any* non-empty `Authorization: Bearer <token>` header. `dispatchControlRequest` defaults to it (`index.ts:989`) and `worker.ts` passes no alternative, so anyone who can reach the Worker can enroll, rotate, suspend, resume, or delete any installation by sending `Bearer x`. §4.5's defining property of this surface — "separately authenticated (operator identity, not clinic identity)" — is not met by the shipped wiring: there is no verification step at all, and the "identity" is whatever string the caller chose. Worse, that raw token is then written into `control_audit.operator_id` on every mutation (e.g. `index.ts:206`, `:262`), so the audit trail whose entire purpose is §4.5 accountability persists live credential material in D1. Contract §3 froze this behaviour verbatim (`contracts/control-plane.md:109-112`), meaning B3/J3/F3 now bind to a contract that sanctions a non-authenticating gate. Unlike B1's public-key gap, every individual piece here does what the tests assert — the failure is that the frozen scheme itself provides no authentication, and the slice's own governing documents said none would be invented.

## Bugs

1. **The lifecycle state machine is unconstrained: `deleted` is not terminal, and no-op transitions are journaled as if they happened** (`ai-platform/src/control/index.ts:284-306`, `:327-353`, `:233-257`). `handleSuspend` never reads the current status — suspending a `deleted` installation sets `status = 'suspended'` (`:297-300`), resurrecting a row the frozen contract calls "lifecycle-terminal" (`contracts/control-plane.md:191`), and from which resume (`:339-342`) then restores it to `active`. `handleRotate` similarly adds key rows to a deleted installation without any status check (`:233-257`). `handleResume` on an installation that was never suspended computes `restoredStatus = installation.status` (a no-op) yet still writes a `resume` audit row and returns 200 (`:344-353`) — the §4.5 journal, which exists so that an unaudited change is "indistinguishable from an attack", here records transitions that never occurred. `handleDelete` on an already-`deleted` installation likewise journals a second `delete`. None of these paths is tested.
2. **One-time enrollment is a check-then-insert race against a schema with no `org_id` uniqueness** (`ai-platform/src/control/index.ts:156-164` then `:171-207`; schema at `ai-platform/migrations/20260731120000_platform_schema.sql:4-11`). The duplicate guard is a `SELECT ... WHERE installation_id = ? OR org_id = ?` followed by a batch insert; `org_id` has no UNIQUE constraint (B2 is correctly forbidden from amending A5's migration, so none could be added here). Two concurrent enrolls for the same `org_id` under different installation ids both observe no row and both insert — FR-010's one-time invariant is not enforced, only probabilistically avoided. The same-installation-id race is backstopped by the PRIMARY KEY, but the resulting constraint violation escapes the handler as an unhandled exception (no try/catch anywhere in the module), surfacing as a 500 rather than the contract §8 `409 already_enrolled` — the deterministic rejection breaks exactly on the concurrent-duplicate path it exists for.
3. **No payload validation or D1-error containment: malformed input becomes an unhandled 500** (`ai-platform/src/control/index.ts:150-153`, `:176-201`, `:227-230`, `:251-257`). Enroll and rotate fields are bound straight from the parsed body with no presence/type checks; a missing field binds `undefined`, which D1 rejects with a thrown error, and a rotate reusing an existing `kid` violates the `installation_key` PRIMARY KEY (`20260731120000_platform_schema.sql:14`) — both propagate out of the handler as runtime exceptions rather than the contract §2.4 JSON rejection shape. A retry of the same rotation (a routine operational occurrence for a "no clinic is offline" flow, §8.1) therefore crashes instead of resolving deterministically.

## Architectural Deviations

1. **The slice invented the operator-auth scheme its governing documents forbade it from inventing, and froze it** (`ai-platform/src/control/index.ts:11-23` vs `specs/022-control-plane-enrollment/spec.md:270-272` and `plan.md:47-51`). Beyond the security consequence (Critical 1), this is a process deviation: the spec Assumption and the plan's R-20 note both record that no scheme would be defined, yet contract §3 (`contracts/control-plane.md:109-112`) freezes `defaultOperatorAuth`'s exact accept-anything behaviour as the production rule that later slices bind to. Architecture wins over Speckit documents, and §4.5 requires genuine operator authentication — the contract should be corrected to name a verifying scheme (or to state plainly that the route is inert until one is wired), and the spec/plan assumption should be reconciled.
2. **`src/control/index.ts` has drifted from the contract's declared "source of truth in code" into a catch-all control module** (`contracts/control-plane.md:10-11` vs `ai-platform/src/control/index.ts:358-984`). The B2 contract names the file as "lifecycle handlers, `OperatorAuth` port, `dispatchControlRequest`", but the merged file now also hosts F3's purge (`:956-984`), A13's support lookup (`:920-954`), and J3/F3-era capability-deprecate, cohort, and routing-policy handlers (`:358-851`) — ~700 of its ~1050 lines belong to later slices. Extension is permitted, but the single shared `OperatorAuth`/dispatch seam means every later control surface inherits B2's frozen (non-)authentication and its error conventions by default; the sibling-per-concern layout the slice itself cites (Clarification Q2, mirroring `src/manifest/`, `src/context/`) argues these should have been sibling modules behind the one dispatcher. Technical debt rather than a B2 implementation fault, recorded here because this is the slice that established the module and the seam.

## Missing or Weak Tests

1. **Three of the five emittable rejection codes have no test, and the two tested ones are pinned only to "status ≥ 400".** Untested: `invalid_json` (`ai-platform/src/control/index.ts:131`), `invalid_route` (`:147`, `:224`, `:280`, `:322`, `:865`), and `installation_not_found` (`:240`, `:291`, `:334`, `:876`) — the last being a named branch of all four lifecycle handlers. T-B2-06 asserts `response.status >= 400` (`ai-platform/test/control.test.ts:553-556`) without pinning 401 or the `unauthorized` body, and T-B2-07 does the same for 409/`already_enrolled` (`:585-586`). The coverage rule requires one case per emittable code; the suite covers two of five, loosely.
2. **No test exercises the route wiring the plan promised to cover end-to-end.** Plan step 6 folds "an end-to-end fetch assertion … (route → handler → D1)" into T-B2-01 (`specs/022-control-plane-enrollment/plan.md:299-301`; tasks T014), but every test calls the handlers directly with an injected fake `OperatorAuth` (`test/control.test.ts:98-100`, `:211-215`) — `worker.ts:85-93`'s method gating and `isControlRoute`/`dispatchControlRequest` routing (`index.ts:896-1051`) are never executed, and `defaultOperatorAuth` itself (missing header, empty token, token-as-identity) has zero coverage. The FR-001 "separate surface" property is untested at the only place it actually lives.
3. **No test pins the terminal-status rules.** T-B2-05 asserts only `status != "active"` and truthy after delete (`test/control.test.ts:468-469`), never `=== "deleted"` as contract §6.1 freezes — and nothing covers suspend-on-deleted (resurrection, Bug 1), resume-on-active (phantom audit), rotate-on-deleted, or double-delete. The state machine is simultaneously unenforced and uncharacterized.
4. **The duplicate-enrollment test covers only the exact-duplicate branch** (`test/control.test.ts:566-591`). The second half of the OR guard — same `org_id`, different `installation_id` (`index.ts:157`) — is never exercised, so an enroll that created a second installation for an enrolled organisation would go undetected. Concurrent duplicates are untestable in this harness as written, which is precisely why Bug 2's race survives.
5. **No test asserts suspend/resume leave the `entitlement` row untouched.** Contract §6 freezes that B2's suspend/resume toggle `installation.status`, not `entitlement.status` (`contracts/control-plane.md:179-180`); a regression writing `suspended` into the `entitlement` row (which §7.3 gives different, guard-visible semantics) would pass the current suite.
6. **Malformed-input behaviour is uncharacterized.** No test sends a missing-field enroll body, a duplicate-`kid` rotate, or a non-JSON body, so Bug 3's 500s are invisible — the suite cannot distinguish a deterministic rejection from a crash.

## Recommended Improvements

- **Replace `defaultOperatorAuth` with a verifying scheme and never journal credentials** (`ai-platform/src/control/index.ts:11-23`): verify an HMAC-signed or secret-compared operator credential against a Workers secret binding, map it to a stable operator id, and write *that* — never the token — into `control_audit.operator_id`. Correct contract §3 to match. This is the one change that makes §4.5's "separately authenticated" true; every other finding is secondary to it.
- **Enforce the lifecycle state machine in the handlers** (`index.ts:284-306`, `:327-353`, `:233-257`): read the current status before every transition; reject suspend/rotate/delete on a `deleted` installation and resume on anything but `suspended` (409-class rejection); journal only transitions that actually occurred. Then pin `deleted` as terminal with tests.
- **Close the enrollment race** (`index.ts:156-207`): catch the D1 constraint violation from the insert batch and map it to `409 already_enrolled` so same-id duplicates resolve deterministically, and raise an A5 amendment adding `UNIQUE(org_id)` to `installation` — the one-time invariant deserves database backing, not application-layer hope.
- **Validate payloads and contain D1 errors** (`index.ts:150-153`, `:227-230`): check required fields for presence/type before binding (400-class rejection), reject a rotate whose `kid` already exists deterministically, and wrap the batches so storage failures surface in the contract §2.4 JSON shape rather than as runtime exceptions.
- **Remove the dead `writeAudit` helper** (`index.ts:111-125`) — every handler inlines its own audit insert into the write batch (correctly, for atomicity), so the unused single-statement helper is pure drift bait; or use it consistently. Either way, one convention.
- **Add the missing cases**: pin 401/`unauthorized` and 409/`already_enrolled` status and body in T-B2-06/07; one case each for `invalid_json`, `invalid_route`, and `installation_not_found` per handler; an end-to-end `worker.fetch` route test (fulfilling plan step 6) including `defaultOperatorAuth`'s header parsing; suspend-on-deleted, resume-on-active, rotate-on-deleted, double-delete; same-`org_id`-different-id duplicate; and a suspend/resume assertion that the `entitlement` row is byte-identical before and after.
- **Split the later-slice handlers into sibling modules** (`index.ts:358-984`) behind `dispatchControlRequest`, restoring the sibling-per-concern layout Clarification Q2 named and stopping the implicit inheritance of B2's auth and error conventions by every future control surface.

### 1.3 Fix implemented

- **B2-R1:** Replaced `defaultOperatorAuth` with `createSecretOperatorAuth` (timing-safe UTF-8 compare). Worker builds auth from `OPERATOR_BEARER_TOKEN` + `OPERATOR_ID`; `dispatchControlRequest` requires explicit `operatorAuth`. Audit journals stable id only. Contract §3 / Spec Assumptions / R-20 reconciled to the verifying scheme.
- **B2-R2:** Handlers read `status`; reject illegal transitions with `409 illegal_lifecycle_transition`; resume only from `suspended`; no phantom journals.
- **B2-R3:** Required-field validation → `400 invalid_payload`; duplicate kid → `409 duplicate_kid`; `runControlBatch` maps UNIQUE → `already_enrolled` / `duplicate_kid`, else `500 storage_error`. Documented A5 follow-up `UNIQUE(org_id)` without editing A5 migration.
- **B2-R4:** Added/pinned rejection cases above (tests-only relative to R1–R3 production work).
- **B2-R5:** Split catch-all `control/index.ts` into sibling modules behind a barrel; `writeAudit` retained for token-contract (not dead after master merge); lifecycle continues inlined batch audit for atomicity.
