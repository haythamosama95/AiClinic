## 1. Executive Summary

H4 is a faithful, well-scoped implementation of its frozen contract. Conversation evals land as a sibling module under `ai-platform/test/eval/`, run in the **same** `ai-platform-eval-golden` CI job as F1 goldens (`ci.yml:104`), add no `src/` module, emit no §5.4 taxonomy codes, and introduce no store or per-request state. All four required §3.11.7 cases exist and are genuinely exercised: T1 converges within the declared budget, T2 requires the *correct* key (not merely any permitted key), T3 routes a scripted out-of-set key through H2's real `applyPermittedKeyAllowlist` drop (`validator.ts:240-256, 302-307`) so the permitted-set enforcement is actually on the scoring path, and T4 pins per-conversation scoring as the acceptance unit. F1's golden/smoke gating and `quality`/`schema` report fields are untouched, proven by T6 re-running the real golden suite.

No critical issues were found. The notable findings are: the suite has **no negative-control case** — every scripted conversation asserts `pass`, so a scorer hardwired to `"pass"` would keep the gate green; **convergence is never actually asserted** (the round-budget criterion only checks that validation did not fail, and the case files' `expect_convergence` / `expected_outcome` fields are dead); the permitted-set criterion is scored only on *obtained* keys, so the assistant's out-of-set **request** in the T3 conversation passes unscored (§13.5 "stay inside the permitted set" vs contract §4 "not obtained"); a validation failure of any kind conflates the `permitted_set` and `round_budget` criteria in the recorded report; and H4 modified F1's `harness.ts` despite the plan declaring it unchanged (tasks.md documents this honestly; plan.md does not).

## 2. Critical Issues

None found.

## 3. Bugs

- **[Medium] Convergence is never scored — only budget non-breach is** — `conversation-harness.ts:271-289` (`scoreRoundBudget`) returns `"pass"` whenever `validateContext` succeeds; nothing requires the scripted conversation to end with a `model` (answer) turn. A conversation whose last assistant turn is `context_requested` within the round limit "converges" per this scorer. The case schema carries `expect_convergence: boolean` (`conversation-harness.ts:46`; all three case JSONs, e.g. `cases/converges_within_round_budget.json:30`) precisely for this, and it is never read. The Done-when criterion is "converge within the round budget"; only the second half is enforced.
- **[Medium] Criterion conflation on validation failure corrupts the recorded per-criterion scores** — `scorePermittedSet` returns `"fail"` for *any* `validateContext` failure (`conversation-harness.ts:241-251`), including a round-budget breach or malformed transcript, and `scoreRoundBudget` does the same (`:280-288`). A budget-exhausted conversation would record `permitted_set: "fail"` even though no forbidden key was obtained — and the frozen §5.1 report payload is the artifact later work (J3's "evals pass") reads. The same inputs are also validated three times per case (`runCase` `:309-317`, then again inside each scorer), and the `suppliedContext` plumbing at `:297, 316-319` is dead: it starts as `{}`, validation of an empty context filters to `{}`, so `Object.keys(validation.filteredContext)` at `:253` always contributes nothing.
- **[Low] `expect_convergence` and `expected_outcome` in every case file are dead declarative data** — `CaseDefinition` (`conversation-harness.ts:40-48`) types `expect_convergence` but never consumes it; `expected_outcome` (e.g. `cases/cannot_obtain_key_outside_permitted_set.json:32-37`) is not even typed. Expected outcomes are instead hardcoded in the tests (e.g. `conversation.test.ts:94-95`), so the case files can silently drift from the assertions that gate CI.
- **[Low] `usedLiveEgress` is a constant, not a guard** — `conversation-harness.ts:84-91` initialises the flag `false` and nothing can ever set it `true`; T5's assertion (`conversation.test.ts:146, 155`) is vacuous. Mitigating: the harness never instantiates a provider adapter or transport at all, so egress is structurally impossible — but then the flag and its two assertions are decoration (the pattern is inherited from F1's `harness.ts:87-92`).
- **[Low] T9 contains a trivially-false, meaningless assertion** — `prohibitions.test.ts:137` asserts `harnessSource.startsWith(EVAL_ROOT)` is `false`, comparing file *contents* against a filesystem path; it can never be true and tests nothing.

## 4. Architectural Deviations

- **[Medium] The permitted-set criterion is scored on obtainment only, not on the assistant's requests** — §13.5 (source of truth) asks "does it stay inside the permitted set"; contract §4 redefines the pass bar as "a key outside the `permittedKeySet` is **not** obtained". In the T3 conversation the assistant's leg-1 fixture *requests* `medication.active_list@v1` (`fixtures/cannot_obtain_key_outside_permitted_set/leg_1.json`) — outside the permitted set — and the conversation still scores `right_keys: pass` (vacuously: `required_key_requests: []`, `conversation-harness.ts:224-233`) and `permitted_set: pass`. `scorePermittedSet` never inspects `context_requested` turns. The runtime stance (H2 drops out-of-set keys regardless of what the model asks) makes "cannot obtain" the enforceable property, and the required T3 case *is* genuinely proven — but the suite as frozen will pass a prompt that habitually requests out-of-set keys, which is exactly the behaviour §13.5's "stay inside the permitted set" reads as covering. Architecture and contract diverge here; under the source-of-truth rule this is a contract/documentation issue to reconcile (either score out-of-set requests as a criterion failure or amend §13.5's wording).
- **[Medium] Conversation evals never render the prompt or run the adapter — a prompt regression in conversational negotiation cannot fail this gate** — A9's rationale is that "without regression evals, every prompt edit is an unreviewable change." F1's goldens honour this by running the real composer and `DeepSeekAdapter` against recorded provider responses (`harness.ts:460-478`). H4's "fixtures" are pre-baked assistant turns appended straight into the transcript (`conversation-harness.ts:185-207, 300-307`); the composer, prompt artifacts, and response validation are never on the path. Editing the chat prompt so the model would request the wrong keys leaves every fixture — and therefore the gate — green. This design is traceable to frozen Clarification Q1 ("each leg runs against recorded fixtures"), so the implementation matches its Speckit documents, but it sits in tension with A9's stated purpose and with §13.5's placement of conversation evals beside capability evals. What the suite actually gates is H2 validator behaviour plus fixture content, not prompt behaviour. Worth an explicit architectural note or a future case leg that runs the composer path.
- **[Low] Plan/documentation mismatch: F1's `harness.ts` was modified though the plan froze it as unchanged** — `specs/047-conversation-evals/plan.md` Files table declares `harness.ts` "CONSUMED (F1) — capability golden runner unchanged" and the Consumes Binding says F1 modules are "imported unchanged", but H4 added the `expectations/`-directory discriminator to `listEvalCapabilities()` (`harness.ts:199-211`; slice commit `f26249ff` touches the file). The change is small, behaviour-preserving for goldens (T6 proves `[clinic.visit_summary]` still gates), and honestly recorded in `tasks.md` T018 — but `plan.md` misstates what happened to an F1-frozen module, weakening the same consumes-audit trail flagged in the H1 review.
- **Verified non-deviations:** no `ai-platform/src/eval/` module and no new §4 component (confirmed; `prohibitions.test.ts:66, 124` guard it); no §5.4 taxonomy code added (pass/fail are CI outcomes only, matching the spec Test plan coverage note); F1 golden/smoke scheduling and the live-smoke workflow untouched; capability `quality`/`schema` report fields unchanged (`conversation.test.ts:163-185`); the conversation report is a JSON artifact under `test/eval/reports/`, not a D1 table; one fixture capability, three cases, single platform matrix (OD-5); the fixture capability reuses the H-band `clinic.chat_assistant` id and declares its own budget/permitted set rather than inventing defaults (`capability.json:18-34`); CI gating joins the existing job rather than creating a second product (`ci.yml:103-104`).

Error-code coverage: correctly N/A — H4 emits no §5.4 codes.

- **[High] No negative-control case: every scripted conversation asserts `pass`, so the gate cannot prove it is able to fail** — T1–T3 all expect `"pass"` (`conversation.test.ts:46-56, 71-73, 94-96`); the only failure-path assertion is T4's hand-constructed synthetic score through the pure function `deriveConversationOverall` (`:103-112`). No scripted case drives `runCase` to a `fail` — e.g. a fixture requesting a *wrong permitted* key (`right_keys: fail`), a transcript exceeding the round budget (`round_budget: fail`), or an allowlist regression (`permitted_set: fail`). A scorer regression that always returned `"pass"` (say, `scoreRightKeys` losing its loop) would leave the entire suite green. F1's gate has the `deliberately_regressed` prompt build for exactly this purpose (`harness.ts:279-340`); H4 has no analogue. Under the §3.10 every-branch rule, the failure branch of each of the three criteria is unexercised end-to-end.
- **[Medium] T4 proves per-conversation aggregation at the pure-function level only** — the "fails the whole conversation when a criterion fails on one leg" claim is asserted on a synthetic `ConversationScore` literal (`conversation.test.ts:103-112`), not on a scripted multi-leg conversation whose second leg fails a criterion. The remainder of the test re-runs the *passing* T3 case and asserts report shape (`not.toHaveProperty("legs")`, `:124-125`). The acceptance-unit claim is structurally sound (scoring happens once at the end over the whole transcript), but no failing multi-leg fixture proves it.
- **[Medium] No case asserts a conversation that fails to converge** — compounded with the §3 bug: there is no scripted case ending in `context_requested` (no answer) within budget, nor one breaching `maxContextRoundsPerTurn: 3` (`capability.json:20`), so neither the convergence branch nor the budget-boundary branch (`validator.ts:297-299`, strict `>`) is exercised. The named boundary — the declared round budget itself — has only a trivial `toBeGreaterThan(0)` assertion (`conversation.test.ts:57`).
- **[Low] T2's required-key case is single-leg** — `assistant_must_request_correct_key` has one leg (`cases/assistant_must_request_correct_key.json:3-13`), so the "right key" criterion is never scored across a multi-leg negotiation where the key request must come after scripted user turns; §13.5 frames the suite as scripted *multi-leg* conversations. The case proves the criterion, but minimally.
- **[Low] Non-portable path assertions propagated from F1** — T5 and T7 assert paths with forward-slash literals (`conversation.test.ts:148-153, 212`; also `prohibitions.test.ts:138`) while `path.join` yields backslashes on Windows, so the suite fails on a Windows checkout though CI (`ubuntu-latest`) passes. The pattern is inherited from F1's `golden.test.ts:51, 77` (already merged and reviewed), but H4 extended it rather than normalising with `path.sep`.
- **[Low] T6 is partly circular** — much of `extends_f1_harness_without_redefining_capability_evals` asserts file existence and `ci.yml` substring presence (`conversation.test.ts:190-202`); deleting the conversation suite's CI wiring *and* its assertions together defeats it. Its strong core is real, though: it re-runs the full F1 golden suite and asserts the capability list and report fields are unchanged (`:175-188`).

## 6. Recommended Improvements

1. **[High] Add a negative-control case per criterion** — e.g. `requests_wrong_permitted_key` (fixture asks for `patient.demographics@v1` when the script requires `visit.chief_complaint@v1` → `right_keys: fail`), `exceeds_round_budget` (a fourth consecutive context round → `round_budget: fail` via H2's real `conversation_budget_exhausted` path), and assert the run `overall` fails. This mirrors F1's deliberately-regressed build and makes the gate falsifiable.
2. **[Medium] Score convergence explicitly** — consume `expect_convergence` in `runCase`: when true, require the transcript's last assistant turn to be `kind: "model"`; fold a non-converged conversation into the `round_budget` criterion (or a fourth recorded field, if the contract is amended) and add a non-converging case. Remove or consume the dead `expected_outcome` blocks — ideally drive test expectations from them instead of hardcoding.
3. **[Medium] Decide and record the request-side permitted-set policy** — either extend `scorePermittedSet` to fail when a `context_requested` turn names a key outside `permittedKeySet` (matching §13.5 "stay inside the permitted set"), or amend the contract to state explicitly that requests are unconstrained because H2 drops at resolution, and cite that decision from the case file whose leg-1 fixture requests an out-of-set key.
4. **[Medium] Deconflate the criteria and deduplicate validation** — run `validateContext` once per case in `runCase`, pass the result to the scorers, and have `scorePermittedSet` fail only on forbidden-key obtainment (treating non-`ok` validation as "not obtained, key was dropped" only when the failure is not itself a budget breach, or recording `not_evaluable` per the contract if amended). Delete the dead `suppliedContext` reassignment.
5. **[Low] Reconcile `plan.md` with the `harness.ts` edit** — update the Files table and Consumes Binding to record the one-predicate extension honestly, as `tasks.md` T018 already does.
6. **[Low] Normalise path assertions** with `path.join`/`path.sep` (or assert on `path.relative` segments) so the suite runs green on Windows checkouts, matching CI.
7. **[Low] Make T2 multi-leg** (append the scripted resolution turn and a closing model answer) so the right-key criterion is scored across a negotiation, and drop the vacuous `usedLiveEgress` flag/assertions or replace them with a real fetch-interception guard if the harness ever gains a provider path.
