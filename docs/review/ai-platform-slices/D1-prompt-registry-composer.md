# Slice Review Report — D1: Prompt Registry and Composer

**Spec:** `specs/028-prompt-registry-composer/spec.md` · **Branch:** `ai/028-d1-prompt-registry-composer` · **Canonical:** §4.3.6, §5.7, §9.5, §5.3

## Executive Summary

D1 delivers the two modules its plan names — `src/prompt/registry.ts` (`resolveArtifact`, `resolvePromptVersion`, `verifyBuildPins`) and `src/prompt/composer.ts` (`composeRequest`) — plus the fixture artifact tree under `prompts/clinic.visit_summary/`, the `wrangler.toml` Text-module rule, and all twelve named tests across two suites. The core composition path matches the frozen contract with high fidelity: the ordered `system`/`system`/`system`/`data`/`user` parts, the schema-derived format instruction, the `<key name="…" shape="…">` delimited rendering with `</` neutralization, and the single `internal_error` failure code are all present and golden-proven. The substantive defects cluster on the registry side and on drift: the pinned context-rendering template is resolved and then discarded — rendering is hardcoded in the composer, so the hash pin guards an artifact that has no effect on output; the build-pin verification is only ever exercised against the test file's inline fixture manifest, so a real deployed manifest pinning a missing or altered artifact would not fail any build; and the composer mints its own request reference when one is not supplied, diverging from the stage-9 journal row the correlation id exists to match. Since D1 froze its contract, H2's conversational machinery (transcript rendering, `assistant` parts, the context-request second output shape) has merged into `composer.ts` with its own test suite without amending the frozen artifact D2/D3/D6 are bound to consume — the same drift pattern as C1's J1, C2's H2, and C3's H3 merges. Coverage meets the named-test floor but tests only one of the four `internal_error` branches, only one of the three pinned artifacts for the altered/missing cases, and pins the hardcoded empty stop-conditions array as expected behaviour rather than manifest-sourced forwarding.

## Critical Issues

None. At the library level this slice scopes itself to, the done-when criteria are met and test-proven: a manifest-pinned ref resolves to its deployed artifact, an altered or missing artifact throws in `verifyBuildPins`, no D1 binding is touched, the composed request matches the golden, the format instruction tracks the output schema, context is rendered as neutralized delimited data, and the failure path emits only `internal_error` with no provider call. As with the C-slices, `composeRequest` has no caller in `src/` outside `src/prompt/` — consistent with the contract deferring pipeline consumption to D2/D3 — an observation rather than a defect here. The dead template artifact (Bug 1) is the most consequential finding, but because the hardcoded rendering is byte-identical to what the contract's concrete syntax prescribes, no composed output is currently wrong; it is classified as a bug rather than a critical violation.

## Bugs

1. **The pinned context-rendering template is resolved, checked, and discarded — the hash pin guards an artifact with no effect on output** (`ai-platform/src/prompt/composer.ts:164-170`, `:59-90`). `composeRequest` resolves `contextRenderingTemplateRef`, returns `internal_error` if absent, and then never reads the resolved content: `renderDelimitedContext` hardcodes the `<key name="…" shape="…">` block format and iterates the manifest's `Context requirements` directly. The template artifact's own content — `{{visit.chief_complaint@v1}}` placeholders (`ai-platform/prompts/clinic.visit_summary/template-visit-summary.md:1-3`) — is substituted by nothing. §4.3.6 and FR-004 require the context payload "rendered through the capability's template"; the frozen contract's input table (contracts/composer-output.md §4.1 row 4) binds the `data` part to `contextRenderingTemplateRef`. As built, editing the template changes no output yet trips the build pin, and the template's pin is ceremony — the one artifact whose whole purpose is to govern rendering does not govern it.

2. **The composer mints a request reference when one is not supplied, diverging from the stage-9 journal row** (`ai-platform/src/prompt/composer.ts:136-138`, `:214`). `resolveRequestReference` falls back to `generateRequestReference()` — a freshly minted correlation id produced inside stage 10. Per §6.1 the request reference is minted at stage 9 (journal the request) *before* composition, and the journal row carries it; a composer-generated fallback would put a reference on the canonical request that no journal row has ever seen, breaking the correlation the field exists for. Contract §4.2 freezes correlation ids as coming from the request and the principal, not invented by the composer. The fallback is unexercised by every test (all pass `requestReference`), so the divergence path is live and unasserted.

3. **Stop conditions are hardcoded to an empty array — the composer invents the default it is forbidden to invent** (`ai-platform/src/prompt/composer.ts:209`). Contract §4.2/§4.3 and spec Assumptions state stop conditions come from the manifest's Output/Input field groups, and the spec's final Out-of-Scope paragraph forbids the composer inventing "any threshold, timeout, limit, or default beyond the manifest values." The implementation emits `"stop conditions": []` unconditionally; no manifest field is read. T-D1-10 (`ai-platform/test/prompt-composer.test.ts:388`) then pins `toEqual([])` as expected behaviour, so the named "output constraints present" test proves presence of a constant, not forwarding of a manifest value — and a manifest that did declare stop conditions would have them silently dropped.

4. **Tone and refusal policy — two of the five named output constraints — appear nowhere on the composed request** (`ai-platform/src/prompt/composer.ts:199-217`). §4.3.6 and FR-004 name the output constraints as "max tokens, stop sequences, language, tone, refusal policy." The composer carries max output tokens, language (as `sampling constraints.allowedLanguages`), and the hardcoded stop conditions; tone and refusal policy are neither forwarded nor derived. Contract §4.3 asserts "the fixture manifest declares them" — it does not: the fixture manifest in both test files has no tone or refusal-policy field, and A4's ten field groups contain none. The contract overclaims the fixture, and the composer under-delivers the architecture; one of the two must move.

5. **The altered/missing-artifact build tests can only ever exercise the system instruction — the mockability machinery exists for one artifact of three** (`ai-platform/src/prompt/registry.ts:11-26`). `loadSystemInstruction` performs a dynamic, `vi.doMock`-able import of the non-`?raw` module id, wrapped in try/catch with a top-level `await` (`:26`), purely so T-D1-02/03 can inject tampered or absent content (`ai-platform/test/prompt-registry.test.ts:241-243`, `:257-259`). The rules fragment and template are static `?raw` imports (`:3-5`) with no equivalent seam, so their altered and missing branches inside `verifyBuildPins`'s loop (`:63-80`) are untestable as written — and untested. Production module-init code carrying a test-only dynamic import and top-level await is also a fragility: under `wrangler deploy` the dynamic non-raw import resolves through the Text rule and its result *replaces* the bundled `?raw` content whenever it has a `default` export, so the deployed artifact content is whichever of two module-resolution paths wins, not a single pinned source.

6. **Build-pin verification runs only against the test file's inline fixture manifest — a real manifest pinning a missing or altered artifact fails no build** (`ai-platform/src/prompt/registry.ts:55`; only callers are `ai-platform/test/prompt-registry.test.ts:249`, `:265`, `:281`). `verifyBuildPins` has no caller in `src/` and no module-init invocation; the build tests construct `validManifest()` inline and verify its three hardcoded refs. The done-when — "the build fails if a pinned artifact is missing or altered" — is therefore proven only for the fixture's pins. A capability manifest resolved by C1 pinning `clinic.visit_summary/system@v2` (absent from the hardcoded `ARTIFACT_MAP`) would pass the build and fail only at request time as `internal_error`, converting a build failure into a runtime one — the exact inversion FR-002 exists to prevent.

7. **Composition failures are swallowed with no logging** (`ai-platform/src/prompt/composer.ts:226-228`). The blanket `catch` discards the error and returns bare `internal_error`. Stage 10 is CPU-only composition of reviewed artifacts; any throw here is by definition a platform defect (corrupt artifact, malformed manifest), and the one diagnostic that would identify it — the error, with the trace id already in scope — is dropped. Same pattern as C3's stage-16 swallow, minus the contract qualifier that permitted it there.

## Architectural Deviations

1. **H2's conversational machinery is merged into `composer.ts` without amending the frozen contract — the same drift pattern as C1's J1, C2's H2, and C3's H3 merges.** The module now carries the `transcript` input and `Transcript` import (`ai-platform/src/prompt/composer.ts:9`, `:20`), the conversational format instruction offering `CONTEXT_REQUEST_SCHEMA_ID` as a second output shape (`:39-46`), a conversational rendering branch (`:65-71`), `renderDelimitedContextObject` and `renderTranscriptPriorTurns` emitting `assistant` parts (`:92-134`), and the transcript splice into the part list (`:177-180`, `:190`) — all exercised by a merged `test/conversational-composer.test.ts` suite. The frozen contract is explicit that none of this exists: §1 states "D1 composes for a `single_shot` capability only" and §4.1 states "the `assistant` tag is reserved for H2's transcript rendering and is not part of this frozen contract's output shape"; spec Out of Scope assigns the conversational paragraph of §4.3.6 to band H. The merged code also violates the frozen rendering rules it sits beside: the conversational branch echoes the key name as the `shape` attribute (`:68`, `:98`) rather than the key's published shape ref, and iterates `Object.entries` order rather than manifest `Context requirements` order. D2/D3/D6 are bound to a contract whose module no longer matches it.

2. **The registry is a hardcoded map of the fixture capability, not the build-time index Clarification Q1 froze** (`ai-platform/src/prompt/registry.ts:2-9`, `:28-32`, `:47`). Q1's answer was "a build-time index of those imports" over the `prompts/<capability-id>/` tree; the implementation is three hand-written imports and a hand-written `ARTIFACT_MAP`, and `resolveArtifact` ignores its `manifest` parameter entirely (`void manifest`). Adding a second capability requires editing `registry.ts` — the registry is neither data-driven nor an index, and the pin index `registry.json` is likewise per-capability hardcoded into the module. For a one-fixture slice this is scope-appropriate, but the clarification's mechanism is unimplemented and the deviation is unrecorded.

3. **The surfaced `promptVersion` has no consumer; C3 records the manifest field independently** (`ai-platform/src/prompt/composer.ts:224`; `ai-platform/src/journal/index.ts:196`). Contract §7 freezes "D1's surfacing … provides the value C3 records," but C3's stage-9 insert binds `manifest["Prompt binding"].systemInstructionArtifactRef` directly and never sees the composer's output. The done-when "the prompt version is recorded on the journal row" is satisfied by C3's own read, so the two answers to "which prompt was live?" agree only because both read the same field today — any future resolution logic in `resolvePromptVersion` (alias, activation pointer) would diverge silently from the journaled value. Relatedly, the journal column is named `prompt_artifact_hash` while both sides write a ref string, not a hash (consumed from C3, not modified — but D1's contract §7 entrenches the naming mismatch by calling the ref "the resolved prompt artifact version" while the schema calls it a hash).

4. **Three module-resolution mechanisms for the same artifacts, with the CI-verified bytes not proven to be the deployed bytes** (`ai-platform/wrangler.toml:8-11`; `ai-platform/src/prompt/registry.ts:2-5`, `:13-16`). The plan and tasks specify Wrangler `[rules]` type `"Text"` imports; the static imports use the Vite `?raw` idiom; the dynamic import uses the bare path. The pin hashes in `registry.json` are computed over whatever Vitest's `?raw` yields, and no build step asserts that `wrangler deploy`'s Text-rule content is byte-identical (line-ending or trailing-newline differences would ship an artifact whose deployed content differs from the CI-pinned content). Combined with Bug 5's prefer-the-dynamic-import logic, which content the deployed Worker actually composes from is determined by module-resolution order, not by the pin.

5. **The composer is unwired; nothing in `src/` calls `composeRequest`** (no reference outside `src/prompt/` and tests). Consistent with the contract deferring consumption to D2/D3 — worth restating, as the prior reports did, because every ordering done-when (stage 10 after stage 9, reference from the journal, prompt version onto the row) is currently proven only against the suites' own fixtures.

## Missing or Weak Tests

1. **T-D1-04's prompt-text schema guard is evadable by any plural or suffixed identifier** (`ai-platform/test/prompt-registry.test.ts:29-30`). `PROMPT_TEXT_IDENTIFIER_PATTERN` is anchored exact-match — `/^(prompt|system_instruction|instruction)$/i` — so a `prompt_text`, `prompt_body`, `instructions`, or `system_prompt` column passes the guard while storing exactly what FR-003 forbids. The one invariant whose entire point is "no prompt text in any D1 table" is enforced by a pattern that catches three spellings.

2. **The altered/missing build cases cover one artifact of three, and the missing-pin branch is untested** (Bug 5; `ai-platform/test/prompt-registry.test.ts:238-268`). T-D1-02/03 mock only `system.md`; no case alters or removes the rules fragment or the template, and no case removes a ref from `registry.json` to hit the "Missing registry pin" throw (`ai-platform/src/prompt/registry.ts:71-73`). The coverage rule demands every branch of every rule; `verifyBuildPins`'s loop has four failure branches and two are unexercised.

3. **Only one of the four `internal_error` branches has a case** (`ai-platform/test/prompt-composer.test.ts:414-449`). T-D1-12 injects a missing template ref (`:168-170`); the missing-system-instruction branch (`ai-platform/src/prompt/composer.ts:151-153`), the missing-business-rule-fragment branch (`:158-160`), and the underivable-format-instruction branch (unknown derivation rule or unhandled mode/schema combination, `:172-175`) are all unexercised. The slice emits exactly one error code and the suite still under-covers its branches.

4. **The golden is a parallel re-implementation in the test file, not a frozen artifact** (`ai-platform/test/prompt-composer.test.ts:141-210`). `goldenCanonicalRequest` duplicates the composer's rendering logic — including its own copy of `renderDelimitedContext` — and T-D1-06 asserts byte-for-byte equality against it. This catches accidental drift but not a shared semantic error: change both copies' understanding of the format (or introduce the same bug in both) and the golden stays green. A checked-in golden file the composer output is compared against would make the fixture independent of the implementation.

5. **T-D1-09 is specced as a Pipeline test and implemented as unit string assertions** (`ai-platform/test/prompt-composer.test.ts:342-374`; spec.md:80). The R-10 enforcement point per §5.3 is the adapter boundary — "no provider mapping may promote it to an instruction role" — yet no test asserts anything at that boundary; the case proves only that neutralized text sits inside a `data` part's payload. The neutralization itself is also only delimiter-deep: `\u003c/` is valid JSON string escaping that any downstream JSON parse decodes back to `</`, so the guarantee rests entirely on the `data` role surviving to the provider — the one link no test touches.

6. **No test joins the surfaced prompt version to the journal row** (Deviation 3). The required case "the prompt version is recorded on the journal row" is asserted only as `resolvePromptVersion` returning the ref string (`ai-platform/test/prompt-registry.test.ts:287-294`) and the composer echoing it (`ai-platform/test/prompt-composer.test.ts:261`); nothing asserts that what C3 writes to `prompt_artifact_hash` equals what the composer surfaces, so the single-answer property of §9.5 is unproven across the seam.

7. **T-D1-11 re-runs the composer's own guard on top-level keys only** (`ai-platform/test/prompt-composer.test.ts:395-412`). The composer already calls `assertNoProviderShapedFieldNames(Object.keys(request))` internally (`ai-platform/src/prompt/composer.ts:219`); the test repeats the identical call, so it cannot fail unless the composer's own call is deleted — and both calls inspect only top-level keys, leaving nested fields (`output format directive`, `sampling constraints`, message-part structure) outside the provider-shape guard.

8. **T-D1-10 pins the hardcoded empty stop-conditions array as correct** (Bug 3; `ai-platform/test/prompt-composer.test.ts:388`). The named test requires max tokens, stop conditions, and language constraints "present"; asserting `toEqual([])` proves presence of a constant and would keep passing if manifest forwarding of stop conditions were never implemented — which is the current state.

## Recommended Improvements

- **Make the template real or unpin it** (Bug 1): either render the `data` payload by substituting the template's `{{key}}` placeholders (so the pin guards live content and the block format can change per capability build as §4.3.6 intends), or drop `contextRenderingTemplateRef` from the pin set and the contract until H-band work needs it.
- **Remove the reference-minting fallback** (Bug 2): require `requestReference` as a mandatory composer input sourced from the stage-9 row, and delete `generateRequestReference` from the composer.
- **Source stop conditions from the manifest and resolve tone/refusal policy deliberately** (Bugs 3, 4): add the manifest fields and forward them, or amend §4.3.6/FR-004/contract §4.3 to drop them — and correct the contract's false claim that the fixture declares them.
- **Generalize the registry to Q1's build-time index** (Deviation 2, Bug 6): generate the ref→content map over `prompts/**` at build time, run `verifyBuildPins` against every deployed capability manifest (or every `prompts/**/registry.json`) rather than an inline fixture, and give all artifacts one uniform import mechanism so the tamper/missing tests cover every pinned ref.
- **Prove the deployed bytes equal the pinned bytes** (Deviation 4): a build smoke test that hashes the artifacts as Wrangler's Text rule delivers them, or switch the static imports to the Wrangler form and drop `?raw` from `src/`.
- **Amend the frozen contract for the merged H2 reality** (Deviation 1): add the `transcript` input, the `assistant` parts, the conversational format instruction, and the conversational rendering branches to contracts/composer-output.md — including fixing the `shape`-echo and ordering deviations — exactly as C1's, C2's, and C3's contracts owe their amendments.
- **Log composition failures** (Bug 7): `console.error` with the trace id before returning `internal_error`; stage-10 throws are platform defects and should be diagnosable.
- **Add the missing cases**: altered/missing rules-fragment and template pins; the missing-registry-pin branch; the three uncovered `internal_error` branches; a frozen-file golden; a journal-row assertion that the recorded prompt version equals the surfaced one; a substring-based prompt-text identifier guard; a manifest that declares stop conditions forwarded onto the request.
