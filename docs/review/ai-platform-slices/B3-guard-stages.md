# Slice Review Report — B3: Guard Stages

**Spec:** `specs/023-guard-stages/spec.md` · **Branch:** `ai/023-b3-guard-stages` · **Canonical:** §4.3.2, §4.2.1, §5.6, §4.3.3, §4.3.4, §4.3.12, §7.5, §6.1 stages 2–4

## Executive Summary

B3 delivers the three guard modules as sibling-per-concern units — `src/identity/` (TokenVerifier port, `EnrolledKeyVerifier`, frozen `Principal`), `src/entitlement/` (AI-enablement, plan tier, grant, four kill-switch scopes), and `src/rate-limit/` (three composite keys, in-isolate tally, bucketed `platform_counter` flush) — with all 24 named tests present and asserting real behaviour against the Miniflare D1 harness. The `alg === "EdDSA"` pin is genuine, the skew math matches the frozen contract, the principal is properly frozen, and the flush is correctly bucketed with an idempotent upsert. But the slice ships one severe security hole: the verification key is selected by `kid` alone and never bound to the token's `iss`, so any enrolled installation can mint a token naming a victim installation as issuer and pass identity with the victim's principal — §4.3.2's "selected by `iss` and `kid`" is only half implemented, and the frozen contract omits the check too. Underneath that: kill-switch evaluation throws an unhandled `ConfigCacheMissError` on the normal no-kill-switch path (the tests mask it by fabricating `{active:false}` rows over a `control_audit` derivation that has no "switch lifted" semantics, and the A5 schema has no kill-switch home at all); `deleted` installations still authenticate; identity and entitlement rejections are never counted despite FR-011 covering stages 2–4; nothing in the Worker ever calls the flush; and the token's `ver` is never checked against the §5.6/§7.3 accepted-`ver` set. Test-wise, the HMAC-alg case, unknown-`kid`, revoked-key, expired-inside-skew, malformed-token, and kill-switch-absent branches are all uncovered, and the verifier-swap test is circular.

## Critical Issues

1. **Cross-installation impersonation: the verification key is selected by `kid` alone and never bound to `iss`** (`ai-platform/src/identity/index.ts:255-267`; frozen contract `specs/023-guard-stages/contracts/token-verifier.md:101-107`). §4.3.2 is explicit — "The key is selected by `iss` and `kid`" (`docs/architecture/ai-platform/01-ai-platform.md:1176`) — and the `installation_key` row carries `installation_id` precisely so the key can be bound to its owner. The verifier loads the installation by `payload.iss` (`:243`) and the key by `header.kid` (`:257`) but never checks `keyRow.installation_id === payload.iss`. Any enrolled clinic can therefore mint a token with `iss` set to a *victim* installation id and `kid` naming its *own* key: the victim's installation row loads `active`, the attacker's own key verifies the attacker's own signature, and the resulting principal carries the victim's `installationId` — full cross-tenant impersonation that then flows into entitlement, rate-limit keys, and the journal. This defeats the tenant-isolation property the guard exists for (§14 "III"; spec Constitution Alignment). The omission is frozen into the contract's 12-step algorithm (steps 6–8 check existence, suspension, and revocation, never ownership), so B4/J4 will bind to a contract that sanctions it — the contract must be corrected alongside the code, and a test that signs with installation B's key while claiming `iss` = A must be added.

2. **Kill-switch evaluation crashes on the normal path, and the state it reads has no production source** (`ai-platform/src/entitlement/index.ts:91-97`, `:151-181`). `loadKillSwitch` calls `loadConfig`, which throws `ConfigCacheMissError` when the reader returns `"miss"` (`src/config-cache/index.ts:97-100`); `evaluateEntitlement` wraps only the *grants* load in a miss handler (`:144-149`) and lets a kill-switch miss propagate as an unhandled exception. The normal state of the world is *no kill switches exist* — so on a cold isolate with an honest reader, the first entitled request throws instead of passing. The tests conceal this: the harness reader fabricates `{ active: false }` rows when no `control_audit` row matches (`test/entitlement.test.ts:343-346`), so the miss branch never executes. Worse, that harness derivation is the *only* definition of kill-switch state anywhere: the A5-frozen schema has no `kill_switch` table (`ai-platform/migrations/20260731120000_platform_schema.sql:4-138`), §7.3 lists no kill-switch entity, and the control_audit derivation the tests invent has no lift semantics — any historical `kill_switch_*` audit row reads as `active: true` forever (`test/entitlement.test.ts:335-346`). B3's stage depends on a `{active: boolean}` row shape that no production component can currently produce, in either direction.

## Bugs

1. **`deleted` installations still authenticate** (`ai-platform/src/identity/index.ts:251-253`). The lifecycle check rejects only `status === "suspended"`; B2's terminal `deleted` status — and any future or unknown status — falls through and verifies. B2's delete leaves the `installation_key` rows in place, so an off-boarded clinic's unexpired tokens keep passing identity and produce a valid principal. The check should be fail-closed (`status !== "active"` → reject), which also covers the `installation_suspended` code path unchanged.
2. **Identity and entitlement rejections are never counted** (no call sites; only `ai-platform/src/rate-limit/index.ts:110` calls `recordRejection`). FR-011 and §4.3.12 require *guard rejections from stages 2–4* to be tallied into bucketed `platform_counter` rows — `unauthenticated`, `installation_suspended`, `forbidden_capability`, and `capability_disabled` increment nothing. Two-thirds of the rejection signal §4.3.12 says the journal cannot supply is simply absent, and the `dimensionSetFor` shape (`rate-limit/index.ts:44-53`) hardcodes `error_code: "rate_limited"`, so even the tally's dimension model only accommodates the one stage.
3. **Nothing ever flushes the tally in production** (`ai-platform/src/rate-limit/index.ts:122-145`; `ai-platform/src/worker.ts:131` runs only retention/rollup on the scheduled event). FR-011's "flushed periodically" is satisfied only by tests invoking `flushRejectionCounters` directly (`test/rate-limit.test.ts:289`, `:390`); no `scheduled` handler, `waitUntil`, or pipeline glue calls it, so as wired, rejections accumulate in a module-level Map that is never persisted and evaporates with the isolate. B4 then duplicated the flush verbatim with its own private tally (`src/admission/index.ts:299-322`) instead of consuming B3's export — two copies of the same frozen behaviour already drifting.
4. **Two incompatible key conventions on the same `D1Reader` port** (`ai-platform/src/identity/index.ts:243`, `:257` pass raw keys — A5's convention, per `test/config-cache.test.ts:80`; `ai-platform/src/entitlement/index.ts:53-59` prefixes `kind:key` via `scopeReaderForKind`). A single production reader cannot serve both stages without straddling both conventions, and no production `D1Reader` implementation exists anywhere in `src/` — the two test harnesses simply encode the two different conventions (`test/identity.test.ts:302-324` vs `test/entitlement.test.ts:281-353`). The prefix workaround has since spread to `src/capability/index.ts:129` and `src/admission/index.ts:82`, so the divergence is compounding; A5's port contract is ambiguous about which is authoritative, and B3 is where the split entered the tree.
5. **Plan-scoped capability grants are never consulted** (`ai-platform/src/entitlement/index.ts:133-149`; harness mirrors it at `test/entitlement.test.ts:314-326`). §7.3 states grants are written at `plan` *or* `installation` scope (`docs/architecture/ai-platform/01-ai-platform.md:2258`), but the grant check looks up only `installation:{id}` scope, so a capability granted at plan scope is falsely rejected `forbidden_capability`. The `EntitlementContext.capabilityVersion` field is accepted and never used (`:27`, `:133-149`) — the grant lookup ignores version entirely.
6. **Malformed `allowed_capabilities` crashes the stage** (`ai-platform/src/entitlement/index.ts:66-68`). A string value that is not valid JSON makes `JSON.parse` throw out of `evaluateEntitlement` — an unhandled 500 on a corrupt entitlement row rather than a fail-closed `forbidden_capability`.
7. **A mid-flush D1 failure double-counts on the next flush** (`ai-platform/src/rate-limit/index.ts:129-144`). The loop writes rows one statement at a time and clears the tally only after the loop; if a `run()` throws partway, the already-written entries remain in the map and are upserted again next flush. Delete each entry (or snapshot-and-clear) before writing so a retry cannot double-apply.

## Architectural Deviations

1. **The token's `ver` is never checked against the accepted-`ver` set** (`ai-platform/src/identity/index.ts` — `ver` is parsed at `:111-127` and carried onto the principal, never validated; contract `token-verifier.md:89-122` omits the check from the algorithm). §5.6 is normative: "The identity stage checks the token's `ver` against the accepted-`ver` set, a single global `token_contract` record in D1 read through the same config cache… A token whose `ver` is not in the set fails verification as `unauthenticated`" (`docs/architecture/ai-platform/01-ai-platform.md:1787-1793`; entity at `:2245`, `:2272-2282`). The spec's Out of Scope carves out only the *overlapping* acceptance (J4); the base membership check is identity's own. Architecture wins over the Speckit documents — report the spec/contract as the documentation mismatch. Note the consumed gap that enables it: A5's frozen schema has no `token_contract` table, so the check currently has nothing to read; an A5 amendment is required either way.
2. **FR-006's Rate Limiting bindings are typed but undeclared** (`ai-platform/src/rate-limit/index.ts:6-11` requires `RATE_LIMITER_INSTALLATION{,_ACTOR,_CAPABILITY}`; `wrangler.toml` declares none, and `specs/023-guard-stages/tasks.md:114` explicitly forbade any wrangler change in the slice). The module can only ever run against test fixtures as shipped; the tasks file froze a contradiction between FR-006 ("using the Rate Limiting binding") and the slice's own constraint list.
3. **The plan's unit/integration harness split was silently abandoned** (`specs/023-guard-stages/plan.md:164-193` places the nine pure-unit identity cases under `vitest.config.ts`; `tasks.md:37` (T001) and the configs route all three files to the workers pool only — `ai-platform/vitest.config.ts:7-10` excludes them). The named "Unit"-layer tests now require the Miniflare pool and do not run under default `npx vitest run`; plan and tasks disagree, and the plan was never corrected.
4. **B3 invented the plan-tier vocabulary and duplicated the frozen `Principal` type** (`ai-platform/src/entitlement/index.ts:51` hardcodes `["starter","standard","professional","enterprise"]` with no § citation — a configuration surface R-20 says not to invent; `:13-24` redeclares `Principal` structurally instead of importing it from `src/identity/`, the contract's named source of truth, so the two can drift without a compile error). Unknown tiers fail closed (`:77-79`), which is the right direction, but the ordering itself is unanchored.

## Missing or Weak Tests

1. **`identity_rejects_non_eddsa_alg` covers only `alg: "none"`** (`ai-platform/test/identity.test.ts:386-389`). The spec names HMAC algorithms explicitly ("`none` or an HMAC algorithm", spec.md:220, 252-254); no `HS256` case exists, so the algorithm-confusion branch the pin exists to defeat is only half pinned.
2. **No case binds the key to the issuer, and the unknown-key and revoked-key branches are untested.** The suite has `identity_rejects_unknown_issuer` (`test/identity.test.ts:425-431`) but nothing for a `kid` that misses (`src/identity/index.ts:258-263`), a key with `revoked_at` non-null (`:265-267`), or a valid key owned by a *different* installation — the case that would have caught Critical 1.
3. **The expiry side of the skew boundary is tested only on the reject side** (`test/identity.test.ts:400-407`). The not-yet-valid boundary has both an accept (`:408-416`) and a reject case; the expiry boundary has only `exp = NOW - skew - 1` — an expired-but-inside-skew token that must be *accepted* per the contract's symmetric window (`contracts/token-verifier.md:109-111`) is never exercised.
4. **No malformed-token coverage.** Two-segment tokens, invalid base64url, non-JSON header/payload, a missing §5.6 claim, and an empty `kid` each hit a distinct rejection branch (`src/identity/index.ts:198-239`) and none has a case; the coverage rule's "every branch of every rule" is unmet for the parse gauntlet.
5. **`verifier_swap_changes_no_outcome` is circular** (`test/identity.test.ts:496-521`). The fake verifier is seeded with a map of the enrolled verifier's *own* outcomes and then asserted to equal them — the test cannot fail for any behavioural reason and proves only that the port type compiles. A meaningful version drives both implementations from an independent expectation table.
6. **No kill-switch-absent case** — the harness fabricates `{active:false}` rows (`test/entitlement.test.ts:343-346`), so Critical 2's crash path is invisible; there is also no kill-switch-*lifted* case, because the invented state model has no such concept.
7. **The revoked-grant branch is dead in the harness** (`test/entitlement.test.ts:321` filters `revoked_at IS NULL` in SQL), so `src/entitlement/index.ts:141-143` never executes; nor is there a plan-scoped grant case (Bug 5).
8. **No counter assertions for identity or entitlement rejections** — FR-011's stage 2–3 tally (Bug 2) has no test; counter cases exist only for `rate_limited` (`test/rate-limit.test.ts:271-405`). Relatedly, nothing pins the flush trigger (Bug 3), and no deleted-installation case exists (Bug 1).

## Recommended Improvements

- **Bind the key to the issuer before verifying** (`src/identity/index.ts:255-267`): reject `unauthenticated` unless `keyRow.installation_id === payload.iss`, correct contract §6 to include the check, and add the cross-installation forgery test. This is the one change without which the guard authenticates nothing that matters.
- **Give kill-switch state a real home and define miss semantics** (`src/entitlement/index.ts:91-97`): treat a kill-switch miss as inactive (fail-open for absence, fail-closed only on an explicit active row), catch the miss like the grants path does, and raise an A5 amendment for a `kill_switch` table (or a §7.3-sanctioned derivation with lift semantics) instead of the test-only `control_audit` fiction.
- **Fail closed on lifecycle status** (`src/identity/index.ts:251-253`): reject anything `!== "active"`.
- **Count every guard rejection and wire the flush** (`src/rate-limit/index.ts`): lift the tally into a shared guard-telemetry seam (or export `recordRejection(code, dimensions)`), call it from identity and entitlement, generalise `dimensionSetFor` beyond `rate_limited`, invoke the flush from the Worker's `scheduled` handler or `ctx.waitUntil`, and delete B4's duplicate copy (`src/admission/index.ts:299-322`) in favour of the B3 export.
- **Unify the reader key convention**: align entitlement/capability/admission with A5's unprefixed convention, or amend A5's `D1Reader` to take `(kind, key)` — but pick one, and add a production `D1Reader` so the convention is pinned by code, not by two disagreeing test harnesses.
- **Enforce `ver` membership** (needs the `token_contract` table — the same A5 amendment): read the accepted set through the config cache and reject unaccepted `ver` as `unauthenticated` per §5.6, leaving the two-value overlap window to J4.
- **Declare the three rate-limiting bindings in `wrangler.toml`** so FR-006 is satisfiable outside test fixtures.
- **Order the cheap checks first** (`src/identity/index.ts`): audience and skew are pure claim checks and can run before the `installations`/`keys` loads, so obviously-dead tokens never touch the cache; consider negative-caching misses in A5 so an unknown-`iss` spray does not cost a D1 read per request per isolate.
- **Fail closed on corrupt entitlement data** (`src/entitlement/index.ts:61-70`): a malformed `allowed_capabilities` should reject `forbidden_capability`, not throw; consult plan-scoped grants and either honour `capabilityVersion` in the grant lookup or drop it from `EntitlementContext`.
- **Import `Principal` from `src/identity/`** in entitlement and anchor the plan-tier ordering to an architecture-cited source (or an A5 config entity), not a module-local constant.
- **Add the missing cases**: HMAC alg; unknown `kid`; revoked key; cross-installation `iss`/`kid`; expired-inside-skew accept; the malformed-token gauntlet; deleted installation; kill-switch absent and lifted; revoked grant; plan-scoped grant; stage 2–3 counter increments; and a non-circular verifier-swap driven by an independent expectation table.
