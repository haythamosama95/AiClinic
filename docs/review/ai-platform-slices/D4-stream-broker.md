# Slice Review Report — D4: Stream Broker, Prose Streaming, and Cancellation

**Spec:** `specs/031-stream-broker/spec.md` · **Branch:** `ai/031-d4-stream-broker` · **Canonical:** §4.3.10, §6.4, §5.5, §6.5, §9.7

## Executive Summary

D4 delivers the two modules its plan names — `src/stream/index.ts` (`createStreamBroker`: ordered relay, injectable-ticker heartbeats, prose incremental guards, one-terminal-event suppression, connection-scoped cancel with credit and journal sinks) and `src/stream/prose-guards.ts` — plus all nineteen named tests in a single integration suite. The happy paths are structurally faithful: chunks relay in order with sequence numbers, heartbeats flow through an injectable ticker, each incremental guard aborts to exactly one `failed` carrying `validation_failed`, disconnect aborts the broker-held `AbortSignal` and terminates as `cancelled` with partial credit and a journal-terminal record, and cancel-before-first-token and mid-stream are separate cases. The substantive failures cluster in three places. First, error containment: the chunk-consumption loops have no `catch` anywhere, so any throw from the chunk source — most importantly the `AbortError` a real provider fetch raises when the broker aborts it on disconnect — escapes `run()` as an untyped rejection with no terminal event, no credit, and no journal record; the entire one-terminal-event and cancel done-when holds only because the test fixtures swallow aborts gracefully. Second, the guard layer: the length ceiling is checked per-chunk rather than against the assembled text and is absent from the completion-time set, so cumulative overflow — the acceptance scenario's own "assembled … exceeds the length ceiling" case — can never trip; and the "full guard set" is a strict subset of the checks already run incrementally on the same assembled text, making completion-time validation structurally vacuous and its throw-on-violation path unreachable (and uncaught). Third, scope: the frozen contract declares structured modes out of scope (D6), yet the module implements a full `structured` / `structured_atomic` path — `partial_structured` placeholder documents, a `progress` event, and a `runValidationPhases` dependency — on the frozen D4 surface. The journal-terminal sink is fed only on cancel, never on `completed` or `failed`, contrary to contract §2.1, and the module is unwired: nothing in `src/` calls `createStreamBroker`.

## Critical Issues

1. **No `catch` anywhere around chunk consumption — a throwing chunk source defeats every terminal-event, credit, and journal guarantee this slice exists to make** (`ai-platform/src/stream/index.ts:210-256`, `:302-353`, `:370-376`; `disconnect` at `:380-386`). Both `runProse` and `runStructured` iterate `chunkSource.stream({ signal })` inside `try/finally` with no `catch`. Two production consequences: (a) on client disconnect the broker aborts the in-flight fetch (`:385`) and then relies on the async iterator *ending gracefully* so the post-loop check (`:258-261`) can call `handleCancel` — but a real provider fetch rejects with `AbortError` when aborted, so `run()` rejects, `handleCancel` never runs, and the request emits no `cancelled` terminal, credits no partial usage, and leaves no journal-terminal record — the three core cancel done-whens, all lost on the exact path they are required on; (b) any mid-stream provider/parse error escapes as an untyped rejection instead of a `failed` terminal with a taxonomy code, breaking §5.5 rule 4 ("exactly one terminal event … never inferred from silence") for every error the source can raise. The suite cannot see this because every fixture generator treats abort as a graceful `return` (`ai-platform/test/stream-broker.test.ts:135-138`, `:147-150`) and no case makes the source throw — the known context that the D2 port is streamless means the first real wiring of this broker is precisely where an abort-rejecting source appears. A `disconnect` against a source that *ignores* the signal is likewise unbounded: the loop never exits, the terminal is never emitted, and the heartbeat keeps ticking forever (`:201-207`, `:380-386`).

## Bugs

1. **The length ceiling is enforced per-chunk, never on the assembled text — cumulative overflow is undetectable, and the acceptance scenario's "assembled exceeds the ceiling" case cannot trip** (`ai-platform/src/stream/prose-guards.ts:34-36`; called from `ai-platform/src/stream/index.ts:235`). `checkIncrementalGuards` compares `chunk.length > thresholds.maxLength`, so a stream of N chunks each under the ceiling whose total exceeds it sails through; conversely one large legitimate chunk false-positives even when total output is within bounds. The completion-time `runFullGuardSet` (`prose-guards.ts:41-49`) omits the length check entirely, so the assembled-length boundary named in spec Acceptance Scenario 3 ("whose assembled or incremental output exceeds the length ceiling") is enforced nowhere. T-D4-03 feeds a single oversize chunk (`ai-platform/test/stream-broker.test.ts:249-252`) — exactly the shape the wrong implementation handles — so the suite is green on the bug.

2. **`runFullGuardSet` throws on violation and nothing catches it — a completion-time guard failure would reject `run()` instead of emitting the required `failed` terminal** (`ai-platform/src/stream/prose-guards.ts:46-48`; call site `ai-platform/src/stream/index.ts:267`). The throw escapes `runProse` (which has `try/finally` but no `catch`) as a bare `Error("guard_violation:…")` — no `failed` event, no taxonomy code, no journal-terminal record, and a leaked promise rejection for the caller. The path is unreachable today only because of Bug 3; the moment the completion set gains any real check, this becomes Critical 1's twin.

3. **The "full guard set" is a strict subset of the incremental checks over the same text — completion-time validation is structurally vacuous and can never fail** (`ai-platform/src/stream/prose-guards.ts:41-49` vs `:29-39`). Incremental checking already runs `checkStopSequenceAndLeak(assembled, …)` after *every* chunk, i.e. over the entire assembled text including the final chunk; `runFullGuardSet` re-runs the identical two checks over the identical text. §6.4's prose row distinguishes cheap incremental guards from a *full* guard set on the assembled text at completion; here the completion phase adds nothing (length is missing per Bug 1, and no deferred/expensive check exists), so T-D4-06's spy can prove invocation but no input can ever make the full set trip — the completion-time failure branch has no behavioural coverage because it cannot occur.

4. **The journal-terminal sink is fed only on cancel — `completed` and `failed` paths leave no terminal record, and `terminalErrorCode` is never populated** (`ai-platform/src/stream/index.ts:131-134` is the sole call site; the success path at `:269-281` and the failure path at `:143-149` never journal). Contract §2.1 freezes the journal-terminal sink as recording "a complete terminal `cancelled` / `completed` / `failed` outcome," and the sink's record type carries `terminalErrorCode` for the failure case (`:42-48`); as built, a guard-aborted request produces a `failed` SSE event but nothing for the journal to record, and the error-code field is dead on the wire. FR-009's explainability guarantee is proven only for the cancel path.

5. **Partial usage is a constructor-time snapshot on the chunk source, not a measure of tokens actually generated before cancel** (`ai-platform/src/stream/index.ts:22`, read at `:122-129`). `ChunkSource.partialUsage` is a plain data property; the broker credits whatever was set before streaming began. Nothing in the frozen surface updates it as chunks stream, so the "partial usage is credited" done-when is satisfied by a value with no causal relationship to the partial generation — under-crediting (quota evasion, the exact §6.5 concern) or over-crediting depending on what the eventual wiring guesses up front. T-D4-10/T-D4-13/T-D4-14 set the fixture value and assert the identical object returns (`ai-platform/test/stream-broker.test.ts:442-448`, `:465-471`, `:517-522`), which passes under any credit policy including crediting nothing-derived.

6. **Heartbeats fire unconditionally on the ticker's schedule — the broker has no notion of provider silence** (`ai-platform/src/stream/index.ts:201-207`, `:293-299`). The scheduled callback emits a `heartbeat` whenever the ticker fires, with no reset on chunk arrival, so heartbeats interleave with live `text_delta` traffic. §5.5 rule 3 scopes heartbeats to keeping "an idle stream" alive "during a slow first token"; emitting them mid-content is harmless on the wire but the injectable `HeartbeatTicker` surface (`schedule(callback) → { cancel() }`, `:30-32`) cannot express silence-driven scheduling at all — there is no activity signal to reset against, so the interval boundary the coverage rule names is neither implemented nor testable beyond "the ticker fired."

7. **Credit and journal sinks run before the terminal event with no failure isolation** (`ai-platform/src/stream/index.ts:122-140`). If the credit sink throws (a Quota DO stub error in production wiring), the journal-terminal record and the `cancelled` event are both skipped — the one-terminal invariant sacrificed to a settlement hiccup, and the client left to infer terminal state from silence, the exact failure §5.5 rule 4 prohibits. Ordering settlement before the terminal event also means a slow credit call delays the `cancelled` frame the client is waiting on.

## Architectural Deviations

1. **Structured modes are fully implemented in D4 although the spec and frozen contract declare them out of scope (D6)** (`ai-platform/src/stream/index.ts:19`, `:50-57`, `:155-194`, `:287-368`; spec Out of Scope and contract §3: "`structured` / `structured_atomic` streaming semantics in §6.4 are **out of scope** (D6)"). The module carries `OutputMode`, `StructuredValidationConfig`, a `runStructured` loop emitting `partial_structured` and `progress` events, `completeStructured` calling D6's `runValidationPhases` (`:162-171`), and wire-surface inventions the contract does not freeze: a `progress` event with `bytesReceived`, a `{ _partial: true }` placeholder document when incremental JSON parsing fails (`:334-345`), and an `_assembledFromChunks: false` marker in the terminal payload (`:187`). None of this is covered by D4's T1–T19. The frozen D4 artifact now contains an unreviewed, untested-by-this-slice implementation of its successor's scope, pre-empting D6's design surface (per-chunk `JSON.parse` of the whole assembled string included, `prose-guards`-independent) — the same "implement ahead of the freeze" pattern the slice program's Consumes rule exists to prevent.

2. **The broker is unwired; nothing in `src/` calls `createStreamBroker`** (sole definition at `ai-platform/src/stream/index.ts:92`; no references outside `ai-platform/test/stream-broker.test.ts`). Consistent with the contract deferring production wiring ("production later wires credit and journal sinks to B4 / C3") — restated, as in prior reports, because every done-when criterion is currently proven only against the suite's own fixtures, and the fixtures' graceful-abort behaviour is exactly what masks Critical 1.

3. **The broker does not consume D3's invocation loop — it defines a parallel `ChunkSource`/`StreamChunk` surface** (`ai-platform/src/stream/index.ts:17-24`). The spec's Consumes freezes that "D4 relays what invocation emits," including `regenerating`; the implementation instead declares its own string-or-regenerating chunk union and relays `regenerating` from that (`:222-231`), with no type or call relationship to `InvocationSink.emitStreamText`/`regenerating` from D3. Given the known context that D3's regenerating path is dead in production and its port is streamless, the relay is proven against a self-defined chunk shape no producer in the tree emits — the same surfaced-but-unjoined hand-off pattern flagged in D1–D3, here on the slice's central input.

4. **`terminalErrorCode` and the `failed`-state journal record sit on the frozen sink type with no producer** (`ai-platform/src/stream/index.ts:42-48`; Bug 4). The contract surface advertises a completed/failed/cancelled journal-terminal feed; the implementation exercises one of the three states, leaving the frozen type to misdocument what the broker actually delivers to C3.

## Missing or Weak Tests

1. **No case where the chunk source throws — neither mid-stream error nor abort-rejection** (`ai-platform/test/stream-broker.test.ts:119-152`). Every fixture generator returns gracefully on abort; Critical 1 (rejection escapes with no terminal, no credit, no journal) is invisible to the suite. The coverage rule's "every branch of every rule" and the §5.5 rule-4 invariant under error paths are unmet: one case needs a source that rejects on `signal.aborted` (asserting `cancelled` + credit + journal still land), and one that throws a provider error mid-stream (asserting a single `failed` terminal with a taxonomy code).

2. **No cumulative-length case for the length-ceiling boundary** (`ai-platform/test/stream-broker.test.ts:247-260`). T-D4-03 uses one 21-char chunk against a 20-char ceiling — matching the per-chunk implementation (Bug 1). The named boundary requires: many sub-ceiling chunks whose assembled total exceeds the ceiling (must abort), and the exact-ceiling edge (must pass). Neither exists.

3. **No completion-time full-guard failure case** (`ai-platform/test/stream-broker.test.ts:288-306`). T-D4-06 spies that `runFullGuardSet` was called once with the assembled text but never drives it to failure — the §6.4 "full guard set on the assembled text → violation fails terminally" behaviour has no red path. Because the full set is currently a subset of the incremental checks (Bug 3), no input can produce that failure, so the gap is structural, not just missing: the test that would expose the uncaught throw (Bug 2) cannot be written against this guard design.

4. **T-D4-12 and T-D4-17 assert absence by export-name pattern matching** (`ai-platform/test/stream-broker.test.ts:558-580`, `:603-620`). A per-request registry or Session-DO client named anything outside the regexes (`/session/`, `/requestregistry/`, `/durableobject/`, `/cancelendpoint/`) passes both tests; and both tests would pass unchanged if the broker internally grew per-request state under an innocuous name. These prove a naming convention, not the §4.4/§9.7 prohibition. A stronger form (as prior slices used for non-consultation) would assert the broker's dependency surface — e.g. that `StreamBrokerOptions` accepts no DO namespace / registry binding and the module imports none.

5. **No negative credit case — cancel with zero recorded usage** (`ai-platform/src/stream/index.ts:122-129`; every cancel test supplies `partialUsage`). FR-011/spec T13 scope credit to "when any exists"; the branch where no usage exists and the credit sink must NOT be called is unasserted, so a regression crediting zero-usage cancels (a phantom credit to the Quota DO) stays green.

6. **No disconnect-after-completion case** (`ai-platform/src/stream/index.ts:381-383`). The post-terminal `disconnect` no-op branch — the guard that prevents a late close from emitting a second `cancelled` after `completed` — is unexercised; T-D4-15 covers guard-abort and mid-stream disconnect only. One-terminal under disconnect-after-terminal is a named §5.5 rule-4 branch the suite does not cover.

7. **T-D4-02 proves ticker wiring, not silence-triggered heartbeats** (`ai-platform/test/stream-broker.test.ts:360-390`). The test manually calls `triggerSilentGap()` — it proves a heartbeat event is emitted when the injected ticker fires, but asserts nothing about the relationship to actual provider silence (no case where content flows and heartbeat behaviour is asserted, no reset-on-activity). Combined with Bug 6, the "heartbeats prevent idle timeouts" done-when is proven only at the level of "the callback is connected."

8. **T-D4-16 compares summaries, not the abort path, for network drop** (`ai-platform/test/stream-broker.test.ts:475-505`). The network-drop half asserts the same terminal/credit/delta summary as deliberate cancel, but unlike T-D4-08 it never asserts the provider fetch's abort signal fired on the network-drop path — and the summary's `deltas` count is timing-sensitive (both runs share `afterMs: 15` against `chunkDelayMs: 30`, passing only while no chunk lands inside 15 ms). The "indistinguishable" claim is proven one level shallower than the cancel claim.

## Recommended Improvements

- **Contain source errors at the loop boundary** (Critical 1): wrap both `for await` loops in `catch` — map an abort-caused rejection (or any rejection observed after `disconnected`/`signal.aborted`) into the existing `handleCancel()` path, and any other source error into exactly one `failed` terminal with a taxonomy code plus a journal-terminal record. Add the two throwing-source cases from Weak Tests 1. Independently, bound the disconnect path so a signal-ignoring source cannot hang the stream forever (e.g. emit `cancelled` synchronously from `disconnect()` rather than waiting for the iterator to end).
- **Fix the length-ceiling semantics** (Bug 1): check `assembled.length` (or cumulative count) against the ceiling in `checkIncrementalGuards`, include the length check in `runFullGuardSet`, and replace T-D4-03's single-chunk fixture with the cumulative and exact-boundary cases.
- **Make the completion guard set real and contained** (Bugs 2–3): either give `runFullGuardSet` checks that are genuinely deferred from the incremental phase (and catch its failure into the standard `failed` terminal path instead of throwing across the module), or — if §6.4's full set for prose genuinely equals the incremental set — fold completion into the same non-throwing violation-returning shape and amend contract §3 to say the prose completion set is the incremental set re-run. Either way, add a failing-completion case.
- **Feed the journal-terminal sink on all three terminal states** (Bug 4, Deviation 4): record `completed`, `failed` (with `terminalErrorCode`), and `cancelled`; isolate settlement failures so a throwing credit/journal sink cannot suppress the terminal SSE event (Bug 7 — try/catch each sink, emit the terminal first).
- **Replace the `partialUsage` snapshot with a live source** (Bug 5): make it a getter or method the chunk source updates as tokens stream (or have the broker derive credited usage from relayed content per the B4 credit shape), and assert in T-D4-10/14 that the credited amount reflects tokens generated *before* the cancel point, not a pre-seeded constant; add the zero-usage negative case.
- **Remove the structured-mode path from the D4 module** (Deviation 1): delete `runStructured`, `completeStructured`, `OutputMode`, `StructuredValidationConfig`, and the `runValidationPhases` import, leaving D6 to land its own freeze; if D6 has already merged on top of this code, move the structured path into D6's module and re-point its tests, so the D4 artifact contains only what its contract froze.
- **Tie heartbeats to idleness or document the simpler contract** (Bug 6, Weak Test 7): either reset the heartbeat schedule on each relayed chunk (ticker needs a `reset()`/`notifyActivity()` surface) and assert suppression during content flow, or amend contract §2 to state heartbeats are unconditional on the open stream and drop the "during provider silence" wording.
- **Join the broker to D3's actual output surface** (Deviation 3): type `ChunkSource` against what the invocation sink/port actually emits once the D2 port repair lands (or amend the contract to name the adapter that bridges them), so the relay — `regenerating` included — is proven against a producer that exists.
- **Strengthen the prohibition tests** (Weak Tests 4, 6, 8): assert the broker's options/import surface carries no DO-namespace or registry binding rather than grepping export names; add disconnect-after-completion (exactly one terminal, still `completed`); assert abort-signal firing on the network-drop path directly rather than via summary equality.
