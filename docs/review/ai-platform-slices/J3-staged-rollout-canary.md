# Slice Review: J3 — Staged rollout and canary cohorts

**Reviewed against:** `docs/architecture/17-ai-platform.md` §12.4, §4.5, §13.4 (source of truth); `specs/050-staged-rollout-canary/` (spec, plan, tasks, contracts).
**Implementation reviewed:** `ai-platform/migrations/20260803100000_routing_policy_canary.sql`, `ai-platform/schema.snap.sql`, `ai-platform/src/control/index.ts`, `ai-platform/src/control/cohort.ts`, `ai-platform/src/control/routing-policy.ts`, `ai-platform/src/control/http.ts`, `ai-platform/src/control/auth.ts`, `ai-platform/src/router/index.ts`, `ai-platform/src/capability/index.ts`, `ai-platform/src/config-cache/index.ts`, `ai-platform/src/worker.ts`, plus the two J3 test files and `ai-platform/test/helpers/control-audit-assert.ts`.
**Method:** Static review only; no build, no test execution.

## 1. Executive Summary

J3 delivers the control-plane half of staged rollout cleanly: five new mutations (routing-policy publish / canary / rollback, cohort activate / promote) land on the existing B2 `/control` boundary, reuse `OperatorAuth` unchanged, extend `control_audit.action` with the five frozen vocabulary values, and are dispatched from `worker.ts` without touching B2 lifecycle handlers. The additive `canary_installation_ids` column respects §13.4 (volatile policy as D1 data, no new entity, no runtime prompt activation pointer). Operator auth, rejection style (401/400/404), and the harness config pair are all in order.

However, the routing-policy state machine is **broken at its core**: the data model cannot represent "published but not active", so publish immediately activates a new policy version globally, and rollback — far from restoring the previous version — promotes the rolled-back version to global active. There is also no routing-policy promote mutation at all, despite contract §5.2 requiring one. On the capability side, promotion only moves installations that already hold installation-scoped grants. And the entire cohort-aware request-path read (the canary-split reconstruction from `canary_installation_ids`) exists **only in test-owned `D1Reader` implementations** — the production reader was never extended, so the split tests prove the tests' own logic.

Required test cases: case 1 (cohort split) and case 4 (`control_audit` with operator identity) are present and real; case 2 (promotion) is present for capabilities but weak and **missing for routing policy**; case 3 (rollback) is present in name only — the capability case never deploys anything and the routing case asserts only the audit row, which is exactly why the inverted rollback semantics ship green; case 5 (journal serving version) is present for capability/prompt hash and partially present for `policy_version` (asserted on the routing decision, not a journal row).

## 2. Critical Issues

- **[Critical] Routing-policy rollback promotes the rolled-back version instead of restoring the previous one** — `ai-platform/src/control/routing-policy.ts:180-184` implements rollback as `UPDATE routing_policy SET canary_installation_ids = NULL` on the version named in the route. Under the frozen read semantics (contract §5.2: `NULL` = "not canary-scoped / promoted global active"; resolution picks `... WHERE canary_installation_ids IS NULL ORDER BY active_from DESC LIMIT 1`, as encoded in the only extant resolver, `test/routing-policy-canary.test.ts:200-211`), clearing the canary column makes that row a global-active candidate — and since the canaried version has the newest `active_from`, it **wins** the global read. Net effect of "roll back v2": v1 stays global-ineligible (older `active_from`), v2 becomes the global policy for every installation. Contract §2 requires "Reactivate prior version; clear canary split" and §5.3 requires reactivating the previous version; the implementation does the opposite. The T-J3-04 rollback step (`test/routing-policy-canary.test.ts:415-424`) asserts only that a `control_audit` row exists, never which version serves afterwards — so the inversion is undetected. §4.5 calls routing-policy changes "the highest-leverage actions in the entire system"; a rollback that silently promotes is the worst possible failure mode for that surface.
- **[Critical] Publishing a routing policy version activates it globally with no canary or promote step** — `handleRoutingPolicyPublish` inserts the new row with `canary_installation_ids = NULL` (`routing-policy.ts:70-81`), which under the same read semantics is immediately the newest global-active row. An operator who merely *publishes* v2 — before any canary decision — has already redirected all non-cohort traffic to v2. Contract §5.2 states "Other installations keep the previously promoted active version. Promotion makes the version the global active policy", and §12.4's Add-a-provider recipe requires "promote by policy version with a canary cohort" (FR-011). The schema has no `active`/`promoted` flag, so "published but not yet serving" is unrepresentable; publish, canary, promote, and rollback collapse onto one nullable column whose semantics differ per operation. Relatedly, **no routing-policy promote mutation exists** (routes are publish/canary/rollback only — `control/index.ts:70-75`), so FR-002's "promotion moves all cohorts" is unimplementable for routing policy except via the mislabeled rollback path. Note the test suite never catches this because its frozen clock (`vi.setSystemTime(FIXTURE_NOW)`) gives v1 and v2 identical `active_from`, and v2 is excluded from the global query only by virtue of having been canaried.

## 3. Bugs

- **[High] `handleCohortPromote` moves only installations that already hold installation-scoped grants** — `control/cohort.ts:130-144` updates `capability_grant` rows `WHERE capability_id = ? AND scope LIKE 'installation:%'` and writes nothing else. Installations entitled through plan-scope grants — a path C1's `assertPlanAllowance` explicitly supports (`capability/index.ts:264-274`) — are not moved to the activated version, and installations enrolled after promotion receive the old version. FR-002 ("Promotion MUST move all cohorts onto the activated version") and the spec boundary "promotion ends the split — no residual canary split" therefore hold only for the subset of installations with pre-existing installation-scoped rows. T-J3-02 passes because it seeds installation-scoped grants for both fixtures (`test/cohort-activate-promote.test.ts:424-425`); the plan/global-grant population is never exercised.
- **[Medium] Cohort activate/promote accept nonexistent capability versions and nonexistent installations** — `handleCohortActivate` (`control/cohort.ts:32-109`) writes grants for whatever `version` string appears in the URL with no existence check, unlike the routing handlers which 404 on a missing policy version (`routing-policy.ts:120-128`, `170-176`). A typo'd version silently redirects the cohort's grants to a build that does not exist; affected requests then fail at `resolve` with `capability_unknown` (`capability/index.ts:422-424`) or `version_mismatch` → `forbidden_capability` (`capability/index.ts:194-199`) — a self-inflicted outage for the cohort, far from the operator's mistake. Contract §2.2 names `404 missing target` as part of the rejection style. Installation ids are likewise unvalidated.
- **[Medium] `before_pointer` / `after_pointer` are NULL on four of the five new audit actions** — `cohort_activate`, `cohort_promote`, `routing_policy_canary`, and `routing_policy_rollback` all insert `NULL, NULL` for the before/after pointers (`control/cohort.ts:100-105`, `146-151`; `control/routing-policy.ts:140-145`, `184-189`); only publish records an `after_pointer` (`routing-policy.ts:82-87`). Contract §3 states each row carries B2's frozen columns including `before_pointer`/`after_pointer`, and §4.5's rationale — "an unaudited change to where requests go is indistinguishable from an attack" — depends on the audit row capturing *what changed from what to what*. As written, the audit log can say who canaried `standard@2` but not which installations were in the cohort or which version was displaced; the cohort membership is overwritten in place on `routing_policy` and lost.
- **[Low] Read-then-write race and duplicate-grant hazard in cohort activate** — `control/cohort.ts:64-97` does a per-installation `SELECT` and only then batches `UPDATE`/`INSERT`. Two concurrent activations for the same installation can both take the INSERT path, producing two live grants for the same `(scope, capability_id)`; the request-path read resolves ties by `ORDER BY changed_at DESC LIMIT 1` (`test/cohort-activate-promote.test.ts:300-309` mirrors this), which is nondeterministic at second precision. Operator-rare, so low impact, but there is no UNIQUE constraint guarding the scope/capability pair. The same loop is also N sequential D1 round trips before the batch (performance, operator-rare — noted only).
- **[Low] Provider kill-switch resolution under a canary uses the global policy, not the cohort's** — `resolveProviderId` (`capability/index.ts:282-304`) consults `active_routing_policy` under the bare `policyRef`, while `selectCandidateChain` consults `${policyCacheKey}/${installationId}` first (`router/index.ts:507-510`). For a canary installation whose cohort policy names a different provider, the provider-scoped kill-switch check (`capability/index.ts:320-324`) evaluates the *previous* policy's provider — it can both miss a kill on the canary provider and spuriously disable on the old one.

## 4. Architectural Deviations

- **[High] The cohort-aware request-path read exists only in test code; the production reader cannot reconstruct the split** — the production `D1Reader`, `createD1ConfigReader` (`config-cache/index.ts:112-149`), handles only `installations`, `keys`, and `token_contracts`; it returns `"miss"` for `active_routing_policy` and `grants`. The canary-split resolution logic — parse `canary_installation_ids`, prefer the canary row for member installations, else the newest `NULL` row, fetch the R2 document — lives in the test helper `makeRoutingD1Reader` (`test/routing-policy-canary.test.ts:158-224`), and the grants read in `makePlatformD1Reader` (`test/cohort-activate-promote.test.ts:259-318`). Neither `preloadRoutingPolicyForInstallation` nor `selectCandidateChain`/`resolve`/`discover`/`getGrantedCapabilityVersion` has any production caller (`worker.ts:108-109` routes the request path to `handleAdapterRequest`, which never touches them). The plan's claim that "cold-isolate config reads reconstruct the split" (plan → Storage; contract §5.2, §5.4) is therefore unproven in `src/`: the split tests exercise the tests' own reimplementation of the resolution semantics — the same circularity flagged in H1's stub-gated test, but here it covers the slice's central behavior. If pipeline wiring is deliberately a later slice's job, the contract should say the read semantics are frozen *for* that wiring; as written, §5.4 asserts the router resolves per-installation today.
- **[Medium] Contract internal inconsistency: §5.2 requires routing-policy promotion; §2 exposes no route for it** — `contracts/staged-rollout-canary.md` §5.2 ("Promotion makes the version the global active policy and clears the canary split (FR-002, FR-004)") has no corresponding row in the §2 route table and no handler. The implementation's only canary-clearing path is rollback, with inverted effect (§2 above). Whichever way this is resolved (add a promote route, or redefine publish as non-activating), the frozen contract currently freezes a semantics the code cannot produce.
- **Verified non-deviations (no-rework rule holds):** B2's lifecycle handlers, `OperatorAuth` port, and `control_audit` row shape are untouched (`control/index.ts:1-24`, `control/http.ts`, `control/auth.ts`); the five new `action` values match contract §3 exactly; no new §5.4 taxonomy code is emitted (rejections are the B2-style 401/400/404); no runtime prompt activation pointer module or D1 prompt-text path exists; prompts/manifests remain deployed artifacts (FR-008); the migration is forward-only and additive with `schema.snap.sql` updated (`schema.snap.sql:105-110`); no new pipeline stage, DO, or per-request server state; both test files are registered in `vitest.workers.config.ts:21-22` and excluded in `vitest.config.ts:22-23` per the harness rule.

## 5. Missing or Weak Tests

Required-case status: **case 1 present** (T-J3-01 + `routing_policy_canary_split`); **case 2 present-but-weak for capabilities, missing for routing policy**; **case 3 present in name only for capabilities, missing in substance for routing policy**; **case 4 present** (T-J3-04 covers all five actions); **case 5 present for capability/prompt hash, partial for `policy_version`** (asserted on `routing_decision`, never on a journaled `ai_request` row).

- **[High] No test asserts which routing-policy version serves after rollback** — T-J3-04's rollback step (`test/routing-policy-canary.test.ts:415-424`) checks only the audit row. A post-rollback `routeForInstallation` assertion for both cohort and non-cohort installations would have caught the Critical inversion in §2. This is the single most valuable missing assertion in the slice.
- **[High] No test for publish-then-serve without canary** — nothing publishes v2 and asserts non-cohort installations still receive v1 before any canary/promote. That is the boundary "activation for a named cohort MUST leave non-cohort installations on the previous build until promotion" (spec Edge Cases) applied to the routing half, and it is exactly the case the current implementation violates.
- **[Medium] T-J3-03 "rollback by deploy" never deploys anything** — `test/cohort-activate-promote.test.ts:472-481` performs rollback by calling `handleCohortActivate` with the old version — a runtime control-plane re-activation, indistinguishable from the runtime activation pointer the slice forbids. The only deploy-specific guard is `assertNoPromptActivationPointerModule` (`cohort-activate-promote.test.ts:371-377`), an `import.meta.glob` path-name regex: a runtime pointer named anything else (or added to an existing module) would not fail it. Same pro-forma weakness as H1's export-name prohibition tests.
- **[Medium] Promotion coverage uses only pre-granted installations** — T-J3-02 seeds installation-scoped grants for both fixtures; no case covers an installation entitled via plan-scope grant or enrolled after promotion (the §3 Bug). FR-002's "all cohorts" is untested at its hard boundary.
- **[Medium] Non-operator rejection is tested only for publish** — `test/routing-policy-canary.test.ts:490-502` covers `handleRoutingPolicyPublish`; canary, rollback, cohort activate, and cohort promote are never exercised with `null` operator auth, though the spec names operator-auth rejection as this slice's only error path (spec Edge Cases; plan Test Layout: "one assert in each suite" — the cohort suite has none).
- **[Low] Rejection branches untested** — empty/missing `installation_ids` → `400 missing_installation_ids` (`control/cohort.ts:52-54`, `control/routing-policy.ts:112-114`), malformed JSON → `400 invalid_json`, and `404 policy_version_not_found` for canary/rollback of an unpublished version all exist in code with no test. Under the every-error-code coverage rule these are missing branches.
- **[Low] `active_from` ordering ties are untested and untestable as written** — both suites freeze the clock, so multiple published versions share an `active_from` second; the global-active read's `ORDER BY active_from DESC` has no tiebreaker (no `version` or rowid secondary sort in the test reader's query, `routing-policy-canary.test.ts:200-211`). A test publishing two non-canary versions would expose the ambiguity.
- **[Low] Cache-miss fallback of the per-installation policy key is untested** — `selectCandidateChain` falls back from `${policyCacheKey}/${installationId}` to the global key (`router/index.ts:507-514`), but `preloadRoutingPolicyForInstallation` propagates `ConfigCacheMissError` when the reader misses (`router/index.ts:580-592`), and the test reader never misses on installation keys. The warm-isolate behavior "no canary row for this installation → global policy" is asserted nowhere.

## 6. Recommended Improvements

1. **[Critical] Fix the routing-policy state machine before anything else**: add an explicit activation state (e.g. a `status`/`promoted_at` column or a single `active_version` pointer row per `policy_id`) so that publish inserts a non-serving row, canary scopes it, promote makes it global, and rollback reactivates the *previous* version. Then add the missing post-rollback and post-publish serving assertions (§5 items 1–2). The current nullable-column-only model cannot express the contract's §5.2 semantics.
2. **[High] Add a routing-policy promote route** (`POST /control/routing-policies/{id}/versions/{v}/promote`) or amend contract §5.2 to state how promotion happens; reconcile §2's route table with §5.2 either way (FR-002, FR-004).
3. **[High] Move the canary-split read semantics into `src/`** — extend `createD1ConfigReader` (or a sibling production reader) with the `active_routing_policy` per-installation resolution and the `grants` read, so the frozen contract's §5.4 behavior is production code with tests, not test code alone. If request-path wiring is a later slice's responsibility, say so in the contract.
4. **[Medium] Make promote complete**: on `cohort_promote`, also write/raise the plan- or global-scope grant (or otherwise define how plan-grant installations and future enrollments land on the promoted version), and add the corresponding tests (FR-002).
5. **[Medium] Validate mutation targets**: 404 cohort activate/promote on unknown capability version (mirroring the routing handlers) and reject unknown installation ids; record `before_pointer`/`after_pointer` (prior version, cohort membership) on all five audit actions per contract §3.
6. **[Low] Harden the rollback-by-deploy test**: assert the absence of a runtime pointer structurally (e.g. no D1 table/column selecting prompt text — grep migrations and `schema.snap.sql`), and rename or re-scope T-J3-03 so its name does not claim a deploy it never performs.
7. **[Low] Add the missing branch tests**: non-operator on all five mutations, empty `installation_ids`, malformed JSON, unpublished-version canary/rollback, and a two-published-versions ordering case with a deterministic tiebreaker in the read query.
