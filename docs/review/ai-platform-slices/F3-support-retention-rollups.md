# Slice Review Report — F3: Support Lookup, Retention Purges, Usage Rollups, and Journal Dashboards

**Spec:** `specs/041-support-retention-rollups/spec.md` · **Branch:** `ai/041-f3-support-retention-rollups` · **Canonical:** §4.5, §8.9, §7.6, §7.7, §13.1, R-6, A13; delivery plan §3.7 row F3, §3.10, §3.11.6 row F3

## Executive Summary

F3 delivers the four modules its plan names with a generally faithful shape: `src/support/index.ts` resolves a reference to request row plus attempts in a single JOINed D1 statement and conditionally performs one `GetObject`, honouring the §7.6 I/O budget; `src/retention/index.ts` implements the four-class table with constants inside the architecture bands; `src/rollup/index.ts` upserts rollups idempotently and produces the R-6 reconciliation report; `src/dashboards/index.ts` answers the six named diagnostics as read-only SELECTs. All twenty named tests exist and the spy cases (one D1 query / one GetObject, no second metrics store) are real assertions. The failures are concentrated where the tests stop: at the production wiring boundary. Most seriously, the per-capability diagnostic horizon — a headline freeze of this slice (FR-008) — is honoured only inside tests that inject a fake resolver; neither the support-lookup route nor the scheduled purge passes a resolver, so both silently fall back to a constant 7-day horizon for every capability, and no production code path reads `Governance.retentionClass` at all. The journal-class horizon is also broken in a subtler way: requests with usage events are retained for the ledger horizon (~7 years) while their attempt rows are still deleted at 90 days, leaving headless traces. On the dashboard side, two of the six named diagnostics measure values the write path never produces (`outcome = 'repair'`, and an `'ok'` counter the counter pipeline never writes) and a third mislabels total attempt latency as time-to-first-token — each with a green test seeded with data production cannot generate. The rollup job aggregates a trailing-30-day window into period-keyed rows, so rollup values drift non-monotonically and cease to equal ledger sums for their period once the window slides past. Finally, the reconciliation report the scheduled job produces is computed and then discarded — nothing logs or persists it.

## Critical Issues

1. **Per-capability diagnostic horizons are honoured in tests only — production wiring never supplies a retention-class resolver, so every capability gets the constant 7-day baseline** (`ai-platform/src/control/support-purge.ts:27-30` — `supportLookup(reference, { db, r2 })` with no `resolveRetentionClass`; `ai-platform/src/worker.ts:205-208` — scheduled `runRetentionPurge({ db, r2 })` with no resolver; `ai-platform/src/retention/index.ts:14-16` — `defaultRetentionClassResolver()` returns the constant `"diagnostic_7d"` for all inputs). FR-008 freezes "the diagnostic envelope's retention horizon MUST be per-capability via the manifest retention class"; §7.7 makes retention class a per-capability manifest field precisely so "a capability handling sensitive free text can carry a shorter diagnostic window than one handling coded data". As shipped: (a) T8 (`retention_per_capability_diagnostic`) passes only because it injects `resolveRetentionClass: (capId) => capId === "cap.long" ? "diagnostic_30d" : "diagnostic_7d"` (`test/retention.test.ts:382-384`) — a fixture resolver nothing in `src/` produces; (b) no function anywhere reads `Governance.retentionClass` from the manifest registry to build a resolver (grep over `ai-platform/src` finds `retentionClass` only as a manifest schema field, `src/manifest/index.ts:74`); (c) the scheduled purge therefore deletes a `diagnostic_30d` capability's envelopes after 7 days (data the operator promised to retain, breaking support lookup's in-horizon envelope fetch for days 8–30) and retains a shorter-window capability's envelopes beyond their horizon (a privacy/liability breach of the per-feature retention decision §7.7 exists to enable). The same unwired path makes `supportLookup`'s within-retention check wrong per capability (`src/support/index.ts:104-106,153-163`). This is the slice's headline freeze passing its test while being absent from the system.

## Bugs

1. **Journal-horizon purge never deletes credited requests, and deletes their attempts anyway — retained `ai_request` rows lose their trace at 90 days** (high) (`ai-platform/src/retention/index.ts:128-144` and `:155-161`). The journal purge deletes `ai_attempt` for all requests older than the 90-day cutoff unconditionally, but deletes `ai_request` only `WHERE request_id NOT IN (SELECT request_id FROM usage_event)` — a guard the ledger 7-year horizon makes permanent for any settled request (FK `usage_event.request_id → ai_request`, migration `20260731120000_platform_schema.sql:111`). Consequences: (a) the journal class's "months" horizon (§7.7) is effectively the ledger horizon for every request that has a usage event — i.e. essentially all completed traffic; (b) at day 91 the request row survives but its attempt rows are gone, so support lookup (FR-003's full trace: provider, model, latency, tokens, error codes) returns a hollow trace for the retained row — worse than either deleting both or keeping both; (c) the same inconsistency would make any wider reconciliation window flag these as false-positive "missing attempt rows". The correct shape is either deleting the request with its attempts (detaching/nulling the ledger FK, or accepting that the ledger keeps only monetary columns) or retaining attempts alongside the request.

2. **Repair-rate dashboard counts a journal value the write path never emits — production repair rate is always 0** (high) (`ai-platform/src/dashboards/index.ts:53-58` — `SUM(CASE WHEN a.outcome = 'repair' THEN 1 ELSE 0 END)`; `ai-platform/src/invocation/index.ts:16-20` — `AttemptOutcome = "success" | "retryable_failure" | "terminal_failure" | "timeout"`, exhaustive for attempt journaling). Nothing writes `outcome = 'repair'` to `ai_attempt`; repair re-asks are reported through `RepairJournalSink` (`src/validate/index.ts:32-37,108-111`), which has no caller outside tests — `validateAndRepair` is invoked only from `test/response-validator.test.ts` and `test/conversational-response-validator.test.ts`, so in the live pipeline no repair signal reaches the journal in any form. The named §13.1 diagnostic "repair rate by capability" therefore returns 0 for every capability in production, indistinguishable from a healthy platform. T16 passes only because it hand-seeds an `ai_attempt` row with `outcome = 'repair'` (`test/journal-dashboards.test.ts:150`) — a row the C3 write path cannot produce (see Missing or Weak Tests 3).

3. **Rollup aggregates a trailing-30-day window into period-keyed rows — values are non-monotonic and diverge from ledger sums once the window slides** (high) (`ai-platform/src/rollup/index.ts:26-29` — `defaultWindow()` = now−30d…now; `:40-52` — `GROUP BY installation_id, period` over `recorded_at` in the window; `:60-90` — upsert keyed by `SHA-256({installation_id, period})` only). §7.6 names this job "Billing period close — Monthly — `usage_event` → `usage_rollup` via cron". A daily run computes *partial* period sums (only the last 30 days of events) and overwrites the period row each run: the stored value for period `2026-08` falls as July events leave the window, then freezes at whatever partial sum the last covering run wrote — after 30 days it no longer equals the ledger sum for that period, violating FR-012's equality in every sense except the test's same-window snapshot. Rollups are "the convenience" for history (§7.6 Usage summary read path); as shipped, historical rollup rows are stale window fragments. The aggregation should be period-aligned (all events of the period, or a closed period) rather than clock-trailing.

4. **The reconciliation report is computed by the scheduled job and then discarded — nothing logs or persists it** (medium) (`ai-platform/src/worker.ts:209-211` — `await runRollupAndReconciliation({ db })` with the return value unused; `ai-platform/src/rollup/index.ts:146-152`). R-6's mitigation is "periodic reconciliation report: requests with terminal state but missing attempt rows"; the delivery plan's done-when says the pass "reports requests". A report returned into the void detects nothing operationally — the first missing-credit incident still surfaces only when a clinic complains. Minimum fix: emit the report as a structured log event (§13.1's log stream) per run; better, expose it through the control plane.

5. **Purge by installation id leaves `usage_rollup` and `platform_counter` rows carrying the installation's id and cost history** (medium) (`ai-platform/src/retention/index.ts:203-238` — deletes `ai_attempt`, `usage_event`, `ai_request` and R2 envelopes only). The frozen contract (§5) names "usage events/rollups as applicable" among the D1 rows to delete; `usage_rollup.dimensions` embeds `installation_id` with aggregated tokens/cost, and `platform_counter.dimension_set` carries `installation_id` for every guard rejection. After an installation deletion, per-installation commercial history and rejection tallies survive in both aggregates — a tenant-isolation/privacy gap on the path §7.7 defines as the installation-deletion recovery. (`installation` / `entitlement` rows are B2's lifecycle concern and reasonably out of scope here.)

6. **Quota-rejection-rate denominator is all guard rejections, and the test's denominator fixture is a counter production never writes** (medium) (`ai-platform/src/dashboards/index.ts:109-122` — rate = quota_exhausted counters ÷ `SUM(count)` over *all* `platform_counter` rows). `platform_counter` records only pre-journal rejections (`recordGuardRejection`, `src/rate-limit/index.ts:70-75` — every call site passes an error code); there is no "ok" or admission-success counter. In production the metric is therefore "share of rejections that were quota_exhausted", not a quota rejection rate (rejections per request/admission). T19 seeds `error_code: "ok"` with count 7 to manufacture a 0.3 rate (`test/journal-dashboards.test.ts:181-188`) — a dimension set the pipeline cannot produce. The named diagnostic as §13.1 means it (a rejection *rate* against traffic) is not answerable from the current query; a defensible approximation would divide quota rejections by journal request count for the window.

7. **Reconciliation is N+1: two COUNT queries per terminal request in the window** (medium) (`ai-platform/src/rollup/index.ts:113-136`). Each terminal request costs one `ai_attempt` count and one `usage_event` count round trip; both flags are expressible as two set-based queries (`LEFT JOIN … WHERE a.request_id IS NULL`). Clinic-scale volume makes this survivable, but the scheduled job's cost grows linearly in D1 round trips against a store with measured write headroom concerns (§13.6).

8. **Retention purge does full-table scans and per-row deletes; no index supports the hot predicates** (medium) (`ai-platform/src/retention/index.ts:99-105` — scans every `ai_request` with `payload_pointer IS NOT NULL`, no cutoff prefilter, then one `r2.delete` plus one `UPDATE` per expired row; `:166-181` — loads every `usage_rollup` row and JSON-parses `dimensions` in JS, one DELETE per expired row). The A5 migration adds no index on `ai_attempt.request_id`, `usage_event.request_id`, or `usage_event.installation_id` (`migrations/20260731120000_platform_schema.sql:86-113`) — the support-lookup JOIN, both reconciliation counts, the purge subqueries, and the installation purge all full-scan. A `created_at < now − min(diagnostic horizons)` prefilter, `json_extract(dimensions, '$.period') < ?` in SQL, and the three FK indexes are cheap, additive fixes.

9. **Support-lookup reference input is normalised but never validated or trimmed** (low) (`ai-platform/src/support/index.ts:103` — straight to `normalizeRequestReference`; `src/reference.ts:19-24` — no whitespace stripping, no format check). FR-006 and the frozen contract (§2) pin the eight-symbol format; a reference typed with a stray space or missing hyphen silently returns `found: false` rather than a control-plane validation error the contract explicitly permits ("MAY be rejected as a control-plane validation error"). An operator reading `7QK4 2B9F` over the phone gets "not found" instead of "malformed reference" — a small but real support-workflow regression against A13's purpose.

10. **Fallback-rate diagnostic counts same-provider retries and repair re-asks as fallbacks** (low) (`ai-platform/src/dashboards/index.ts:70-88` — `attempt_no > 1` grouped by the attempt's provider). `attempt_no > 1` includes bounded retries against the same provider (D3) and any repair re-ask, so the metric conflates retry rate with the named "fallback rate by provider". The journal has the signal needed to do this properly (`routing_decision` on `ai_request`, `selection_reason` values `fallback_after_retryable_error` / `fallback_after_timeout` in `src/invocation/index.ts:11-14`) but the query doesn't use it.

11. **Validation-failure-rate denominator includes `Cancelled` and `AwaitingContext` requests** (low) (`ai-platform/src/dashboards/index.ts:35-38`). Requests cancelled before validation or parked awaiting context never had a chance to fail validation; including them in `COUNT(*)` dilutes the rate per prompt version. Filtering to states that reached validation (`Completed`, `Failed`) matches the diagnostic's intent.

## Architectural Deviations

1. **§7.7 / FR-008 per-capability diagnostic retention — absent from production wiring** (see Critical 1). Documentation mismatch to report: the spec (FR-008, Edge Cases), plan (T006, horizon constants), and frozen contract (`contracts/retention-purge.md` §3) all describe the purge and support lookup reading manifest `retentionClass`; no code does.

2. **§7.7 journal class horizon ("months") — not enforced for credited requests, and applied inconsistently between `ai_request` and `ai_attempt`** (see Bug 1). The architecture's class table expires `ai_request` and `ai_attempt` metadata together on the journal horizon; the implementation expires attempts alone and requests effectively never (until the ledger horizon plus FK release), an arrangement no document describes.

3. **§13.1 "time to first token by provider" — the journal holds no TTFT signal, and the dashboard substitutes total attempt latency** (high) (`ai-platform/src/dashboards/index.ts:13-16` — `AVG(latency_ms)` of first attempts labelled `avg_ttft`; envelope timing fields are `queue_ms / provider_ms / total_ms`, no first-token mark; nothing else in the schema carries TTFT). The named diagnostic is architecturally required "from the first working request"; as implemented it reports full provider round-trip latency — materially different for streaming requests and silently misleading on an incident dashboard. Either the journal must capture TTFT per attempt (a C3-side write-path addition this slice cannot make under §2.3, so the gap should have been flagged as a cross-slice dependency) or the diagnostic must be honestly renamed.

4. **§7.6 "Billing period close — Monthly" — implemented as a daily trailing-30-day re-aggregation** (see Bug 3). The read-path table's monthly, period-closing semantics are replaced by a sliding window whose rollups are neither period-complete nor stable.

5. **Frozen contract §3.1 drift: reconciliation treats `AwaitingContext` as terminal** (low) (`ai-platform/src/rollup/index.ts:104` — `state IN ('Completed','Failed','Cancelled','AwaitingContext')`; `contracts/usage-rollup-reconciliation.md` §3.1 names `Completed` / `Failed` / `Cancelled` "as journaled by C3"). `AwaitingContext` legs do carry attempts and usage, so the practical effect is near-nil, but the implementation extends a frozen contract silently — the contract should be amended (H-band legs are terminal) or the state list tightened.

No deviation on the positive side worth flagging: the one-indexed-D1-lookup-plus-one-GetObject budget (§7.6) is genuinely met by the JOIN, and the dashboards write nothing (§13.1's journal-side rule) — both spy-proven.

## Missing or Weak Tests

Coverage is measured against the §3.11.6 F3 floor and §3.10 (every branch of every rule; behavioural; spies on work *not* done).

1. **No test exercises the production wiring for per-capability horizons** (critical — mirrors Critical 1). The floor case `retention_per_capability_diagnostic` is proven against `runRetentionPurge` with an injected resolver; nothing tests the scheduled handler (`worker.ts:205-208`) or `handleSupportLookup` with a non-default horizon, so the constant-fallback wiring is invisible to the suite. Add a test through the actual scheduled entry point (or at minimum through `handleSupportLookup`) seeded with two capabilities whose manifests differ in `retentionClass`.

2. **T2 (`support_lookup_expired_envelope_metadata`) does not spy the GetObject count** (high) (`test/support-lookup.test.ts:263-283`). §3.11.6's I/O budget is "exactly one D1 query and one `GetObject`" *when in horizon* — the complementary invariant for the expired case is **zero** GetObject calls, and that is the assertion that would catch a regression to unconditional fetching. The happy-path spy (`:256-259`) counts both; the expired case counts neither. The contract (§4: "Expired / missing envelope → no second fetch attempt") makes this a named boundary the suite leaves unproven.

3. **Two dashboard tests seed journal rows the write path cannot produce** (high) (`test/journal-dashboards.test.ts:150` — `outcome = 'repair'`, impossible under `AttemptOutcome`; `:181-188` — `error_code: "ok"` in `platform_counter`, impossible under `recordGuardRejection`). "Correct values against a seeded journal" (§3.11.6) presumes seeds the journal can actually hold; these tests prove the SQL arithmetic and nothing about the diagnostic's production truth (Bugs 2 and 6). Seeds should be generated through, or at least constrained to, the write path's vocabulary — and the repair-rate case cannot be made honest until the journal carries a repair signal.

4. **Reference input handling is untested** (medium) (FR-006). No case covers: lowercase input resolving; `I`/`L`/`O` confusion characters resolving (`7QK4-2B9F` read as `7QK4-2B9F` with `I`→`1` etc.); a malformed-after-normalisation reference; an unknown-but-valid reference → `found: false` → 404 on the route. The normalisation rule is a frozen contract (§2) with four stated branches — §3.10 item 3 requires each.

5. **Journal-expiry test never seeds a request with a usage event** (medium) (`test/retention.test.ts:140-217` — both seeded requests have no `usage_event`). That is precisely the population Bug 1 mis-handles; a case seeding an old credited request would expose the 90-day-vs-7-year split-brain (or, after a fix, pin the intended behaviour for credited rows).

6. **Rollup equality is proven only for window-aligned, same-period data** (medium) (`test/rollup-reconciliation.test.ts:146-166`). No case spans two periods in one window, re-runs after the window advances (Bug 3's drift), or aggregates events recorded outside any covering window. The idempotency case (T13) re-runs the *same* window — §3.10's boundary reading suggests also proving a re-run with an *advanced* window does not corrupt prior period rows.

7. **Reconciliation has no negative cases and no surfaced-report assertion** (medium). Missing: a terminal request *with* attempts and usage is not flagged; a non-terminal (in-flight) request is not flagged; a terminal request outside the window is not flagged; and — mirroring Bug 4 — no test asserts the scheduled handler does anything observable with the report (a log spy would do).

8. **No test for the in-horizon-but-missing R2 object path** (low) (`src/support/index.ts:165-170` — pointer present, `r2.get` returns null, `envelope` stays null). The contract names "object absent" alongside "outside retention" for the metadata-still-resolves rule; only the retention branch is tested.

9. **Dashboard queries are not tested through any operator-authenticated surface, and dimensions drop version** (low). The contract (§5) permits helper-only exposure, so the missing route is not itself a deviation — but no test pins operator auth around `runAllDashboardQueries` consumers, and `repair_rate_by_capability`/`cost_per_capability_per_installation` group by `capability_id` alone where the contract (§3) says "by `capability_id` (+ version as stored)", merging versions the journal distinguishes.

## Recommended Improvements

- **Wire a manifest-backed retention resolver and test it at the boundary** (Critical 1): build `RetentionClassResolver` from the published manifest registry (`src/manifest/index.ts` already loads entries) mapping `(capabilityId, version) → Governance.retentionClass`, pass it in `handleSupportLookup` and the scheduled purge, keep the constant as the unknown-manifest fallback (contract §3 already defines that fallback), and add the production-wiring test from Weak Test 1. Mind the one-D1-query budget: the resolver must resolve from bundled artifacts, not a D1 read.
- **Fix journal-class expiry as a unit** (Bug 1): decide the credited-request story explicitly — either purge `ai_request` with its attempts at 90 days (nulling or dropping the `usage_event → ai_request` FK, which carries no monetary data the ledger needs) or retain attempts alongside the request for the FK-extended lifetime; encode the choice in `contracts/retention-purge.md` §2 and add the Weak Test 5 case.
- **Give repair a journal signal or drop the diagnostic honestly** (Bug 2 / Deviation 3): the durable fix is a C3/D6-side attempt-outcome or repair flag the validator's `RepairJournalSink` already anticipates — file it as a cross-slice gap rather than leaving a permanently-zero dashboard; until then, rename/remove the query so the dashboard cannot be misread. Apply the same honesty pass to TTFT (report `avg_attempt_latency` until a TTFT field exists).
- **Make rollups period-aligned** (Bug 3): aggregate complete periods (e.g. all `usage_event` rows for each closed `period`, or the period containing the window) rather than a trailing clock window, keeping the dimensions-keyed upsert for idempotency; add the advanced-window re-run test.
- **Surface the reconciliation report** (Bug 4): emit it as a §13.1 structured log event per scheduled run (and consider a control-plane read endpoint); assert the emission with a spy in the rollup suite.
- **Close the installation-purge residue** (Bug 5): delete `usage_rollup` rows whose `dimensions` match the installation (`json_extract`) and `platform_counter` rows whose `dimension_set` does, or document in contract §5 why aggregates are exempt.
- **Set-based reconciliation and purge SQL, plus the three FK indexes** (Bugs 7–8): two `LEFT JOIN … IS NULL` queries for reconciliation; a `json_extract` predicate for rollup expiry; a horizon prefilter for the diagnostic scan; indexes on `ai_attempt.request_id`, `usage_event.request_id`, `usage_event.installation_id` as an additive migration.
- **Fix the two mis-seeded dashboard tests and the quota-rate denominator** (Bugs 2, 6 / Weak Tests 3): seed only write-path-producible rows; for quota rejection rate, divide quota-coded counters by journaled request volume for the window (documenting the approximation in `contracts/journal-dashboards.md` §3), and drop the `'ok'` fixture.
- **Tighten the remaining branches** (Bugs 9–11, Weak Tests 2, 4, 7, 8): validate/trim the reference and return a control-plane 400 for malformed input with tests per normalisation branch; add the zero-GetObject spy to T2; add reconciliation negative cases; use `selection_reason`/`routing_decision` for the fallback diagnostic; exclude pre-validation states from the validation-failure denominator.
