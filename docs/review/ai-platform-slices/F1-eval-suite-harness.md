# Slice Review Report — F1: Eval Suite Harness and First Capability Eval

**Spec:** `specs/039-eval-suite-harness/spec.md` · **Branch:** `ai/039-f1-eval-suite-harness` · **Canonical:** §13.5 (Capability evals row), A9; delivery plan §3.7 row F1, §3.10, §3.11.6 row F1

## Executive Summary

F1 delivers the harness skeleton its contract names: a `test/eval/` runner (`harness.ts`) that composes the D1 canonical request for `clinic.visit_summary`, replays a recorded DeepSeek response through the D5 adapter, scores quality and schema per case, and writes the frozen JSON score report (`score-report.ts`); one golden case with expectations; a checked-in deliberately-worse prompt; the eight named tests T1–T8; a CI golden gate job (`.github/workflows/ci.yml:82-113`); and a weekly scheduled workflow. The CI-side done-when mostly holds: T1 green on the current prompt, T2 red on the worse prompt, T3 proves the report shape. The failures are concentrated on the *live* half of the slice and on the *strength* of the gate. Most seriously, the "scheduled live smoke set runs against pinned model versions" done-when is not implemented at all: the scheduled workflow runs `live-smoke.test.ts`, which contains only static assertions over the routing-policy file and the workflow file itself — no provider egress, no adapter invocation, no secrets in the workflow, and no score report with `run_kind: "live_smoke"` is ever written. Compounding it, the routing-policy `model_id` values the smoke set is pinned to (`deepseek-chat`, `gemini-1.5-flash`) are floating aliases, not pinned versions, and T4's pin check is a regex that explicitly passes them. On the golden side, the fixtures are static recordings, so model output is invariant to the prompt under evaluation: T2's "deliberately regressed prompt fails" is proven by substring-matching the *composed system prompt* (`system_instruction_must_contain`), not by observing regressed output — a real prompt edit that degrades output while retaining those needle strings passes the gate. The harness also does not actually bind to D5's recorded fixtures as the spec and plan claim: the `d5_fixture_subdir` binding field and `D5_FIXTURES_ROOT` constant are dead code, and the golden replays a duplicate fixture checked into the eval tree. Several scorer branches (output-content failure, min-length failure, every schema-failure path) have no test coverage, the T5 "recorded fixtures" spy asserts a flag nothing can set, and two T3/T5 assertions use forward-slash path literals that fail on Windows working trees.

## Critical Issues

1. **The scheduled live smoke set never runs anything live — the slice's headline scheduled done-when is unimplemented** (`.github/workflows/ai-platform-eval-live-smoke.yml:1-40`; `ai-platform/test/eval/live-smoke.test.ts:9-26`; `ai-platform/test/eval/harness.ts:535-555`). The workflow's only run step is `npx vitest run test/eval/live-smoke.test.ts`, and that file contains exactly two tests: one asserting that `getLiveSmokeModelTargets()` returns the routing-policy model IDs (a static read of `control/routing-policy/platform-default/1.json`), and one asserting that the workflow file exists, contains the string "live-smoke.test.ts", and has a cron schedule. No code path — in the test, in `harness.ts`, or anywhere — invokes an adapter against a live endpoint; the workflow declares no secrets or env (no `DEEPSEEK_API_KEY`/`GEMINI_API_KEY`), so it *could not* perform egress. A9 requires "a smaller live smoke set" against pinned models to catch silent model drift; §13.5 repeats it; the delivery plan's F1 done-when makes it the second half of the slice's acceptance shape; FR-003/FR-008 and contract §2.3 ("Smaller set that catches silent model drift") freeze it. As shipped, the scheduled job is a self-referential metadata check that would pass even if both providers deleted the named models entirely — the exact drift the smoke set exists to catch. Because nothing live runs, the upload-artifact step (`:32-39`) has nothing to upload (fresh checkout, `reports/` is gitignored, `if-no-files-found: ignore`): **no score report with `run_kind: "live_smoke"` is ever produced**, so FR-007's "scores recorded per run" and the contract §4 `run_kind: "live_smoke"` variant are dead for the scheduled path as well.

## Bugs

1. **Live-smoke targets are floating aliases, not pinned model versions, and T4's pin assertion is written to pass them** (high) (`ai-platform/control/routing-policy/platform-default/1.json:20-21,32-33`; `ai-platform/test/eval/live-smoke.test.ts:12-16`). The policy carries `deepseek-chat` and `gemini-1.5-flash` — provider aliases that float to whatever the provider currently serves (a true pin would be e.g. `gemini-1.5-flash-002`). T4 asserts only that the IDs do not match `/^(latest|auto|default)$/i` and contain no `":"` — a check both aliases pass trivially. The contract is explicit: "Smoke **MUST** target **pinned model versions** from routing policy (never floating aliases)" (`contracts/capability-eval-harness.md` §2.3; spec FR-008, Edge Cases "Pinned models only"). The test enshrines the violation it exists to prevent: even once Critical 1 is fixed and real smoke egress exists, it would run against unpinned models with a green test asserting otherwise. (The policy document predates F1 — D2/D7 own it — but F1 is the slice that froze "never floating aliases" and then codified a check that accepts them.)

2. **The golden regression gate cannot detect output-quality regressions — fixtures make the model output prompt-invariant, so T2's failure is produced by substring-matching the prompt, not the output** (high) (`ai-platform/test/eval/harness.ts:384-414`; `ai-platform/test/eval/clinic.visit_summary/expectations/visit_summary.happy_path.json:3-8`; `ai-platform/test/eval/prompts/clinic.visit_summary.worse/system.md:1`). The fixture transport replays the same recorded body regardless of the composed request (`harness.ts:250-263`), so `output_must_contain` and `output_min_length` yield identical results for the current and regressed builds. The only scorer input that varies with the prompt is `system_instruction_must_contain`, checked against the *composed request's system parts* — and the worse prompt fails because it lacks the needles "advisory only" / "clinical documentation assistant". Three consequences: (a) a genuinely regressed prompt that retains those two strings (e.g. one that degrades structure, tone, or safety phrasing elsewhere) passes the gate — the "block a prompt change that regresses them" done-when holds only for prompt edits that delete the specific needle substrings; (b) the check is recorded in the report as `quality` (§4.1 `cases[].quality` = "Output-quality outcome for the case"), mislabelling a prompt-content assertion as an output-quality measurement against §13.5's "Output quality and schema conformance"; (c) output quality against a *new* prompt is structurally unmeasurable from canned responses, so the CI gate's quality leg is a proxy — defensible as a design choice, but the contract (§2.2 "What is tested: Output quality") and spec (Clarification Q5) present it as the real thing, and the live smoke that would close this gap is the piece Critical 1 shows is missing.

3. **Goldens do not bind to D5's recorded fixtures — the binding field and fixtures-root constant are dead code, and the golden replays a duplicated fixture** (medium) (`ai-platform/test/eval/harness.ts:30` — `D5_FIXTURES_ROOT` defined and never used; `:241-249` — `resolveProviderResponsePath` ignores `binding.d5_fixture_subdir`; `ai-platform/test/eval/clinic.visit_summary/fixtures/visit_summary.happy_path.json:3` declares `"d5_fixture_subdir": "usage"`). The spec (Consumes D5; FR-002/FR-009), plan (T011: "bind goldens to D5 recorded fixtures behind the D2 provider port"), and contract (§2.1 "D5 recorded fixtures … unchanged") all state the golden suite reuses D5's fixture tree (`test/fixtures/deepseek/`). The implementation instead reads `visit-summary-provider-response.json` from the eval tree — a separately authored recording that nothing ties to D5's `usage/provider-response.json` — and the binding's `d5_fixture_subdir` field is never read. The fixture can now drift from the adapter's proven wire fixtures with no test to notice, and the "Consumes D5 fixtures" claim is documentation, not behaviour.

4. **T3 and T5 assert forward-slash path literals — both tests fail on a Windows working tree** (medium) (`ai-platform/test/eval/golden.test.ts:51` — `expect(result.reportPath).toContain("/test/eval/reports/")`; `:76` — `toContain("/test/eval/clinic.visit_summary/fixtures/")`). `harness.ts` builds both paths with `path.join`, which emits backslashes on win32; CI is ubuntu so the gate stays green, but any developer running the suite on Windows (this repo's primary desktop platform) gets two red tests in a suite whose purpose is a trustworthy gate. Normalize with `path.sep`/`path.normalize` or assert on `path.join`-built expectations.

5. **`runCase` ignores its `capabilityId` parameter — the "per-capability" harness is hardwired to `clinic.visit_summary`** (medium) (`ai-platform/test/eval/harness.ts:447` — `const manifest = visitSummaryManifest()` regardless of `capabilityId`; `:242-244` — `resolveProviderResponsePath` uses the `FIRST_CAPABILITY_ID` constant, not the parameter). `runGoldenSuite` accepts an arbitrary `capabilityId` and enumerates that capability's cases, but composes every case against the visit-summary manifest and resolves provider responses under the first capability's tree. The T6 "evals are per capability" claim is proven by directory layout (`listEvalCapabilities`), while the runner itself would silently evaluate the wrong capability for any second golden capability — the `expectations/`-directory filter (`:200-210`) currently hides this by excluding `clinic.chat_assistant`.

6. **An empty case set scores `pass` — a vacuously green golden run** (low) (`ai-platform/test/eval/score-report.ts:19-26` — `deriveOverall([])` returns `"pass"`). A capability directory that exists but contains no cases produces a passing report and a passing `runGoldenSuite.passed`. T1's `cases.length > 0` assertion catches this for `clinic.visit_summary` only; the harness itself has no empty-suite guard, so the failure mode returns as soon as a second capability is added.

7. **`GoldenRunResult.capabilityIds` returns every eval capability, not the one evaluated** (low) (`ai-platform/test/eval/harness.ts:517` — `capabilityIds: listEvalCapabilities()`). The field name implies the run's scope; it is populated with the global directory listing. No consumer reads it outside T6's indirect use, but it misstates the report's provenance and will mislead the first consumer that trusts it.

## Architectural Deviations

1. **§13.5 / A9 "small live smoke set on schedule against pinned models" — not implemented** (see Critical 1 and Bug 1). This is the slice's largest deviation from the architecture-as-source-of-truth: the architecture row names two mechanisms (CI goldens, scheduled live smoke), and the second exists only as a scheduled job that asserts its own schedule. Documentation mismatch to report: the spec (FR-003, FR-008), plan (Summary, Technical Context "Live smoke uses the existing adapter/routing path"), contract (§2.3), and quickstart all describe live smoke as running against pinned models through the adapter path; the implementation matches none of those sentences.

2. **Contract §2.2 / Consumes D5: "golden cases MUST run against recorded provider fixtures … unchanged" — the harness replays an eval-local duplicate and leaves the D5 binding inert** (see Bug 3). The deviation is entrenched in the frozen artefact itself: contract §2.1's Consumes row describes reuse of `test/fixtures/deepseek/` that the code does not perform, so the frozen contract now misdescribes the harness it freezes for D7/H4/J3 consumers.

3. **The quality leg of "output quality and schema conformance" (§13.5) is implemented as prompt-content substring matching** (see Bug 2). The architecture assigns capability evals two orthogonal duties; the harness implements one (schema conformance of the fixture-backed result) faithfully and the other (output quality) as a check on the composed request plus substring/length checks on a canned response. Given static fixtures this may be the strongest CI-local approximation available — but then the live smoke set is load-bearing for the quality duty, which loops back to Critical 1: with no live smoke, output quality is effectively ungated anywhere.

4. **Contract §4's `run_kind: "live_smoke"` report variant is unreachable** (low) (`ai-platform/test/eval/score-report.ts:11`; nothing calls `runGoldenSuite` with `runKind: "live_smoke"`). The frozen score-recording contract freezes a payload shape half of which no code can produce — later slices (H4, J3) binding to §4 inherit a dead variant.

## Missing or Weak Tests

Coverage is measured against the §3.11.6 F1 floor and §3.10 (every branch of every rule; behavioural, not line-based).

1. **No test exercises any live-smoke execution path, because none exists** (critical — mirrors Critical 1). The floor case "the scheduled live smoke set runs against pinned model versions" is proven only as "a workflow file exists and a policy file parses". Missing: a smoke case that invokes the adapter against a live (or recorded-live) endpoint per pinned model, asserts a sane response, and writes a `run_kind: "live_smoke"` report; plus a workflow assertion that the job supplies the required secrets.

2. **T5's "no live egress" spy asserts a flag nothing can set** (high) (`ai-platform/test/eval/harness.ts:87-95` — `harnessRuntime.usedLiveEgress` initialized `false`; no code path ever assigns it `true`; asserted at `golden.test.ts:73`). The spy is decorative: a harness change that swapped the fixture transport for a real `fetch` would leave T5 green. There is no instrumentation at the transport boundary (e.g. a fetch spy, a forbidden-network assertion, or an egress guard in the fixture adapter) for the flag to observe. The remaining T5 assertion — that `fixturePathsUsed` is non-empty and under the eval fixtures tree — proves files were read, not that live egress was absent.

3. **Every schema-failure branch and most quality-failure branches are unexercised** (high) (`ai-platform/test/eval/harness.ts:417-440`, `:399-412`). The single golden case is a happy path; the worse-prompt run fails only on the system-needle branch (`:393-397`). No case drives: non-success provider outcome → schema fail (`:420-422`); missing canonical result fields (`:424-426`); empty prose content (`:431-433`); JSON-shaped prose (`:434-436`); `output_must_contain` failure (`:400-404`); `output_min_length` failure (`:407-411`); `deriveOverall` failing on schema alone (`score-report.ts:20-24`). §3.10 item 3 ("every branch of every rule") is unmet for the scorer — the component that decides whether the gate blocks.

4. **T2 asserts only `overall: "fail"` — any failure mode satisfies the regression proof** (medium) (`ai-platform/test/eval/golden.test.ts:38-40`). The test would pass if the worse-prompt run failed for an unrelated reason (composition throw surfaced as a case failure, a broken fixture, a scorer regression). It should assert *which* case failed and that `quality === "fail"` for the reason the worse artifact was constructed to produce — otherwise the deliberate-regression control does not control for the intended mechanism (see Bug 2).

5. **T7 does not scan the Flutter client** (medium) (`ai-platform/test/eval/prohibitions.test.ts:38-61`). T7 asserts that five hardcoded eval file paths live under `ai-platform/` and that `frontend/lib/eval/` is empty — it never reads a single client source file. The actual forbidden-pattern sweep over `frontend/lib` exists only in the later H4-authored describe block (`:111-117`), which F1 cannot take credit for and which is coupled to conversation-module paths. The inherited R-12 prohibition the slice claims to prove (T7 / SC-006) has no F1-authored behavioural check; meanwhile E1's architecture guard already covers this ground properly, making T7 a weaker duplicate that could mask that fact.

6. **T6 proves directory layout, not per-capability gating, and is brittle against the next capability** (medium) (`ai-platform/test/eval/golden.test.ts:82-90`). Asserting `listEvalCapabilities()` equals `["clinic.visit_summary"]` and the case list equals one entry means the test goes red the moment a *correct* second golden capability is added — a gate that punishes the behaviour the harness exists to support — while proving nothing about scoring independence (which Bug 5 shows is in fact broken in the runner).

7. **Single-case golden set; no unhappy-path golden case** (medium). The floor "the golden set passes on the current prompt" is met by one happy-path case. Nothing exercises a case whose expectation is a *fail* verdict on the current build (e.g. a known-limitation case pinned to fail), so the suite has no proof its pass/fail discrimination works in the green configuration — the only failing run in the entire suite is the synthetic worse-prompt one.

8. **The module-mock dance in `composeWithPromptBuild` is untested for isolation** (low) (`ai-platform/test/eval/harness.ts:272-358`). `vi.resetModules()` + `vi.doMock`/`vi.unmock` per invocation, with a mocked `resolveArtifact` that returns `undefined` for any unlisted ref and a `resolvePromptVersion` that returns a hardcoded string, is order-dependent across the three `runGoldenSuite` calls in the file (mock in T2, unmock in T1/T3). No test pins that the "current" build truly resolves the production registry after a mocked run — a leak would make T1/T3 silently evaluate the worse prompt and is exactly the kind of false-green a regression gate must not have. (Note also the mock's `resolveArtifact(ref)` drops the composer's second `manifest` argument — currently harmless, but a signature drift away from `src/prompt/composer.ts:213,223,230`.)

## Recommended Improvements

- **Implement the live smoke path or narrow the contract honestly** (Critical 1): add a smoke runner that iterates the pinned targets, invokes the real adapter (D5/D7 wiring) with a minimal request, asserts a classified success, and writes a `run_kind: "live_smoke"` report via `score-report.ts`; wire the provider secrets into `.github/workflows/ai-platform-eval-live-smoke.yml` (`env:` from GitHub secrets); keep the fixture-based skip for credential-less local runs as the tasks note (T018) already anticipates. If live egress is deliberately deferred, amend A9's delivery-plan F1 row and contract §2.3 to say so — do not leave the done-when claimed on a metadata check.
- **Pin real model versions and make the pin test semantic** (Bug 1): version-pin the routing-policy targets (e.g. `gemini-1.5-flash-002`, DeepSeek's dated snapshot where available) in coordination with D2/D7, and replace the denylist regex with an allowlist/shape check that a floating alias fails — plus an adapter-side assertion that the model sent on the wire equals the policy `model_id` (D7's review already flagged that the Gemini adapter hardcodes its model, which would make smoke pinning decorative even after this fix).
- **Close the output-quality gap explicitly** (Bug 2): acknowledge in contract §2.2 that fixture-based goldens gate *composition and schema*, and that output quality is gated by (a) the system-instruction needle checks and (b) live smoke; then strengthen the needle mechanism from fixed substrings to per-case expectation sets so a regressed prompt has more surface to fail on, and have T2 assert the specific failing case and dimension (Weak Test 4). Consider request-golden comparison (diff the composed request against a recorded canonical request per case) — that detects *any* prompt/composition drift deterministically, unlike output checks on canned responses.
- **Bind goldens to the D5 fixture tree for real** (Bug 3): resolve `d5_fixture_subdir` against `D5_FIXTURES_ROOT`, delete the eval-local duplicate (or, if a purpose-built recording is intentional, drop the `d5_fixture_subdir` field and correct the Consumes row in the contract so the freeze matches behaviour).
- **Fix the runner's capability plumbing before a second golden capability lands** (Bugs 5–7): thread `capabilityId` into manifest resolution (per-capability manifest fixtures), use it in `resolveProviderResponsePath`, guard `deriveOverall` against empty case sets (empty suite → fail), and rename/repopulate `capabilityIds` to the evaluated set.
- **Make the T5 spy observable** (Weak Test 2): instrument egress at the fixture-transport boundary (wrap or spy on global `fetch`, or assert the adapter was constructed with the fixture transport) so `usedLiveEgress` can actually flip; alternatively drop the flag and assert the transport object identity directly.
- **Add scorer branch cases** (Weak Test 3): one cheap synthetic case per failure branch (failing output needle, short output, non-success outcome, JSON-shaped prose, missing result field) — these need no new fixtures beyond small expectation/response files and bring §3.10 item 3 to met for the scorer.
- **Fix the Windows path assertions** (Bug 4): build expected substrings with `path.join` or normalize both sides before `toContain`.
- **Lean on E1's guard for T7 and make T6 forward-compatible** (Weak Tests 5–6): either delete T7's path-shape assertions in favour of a pointer to the E1 architecture-guard coverage, or give T7 its own client sweep; change T6 to assert structural per-capability properties (each capability with `expectations/` has cases, bindings, and expectations that align 1:1) rather than equality with today's single-capability layout.
