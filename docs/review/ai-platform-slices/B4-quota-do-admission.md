# Slice Review Report — B4: Quota Durable Object and Admission Stage

**Spec:** `specs/024-quota-do-admission/spec.md` · **Branch:** `ai/024-b4-quota-do-admission` · **Canonical:** §4.3.3, §4.4, §9.17, §7.7, §6.1 stage 8, §6.2, §6.6, §15 #3

## Executive Summary

B4 delivers the three modules the plan names — `src/quota-do/` (admission and credit RPC handlers over a single serialized state blob, lazy ephemeral sweep, period rollover), `src/admission/` (stage-8 caller with config-cache entitlement load, outcome mapping, rejection tally, fail-open grace), and `src/credit/` (stage-15 caller plus grace reconciliation) — with all 16 named tests present and exercising the real Miniflare DO binding. The core RPC logic is sound: evaluation order matches the frozen contract, the lazy sweep works, `blockConcurrencyWhile` gives the serialized counting §4.4 demands, and the one-fetch-per-request invariant is genuinely held. But the slice ships two defects that each defeat a "Done when" criterion outright. First, the DO instance is derived with `env.DO.idFromString(installationId)` — which throws on a dashed UUID installation id, so every production admission would fall into the grace path and then permanent `internal_error`; the entire test suite masks this by using DO-generated hex ids as installation ids, and the frozen contract codifies the wrong API. Second, grace reconciliation is structurally impossible: the grace path mints a `requestId` the DO has never admitted, so the reconciliation credit always returns `unknown_request`, is counted as reconciled anyway, carries zero usage, and — at cap exhaustion — the code deletes the reconciliation queue, so every grace admission's usage is silently dropped on every path, exactly what FR-013 forbids. Underneath: `concurrency_exhausted` is emitted as a client-facing code outside the closed §5.4 taxonomy, the grace cap is per-isolate rather than per-installation, the DO accumulates an unbounded permanent record of every request id it has ever seen (§4.4's "never holds long-term records"), in-flight leaks have no recovery path, idempotency record states never transition past `"admitted"`, and nothing in the Worker pipeline actually invokes stage 8 or 15. Test-wise the reconciliation test asserts no counter delta (so it cannot catch the reconciliation bug), the parallel-count test reads a mid-flight snapshot, and the duplicate-credit, unknown-credit, rollover, token/cost-budget, idempotency-expiry, and replay-tally branches are all uncovered.

## Critical Issues

1. **The DO instance id is derived with `idFromString(installationId)`, which throws on a real installation UUID — no production request can ever be admitted** (`ai-platform/src/admission/index.ts:174`; `ai-platform/src/credit/index.ts:38`; frozen contract `specs/024-quota-do-admission/contracts/quota-do-rpc.md:43-50`). `DurableObjectNamespace.idFromString` accepts only the 64-hex-character string form of an existing DO id; installation ids are dashed UUIDs minted at enrollment (B1/B2, e.g. `backend/tests/ai_keystore_rls.sql:85`). In production, `idFromString(principal.installationId)` throws synchronously inside `runAdmission`'s `try` (`src/admission/index.ts:286-296`), every admission degrades to `admitUnderGrace`, and after five requests the installation gets `internal_error` forever — stage 8's "Done when" is unreachable end to end. The correct API for "one instance per installation id" is `idFromName`, which is also the only variant that gives the stable per-installation mapping §4.4 requires (`docs/architecture/ai-platform/01-ai-platform.md:1470`). Every test conceals the bug: both suites fabricate installation ids with `env.DO.newUniqueId().toString()` (`test/quota-do.test.ts:140-142`; `test/admission-credit.test.ts:191-193`) and seed D1 with that same hex string, so the DO-id/installation-id conflation is invisible. The frozen contract's transport section codifies `idFromString(installationId)`, so the contract must be corrected alongside the code, and one test must use a dashed-UUID installation id to pin it.

2. **Grace reconciliation can never reconcile anything: the queued `requestId` was never admitted by the DO, the result is ignored, the usage carried is zero, and cap exhaustion destroys the queue** (`ai-platform/src/admission/index.ts:229-255`; `ai-platform/src/credit/index.ts:83-102`; `ai-platform/src/quota-do/index.ts:321-326`). `admitUnderGrace` mints a local `requestId` with `crypto.randomUUID()` (`src/admission/index.ts:243`) and queues it; the DO has no `admittedRequests` entry for that id, so `creditRPC`'s guard (`src/quota-do/index.ts:321-326`) returns `unknown_request` for every reconciliation attempt. `reconcileGraceUsage` never checks the RPC result and increments `reconciled` unconditionally (`src/credit/index.ts:89-99`), and even the attempt carries `{tokens: 0, cost: 0}` (`src/credit/index.ts:94`), so a "successful" reconcile would still record no usage. Worse, when the grace cap is hit, `admitUnderGrace` calls `removeGraceQueueEntriesFor` (`src/admission/index.ts:237-239`, `:221-227`), deleting the reconciliation record for the grace admissions already served. The same `unknown_request` wall also meets the *normal* stage-15 credit call for any grace-admitted request, since that `requestId` is equally unknown to the DO. Every one of FR-013's outcomes — "reconciled against the DO's counters afterwards, never silently dropped" (spec.md:283-287; §15 #3, `docs/architecture/ai-platform/01-ai-platform.md:3723`) — fails on every path; grace usage is always silently dropped. The test `grace_usage_reconciled_afterwards` (`test/admission-credit.test.ts:527-549`) asserts only that one fetch occurred and `reconciled >= 1`, never that the DO's counters moved, so it structurally cannot catch this. A working design must re-present the queued admission (jti, idempotency key, entitlement) to the DO once it is reachable so the DO itself establishes the record, then settle actual usage against the DO-issued `requestId`.

## Bugs

1. **Unbounded, permanent per-request growth inside the DO violates §4.4 and degrades every admission over time** (`ai-platform/src/quota-do/index.ts:54-55`, `:292-294`, `:332`). `creditedRequests` (an ever-growing array) and `admittedRequests` (a map) are never swept — the DO accumulates every request id it has ever admitted or credited, forever. §4.4 is explicit: the Durable Object "Never holds: Long-term records; per-request objects" (`docs/architecture/ai-platform/01-ai-platform.md:1470`), and spec FR-002 repeats it (spec.md:310-313). Because the entire state lives under one `"state"` key and every RPC does a full read-modify-write of the blob (`src/quota-do/index.ts:156-159`, `:244`, `:302`), admission latency and DO storage grow linearly with installation lifetime. `admittedRequests` should be evicted on credit, and `creditedRequests` should not persist beyond the duplicate-credit window (or should reuse the ephemeral horizon).

2. **In-flight leaks have no recovery path, and period rollover silently zeroes the in-flight count** (`ai-platform/src/quota-do/index.ts:295`, `:331`, `:175-190`). A request admitted at stage 8 whose Worker invocation dies before stage 15 never decrements `inFlight`; sixteen such deaths permanently exhaust the installation's concurrency headroom with no timeout, sweep, or administrative reset. Separately, `maybeResetPeriod` resets the whole counter block — including `inFlight` — on period rollover (`:185-189`) while requests admitted in the old period may still be running, opening an over-admission window; and the `Math.max(0, …)` floor on credit (`:331`) then masks the resulting underflow, so the miscount is never observable.

3. **Idempotency record state never transitions past `"admitted"`** (`ai-platform/src/quota-do/index.ts:286-291`; written once, never updated). Five of the six `IdempotencyRequestState` values (`:12-18`) are unreachable from any code path: `creditRPC` adjusts counters but never marks the idempotency record `completed` — or `cancelled` when `partial: true`. A repeated key after the original request finished still returns `state: "admitted"`, so the `idempotent` outcome does not return "the existing request's state" as §6.6 requires (`docs/architecture/ai-platform/01-ai-platform.md:2026`) — it returns a permanently stale one. The contract assigns terminal-state updates to C3 as an extension (`quota-do-rpc.md:384`), but B4's own credit RPC is stage 15's settlement and is the natural place to at least close out `completed`/`cancelled`; as shipped, no test covers any state other than `"admitted"`.

4. **The stage-8 caller re-implements identity's expiry check with different semantics and no tally** (`ai-platform/src/admission/index.ts:265-267`). `principal.exp <= now` duplicates stage 2's job with no skew window, so a token identity accepted inside B1's skew is rejected here — two stages disagreeing on the same boundary. The rejection also bypasses `recordRejection`, so it is invisible to the §4.3.12 counters. The branch exists only to let `admission_expired_token_same_key_unauthenticated` exercise §6.2 without stage 2 in the harness; in the real pipeline an expired token never reaches stage 8.

5. **Entitlement load and parsing can throw out of the stage** (`ai-platform/src/admission/index.ts:269-275`, `:93-95`). `loadConfig` throws `ConfigCacheMissError` on a reader miss (A5's contract), and `runAdmission` does not guard the entitlement load — an installation with no entitlement row produces an unhandled 500 instead of a fail-closed rejection. Likewise `parseAllowedCapabilities` calls `JSON.parse` on the raw D1 string with no guard, the same crash class B3 shipped in entitlement evaluation.

6. **Non-2xx DO responses — including contract-drift 400s — are treated as DO unavailability and burn the grace cap** (`ai-platform/src/admission/index.ts:182-184`, `:288-289`). `callAdmissionDo` maps any non-ok status to `null`, which `runAdmission` reads as "DO unreachable" and routes into `admitUnderGrace`. But `GatewayObject.fetch` returns 400 for `invalid_json` and `unknown_kind` (`src/worker.ts:45-47`, `:65`), so a wire-shape bug or dispatch regression is masked as an infrastructure blip, consumes grace admissions, and pollutes the reconciliation queue. The same conflation exists on the credit side, where a non-2xx transport failure is reported as `unknown_request` (`src/credit/index.ts:53-55`), making a DO outage indistinguishable from a bad id at stage 15.

7. **The grace allowance is capped per isolate, not per installation, and the queue evaporates with the isolate** (`ai-platform/src/admission/index.ts:75-80`). `graceAdmissionsUsed` and `graceReconciliationQueue` are module-level isolate memory: with N warm isolates the effective cap is 5×N, the cap resets on isolate eviction, and any isolate that dies mid-episode takes its queued grace admissions with it — usage that is then reconciled by nobody. Open Decision 3's "capped grace allowance" (`docs/architecture/ai-platform/01-ai-platform.md:3723`) is therefore not actually capped, and the module-level queue is also per-request server-side state, which the slice's own inherited prohibitions forbid (spec.md:437-438; §4.4 "no store for live request state", `:1485-1487`). Two overlapping reset paths (`resetGraceCounterOnDoSuccess` at `:151-153`, exported `resetGraceAdmissionCounter` at `:164-167`, never called from production code) add drift.

8. **Nothing in the Worker pipeline invokes stage 8 or stage 15** (`ai-platform/src/worker.ts:69-146`; the only call sites for `runAdmission`/`creditUsage` are test files). As wired, `handleAdapterRequest` never runs admission and no stage-15 path calls `creditUsage`, `reconcileGraceUsage`, or `flushRejectionCounters` — the same never-wired pattern B3 shipped for its flush (B3 report, Bug 3). The "Done when" pipeline behaviour — one DO round trip per request, idempotent replay short-circuiting inference — cannot occur outside the test harness, and B4's private copy of the tally/flush (`src/admission/index.ts:74-138`, `:299-322`) duplicates B3's export instead of consuming it, so the two are already drifting (B3 report, Bug 3, flagged there as carried-in).

## Architectural Deviations

1. **`concurrency_exhausted` is emitted as a client-facing code outside the closed §5.4 taxonomy** (`ai-platform/src/admission/index.ts:59`, `:213-215`). §5.4's set is closed and frozen by A2 (`docs/architecture/ai-platform/01-ai-platform.md:1663-1685`), §6.1 stage 8 owns exactly `unauthenticated` and `quota_exhausted` (`:1867`), and the spec's Edge Cases state "No other code is emitted by stage 8" (spec.md:255-262). The contract's mapping table (`quota-do-rpc.md:240`) claims "no separate §5.4 code in B4" while the code returns precisely that code — contract and implementation contradict each other and both contradict the taxonomy. The outcome needs to map onto an existing code (the natural reading of §6.1 is `quota_exhausted`) or the taxonomy needs an amendment; shipping a non-taxonomy code breaks A2's frozen envelope that clients branch on.

2. **Grace-cap exhaustion rejects with `internal_error`, a code stage 8 does not own and whose semantics mislead** (`ai-platform/src/admission/index.ts:239`). §5.4 defines `internal_error` as "Platform defect", retryable, 500 (`:1685`) — a DO-outage rejection is none of those, and §6.1 stage 8's failure column names only `unauthenticated` and `quota_exhausted`. The rejection is also not tallied (no `recordRejection` call on either grace path), so an entire unavailability episode leaves no §4.3.12 signal. Open Decision 3 names the behaviour but not the code; the slice chose one silently, and it should be recorded in the spec's Edge Cases whichever way it lands.

3. **F4's soft-threshold verdict is pre-built into the admission response** (`ai-platform/src/quota-do/index.ts:203-233`, `:77`, `:297-307`; `ai-platform/src/admission/index.ts:52-53`, `:199`). The spec's Out of Scope is explicit — soft-threshold degraded routing is F4, and "B4 exposes the remaining budget that F4 will read" (spec.md:402-404). What B4 ships is not remaining-budget exposure but a computed `degraded` boolean — a routing-input decision, with threshold semantics (any-of request/token/cost ratios) invented here, absent from the frozen contract's `AdmissionAdmitted` (`quota-do-rpc.md:174-178`), and untested in this slice. This is exactly the "mechanism added because it looks prudent" shape R-20 prohibits; F4's merged test now consumes the field (`test/soft-threshold-routing.test.ts`), so the contract amendment is overdue either way.

4. **Contract/code drift on frozen response shapes** (`ai-platform/src/quota-do/index.ts:91-95`, `:273` vs `quota-do-rpc.md:191-194`). The implementation's `AdmissionQuotaExhausted` carries `period_end`, the caller maps it to `periodReset` (`src/admission/index.ts:208-211`), and the DO unit test asserts it (`test/quota-do.test.ts:371-375`) — but the frozen contract's type omits the field. The field is architecturally *right* (§5.4: 429 `quota_exhausted` carries the period reset instant, `:1697-1698`), so the contract is stale and must be amended; as frozen, C3 and F4 are bound to a shape that does not match the code the same contract names as its source of truth (`quota-do-rpc.md:10-12`).

5. **The `installationId` field on both RPCs is never validated against the DO instance** (`ai-platform/src/quota-do/index.ts:235-342` — `request.installationId` is accepted and ignored everywhere). The contract makes the field required with the semantics "must match the DO instance id" (`quota-do-rpc.md:123`, `:253`), but no handler checks it; combined with Critical 1's id conflation, the field is decorative and a misrouted or cross-installation body would be silently processed against the wrong instance's state.

6. **Admission's `now` seam is test-only and the DO dispatch never passes it** (`ai-platform/src/quota-do/index.ts:239-241`; `ai-platform/src/worker.ts:50-55`). `admissionRPC` accepts an injectable `now`, but `GatewayObject.fetch` never supplies it, so production expiry depends solely on the DO isolate's wall clock while `ephemeral_entries_expire_in_place` depends on `vi.setSystemTime` propagating across the Miniflare DO boundary (`test/quota-do.test.ts:511-536`) — a fragile coupling the seam exists to avoid but is not wired for.

## Missing or Weak Tests

1. **`grace_usage_reconciled_afterwards` cannot fail for the reason that matters** (`test/admission-credit.test.ts:527-549`). It asserts one DO fetch and `reconciled >= 1` but never reads the DO's counters, so Critical 2 — reconciliation always returning `unknown_request` and recording nothing — passes green. The test must assert the counter delta the spec's own name promises.

2. **`parallel_admissions_exact_final_count` asserts totals from a mid-sequence snapshot** (`test/quota-do.test.ts:489-507`). The final assertion reads `credits[7]`'s `periodCounters` — a snapshot taken when that particular credit executed inside `blockConcurrencyWhile`, not after all eight settled; array order is submission order, not DO execution order, so the assertion is order-dependent and can observe a partial sum. The exact final count should be read after all promises settle (e.g. one trailing credit's snapshot or a fresh admission's view of the counters).

3. **No duplicate-credit or unknown-credit cases** (`ai-platform/src/quota-do/index.ts:321-326`). The contract's "duplicate credit is idempotent or returns `unknown_request`" (`quota-do-rpc.md:301`) and the unknown-`requestId` branch each have no test; the credited-set guard is dead code as far as the suite is concerned.

4. **No idempotency-record expiry case** (`test/quota-do.test.ts:511-536`). `ephemeral_entries_expire_in_place` exercises only the `jti` replay half of `sweepEphemeral` (`src/quota-do/index.ts:161-173`); the idempotency-map eviction branch — the half FR-005's replay guarantee depends on — is never swept in any test.

5. **No token-budget or cost-budget exhaustion cases** (`src/quota-do/index.ts:196-200`; `test/quota-do.test.ts:354-377` drives only `request_quota`). `isQuotaExhausted` has three independent branches and the coverage rule's "every branch of every rule" is met for one of three; the token and cost budget boundaries (including the exact-equality edge) are untested.

6. **No period-rollover, `degraded`-flag, replay-tally, or concurrency-tally cases.** `maybeResetPeriod`'s counter reset (`src/quota-do/index.ts:175-190`) — including the observable reset the contract promises (`quota-do-rpc.md:370-372`) — has no test; the soft-threshold `degraded` computation (`:203-233`, `:297-307`) has none in this slice; and `admission_rejection_counted_not_journaled` (`test/admission-credit.test.ts:551-611`) covers only `quota_exhausted`, leaving the `unauthenticated`-replay and `concurrency_exhausted` tally paths (`src/admission/index.ts:202`, `:214`) unasserted. There is also no case for the caller's `body.kind !== "admission"` defensive branch (`src/admission/index.ts:288`).

## Recommended Improvements

- **Fix the DO id derivation and pin it with a realistic id** (`src/admission/index.ts:174`; `src/credit/index.ts:38`): switch to `env.DO.idFromName(installationId)`, correct contract §2, and change at least one test in each file to use a dashed-UUID installation id so the conflation cannot regress.
- **Make grace reconciliation real**: re-present the queued admission to the DO on recovery (so the DO itself records the `jti`, idempotency key, and issues the `requestId`), settle actual usage against that id, propagate RPC failures instead of counting them, and stop deleting the queue at cap exhaustion — a rejected request must not destroy the reconciliation record of admitted ones. Move the cap and queue out of isolate memory (the DO is the natural home once reachable; a D1 grace ledger is the honest fallback) so the cap is per-installation and survives isolate death, and assert the counter delta in the test.
- **Bound the DO's memory** (`src/quota-do/index.ts:54-55`): delete `admittedRequests[requestId]` on credit, expire `creditedRequests` on the ephemeral horizon (or replace the array with the idempotency records' own expiry), and consider sharding the single `"state"` blob so admissions stop rewriting permanent history.
- **Give in-flight a recovery story**: document and implement one of — a credit-side sweep of `admittedRequests` older than a request TTL that decrements `inFlight`, a journal-driven reconciliation at rollup time, or an explicit operator reset; and stop resetting `inFlight` on period rollover (carry it across; only usage counters belong to the period).
- **Bring the emitted codes inside the taxonomy**: map `concurrency_exhausted` and the grace-cap rejection onto §5.4 codes stage 8 owns (or amend the taxonomy and §6.1 deliberately), tally every rejection path including grace and the early `exp` return, and record the chosen grace-rejection code in the spec's Edge Cases.
- **Remove the duplicated expiry check** (`src/admission/index.ts:265-267`) once the pipeline runs stage 2 in front of stage 8 — or, if a defensive recheck is kept, apply B1's skew window and tally the rejection.
- **Fail closed on entitlement problems** (`src/admission/index.ts:269-275`, `:93-95`): catch the cache-miss throw and reject (a missing entitlement is not grace-worthy DO unavailability), and guard the `allowed_capabilities` parse.
- **Distinguish transport failure from contract failure**: treat only fetch-thrown errors and 5xx as DO unavailability; surface 4xx (`invalid_json`, `unknown_kind`) as `internal_error` immediately, and do the same split on the credit side instead of flattening everything to `unknown_request`.
- **Wire the stage and delete the duplicate tally** (`src/worker.ts`): invoke `runAdmission` from the pipeline and `creditUsage` at stage 15, drive `flushRejectionCounters` and `reconcileGraceUsage` from `scheduled`/`waitUntil`, and replace B4's private tally with B3's export as the B3 report already recommended.
- **Reconcile the contract with the code**: amend `quota-do-rpc.md` for `idFromName`, the `period_end` field, and either the `degraded` extension (with F4) or its removal from B4; drop the untriggered `now` parameter or pass it from `GatewayObject.fetch`; and validate `installationId` against the instance or stop claiming the check exists.
- **Add the missing cases**: UUID installation id; reconciliation counter delta; settled-state final count; duplicate and unknown credit; idempotency expiry; token- and cost-budget exhaustion at the equality boundary; period rollover; replay and concurrency tally rows; the grace-cap rejection's code and tally; and the stale idempotency-state transition once credit closes out records.

- **R1:** `idFromString` → `idFromName` in admission/credit callers; contract §2 + Spec Kit plan/tasks/quickstart aligned; tests use dashed UUIDs.
- **R2:** Grace queue stores re-admission params + local `graceRequestId`; reconcile re-admits then credits DO-issued id with attached usage; failures re-queue; cap reject preserves queue and emits tallied `quota_exhausted`; 4xx ≠ grace.
- **R3:** Evict admitted on credit; TTL `creditedRequests`; abandon sweep frees `inFlight`; period rollover preserves `inFlight`; credit closes idempotency; bind `installationId` on first admit.
- **R4:** Stage-8 client codes reduced to taxonomy-owned set; concurrency maps to `quota_exhausted`; defensive exp uses B3 skew + tally.
- **R5:** Entitlement miss fail-closed; credit transport codes split.
- **R6:** `scheduled` runs `reconcileGraceUsage` after flush; Spec Kit records isolate grace limitation and orchestrator ownership of POST `/v1/requests` composition (B3/C* precedent); B3 shared tally already consumed.
- **R7:** Contract fields/`now` seam/`degraded` extension; GatewayObject forwards `now`.
