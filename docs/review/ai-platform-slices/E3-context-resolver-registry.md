# Slice Review Report — E3: Context Resolver Registry, First Context RPC, and Client Contract Test

**Spec:** `specs/037-context-resolver-registry/spec.md` · **Branch:** `ai/037-e3-context-resolver-registry` · **Canonical:** §4.1, §5.2, §4.2, §13.5

## Executive Summary

E3 delivers the artifacts its slice names: a generic `ContextResolver` registry (`frontend/lib/core/ai/context_resolver.dart`) with a key-list-in / payload-or-typed-failure-out API, no capability-id surface, and an instance-scoped cache; a closed static registration map (`context_registration.dart`) binding the first published key `visit.chief_complaint@v1`; an ordinary clinic read RPC (`backend/supabase/migrations/20260802120000_context_provider_chief_complaint.sql`) following the established `public` INVOKER → `auth_internal` SECURITY DEFINER pattern with branch-scope and clinical-access checks; a four-case SQL suite wired into the trust runner; and a Flutter contract suite with a fail-closed unknown-key case. The Resolver core loop is clean — unknown keys are rejected before any resolution, so no partial payload can be returned as success. The substantive failures are in proof and wiring rather than in the registry itself. First, the client contract test — the component §13.5 says makes the Context Contract a *verified* interface — never fetches live manifests: it iterates hardcoded fixture maps from `fakes.dart`, so it cannot fail when the platform adds or changes a key, and the plan explicitly froze this downgrade ("fixtures representing the live active set in CI", "No live Worker required") against the architecture's "fetched manifests" language. Second, the one security-relevant SQL case, `context_rpc_rls_denies_out_of_scope`, is vacuous: no clinical-note row exists for the out-of-scope visit, so the pass condition holds even if the branch-scope enforcement is deleted outright. Third, no production implementation of `ContextProviderPort` exists anywhere under `frontend/lib` — only test fakes — and the port method takes no `visit_id` although the RPC requires one, so the Resolver cannot actually reach the first context RPC in the running app; the end-to-end "assembles a payload" done-when is unproven and currently impossible outside tests. Finally, the Resolver's result type has no channel for resolution *errors* (only unknown keys), so a failing RPC propagates as an arbitrary exception past callers written against the frozen API.

## Critical Issues

1. **The client contract test never fetches live manifests — the drift-catching purpose of §13.5 is defeated by construction** (`frontend/test/unit/core/ai/context_contract_test.dart:50-52`, `:68-70`; `frontend/test/unit/core/ai/fakes.dart:271-278`, `:280-361`). `runContextContractSuite` reads its "discovery body" from `FakeActiveManifestSource`, which returns hardcoded Dart map literals written in the same commit as the registration map. The done-when is "the Flutter test suite **fetches live manifests** and fails if the Resolver cannot satisfy every declared key of every active capability" (delivery plan §3.6, row E3); §13.5 specifies "Runs in the Flutter test suite against **fetched manifests** — catches 'platform requires a key the client cannot produce' *before* release"; the spec's own FR-011 and acceptance scenario 8 repeat "live active capability manifests fetched via discovery." A hardcoded fixture can never drift, so the failure mode the test exists to catch — C1/A5 shipping a manifest that declares a key the client cannot resolve — produces no signal: the fixture simply isn't updated, and the suite stays green. The plan ratifies the downgrade in plain text ("fixtures representing the live active set in CI"; "No live Worker required for the Flutter suite", plan.md Technical Context / Testing), which is a spec/plan-vs-architecture conflict; per the review rule the architecture wins, and this is a documentation issue as well as an implementation gap. As shipped, E3-T09 proves only that two artifacts written by the same author agree with each other, and E3-T10 proves the suite fails only for a synthetic manifest nobody will ever accidentally introduce — the exact tautology pattern of E1's T5.

2. **`context_rpc_rls_denies_out_of_scope` (E3-T06) is vacuous — it passes even with branch-scope enforcement removed entirely** (`backend/tests/context_provider_rpc.sql:134-138`, `:159-173`). The seed data inserts exactly one clinical-note row, `v_note_a` for the *in-scope* visit A; no `visit_clinical_notes` row exists for the out-of-scope visit B. The pass condition is `(NOT v_result.success) OR (v_result.data IS NULL) OR (NOT (v_result.data ? 'complaint'))`. Because the RPC omits `complaint` whenever no note row is found (migration `:38-50`), deleting `auth_internal.assert_visit_branch_scope` and `staff_has_visit_clinical_access` from the function body still yields `{visit_id}` with no `complaint` key — third disjunct true, test green. The one case the delivery plan names as the RPC's security proof ("RLS denies out-of-scope rows", §3.11.5 E3; spec acceptance scenario 6; §5.2 Authorization) therefore proves nothing: there is no out-of-scope row available to leak, and the condition would also accept a *successful* response that leaked `visit_id` and `recorded_at`. This is the RLS-correctness case the review brief flags as security-relevant, and it cannot fail.

## Bugs

1. **No production `ContextProviderPort` implementation exists — the Resolver cannot reach the first context RPC outside tests** (`frontend/lib/core/ai/context_provider_port.dart:2-5`; only implementors are `FakeContextProviderPort` and `DenyingContextProviderPort` in `frontend/test/unit/core/ai/fakes.dart:251`, `:456`, and `HarnessContextProviderPort` in `frontend/test/widget/ai/ai_surface_test_harness.dart:51`). The plan names the port's production role ("production: Supabase RPC; tests: in-memory fake", plan.md Files) but no task created the production half, and none exists under `frontend/lib`. Compounding this, the port method is `fetchVisitChiefComplaint()` with **no `visit_id` parameter**, while the RPC signature is `get_visit_chief_complaint(p_visit_id uuid)` — and the only production consumer, `AiFeatureHostPage`, holds `visitId` as a separate dependency and passes it to the surface, not to the port (`frontend/lib/features/ai/host/ai_feature_host_page.dart:41-42`, `:53`, `:112`, `:141-144`). There is therefore no code path — existing or sketched — by which the registered resolver for `visit.chief_complaint@v1` obtains the visit id it must supply to the RPC. The done-when's "assembles a payload from a key list" is proven only against fakes; in the running app the registry is unwired and, as frozen, unwireable without either a per-visit port construction convention the slice never establishes or an arguments channel the frozen key-list API (`resolve(List<String> keys)`, `context_resolver.dart:40`) does not have.

2. **The Resolver has no typed failure channel for resolution errors — a failing RPC escapes as an arbitrary exception** (`frontend/lib/core/ai/context_resolver.dart:63-66`). `ContextResolveFailure` exists only for `unknown_context_key`; if the registered resolver's port call throws (RPC `FORBIDDEN`/`NOT_FOUND`, network error, malformed payload), the exception propagates raw out of `resolve`. The frozen contract (`specs/037-context-resolver-registry/contracts/context-resolver.md` §2.3) defines exactly two outcomes — success or typed unknown-key failure — so every consumer written against the contract handles neither: the first surface awaits `resolve` with no try/catch and maps only `ContextResolveFailure` (`frontend/lib/features/ai/surface/first_ai_feature_surface.dart:120-124`), and the J2/H-band consumers (`context_required_self_heal.dart:61`, `conversation_loop.dart:87`) do the same. A transient clinic-DB error during resolution thus crashes the invoke flow instead of surfacing a typed failure. The spec's Edge Cases name the unknown-key failure but are silent on known-key resolution failure — a gap the frozen API should have closed, since E4+ consumers are already binding to it.

3. **The only production Resolver instance is never disposed — FR-005's "discarded on dispose" is unexercised in real wiring** (`frontend/lib/features/ai/host/ai_feature_host_page.dart:70-151`). `_AiFeatureHostPageState` creates `ContextResolver` in `_bootstrap` (`:111-113`) but overrides no `dispose()` and never calls `_resolver?.dispose()`. The cache is instance state, so it dies with the State object by GC rather than by the explicit discard path the slice froze (Clarification Q1; contract §4: "Disposing the screen/host discards the instance and its cache"); the unit test T04 proves discard only by constructing a *second* resolver and observing a refetch (`context_resolver_test.dart:55-70`), never by exercising `dispose()` itself. The file belongs to E4, but the freeze is E3's, and the one integration point that should demonstrate the behaviour does not.

4. **`recorded_at` is sourced from the note's `updated_at`, so any later edit rewrites the "recorded" timestamp** (`backend/supabase/migrations/20260802120000_context_provider_chief_complaint.sql:43-49`). The A5 shape declares `recorded_at` as optional iso8601 (`ai-platform/src/context/index.ts:50-55`); semantically it is when the complaint was recorded, for which the row's `created_at` is the stable source. As implemented, editing any field of the clinical note changes the `recorded_at` the platform receives and journals, undermining the §5.2 freshness/trust story ("the journal records exactly what context was used"). Minor, but the field is part of the frozen first-key shape comparison.

## Architectural Deviations

1. **"Fetches live manifests" narrowed to static fixtures — spec/plan conflict with the architecture, unflagged** (plan.md Technical Context → Testing; spec.md FR-011 and acceptance scenario 8 vs. the plan's own Contract-suite paragraph). See Critical 1 for the mechanism. The deviation is recorded here separately because it is also a *documentation* mismatch: the spec's Freezes and FR-011 state the architectural requirement ("fetches live manifests"), while the plan's Testing section and the implementation deliver fixtures, and neither document flags the narrowing. Per the review rule the architecture (§13.5 "against fetched manifests"; delivery plan §3.6 done-when) takes precedence; the mismatch must be recorded even if the fixture approach is accepted as a staging step.

2. **The "RLS denies" posture is actually imperative branch-scope checks inside a SECURITY DEFINER function, with no RLS backstop on the table read** (migration `:5-8`, `:14-22`, `:24-28`, `:30-36`). §5.2 Authorization states "Resolution happens under the caller's own Supabase permissions **and RLS**", and the spec's acceptance scenario 6 and test name (`context_rpc_rls_denies_out_of_scope`) claim RLS denial. In fact the function runs as its owner: the `SELECT` from `public.visit_clinical_notes` bypasses that table's RLS policies entirely, and isolation rests wholly on two hand-rolled predicates — `assert_visit_branch_scope` (a `branch_id = ANY(jwt_branch_ids())` filter, `20260531180000_visit_medical_records.sql:313-322`) and `staff_has_visit_clinical_access()`. §4.2 does sanction the established `public` wrapper → `auth_internal` SECURITY DEFINER pattern for clinic additions, so SECURITY DEFINER per se is not the deviation; the deviation is the spec/test language asserting an RLS guarantee that the mechanism does not provide, and the absence of any defence-in-depth: a future edit that drops or weakens one imperative check leaks cross-branch clinical notes with no policy layer to catch it — and per Critical 2, the test suite would not catch it either.

3. **The contract suite proves "resolvable" against a fake port and never checks the resolved payload against the declared shape** (`context_contract_test.dart:23-27`; `fakes.dart:263-268`). §13.5's client contract row is "The Context Resolver **satisfies** every declared key for every active capability." The suite asserts registration membership and that `resolve` returns `ContextResolveSuccess` — against `FakeContextProviderPort`, whose canned payload is hardcoded in the test substrate. A key whose real RPC is broken, returns the wrong shape, or violates its `shapeRef` passes the suite. The A5 side owns shape validation (`validatePayload`, `ai-platform/src/context/index.ts`), but nothing on the client side ever compares a resolved payload to the published shape, so "satisfies" is demonstrated only in the weakest sense (a map with the key present). Combined with Deviation 1, neither half of the verified-interface claim — live keys, real shapes — is currently exercised.

## Missing or Weak Tests

1. **E3-T09/T10 have no live or even derived manifest source** (`context_contract_test.dart:48-84`; `fakes.dart:280-361`). Beyond Critical 1's point, there is no mechanism keeping the fixture honest: the fixture manifest is not generated from, diffed against, or even co-located with the platform's published manifest artifacts (`ai-platform/src/manifest`, C1 discovery), so nothing fails when the two drift apart. The T10 negative case injects `patient.demographics@v1` — a key §5.2 itself lists as an example — proving the fail-closed branch only for a key nobody will register by mistake.

2. **E3-T06's pass condition is three-way loose and its fixture lacks the row that could leak** (`context_provider_rpc.sql:159-173`, seed at `:134-138`). See Critical 2. The required fix is a test, not just data: insert a clinical note for the out-of-scope visit and assert `NOT success` with the specific `NOT_FOUND`/`FORBIDDEN` code, so the case fails if enforcement is removed, and cannot be satisfied by a successful-but-empty leak.

3. **E3-T03 proves only a Dart method signature, which the compiler already enforces** (`context_resolver_test.dart:42-53`). Tearing off `resolver.resolve` as `Future<ContextResolveResult> Function(List<String>)` and expecting completion cannot detect capability-id *branching* inside the implementation — the actual prohibition (FR-003, §4.1). A regression that threaded a capability id through the port or the registration map (e.g. a resolver closure switching on a captured capability) would leave this test green. Dart's lack of mirrors limits static options, but the test as named overstates what is proven; at minimum a spy-based case (a `ResolverSpy` exists unused for this in `fakes.dart:432-443`) could assert that resolution output is invariant to which capability's manifest supplied the key list.

4. **No case exercises the resolution-failure path, the no-note payload, or the shape boundaries** (`context_resolver_test.dart`; `context_provider_rpc.sql`). (a) No test has the port throw, so the raw-exception behaviour of Bug 2 is unobserved. (b) No SQL case covers a visit with no clinical note or a NULL `complaint` — the payload then is `{visit_id}` only, and while A5's cardinality (`{maxLength: 10000}`, not `required`; `index.ts:44-49`, `:124-125`) makes that conformant, the conformance is asserted nowhere. (c) The 10000-character `complaint` boundary the architecture names (§3.10: "every named boundary") is untested at, below, and above the limit. (d) E3-T08 checks presence and types of declared fields but never asserts the *absence* of undeclared fields (`context_provider_rpc.sql:210-218`), so an RPC that starts leaking extra note columns still "matches the A5 shape."

5. **E3-T04 never tests `dispose()` itself, and no case proves two Resolver instances cannot share cache state** (`context_resolver_test.dart:55-70`). The test proves instance-scoping by replacement, not discard: `resolve` after `dispose` throws an untested `StateError` (`context_resolver.dart:41-43`), and the disposed instance's cleared cache is asserted only indirectly via a fresh instance. The named boundary ("discarded on dispose", §3.11.5 E3) has its failing branch — cache surviving dispose — unproven, and the production wiring (Bug 3) never calls `dispose` at all.

## Recommended Improvements

1. **Give the contract suite a live or derived manifest source**: either an integration job that fetches the real C1 discovery body from a running Worker (the §13.5 reading), or — if CI hermeticity forbids that — a fixture *generated from* the platform's published manifest artifacts with a CI assertion that the two agree, so key drift breaks a build somewhere. Record the narrowing in the spec/plan if the fixture approach is retained (Deviation 1).
2. **Fix T06**: seed a `visit_clinical_notes` row for the out-of-scope visit and require `NOT success` with the specific error code; drop the `data ? 'complaint'` disjunct. Consider a second case proving the denial comes from scope enforcement (in-scope visit with note succeeds in the same suite — already T05 — so a regression that denies *everything* is also caught).
3. **Wire the production half of the port**: implement `ContextProviderPort` over the Supabase client calling `public.get_visit_chief_complaint`, and resolve the `visit_id` gap explicitly — either construct the port per-visit at the screen (and document that convention in `contracts/context-resolver.md`) or extend the frozen API with an arguments channel before E4/H3 consumers multiply. Until then the slice's done-when is met only in tests.
4. **Add a typed resolution-failure outcome** to `ContextResolveResult` (or document port-throws as the contract) and cover it with a unit test; update the two existing consumers' unguarded `await resolve(...)` calls accordingly.
5. **Dispose the Resolver in `_AiFeatureHostPageState.dispose()`** and extend T04 to assert post-dispose behaviour (`StateError`) and that a disposed instance's cache is not merely shadowed but cleared.
6. **Tighten the SQL suite**: assert absence of undeclared payload fields in T08, add the no-note/NULL-complaint case, and add the 10000-character boundary cases for `complaint`; align the test names and spec scenario 6 wording with the actual enforcement mechanism (imperative scope checks, not table RLS), or add `FORCE ROW LEVEL SECURITY`-equivalent defence so the "RLS denies" claim is literally true.
7. **Note the CI trigger caveat from the E1 review**: the `flutter test` step (`.github/workflows/ci.yml:61`) that runs this slice's unit and contract suites is in the workflow whose triggers do not fire on `ai/*` pushes, so E3's Flutter suites join CI permanently only on the `main`/`master` line — the same dormancy as E1 Critical 1, inherited by every Band E suite until the triggers are widened.
