# Slice Review Report — F2: Acceptance Recording RPC and Client Accept Path

**Spec:** `specs/040-acceptance-recording/spec.md` · **Branch:** `ai/040-f2-acceptance-recording` · **Canonical:** §4.2, §4.2.2, §4.1, A5

## Executive Summary

F2 delivers the artifacts its plan names: the `ai_internal.acceptance_targets` registry with the single demonstration row `visit_clinical_notes` → `save_visit_documentation`, the `public.ai_accepted_output` table with the §4.2.2 columns, §8.9-format CHECK, uniqueness, indexes, and a SELECT-only RLS policy, the `auth_internal.record_ai_acceptance` SECURITY DEFINER half plus its `public` INVOKER wrapper, a Flutter port/client/controller trio under `frontend/lib/features/ai/acceptance/`, and SQL + Flutter suites covering the ten named tests, wired into `run_ai_platform_trust_tests.sh`. The core shape honours §4.2.2: the clinical write is genuinely *delegated* to the existing domain RPC (not re-implemented), the domain write + `ai_accepted_output` + `ai.acceptance_record` audit entry are one function call and therefore one transaction, provenance resolves in both directions, and the demonstration target promotes no product capability. The substantive concerns are three. First, the registry is not actually the dispatch mechanism the architecture freezes: two hardcoded `IF p_domain_function = 'save_visit_documentation'` chains (one in the dispatcher, one in `record_ai_acceptance` itself) mean a migration that adds a registry row — which §4.2.2 says is the *entire* enablement cost of a new target — produces a runtime `INTERNAL_ERROR`, so the "registry is the only source" claim holds only for rejection, not for enablement. Second, the `EXCEPTION WHEN OTHERS` handler in `record_ai_acceptance` converts any exception whose message is exactly `'FORBIDDEN'` into a normally-returned failure `rpc_result`; because the handler wraps the whole body *including the inserts that follow the delegated domain write*, any future trigger or policy raising that idiom after the domain write would commit the domain change with no acceptance row and no audit entry — a silent violation of the slice's central "together or not at all" invariant. It is unreachable today, which is exactly why it will survive until it fires. Third, several of the prohibition tests are vacuous in the same way the E4 review flagged: the T8 spy port is never injected into the E4 surface it supposedly watches, the SQL halves of T3/T4 assert row counts and the absence of content nobody attempted to write, and the unit no-auto-commit test asserts that a freshly constructed capture client was never called. Coverage-rule gaps compound this: no test denies a caller lacking `visits.edit_soap`, no test fails the transaction at the acceptance-write stage, and the malformed-reference branch the RPC implements has no case.

## Critical Issues

None. The atomic write path as exercised today is correct: delegated failure returns before any acceptance write (T9), and any exception that escapes the function aborts the PostgREST transaction wholesale, rolling back the domain write with it.

## Bugs

1. **The `EXCEPTION WHEN OTHERS` handler can commit a partial acceptance — domain write without `ai_accepted_output` or audit entry** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:194-200`). The handler wraps the entire function body and returns `rpc_error('FORBIDDEN', …)` — a normal return, i.e. a commit — whenever `SQLERRM = 'FORBIDDEN'`. The clinic idiom of `RAISE EXCEPTION 'FORBIDDEN'` is used by permission/scope assertions throughout the codebase (e.g. `20260628140000_visit_documentation_redesign.sql:317`), and the delegated RPC's own identical handler is safe only because its FORBIDDEN sources fire *before* its writes. Here the handler also covers the `audit_log` INSERT and the `ai_accepted_output` INSERT, which run *after* the delegated domain write has succeeded. Any future trigger, `FORCE RLS` change, or helper on those tables that raises the same idiom would return a clean failure to the caller while the clinical write commits — the exact half-written state FR-009 and the §3.11.6 floor exist to make impossible, and no test would catch it (T9 fails *before* the write; nothing fails *after* it). The fix is structural: scope the conversion to the delegated call, or let all post-write exceptions propagate. **Severity: high (latent).**

2. **A duplicate acceptance escapes as a raw PostgREST 500 instead of a clean `rpc_error`** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:37-39`, `:194-200`). Re-accepting the same `(table_name, record_id, ai_request_reference)` hits the unique constraint; the message is not `'FORBIDDEN'`, so the handler re-raises and the client receives an HTTP 500 carrying a raw constraint-violation payload. Atomicity is preserved (the domain write rolls back too), but the slice's "no new error vocabulary" posture (FR-005) is honoured only on the happy paths — a foreseeable, client-reachable conflict is surfaced through the ugliest channel available, and the Flutter client (`clinical_acceptance_client.dart:18-27`) has no `try/catch`, so the `PostgrestException` propagates to whatever future surface hosts the accept button. **Severity: medium.**

3. **`record_id` and `branch_id` are sourced from client-supplied args, not from what the delegated RPC actually wrote** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:137-146`). `v_record_id := (p_target_args ->> 'p_visit_id')::uuid` trusts the caller's JSON rather than `v_domain_result.data ->> 'visit_id'`, which the delegated RPC returns (`20260628140000_visit_documentation_redesign.sql:423`). Today the two are identical by construction, but the provenance row is supposed to record the write that happened; any future target whose RPC normalizes, redirects, or resolves its target row internally would leave `ai_accepted_output` pointing at a row that was never written, with the audit entry agreeing with it. The architecture's "same vocabulary as `audit_log.record_id`" is a statement about the *domain row written*, not about the request payload. **Severity: low.**

4. **`ClinicalAcceptController.discard()` is an empty method — the discard contract is satisfied by a no-op** (`frontend/lib/features/ai/acceptance/clinical_accept_controller.dart:41-42`). "Discard writes nothing" is trivially true of `void discard() {}`, and even local draft clearing is left to the caller (the test harness does its own `setState`). The method exists so tests can call something named discard; it carries no behaviour a regression could break, so T3's Flutter half can never fail for a real reason. **Severity: low.**

## Architectural Deviations

1. **The registry is not the dispatch mechanism — enabling a target requires editing two hardcoded `IF` chains, not "adding a registry row"** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:73-86`, `:137-146`). §4.2.2 freezes that "`p_target_key` resolves, in an allow-list registry … to exactly one existing `public` domain RPC" and that "enabling a new clinical capability therefore adds a registry row, never a second acceptance path." In this implementation the registry row is looked up, its `domain_function` value is then *compared against a hardcoded literal* in `auth_internal.invoke_acceptance_domain_rpc`, and a second hardcoded literal in `record_ai_acceptance` re-derives `record_id` per function. A migration that registers a new target — the exact act the architecture says is sufficient — yields `INTERNAL_ERROR: Domain function is not configured` at runtime, *after* registry validation passed. The registry is thus the source of rejection but not of dispatch; the frozen contract (`contracts/acceptance-recording.md` §3, "The only source of which domain RPC acceptance may invoke") overstates what the code does. A static dispatch table is a defensible implementation choice (named-argument dynamic SQL is genuinely awkward), but then the contract and the §4.2.2-derived Freezes should record the narrowing — as built, the documentation claims a property the code does not have, and Open Decision 14's later Consumes will bind to the claim. **Severity: high.**

2. **The migration grants EXECUTE on the `auth_internal` definer functions to `authenticated`, where the clinic pattern revokes it** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:220-222`). Every comparable migration revokes EXECUTE on the `auth_internal` SECURITY DEFINER half from `PUBLIC, authenticated, anon` so the `public` wrapper is the only gate (the E4 slice was flagged for merely *omitting* the revoke; this slice goes further and grants). Worse, `auth_internal.invoke_acceptance_domain_rpc` — an internal dispatch helper that is not even part of the frozen contract — is directly callable by any authenticated session. No privilege escalation results (the delegated RPC self-authorizes via JWT claims), but the F4 wrapper-gate discipline exists so that the exposed surface is enumerable; this adds two entries to it for no reason. **Severity: medium.**

3. **No production AI Feature Surface exposes the clinical accept path — the "client accept path" is a library exercised only by a test-local harness** (`frontend/lib/features/ai/acceptance/`; the only call sites are `frontend/test/widget/ai/clinical_accept_path_test.dart` and `frontend/test/unit/ai/clinical_acceptance_client_test.dart`). FR-013 states AI Feature Surfaces MUST expose explicit accept/discard for the clinical accept path, and the plan's Structure Decision says the path "lives beside E4 surfaces." What shipped is a port, a client, and a controller that nothing in `frontend/lib` instantiates; the accept/discard UI exists only as the private `_ClinicalAcceptHarnessSurface` inside the test file. Given Open Decision 1 keeps every product capability `advisory_display`, a harness-only path is arguably the *correct* scope — but then the spec's Freezes ("The client clinical accept path on AI Feature Surfaces") and tasks.md's completion claims oversell what exists, and the quickstart's "clinical accept harness" is a test fixture, not a runnable surface. The architecture (§4.1) names accept/discard as a Feature Surface responsibility; the deviation should be recorded, not implied away. **Severity: medium.**

4. **Unnecessary `service_role` grant on the registry, justified by an incorrect comment** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:11-14`). The comment claims "F2 needs service_role read of the registry," but nothing in the slice reads `acceptance_targets` via `service_role` — the SECURITY DEFINER RPC reads it as owner. The grant (and the schema-USAGE grant on `ai_internal`, which B1 deliberately narrowed) is dead surface area; `service_role` bypasses RLS regardless. **Severity: low.**

## Missing or Weak Tests

1. **No test that acceptance grants no privilege — a caller without `visits.edit_soap` is never exercised** (`backend/tests/ai_acceptance_recording.sql`). §4.2.2's central security claim is that "acceptance grants no privilege the clinician did not already have," because the delegated RPC runs its own authorization. Every SQL case runs as a doctor who holds the permission. A staff role without `visits.edit_soap` calling `record_ai_acceptance` with valid args should return the delegated denial and write nothing; under §3.10 ("every invariant … it inherits") this is a required behavioural case, and it is also the only test that would catch a future regression where the SECURITY DEFINER chain accidentally authorizes the write itself. **Severity: medium.**

2. **No partial-failure atomicity test at the acceptance-write stage** (`backend/tests/ai_acceptance_recording.sql`). The spec's own Edge Cases name it: "if the domain change cannot be committed with the `ai_accepted_output` row and `audit_log` entry in the same transaction, none of the three persist." T9 fails *inside the delegated RPC*, before any acceptance write. The complementary case — the domain write succeeds, then the acceptance insert fails (most cheaply: a second accept with the same reference tripping the unique constraint) must roll the domain write back — is untested. This is precisely the branch Bug 1 lives in. **Severity: medium.**

3. **The malformed-`p_request_reference` rejection branch has no test** (`backend/supabase/migrations/20260802150000_ai_acceptance_recording.sql:109-112`; `backend/tests/ai_acceptance_recording.sql`). The RPC implements pre-write rejection of a reference failing the §8.9 shape, and contract §2.3 freezes that behaviour; §3.10 requires every branch of every rule. Only well-formed `'A1B2-C3D4'` references appear in the suite. **Severity: medium.**

4. **T8 (`advisory_display_accept_unchanged`) is vacuous — the spy port is never connected to the surface it watches** (`frontend/test/widget/ai/clinical_accept_path_test.dart:153-176`). The test constructs `SpyClinicalAcceptancePort` and then pumps the E4 surface, which has no reference to the port and no way to reach it; `expect(spy.calls, isEmpty)` cannot fail. The companion assertion, `harness.persistenceProbe.writes isEmpty`, relies on the E4 probe the E4 review already flagged as having no production call sites. The test therefore proves that a widget which cannot invoke acceptance does not invoke it — the same self-reported-spy pattern flagged in E4's T8/T16/T17. **Severity: medium.**

5. **The SQL halves of T3 and T4 are tautologies** (`backend/tests/ai_acceptance_recording.sql:296-324`). T3 asserts `acceptance_count = 1 AND audit_count = 1` — i.e. that the earlier tests wrote what they wrote; no discard action exists at the SQL layer to exercise. T4 asserts the absence of the string `'Provisional unaccepted draft'` and of reference `'Z9Y8-X7W6'`, neither of which any code path attempted to persist. Both pass on any database, including one with no F2 code at all. **Severity: low.**

6. **The unit no-auto-commit test asserts a fresh capture client was never called** (`frontend/test/unit/ai/clinical_acceptance_client_test.dart:32-41`). `expect(client.lastFunction, isNull)` twice, with a comment between them, on a client nothing has touched. It supports T7 in name only. **Severity: low.**

7. **T6 checks only the absence of forbidden columns, never the presence of the required ones** (`backend/tests/ai_acceptance_recording.sql:255-273`). The §4.2.2 column list, the CHECK constraint, the unique constraint, and both indexes are frozen contract items; a migration missing `branch_id` or the uniqueness would pass T6 as written. **Severity: low.**

8. **T1/T2 under-assert the frozen success shape** (`backend/tests/ai_acceptance_recording.sql:220-253`). T1 never asserts that the delegated RPC's own `data` keys survive the merge (FR-005 requires `visit_id` / `updated_at` preserved alongside the four acceptance keys). T2 verifies the forward reference and the `audit_log_id` back-link but never cross-checks `new_data_json ->> 'acceptance_id'` against the `ai_accepted_output` row, leaving half of FR-008's payload unproved. **Severity: low.**

9. **No RLS tenant-isolation case for `ai_accepted_output`** (`backend/tests/ai_acceptance_recording.sql`). The SELECT policy (`20260802150000_ai_acceptance_recording.sql:49-57`) is the only read path and is never exercised cross-tenant; a second-org read should return nothing. **Severity: low.**

## Recommended Improvements

1. **Fix the exception handler's scope** (Bug 1): convert `FORBIDDEN`-message exceptions only around the delegated invocation, or drop the conversion and let the delegated RPC's own handler do its job; every exception raised after the domain write must propagate so the transaction aborts. Then add the Missing-Tests-2 case (duplicate reference) to prove the rollback.
2. **Reconcile dispatch with the contract** (Deviation 1): either make dispatch genuinely registry-driven (e.g. a dispatch table keyed by `domain_function` populated from the registry, or dynamic SQL with named-argument marshalling), or amend `contracts/acceptance-recording.md` §3 and the spec Freezes to state that enabling a target is a registry row *plus* a dispatcher branch — the architecture document claims the former, so prefer the former or escalate the deviation.
3. **Return a clean conflict for duplicate acceptance** (Bug 2): catch `unique_violation` on the acceptance insert and return an existing clinic `rpc_error` code (or document the 500 as the deliberate posture); add a `try/catch` in `ClinicalAcceptanceClient` so transport and PostgREST failures surface as a typed result rather than a thrown exception.
4. **Restore the wrapper-gate discipline** (Deviation 2): replace the two `GRANT EXECUTE … TO authenticated` on `auth_internal` functions with the sibling migrations' `REVOKE ALL … FROM PUBLIC, authenticated, anon`, and drop the `service_role` grants with their incorrect comment (Deviation 4).
5. **Source provenance from the write, not the request** (Bug 3): take `record_id` from `v_domain_result.data` (the delegated RPC already returns `visit_id`) so `ai_accepted_output` records what was written.
6. **Make the prohibition tests honest** (Weak Tests 4–6): delete the SQL halves of T3/T4 or replace them with a real negative drive (e.g. attempt the write path the prohibition guards and assert refusal); connect T8's spy through an actual injected dependency or replace it with a static guard assertion; replace the unit no-auto-commit test with a controller-level case that drives idle/discard and asserts zero port invocations.
7. **Close the coverage-rule gaps** (Missing Tests 1–3, 7–9): add the no-`visits.edit_soap` denial case, the malformed-reference case, positive column/constraint/index assertions in T6, the merged-`data` and `acceptance_id` cross-checks in T1/T2, and a cross-tenant RLS read case.
8. **Decide the accept path's production status** (Deviation 3): either wire `ClinicalAcceptController` into a real (possibly internal/demonstration) surface in `frontend/lib`, or amend the spec Freezes, plan, and quickstart to state plainly that F2 ships the accept path as a tested library whose UI integration awaits the first `human_accept_required` capability — the current documents claim a surface that does not exist.

### 1.3 Fix implemented

- Removed the outer `EXCEPTION WHEN OTHERS` → `RETURN rpc_error('FORBIDDEN')` path so post-write failures abort the transaction; org check moved before the delegated write; missing record id after write raises.
- Duplicate accept: pre-write `INVALID_INPUT` when `(ai_request_reference, table_name)` already exists; residual transport failures mapped in `ClinicalAcceptanceClient`.
- Dispatch: registry-gated dynamic SQL from `public` `rpc_result` signatures (`proargnames` / `proargtypes`); public wrapper is `SECURITY DEFINER` with `auth_internal` EXECUTE revoked from `authenticated`.
- Provenance: `record_id` from delegated success payload; dropped hardcoded per-function IF for id derivation.
- Flutter: real `discard()` clears staged draft; T8 no longer uses a disconnected spy; Spec Kit states library-only scope until `human_accept_required`.
