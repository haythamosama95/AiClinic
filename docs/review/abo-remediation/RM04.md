## 1. Findings implemented

### R2-C1 — Exact HP binding depends on JSON insertion order

`ai-platform/src/vendor/entrypoint.ts`:

- Added `canonicalParamsEqual(params, expected)`: byte equality of the
  RFC 8785 `canonicalize()` forms of both maps; any canonicalization error
  (an `undefined` member, an invalid number) is a failed match, never a
  throw.
- `operationParamsMatch` now ends with `return canonicalParamsEqual(params,
  expected)` instead of `stableJson(params) === stableJson(expected)`
  (insertion-order-sensitive `JSON.stringify`).
- `stableJson` is retained for the `publishPlanVersion` idempotency
  comparison (line ~456); that comparison is outside the finding.

Completion: reordered identical maps are accepted; changed, extra or
missing fields are rejected (see §3, test 1).

### R2-P2 — Ceiling override accepts an unrelated or stale second approval

`ai-platform/src/vendor/entrypoint.ts`:

1. `verifyCeilingOverrideAssertion` now binds the second approval to the
   current call:
   - top-level negotiated version: `operation.contract_version === version`;
   - canonical params equality (reusing R2-C1's `canonicalParamsEqual`) to
     `{contract_version: version, access_jwt: verifiedJwt,
     envelope: envelopeWithoutCeilingOverride(currentEnvelope)}`; only the
     separate ceremony's `nonce`/`issued_at` may differ from the grant
     operation's;
   - `op === "ceiling_override"` (kept) and the same verified Access actor
     (`actor_email` vs the verified Access email, `actor_email_mismatch`);
   - `assertionIssuedAtFresh` on the override `issued_at`
     (`assertion_expired`);
   - active-signer verification (`signer.status === "active"`,
     `credential_not_active`).
2. An absent explicit `ceiling_override_operation` derives only the exact
   existing grant-metadata form (`buildCeilingOverrideOperation`); the
   timestamp-search fallback (the previous second `verifyAssertion` retry
   loop over `ASSERTION_FRESHNESS_MS` candidate `issued_at` values) is
   removed. `clientDataJSON` is now parsed inside try/catch: invalid JSON
   returns `assertion_invalid` instead of throwing.
3. Replay is verified against the actually verified digest, which must
   differ from the first (grant) digest (`assertion_used` on equality, in
   addition to the kept challenge comparison and the `assertion_used`
   table check). In the `grant` flow, when an override is present, the main
   claim, the override claim and the entrypoint audit row land in **one
   atomic `env.DB.batch([...])`** before coverage dispatch; a batch
   failure writes the refusal audit and returns `assertion_used`, so a
   second-claim failure never leaves a main-only claim. Duplicate
   rejection (pre-checks) and the DO-side AL-12 alert behavior are kept.

Completion: changed envelope/org/actor/version or a stale second approval
never reach coverage dispatch; correctly bound sequential touches work
once; exact replay returns `already_applied` (the completed result) and
reuse of the signed operations with a changed envelope fails (see §3,
tests 2–3).

### R2-P3 — Concurrent bootstrap admits multiple unapproved passkeys

`ai-platform/src/vendor/entrypoint.ts` (`bootstrapRegister`):

1. The plain `INSERT` is replaced with
   `INSERT … SELECT ?, … WHERE NOT EXISTS (SELECT 1 FROM operator_credential)`;
   emptiness and insertion are now one atomic D1 statement. The decision
   comes from the statement's `meta.changes`. The early `registrySize`
   count in `registerOperatorCredential` is retained only as a fast
   refusal.
2. Zero changes (lost race, including rows inserted by a concurrent
   winner) writes the refusal audit and returns `assertion_required`;
   there is no bootstrap success alert — only the inserted winner receives
   the bootstrap success audit and AL-13. Because the `NOT EXISTS` guard
   sees any row, pending and revoked rows also close bootstrap
   permanently. Pending+24 h activation and normal HP registration /
   idempotency are unchanged.

Completion: simultaneous distinct no-assertion registrations create
exactly one row (the race goes through the real `Promise.all` path, not
only the early count); pending/revoked-only registries refuse
no-assertion registration with `assertion_required` and no AL-13 (see §3,
tests 4–5).

## 5. Seams for later phases

- **Seam for RM05:** the platform now accepts a ceiling-override operation
  only in the bound form — `op: "ceiling_override"`, top-level
  `contract_version` equal to the negotiated version, params exactly
  `{contract_version, access_jwt, envelope: <submitted envelope minus
  ceiling_override>}`, same Access actor, fresh `issued_at`, active signer.
  For separate-time ceremonies the producer **must send the explicit
  `ceiling_override_operation`** (R2-P2 step 2); only the derived
  grant-metadata form (grant `issued_at`/`nonce`) is accepted when the
  operation is absent, and the timestamp-search fallback is gone. The
  browser ceremony built in RM05 must serialize and submit that exact
  explicit operation.
- **Seam for RM17:** accepted complimentary operator commands depend on
  this phase's binding (`operationParamsMatch` canonical comparison and the
  override ceremony); RM17's ABO accepted-command work should reuse
  `canonicalParamsEqual` semantics rather than re-deriving a comparison.
