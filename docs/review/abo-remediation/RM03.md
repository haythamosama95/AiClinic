## Changed files and symbols

New forward migrations in `ai-platform/migrations/` (in order):

1. `20261018120000_r1_c3_malformed_issuer_key_cleanup.sql` — R1-C3: revokes `active`/`retiring`
   `issuer_key` rows whose bounds are unparseable or reversed (`julianday(not_before) IS NULL` /
   `julianday(not_after) IS NULL` / `julianday(not_before) >= julianday(not_after)`). `revoked` rows
   are never touched (revoked kids are never revived, decision D-5) and no replacement dates are
   guessed.
2. `20261018120100_r1_c2_tenant_creation_cap_trigger.sql` — R1-C2: `CREATE TRIGGER
   tenant_creation_cap_guard BEFORE INSERT ON tenant_binding WHEN NEW.epoch = 1` aborts with
   `RAISE(ABORT, 'tenant_creation_cap')` when 50 or more epoch-1 rows have `created_at` strictly
   after `NEW.created_at - 24 hours` (string comparison over the code's normalized UTC millisecond
   format; exactly-24-hour-old rows no longer count).

## Discovered issues

- `resolveOrInsertGrantBinding` (grant path) has no cap handling of its own. With the R1-C2 trigger
  authoritative, an at-cap epoch-1 insert from the grant path now throws
  `tenant_binding insert conflict without live row` (its catch re-reads, finds no live binding, and
  raises) instead of silently exceeding the cap. The outcome is fail-closed, but it is a raw 500-style
  vendor error rather than a classified refusal — left to the phase that owns the grant binding
  writer (seam above), per the R1-C2 recipe which scopes this phase's changes to
  `resolveInstallationId` only.
- The e2e fullstack harnesses forwarded PostgreSQL `timestamptz::text` values (`2026-10-18
  09:00:00+00`) as issuer-key validity bounds; pre-RM03 this was tolerated by the fail-open verifier.
  Normalized in this phase (see R1-C1 e2e alignment); no production defect remains because
  registration now rejects such strings up front.
- Pre-existing baseline flake `E2E-P3.9-01 FM-06 …` (`ai-platform/workers`) is unrelated to this
  phase (intermittent, documented in RM00/RM02).
- Round-1 lesson (fixed in `c6ed3dd6`): tightening a fail-open time comparison to fail-closed must
  not silently change its granularity. The original checks compared `nowSeconds` against
  `floor(notBeforeMs/1000)` / `floor(notAfterMs/1000)`; an over-literal ms-precision rewrite
  rejected freshly registered keys for up to one second. Harnesses register keys with
  `new Date().toISOString()` (ms fraction) and verify immediately, so CI caught it as ~50% of
  e2e/workers/version-matrix tests failing at the first authenticated request.
