# RM26 — Transfer conservation

## Findings implemented

- **R6-DM1:** transfer preserves active settled usage and grace accounting, validates imported accounting values before writes, freezes new source admission, and waits for pending platform accounting, fallback admission, and Durable Object reservations before exporting.
- **R6-DM2:** transfer-in/out replay remains tied to exact Durable Object request content and receipts. Destination conflicts fail closed; imported grant evidence carries the transfer authorization; the receiver emits a `grant_applied` event per imported term followed by the transfer event. A lost D1 step write recovers from the Durable Object replay record without creating a second copy.
- **R6-PT2:** begin-transfer now accepts a durable preparation containing the immutable source/destination epochs, destination ID, reason, actor, signer, command, and assertion hash. Destination initialization and source freeze are fenced to the preparation ID. Publication atomically retires the accepted source epoch, activates the reserved destination, moves the routes, and creates the transfer only after both Durable Object acknowledgements. Exact retries and a bounded leased dispatcher resume uncertain or caller-abandoned operations.
- **Sol pre-CI findings:** all seven findings were addressed, including fallback-admission fencing, grant-application fencing, legacy transfer adoption based on verified historical evidence, lost-step recovery, conservation assertions, immutable D1 completion retries, and validation of active legacy packages.

No recipe steps were intentionally deferred. The ordered implementation steps and acceptance-test mapping are in [RM26.todo.md](RM26.todo.md).

## Operator checklist

1. Apply `20261020140000_r6_rm26_transfer_preparation.sql` after the RM25 fallback-settlement migration and before deploying code that reads `transfer_preparation`.
2. Deploy the Worker and Durable Object code together so the new epoch/transfer-ID fences and transfer dispatch protocol are available.
3. Keep the five-minute scheduled trigger enabled so accepted preparations recover after transient or unknown external outcomes.
4. Review aged nonterminal preparation rows and their source/destination Durable Object acknowledgements before any manual repair; do not create a replacement transfer or destination epoch by hand.
