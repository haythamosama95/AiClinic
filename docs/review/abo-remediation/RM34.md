# RM34 — Offer publication and console views

Status: implementation written, not committed, not validated by CI (orchestrator assigns commit, push and CI).

## Implementation record

- R8-PUB1 (offer terms half), steps 1–4:
  - Terms text is stored at `terms/sha256/<text_sha256>.txt` (`termsTextR2Key` in `abo/src/ops/index.ts`). Distinct bytes never share a key. Existing `terms/en/N.txt` rows are not rewritten.
  - Publication allocates `offer_version` and `terms_version` numbers per attempt and commits the approval (`assertion_used`), its `operator_action`, terms, offer, events and facts in one D1 batch (`publishOfferStatements`). A uniqueness conflict on a number rolls the batch back and retries with fresh numbers (5 attempts). A conflict on `assertion_used` refuses with `assertion_used`, so an exact retry mints no version. An exact lost-response retry of a committed publication therefore gets `assertion_used` (a refusal, HTTP 400), not the original result. If all 5 allocation attempts conflict, the request is refused with `allocation_conflict` through `refuseHpAction` (HTTP 400). The batch rolled back, so no assertion is consumed and the operator may resubmit.
  - `currentTermsText` in `abo/src/clinic-api/offers.ts` recomputes SHA-256 of the served bytes and throws `terms_hash_mismatch` on disagreement.
  - Routing half is RM33 and is not touched here.
- R8-CONSOLE5, steps 1–3:
  - Publish validates `price_minor` (positive safe integer), non-empty `terms_text` and `copy` (`en` plus any other locale, each with a non-empty `name` and a string `summary`) before any approval is consumed. Invalid input is refused with `assertion_invalid` and records only the refusal (`abo/src/offers/copy.ts`, shared validator).
  - Catalogue reads skip a stored offer that fails the same validator, raise alert `offer_malformed:<offer_id>:<version>` (new `AlertCode`), and load the other offers. Checkout treats a malformed sellable version as not sellable.
- R8-CONSOLE1, steps 1–3:
  - Reinstatement writes `published` for the last published version; `reinstate_offer` stays in `operator_action`.
  - Catalogue and checkout readers accept historical `reinstated` as an activation alias (`abo/src/clinic-api/offers.ts`, `abo/src/clinic-api/checkouts.ts`). Never-published offers are still refused.
  - `docs/architecture/ai-billing-orchestration/03-abo-data-model-and-lifecycle.md` §2.2 clarified (the amended lifecycle reference named by step 2).
- R8-CONSOLE4, steps 1–2: clinic action history (`abo/src/ops/index.ts`, clinic page query) adds org-scoped payment subjects, grant request subjects, reverse work of reversals on the org's payments, and grant IDs from the platform `inspectCoverage` result (validated pattern, bound via `json_each`). Membership is by exact ID, not substring.

## Seams and deviations

- Seam for RM33: none new. RM33 owns the routing digest half of R8-PUB1.
- Decision (recorded for review): the recipe asks to retry allocation "using the same R6-O1 accepted payload". The R6-O1 accepted-command store (RM12) covers release, manual chargeback, erase and begin-transfer only; `publish_offer` is not in it. Instead, the approval, operator action, terms, offer, events and facts commit in one D1 batch, which gives the same guarantee for this path: a failed allocation consumes nothing and an exact retry is refused. If the reviewer requires `publish_offer` in the accepted-command store, that is a follow-up.
- Decision: `validateOfferCopy` checks every locale key present in `copy`, since the code has no supported-locale list. Only `en` is required.

## Operator checklist

- Existing terms rows whose stored `text_sha256` does not match the R2 bytes (possible from the old `terms/en/N.txt` overwrite race) make `GET /v1/offers` fail with `terms_hash_mismatch` until fixed. Per R8-PUB1 step 3, the maintainer must establish the original text from retained evidence, stop affected sales and policy activation meanwhile, and publish a new terms version. Do not rewrite history.
- Existing offer versions flagged `offer_malformed` are left out of the catalogue. Correct them by retiring and publishing a new version through the console. There is no in-place repair.
- Rows written before this phase with kind `reinstated` are read as activation; no backfill is needed.
