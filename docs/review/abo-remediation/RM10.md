# RM10 — Inquiry budget, discovery and multiple captures

## Findings implemented

- **R3-C7:** Provider inquiries atomically reserve one of two shared logical attempts for the current minute before provider HTTP. Failed and unbound attempts keep their reservation. Confirmation work is scheduled before grants, then sweep and reversal inquiries; grants no longer consume provider budget. Callers preserve deferred work, and sweep confirmation reuses its matching authoritative result. Rebuild checks operator-supplied transaction references before broad inquiry scans.
- **R3-C4:** Removed the placeholder transaction id. When no transaction identity is known, inquiry returns `discovery_unavailable`; sweeps retain due work and raise one AL-03 recovery alert per checkout. Added the class-H `/ops/checkouts/{checkout_id}/transaction-id` action. It records the operator action, queues durable confirmation work and uses the normal authenticated transaction inquiry and order binding.
- **R3-C6:** Different successful transaction ids on one checkout are recorded separately. Same-checkout payments with the same coverage snapshot are classified as likely duplicates, including null coverage endpoints; payment identity remains the dedupe key.

## Deferred steps and gates

- R3-C4 steps 3–4 (automatic order-scoped enumeration and complete-success-set processing) remain deferred until recorded R-2 sandbox evidence confirms complete listing and stable transaction identity semantics. The implementation does not guess provider response fields.
- R3-C6 currently processes every successful transaction available from an individual callback or operator submission. Automatic order enumeration remains subject to the R-2 gate above.
