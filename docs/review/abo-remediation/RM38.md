# RM38 — Desktop billing refresh and notices

Findings: R7-UI2 (P2), R7-UI3 (P3, optional). Depends on RM11, RM37 (both complete).

## Findings implemented

### R7-UI2 — checkout completion refreshes billing siblings

| Step | Status | Notes |
| --- | --- | --- |
| 1. `onCheckoutStateChanged` on `CheckoutScreen`; one billing-read generation in `AdministratorBillingPage`; Paid/Active bump it | Done | Callback fires only when shown state or reference changes. The parent never creates a checkout and never touches the checkout's idempotency key. |
| 2. Generation input on `SubscriptionSummary`, `CommercialNotices`, `PaymentHistory`; stale results ignored; history resets cursor/list and restarts at page one; explicit refresh control | Done | `PaymentHistory` sequence number discards any in-flight page after a reset. Refresh control is `billing_refresh` on the page. |
| 3. Flat projection mapping kept; bounded reread after `request_ai_status_refresh` (4 reads, 30 s apart, last at 2:00); identity and generation checks; pending/stale message; no inference from browser return or payment | Done | The pull moved from `CheckoutScreen` to the parent so the parent owns the reread chain. A reread counts as confirmation only when its summary read is issued after the pull and shows a plan (`onLoaded`). A failed pull shows `billing_projection_pull_failed`; manual refresh re-requests it. |
| 4. Completion: empty page gains payment, notices and projected plan without navigation; failed pull visible and refreshable; stale next page cannot corrupt the list; read refresh never mutates | Done | Covered by the tests listed below. |

Deliberate changes in the parent:
- `PaymentHistory` is now mounted on every billing step (previously only the offers step), so the payment appears while the checkout is open.
- `CommercialNotices` is now mounted on the billing page. It was defined but not mounted anywhere before this phase, so its notices never rendered.
- `CheckoutScreen.supabaseClient` was removed because the checkout no longer calls RPC. The parent passes no such argument.

## Precedence conflicts

None. The recipe's "reject any retry whose billing-read generation or current identity no longer matches" is implemented as: the chain carries its epoch, the checkout reference (identity) and the generation it last set; a retry whose epoch, reference or generation differs is dropped, and manual refresh remains available.
