# RM27 — Deletion and held status

Implemented R6-PT3 (P1: durable deletion and purge) followed by R7-PS1 (P2: held-binding unavailable projection). RM26 was complete before this phase began.

## Implementation

- `ai-platform/src/coverage/transfer.ts`: `acceptDeleteInstallation`, `resumeDeleteInstallation`, `dispatchDeletionCommands`, `retireHeldBindingIfEmpty`, and fail-closed coverage inspection. Acceptance pins org, installation, epoch, actor, reason, signer, accepted command and canonical `freeze_id`. Acknowledged freeze inventory includes open terms and reservations; held/retired CAS follows that acknowledgement. Open term and reservation identities survive purge. Accepted freeze and purge resume through the five-minute dispatcher, including after a valid final-grant void retires the pinned binding.
- `ai-platform/src/quota-do/coverage.ts`: `setTransferPendingRPC` serializes the deletion fence, clinic sequence increment and full `transfer` snapshot. `emitDeletionSnapshot` is explicit, so ordinary and legacy transfer fences keep their existing request semantics. Held open coverage projects as `transfer_pending`, retaining term, queue, held and suspension metadata. Existing-fence replay re-arms pending shipment without another event. RM26 transfer can adopt only the matching completed deletion fence for the exact source installation and epoch.
- `ai-platform/src/vendor/entrypoint.ts` and `ai-platform/src/worker.ts`: authenticated durable delete replay, completion detail, cron dispatch and Durable Object RPC wiring.
- `ai-platform/src/retention/index.ts`: stable purge audit identity and idempotent audit insertion.
- `ai-platform/migrations/20261020150000_rm27_durable_deletion.sql` and `ai-platform/schema.snap.sql`: durable `deletion_command` storage and indexes. System, E2E, ABO cross-worker, admission-credit, request-orchestrator and load harnesses install the migration; reset/table lists include the command table.

## Sol pre-CI review fixes

All six REQUEST CHANGES items were addressed before CI dispatch:

1. A fresh completed-delete assertion no longer changes the Durable Object fence identity: `freeze_id` is persisted and reused by transfer adoption. The regression asserts a fresh delete replay followed by transfer.
2. Purge recovery accepts the same pinned epoch after its final grant is voided and the held binding retires. The regression interrupts purge, voids the final grant, then resumes deletion cleanup.
3. Worker dispatch now casts the `setTransferPendingRPC` request at parameter index `[3]`, matching its four-argument signature.
4. `DeletionCommandRow` includes `freeze_ack_at`, which is selected and copied with the durable row.
5. Replaying an existing `transfer_pending` fence calls the existing outbox-alarm recovery path; a regression removes the alarm and confirms replay ships one event.
6. The malformed-inventory fixture carries a valid platform DO contract version and provisions its signer with `coverClinic`, so the malformed reservation is the invalid field under test.

## Seams, discoveries and operations

- **RM26 seam:** transfer preparation adopts a completed deletion's canonical Durable Object fence only when the durable deletion row matches its exact source installation and epoch. The transfer preparation ID owns replay after adoption.
- **RM29 seam:** platform rebuild work must preserve the durable deletion command and canonical freeze identity, and must not discard or reopen the corresponding admission fence while reconstructing platform/DO state.
- No precedence conflicts or unrelated defects were identified. No operator action or checklist item is required; accepted deletion and purge work recover through the scheduled dispatcher.
