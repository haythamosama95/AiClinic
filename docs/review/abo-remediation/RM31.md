# RM31 — Alert delivery and scheduled job health (ABO and platform scope)

Status: not yet complete. The implementation is committed for complete CI validation and is not yet complete. Local tests, builds, linters, and type checks were not run, per the phase constraint. Complete CI result: pending (see "CI history and completion").

Scope: RM31 spans `abo/` and `ai-platform/`. This ABO worker changed `abo/` and this record only. The platform-side alert and heartbeat work (R9-PAL1, `ai-platform/`) belongs to the ai-platform worker and is listed under seams.

## Findings implemented

- **R9-CRON1 (ABO side):** Each logical scheduled job has its own row in `scheduled_job_state` with `last_started_at`, `last_succeeded_at`, `last_succeeded_period` (the persisted due-period checkpoint), `last_error_at`/`last_error_code`, `next_attempt_at`, and a lease. A job's period is stamped as succeeded only after its work returns `succeeded`. The digest success heartbeat is pinged only after the digest email send is acknowledged. A failed, deferred, or abandoned period stays pending. The minute cron claims every period that has not succeeded, so retries and never-attempted periods (catch-up) both run there. Overlapping runs cannot consume the same period, because the claim is one conditional `UPDATE` guarded by the lease and the period. Platform reads that are refused or malformed are treated as incomplete (thrown or returned as failed), not as empty success. Minute steps are isolated, so one failing step does not stop the others.
- **R9-AO4:** Reconciliation findings have a unique identity `(kind, subject)` in `finding_identity`. The first detection claims it. The finding, its fact, and its `AL-10:<finding_id>` alert are written in one D1 batch. A concurrent claim rolls the batch back. A replayed identity never reopens a resolved finding. An existing unresolved identity has its alert ensured without resetting `last_sent_at`. A daily sweep gives an alert to any unresolved finding that lacks one.
- **R9-AO5:** Export lag clears whenever the oldest unexported fact is absent or no longer over one hour, even after it was sent (last-sent metadata is kept). The hourly watch clears `AL-15:feed` after a valid fresh health read, and clears active `AL-22:issuer:*` and `AL-22:credential:*` keys whose mismatch is absent, but only after complete successful reads. A thrown, refused, or malformed read is unknown and clears nothing. Finding resolution deactivates `AL-10:<finding_id>` in the same batch as `finding_resolution` and its fact.
- **R9-AO6:** The invalid-callback sweep (`hmac-invalid/` prefix only) iterates R2 list pages with the same cutoff. It persists the page cursor only after that page's deletions finish, and it is bounded per invocation by a deletion budget. It returns `deferred` until drained, and the minute cron resumes it. Keys at or after the cutoff end the eligible range. Evidence, ledger, and payout prefixes are not touched.

## Decisions applied (orchestrator decisions a to e)

- **(a) Operations failure alert (R9-CRON1 step 2).** Code `scheduled_job_failed`, key `scheduled_job_failed:<job>`, following the spec 065 platform precedent (`ai-platform/src/alert/index.ts`, `insertScheduledJobFailedAlert`, which uses the same key and code).
  - ABO catalogue: `abo/src/alert/index.ts:43` adds `"scheduled_job_failed"` to `AlertCode`. `abo/src/alert/index.ts:67` puts it on the daily repeat cadence, as for AL-10, AL-14 and AL-16.
  - Raised durably: `abo/src/scheduler/jobs.ts:66-80` (`raiseJobFailedAlert`, one `prepareRaiseAlert` upsert, deduplicated by key). It is called from the failed branch of `finishLeased` (`jobs.ts:139-150`), from `requeueScheduledJob` (`jobs.ts:244-260`), and from the failed branch of `recordUngatedOutcome` (minute processing).
  - Cleared on success: `jobs.ts:84-90` (`clearJobFailedAlert`), called from `finishLeased` success (`jobs.ts:111-119`) and from `recordUngatedOutcome` success. Clear and reopen follow the existing lifecycle: deactivation sets `active=0, unsent=0`, and a new failure reactivates the row.
  - 05 catalogue: `docs/architecture/ai-billing-orchestration/05-abo-operations-and-traceability.md` has no row for scheduled-job failures (its AL table ends at AL-23, line 75). No catalogue row was added here, because that doc is outside this worker's scope. The docs owner should add one, with `scheduled_job_failed` as its code.
- **(b) Catch-up of missed runs.** The minute cron now claims every due period that has not succeeded, not only retry-marked ones. `abo/src/worker.ts:524-530` runs `runCronJobs(env, ["six_hour", "hourly", "daily"])` with no `retryOnly` option, and the option was removed from `abo/src/scheduler/jobs.ts`. The claim (`jobs.ts:174-186`) keeps the lease and the period-key checks. The period key is unchanged.
- **(c) Heartbeat streams (RT2).** The two ABO streams are implemented now.
  - `abo_minute`: pinged by the minute cron through `HEARTBEAT_URL_MINUTE` (`abo/src/worker.ts:529`). The window is 5 minutes.
  - `abo_daily_digest`: pinged through `HEARTBEAT_URL_DIGEST` (`abo/src/worker.ts:205`), only after the digest send is acknowledged. The window is 26 hours.
  - Each stream uses its own URL when set. Otherwise it falls back to the legacy `HEARTBEAT_URL` (`abo/src/worker.ts:266-278`, `heartbeatUrlFor`). Existing deployments keep working.
  - The platform ping (`platform_5min`) is not changed here. That is RM35.
- **(d) Rebuild gate.** `abo/src/rebuild.ts:1982-1984` keeps the throw `reconciliation_incomplete`. A test asserts it: "rebuild throws reconciliation_incomplete when reconciliation is not succeeded" (`abo/test/system/digest-watch-rebuild.cross-worker.test.ts`, about line 1849).
- **(e) Sorted-key JSON bodies.** No change.

## Findings F1, F4, F7

- **F1 (CRITICAL), claim next_attempt_at.** Fixed in `abo/src/scheduler/jobs.ts`. The claim sets `next_attempt_at` to the lease expiry (`jobs.ts:174-186`). A run that crashes or times out leaves an expired lease that is eligible again. Both the success and failure writes overwrite `next_attempt_at` (`jobs.ts:111`, `jobs.ts:125`, `jobs.ts:139`). Catch-up (b) also covers the case. Test: "R9-CRON1 abandoned lease after a crash is retried by the minute cron".
- **F4 (feed divergence), fixed.** `getCoverage` (`ai-platform/src/vendor/entrypoint.ts`, around line 6719) returns `rejected(version, "coverage_not_found")` when the org has no active tenant binding. That is a definitive not-found. A coverage Durable Object that cannot be reached still returns `coverage_unknown`. ABO (`abo/src/reconciliation/run.ts`, around lines 646-656) treats `coverage_not_found` as a complete check with no divergence to report. Any other non-ok result, and any malformed detail, throws `PlatformReadUnavailableError` and stays incomplete.
- **F7(i), import-time reconciliation.** `abo/src/ops/index.ts:2557-2562`: the import now captures `runReconciliation`'s outcome. A non-`succeeded` outcome calls `requeueScheduledJob(env, "reconciliation", "import_reconciliation_incomplete")`. That helper (`abo/src/scheduler/jobs.ts:244-260`) clears `last_succeeded_period` and sets `next_attempt_at` to now, so the minute cron runs the current period once even if the daily run already succeeded for it. The comment that said the daily job retries it is corrected. The committed import response is unchanged.
- **F7(ii), heartbeat pings.** The minute cron pings unconditionally, after its minute work (`abo/src/worker.ts:529`). It is a cron-liveness signal only. The digest success stream is pinged separately, from the digest job's `onSucceeded` hook (`abo/src/worker.ts:205`). The per-stream URLs in (c) replace the single shared URL, so the two signals no longer share one URL.

Discovered issues (not changed):
- `abo/src/work/reversal.ts` writes its own `finding` rows (`reversal_kind_conflict`, `inquiry_disagrees`) without claiming `finding_identity`. Those kinds never collide with reconciliation kinds, so no duplicate is possible today. Bring them under the registry in a later reversal-area phase.

This is not a deletion path and is outside RM31's findings. Record for the phase that owns callback intake rate limits.
- A period whose retries are exhausted within its own cadence (for example an hourly job that fails for the whole hour) is not retried after the period rolls over. The next period's run supersedes it. This is the period-key design, not a regression, and it is recorded here for the reviewer.

Operator checklist:

- Legacy `scheduled_job_run` rows are not migrated. They are not evidence of success, and they are safe to leave in place.

- Set `HEARTBEAT_URL_MINUTE` to the external monitor URL for the `abo_minute` stream (5-minute window). Set `HEARTBEAT_URL_DIGEST` to the URL for the `abo_daily_digest` stream (26-hour window). Both are operator secrets or per-environment vars, not checked-in values.
- `HEARTBEAT_URL` is still read. It is the fallback for any stream whose own URL is unset. Remove it only after both new variables are set in every environment. Until then, a shared URL will not distinguish the two streams.
- A job-failure alert (`scheduled_job_failed:<job>`) appears in the open-alert list and in email, once per failing job. It clears when that job next succeeds.

2. **Kill-switch alert in the mutation batch.** The kill-switch AL-19 alert body is written in the same D1 batch as the arm or disarm (`ai-platform/src/control/kill-switch.ts`, `options.buildAlertStatement`; `ai-platform/src/alert/index.ts`, `buildAl19KillSwitchAlertKey` and its statement builder; `ai-platform/src/vendor/entrypoint.ts`, `armKillSwitch` and `disarmKillSwitch`). If the in-batch alert insert fails, the whole mutation rolls back and the caller gets a 500. Before this change the mutation committed without the alert. The post-batch `raiseAl19FromOutbox` call is kept and uses `persistCommittedAlertBody`.
