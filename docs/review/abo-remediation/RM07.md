# RM07 — Contract version metadata and strict DO decoders

## Findings implemented

- **R2-C2 (P2):** The final billing-token issuer errors preserve `p_contract_version`; ABO operator-access failures use the negotiated console version; every post-negotiation DO response carries the sent version; platform clinic JSON bodies and unsupported-version refusals carry current public metadata; vendor unsupported-version envelopes include `accepted_versions`. The vendor result validator allows that optional field only for `rejected` / `contract_version_unsupported`, and accepts unique non-negative integers, including launch versions `[0,1]`.
- **R2-C3 (P2, steps 1 and 3):** A shared DO response decoder rejects non-objects, missing/non-integer versions, version mismatches, and `contract_version_unsupported` replies before business casts. Every DO transport named in the recipe uses it, including rebuild and refresh. Invalid replies map to the recipe's caller-specific failure result; coverage-read returns `coverage_unknown` with negotiated public metadata. No invalid response advances a grant ledger, transfer step, fallback usage row, coverage event, or coverage mirror.
- R2-C3 step 2 (Dart response-version validation) is intentionally deferred to RM37, as the phase plan directs.
