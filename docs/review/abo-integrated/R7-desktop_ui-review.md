## R7-UI1 — P1: changing the visit retains the previous visit's live AI composition

**High confidence, implementation-ready.** In `frontend/lib/features/ai/presentation/pages/ai_page.dart:377–379,425`, load visit A then load a different visit B without leaving `/ai`. `_LiveVisitSummaryHost` has no key. Its retained state composes dependencies only from `initState` (`667–688`) and has no `didUpdateWidget`. `build` labels the surface with the new B (`702–704`) and calls `liveVisitSummaryHostBody` with B (`710`), which creates an `AiFeatureHostPage` keyed B (`350`) using retained dependencies A. Those dependencies carry the A context provider and visit ID (`257–259`). The fresh host uses that context provider (`ai_feature_host_page.dart:202`) and sends `dependencies.visitId` to the surface (`401–405`); the surface invokes AI with that visit/context (`first_ai_feature_surface.dart:175–195`). Thus another A summary can appear beneath B's live-host label. This is a substantial wrong-patient advisory-output defect. No persisted wrong-patient write or runtime reproduction is claimed. The visit retention predates ABO, but it controls the current modified production composition and its consumers.

The same one-time composition freezes `staffIsAdministrator` from `ref.read(authSessionProvider)` (`ai_page.dart:674–679`). On the supported resume path, `app.dart:76` reloads auth context, while the ready-to-ready transition is not handled (`82–87`) and `/ai` remains an unkeyed const page (`router.dart:118`). Role downgrade therefore keeps administrator Renew forms (`ai_feature_host_page.dart:530–544`); promotion keeps staff presentation. Current coverage parsing failure (transport-owned term-versus-snapshot finding) masks actual gauge/reference/plan display, so **no present commercial-data leak is asserted**. There is no established production org-switch caller, so this is not an asserted cross-org exposure.

**Fix steps**

1. In `_AiPageState.build`, watch the current authenticated context and derive an immutable composition identity from authenticated user, active organization, current role and selected visit ID. Pass that identity as the `_LiveVisitSummaryHost` key; change `_loadVisitSummaryHost`/construction together so changing any identity component disposes the old host before showing the new label. Use the existing auth context fields; do not use cached billing token claims as role authority.
2. In `_LiveVisitSummaryHostState`, capture the visit/role/client inputs before the first await and render a loading state for the new identity. Retain the mounted guard so a disposed A load cannot install into B. Keep the same key identity through the child `AiFeatureHostPage`; dispose the previous resolver/session with its old subtree. Directly supported injected host/dependency entry points must either remount by this identity or implement equivalent generation invalidation.
3. In `AiFeatureHostPage._bootstrap` and `_refreshAdministratorCoverage`, capture a request generation/identity before awaited reads and commit only when it still matches and the current role remains administrator for commercial fields. Clear commercial fields synchronously on loss of that role. Coordinate with the transport review's reactive status integration; one identity mechanism must protect both status and coverage callbacks.
4. Completion: A→B before/after A composition resolves produces only B context/visit requests under B's label; A's late response cannot replace it. Resume-time downgrade immediately removes administrator actions and cached commercial fields, promotion builds administrator dependencies, and an unchanged identity does not unnecessarily restart AI. Implement the transport coverage-shape repair together with role-safe caching so that fixing the currently masked path does not expose retained administrator data.

## R7-UI2 — P2: completed checkout leaves subscription, notices and payment history frozen

**High confidence, implementation-ready after R3-C1 layout repair.** Open billing before payment. Summary, commercial notices and payment history load once (`subscription_summary.dart:65–89`, `commercial_notices.dart:23–40`, `payment_history.dart:25–45`). They stay at the same positions/types across `_BillingStep` changes (`administrator_billing_page.dart:132–164`), with no refresh input or `didUpdateWidget`. Checkout becoming Active only requests a backend pull (`checkout_screen.dart:127–136,344–357`); it neither notifies this parent nor reloads these siblings. Consequently the same page shows Active beside old plan/counts, absent new payment and absent duplicate/held notices indefinitely. If initial history had no further page, even its next-page control is absent. Leaving/reopening can recover, so P2. The backend request is asynchronous, so merely immediately rerunning the RPC once may still read the old projection.

**Fix steps**

1. Add an explicit `onCheckoutStateChanged` callback on `CheckoutScreen`, invoked after a new authoritative read changes shown state/reference. Wire it in `AdministratorBillingPage` and maintain one billing-read refresh generation. Fire an immediate refresh on Paid/Active; the parent must not create a new checkout or reset its idempotency key during read refresh.
2. Add a generation input or shared controller to `SubscriptionSummary`, `CommercialNotices` and `PaymentHistory`; reload on generation change and ignore results from earlier generations. For history, reset cursor/list and restart at the first page; never append an old in-flight page after reset. Provide an explicit refresh control for changes made on another desktop/reversals while this page stays open.
3. Preserve the flat backend-projection mapping required by 088:5. After requesting `request_ai_status_refresh`, use a bounded delayed reread (at most four reads separated by 30 seconds, ending within two minutes) and then leave manual refresh available if the projection has not caught up; reject any retry whose billing-read generation or current identity no longer matches. Keep ABO payment/notices independently refreshable and show a pending/stale message instead of implying the pull was already applied. Do not infer coverage activation from browser return or payment alone.
4. Completion: an initially empty page that reaches Paid/Active gains its payment, refreshed notices and eventually projected plan/counts without navigating away; backend-pull failure remains visibly pending and refreshable. A concurrent old next-page response cannot corrupt the restarted list. Read refresh never issues another checkout/payment mutation.

## R7-UI3 — optional P3: notice records are shown as wire codes and omit grace time

**High confidence, implementation-ready.** `ai_feature_host_page.dart:530–538` displays `notice.code` verbatim for administrators. In particular an `in_grace` record loses its `grace_days_left` value, whose defined purpose is to show remaining grace time (04 §3.2/088:2). Commercial notices likewise display raw ABO code strings (`commercial_notices.dart:80–84`). The Arabic and English `.arb` inputs have no mappings for these notices. The desktop therefore shows internal identifiers such as `in_grace` and `payment_withheld` instead of the specified audience-specific explanation. This is a bounded information/presentation defect, not a commercial-data leak or a failure to enforce coverage. It is separate from transport T1: connecting new status records still leaves their visible contents unchanged.

**Fix steps**

1. Add English/Arabic localization entries in `frontend/lib/l10n/app_en.arb` and `app_ar.arb` for all eight status codes in 04 §3.2 and five commercial codes in 04 §2.2. Give the in-grace message an integer days-left parameter; render zero as less than one day rather than a completed grace period.
2. In `_AiStatusNoticeBanner.build`, map each recognized status code to its localized administrator/member wording and pass `notice.graceDaysLeft` to the in-grace message. In `CommercialNotices._buildBody`, map the five recognized ABO strings to localized explanations. Preserve wire enums/values and server notice conditions; unknown values use a neutral localized status-unavailable message instead of printing arbitrary code text.
3. Completion: an administrator and staff member both understand in_grace with zero/nonzero grace days, Arabic locale receives Arabic notice text, and duplicate/withheld/held/reversal notices retain their distinct meaning. Transport T1 refresh then updates these same mapped messages. No prices or references are introduced into staff notice copy.
