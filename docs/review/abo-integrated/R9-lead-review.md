## R9-REC1 — P1: ledger import does not validate original identity and ABO restore cannot resume

High confidence, implementation-ready forward algorithm; ambiguous historical inputs require maintainer/frontier adjudication. `abo/src/rebuild.ts:121–164` accepts arbitrary JSON objects, silently skips a missing object or missing row, never checks the object key, canonical row hash, sequence uniqueness/gaps, table/column/key schema or stored version, and inserts the business row, a newly numbered fact_log and the *input* fact_export marker in three separate commits. A process failure immediately after the business insert makes the next invocation fail on its primary key; the command has no checkpoint or equality replay. A gap renumbers later fact_log entries but marks their old sequence exported, potentially leaving one restored fact unexported and allowing the next new fact to collide with an existing immutable R2 key. A corrupted/mismatched record is trusted rather than stopping before mutation. `recomputeCheckoutStatus:177–228` also uses plain INSERT, so even completed projection replay is not repeatable. The wrapper instructs operators to start with an empty D1 (`abo/scripts/rebuild-abo.ts:16–20`) but offers no recovery from its own partial run. These are distinct from ordinary callback atomicity R3-C5. Platform `ai-platform/src/quota-do/coverage.ts:4155–4206` has the same unchecked-import root: missing/empty objects are skipped, only the first line is parsed, key/schema/hash/receipt linkage are unchecked, and conflicting existing rows are hidden by INSERT OR IGNORE while counters increment. The object can therefore disagree with the retained D1 row without a conflict result. This platform consumer is included in REC1, not another counted finding.

**Fix steps**

1. Introduce versioned ledger decoders and fixed table/column/key registries shared by `exportFacts`/`replayLedger` and platform `runRebuildGrantLedger`. For platform grant/void objects require filename ID/suffix consistency, complete field schema, exact receipt identity/hash/version and cryptographic verification against retained historical trusted public keys, plus original command/lineage corroboration for fields outside the signed receipt. RT3 compromised-key history cannot be authenticated by that signature alone. Conflicting D1 rows fail with a recovery conflict; replace blind INSERT OR IGNORE with equality acknowledgment. Never infer original signed envelopes from the current plan: the old summary has no original bytes; require the R4-D5 recovery capsule addendum or an explicit historical stop. For ABO facts, Require object key `ledger/<fact_seq>.ndjson`, positive safe sequence, canonical row hash equal `row_sha256`, exact per-table identity, known stored record/payload version and permitted fields. Validate the complete replay input before publishing it. Missing/duplicate/different-hash sequence or missing row is an explicit recovery stop, never silently skipped. Use a persisted export high-water manifest to distinguish a legitimate exported prefix from missing objects; do not claim the unexported tail is recoverable from R2 alone.
2. Preserve `fact_seq` explicitly. For each fact commit its business row, original fact_log identity/hash/JSON and export marker in one D1 batch, advancing a persisted replay checkpoint only with that batch. An existing equal canonical business row and matching original fact identity is a no-op; a conflict stops without INSERT OR REPLACE or deleting append-only evidence. Restore sqlite sequence to at least the largest original fact sequence. Do not fabricate historical `created_at` as the current clock/epoch zero: extend new ledger envelopes with original fact creation metadata and require an adjudicated mapping for older objects that lack a recoverable timestamp.
3. Build projections into a clean recovery generation, then publish after validating facts; make their upserts repeatable. Fence ordinary export/feed/work while recovery owns that generation. In `records/export.ts:43–58`, treat an existing object as success only after exact bytes/hash equality and idempotently insert the export marker; never overwrite differing immutable content. This also closes the R2-success/D1-failure retry boundary without depending on a provider's overwrite-under-lock behavior.
4. Completion: interruption before/after each batch resumes with identical IDs/hashes/sequences; a gap/tampered row/conflicting existing record stops before publication; the next new fact gets a fresh unused sequence and cannot overwrite an old object; repeated status replay is harmless. Run the wrapper through a declared/pinned local TypeScript launcher rather than unpinned `npx tsx` (runtime metadata shows tsx is absent).

## R9-REC2 — P1: restored facts do not recreate the due work, and gap recovery creates new checkouts instead of recovering old transactions

High confidence. `rebuildAbo:708–720` replays facts, but no replay step derives `work` from payment/reversal/transfer/accepted-command facts. `inquireGapPayments:624–635` discards every known checkout/payment inquiry response. `preapplyPlatformGrants` receives only payment IDs newly created during this invocation (`715–718`), and `runDueGrantWork` only selects existing open work (`abo/src/work/grant.ts:934–944`). Therefore an exported paid payment whose grant work was lost stays paid with no grant forever after the rebuild. Similarly retained reversal facts cannot restart their void delivery. Reconciliation only writes a finding, not due work.

Missing adapter state makes recovery worse: `ensurePaymobIntentions:580–612` calls the *creation* API for every restored unpaid checkout because paymob_intention is not a ledger fact. It creates a new order, then dashboard transaction candidates (`638–649`) are checked against that new order; the adapter requires original order equality (`provider/paymob/adapter.ts:691–697,724–727,756–759`). The old paid transaction is refused, and new provider intentions were created during a supposedly restorative operation. Discovery of a platform-paid grant also asks for `grant.source.ref` (`678–684`), although the specified listGrants row has source_kind but no source object; even a known payment_id cannot be inquired without an existing ABO payment (`adapter.ts:680–686`). Synthetic preapplication rebuilds current-version/month envelopes (`365–437`) rather than reusing an existing signed historical request. R3-C2/C4/C7 and R4-PG1 remain canonical underlying producer/provider/identity prerequisites.

**Fix steps — forward replay ready; historical provider discovery is not implementation-ready until R3-C2/C4 owner resolves the missing adapter contract**

1. Remove `ensurePaymobIntentions` from recovery. Restore retained immutable provider order/transaction correlation via an adapter-owned recovery record, excluding client secrets/contact values from the locked ledger. For an old row lacking correlation, operations/provider owner must specify read-only dashboard/API evidence and exact schema/identity mapping. Keep that checkout flagged and stop its provisioning; never create a replacement order or guess transaction IDs to establish payment.
2. Add a resumable recovery pass deriving deterministic due commands from immutable facts: every `disposition=grant` payment lacking a verified applied outcome; every eligible full reversal lacking verified terminal void/tombstone; accepted transfer/erasure/operator commands lacking acknowledgments. Use unique command/dedupe keys and one D1 batch to persist missing work plus its recovery checkpoint. Apply R4-A1's append-only attempt/current-outcome design and R8-RETRY1 for parked reversal recovery; do not reinterpret parked rejection as success.
3. Reuse each existing grant_request's exact envelope bytes/hash/contract_version and verified actor/signer/lineage. For a genuinely never-created paid request, use immutable checkout/payment/evidence through the normal producer, not the rebuild-only `buildGrantEnvelope`. Dispatch through normal key gates, receipt validation and R3-C7's reserved shared inquiry budget. Preserve global grant claims and installation/epoch seals from R4-PG1; a rebuild must not move a grant to the current binding.
4. Persist and process every authoritative inquiry result using the same confirmation/reversal transaction as normal work. Replace discarded responses with resumable decisions and explicit unavailable/deferred states. `listGrants` is only an independent witness, never a source of invented payment identity. Completion: an exported payment without work gets exactly one deterministic grant attempt; interrupted reversal/transfer resumes original intent; old provider orders are recovered without creation; missing correlation cannot grant value; restored signed requests keep their original bytes/version and receipts.

## R9-REC3 — P1: rebuild bypasses the normal amount/currency withholding rule

High confidence, implementation-ready. `maybeRecordSucceededPayment:523–548` checks only success kind/existing payment/checkout and invokes `recordPaidConfirmation`. The adapter's `bound=true` proves order/transaction linkage, not price (`adapter.ts:724–767`). Normal runner explicitly checks amount and currency and records `withheld_mismatch` (`runner.ts:735–794`); `recordPaidConfirmation:411–456` unconditionally writes disposition grant and enqueues grant work. A correctly order-bound success with the wrong amount/currency therefore becomes grant-eligible during restore, even though ordinary confirmation withholds it. This is a recovery-only financial validation bypass, not R3's provider-discovery defect.

**Fix steps**

1. Factor a single decision function used by `processConfirmWork` and rebuild inquiry ingestion: require successful normalized state, `txn.checkout_id=checkout.checkout_id`, authoritative original order/payment binding, exact integer `amount_minor=charged_price_minor` and exact currency. Return grant/withheld/reversal/pending with an explicit reason; do not call the unconditional granting helper directly from rebuild.
2. Persist mismatched payment plus exact evidence/inquiry fact and `AL-05` outbox atomically, with disposition `withheld_mismatch` and no grant command. A later release requires the existing HP payment_release intent and normal audited dispatch. Keep the same deterministic payment/grant identities across normal and recovery races.
3. Completion: amount or currency mismatch recovered from a dashboard transaction stays withheld and has no platform grant; exact matches provision once; a repeated mismatch creates no duplicate fact/work and cannot silently become grant because the rebuild was rerun. Retain R6 cumulative reversal predicates and R3-C7 inquiry budget.

## R9-FACT1 — P1: immutable callback/inquiry and cancellation facts are absent from the locked recovery ledger

High confidence. notification and inquiry_result have append-only triggers (`abo/migrations/0003_notify_work.sql:81–103`), but notification writers (`notify/intake.ts:151–175,219–264,267–320,394–410`) never append fact_log. Runner inquiry insert (`work/runner.ts:612–649`) likewise omits it. The exporter only reads fact_log (`records/export.ts:17–26`), so a >30-day D1 rebuild loses the HMAC-validity/disposition/adapter/correlation records needed for callback-vs-inquiry reconciliation even while raw R2 bodies survive. Normal inquiries store normalized transaction JSON instead of raw authenticated answers (`runner.ts:617–619`), and payment can name a new inquiryId when the dedupe predicate did not insert it (`625–649,819–824`). Rebuild creates a new inquiryId plus SHA256(empty) but no inquiry/evidence row (`rebuild.ts:539–547`). Cancellation event has no fact_log (`ops/index.ts:2047–2059`), so replay can reopen a cancelled checkout; R6-O1 already owns acceptance/audit atomicity, not this missing export membership.

**Fix steps — forward ready; historical missing authenticated bytes/identity requires maintainer/frontier evidence**

1. Add production append helpers for notification/inquiry_result and use them at every listed writer; prepare exact canonical row and fact_log in the same D1 batch as its dependent payment/event/due work, integrating R3-C5's lease/dedupe transaction. Capture original receipt time and original version/adapter metadata explicitly where absent; do not add payer contact fields to the locked ledger. Include cancellation checkout_event and its fact in R6-O1's accepted-command batch.
2. Extend provider inquiry port/result to return an evidence reference/hash for the actual authenticated response before normalization. Persist raw bodies under the existing erasure-fenced evidence lifecycle (R6-O2) and retain canonical commercial facts/hashes separately. Either always create the decisive per-transaction inquiry, or reuse the exact existing matching inquiry identity; never reference a newly generated uninserted ID. Rebuild must use that same producer; remove empty hashes/fake inquiry IDs.
3. Extend REC1's whitelist/decoder to these facts and REC2's command derivation to their references. Preserve original signed bytes, actor/signer, receipt and lineage; missing historic raw/authenticated evidence is explicitly unverified, not regenerated from today's provider/catalogue/current key. Retained bodies may support adjudication only when their original identity/hash can be proven; erasure still removes raw data as promised.
4. Completion: every new immutable production fact is paired atomically with its exact log entry; restoration preserves valid callback/inquiry links and cancelled state; same notification/state retries neither duplicate value nor lose decisive inquiry evidence; erased raw bodies remain erased, with original commercial hashes retained.

## R9-CRON1 — P1: scheduled failures are reported as successful health and are never retried as missed jobs

High confidence. `abo/src/worker.ts:133–144,365` stamps `last_run_at` before running anything. Most minute/hourly/daily subjobs catch and discard errors (`366–441`) and heartbeat follows swallowed daily reconciliation/digest failures (`420–437`). Daily digest ping is therefore sent even when the digest was not sent. Nothing records completion/error/catch-up due state; a missed or failed 06:00 run waits another day, and repeated daily failure can look healthy indefinitely. This contradicts 02 §1.1's logging/alert obligation and 05 §§1,3.4's meaningful job liveness. RT2 owns external acquisition/stream identity; this independent producer defect remains even with a functioning monitor.

**Fix steps**

1. Replace `scheduled_job_run`'s single timestamp with per logical job `last_started_at`, `last_succeeded_at`, `last_error_at/code`, and a persisted due-period/checkpoint using a forward migration. Name jobs (reconciliation, digest, lock check, watches, housekeeping, each reversal population, minute processing), not just cron strings. Stamp success only after actual successful completion, including digest send acknowledgment; make subjobs return explicit succeeded/deferred/failed states instead of swallowing a failed operation as success.
2. In one scheduler helper, log bounded job/error/reference data and durably upsert an independently deduplicated operations failure alert, preserving other independent jobs' progress. Keep due daily/hourly work pending and retry it from the existing minute cron with a lease/idempotent period key; do not add services or replay whole financial mutations blindly. Recovery references must retain accepted original commands and version.
3. Ping cron liveness separately from successful daily digest; only send the digest-success stream after its delivery succeeds. Digest reports last_success and current failure/deferred state. Integrate RT2's selected per-stream protocol; its external deadlines remain a named decision stop, not an excuse to claim producer success.
4. Completion: forced source-visible failure path leaves last_success unchanged, due job pending and an alert/log; later minute recovery completes the missed period once; failed digest cannot generate digest-success heartbeat; overlapping schedulers cannot consume the same due period twice. No provider/monitor uptime is established by this static review.
