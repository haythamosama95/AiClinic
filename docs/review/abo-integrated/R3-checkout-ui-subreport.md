## Established flow and boundary

Actual worker checks clinic version then billing authentication then token use before dispatch. All contact access uses authenticated org; checkout id detail checks owner org, lists constrain org, and checkout fact carries authenticated sub/JTI/org. No request-provided org overrides these. Expired token authority remains canonical **R1-C1**, not a new finding here. R2 owns accepted-response version metadata/decoding issues.

Offers load the highest published version when latest event is published; English terms come from R2 using that offer's stored terms version. Flutter forwards the selected id/version/terms through contact to checkout, which snapshots plan/price/contact hash. The provider intention is created and persisted before the checkout snapshot; checkout/status, fact and opened event then commit separately. Only a successful 201 triggers immediate sweep scheduling. Scheduled rematerialization also requires an opened event. Existing key returns original redirect without checking the new payload. Browser launch only starts polling; this UI never interprets a browser return as paid. Payment/grant authority is delegated to sibling confirmation review.

## CU-1 — P1: actual billing page gives every checkout step unbounded height

`administrator_billing_page.dart:128–168` places step widgets inside `SingleChildScrollView > Column`. `offers_screen.dart:124–139` uses Expanded for loading/error and `:140–166` Expanded for offers; contact `:143,175` and checkout `:416` use Expanded/Spacer flex. The scroll parent gives their vertical Columns unbounded height. Flutter cannot allocate nonzero flex in that constraint, so loading/offers/contact/checkout layout fails in the real parent. This blocks administrator purchasing independent of provider correctness. Static framework constraint reasoning; no runtime reproduction claimed.

Fix: (1) Choose the existing outer page as the scroll owner. (2) Remove vertical Expanded/Spacer from all three step bodies, use shrink-wrapped loading/error content, and replace the offers inner ListView with a shrink-wrapped non-scroll list (or ordinary Column). (3) Keep page padding/button spacing explicit and make long terms scroll through the outer page. (4) Completion: real AdministratorBillingPage can lay out each loading/error/offers/contact/new/resumed-checkout state at short and tall window heights, including long terms, without overflow/unbounded-flex errors. Do not verify only a screen mounted directly in a bounded Scaffold.

## CU-2 — P1: checkout creation has no durable key claim before provider side effects

`checkouts.ts:540–547` reads the key, `:578–604` generates a fresh checkout id and calls the provider, and only `:637–759` inserts checkout/status then separately fact/opened event. Adapter `:183–207` checks by generated checkout id, calls provider and stores intention first. Concurrent same-key requests both call Paymob with different checkout ids; uniqueness on `(org_id,client_request_id)` eventually rejects one only after both intentions exist. A crash after intention storage but before checkout insertion leaves an orphan intention and retry generates another. A crash after checkout/status commit but before fact/opened event means retry returns 201 without repairing the missing fact/event. Sweep schedule materialization requires opened event (`sweep.ts:123–126`), so callback-free recovery never starts for this row. Hourly count also counts checkout fact rows, excluding that row. No external provider idempotency guarantee is asserted.

Fix: (1) Add migration-backed durable checkout creation state keyed by org/request id, with fingerprint and stable checkout id; reserve immutable checkout snapshot, checkout fact and creation event in one D1 batch before external HTTP. Do not attempt to span a D1 transaction across HTTP. (2) Use a conditional per-checkout creation lease so concurrent retries reuse one stable operation and cannot both create intentions; retry losers reread the winner. (3) Persist provider outcome and its fact together, then atomically advance status/opened event/work schedule (or make schedule rematerialization derive from the durable creation event), allowing resume after every local commit. (4) Explicitly represent ambiguous provider timeout/crash-after-HTTP-before-store: recover by the stable provider reference using an approved provider lookup/idempotency capability; if that external guarantee cannot be proven, leave the creation recoverable/held for reconciliation rather than blindly creating another intention. This last capability is an external contract limit, not something local atomicity solves. (5) Same-key concurrent/lost-response recovery must return one checkout/redirect; every durable checkout must have export fact/event and scheduled recovery. R9 should own export/rebuild consequences.

## CU-3 — P2: poller exhausts its billing token long before renewal

`checkout_screen.dart:155` polls every second. `rate.ts:42–45` rejects after 60 requests per JTI. `billing_token_client.dart:47–52,62–64` reuses its session until 30 seconds before its roughly 300-second expiry. `abo_client.dart:673–699` neither counts use nor invalidates on rate response. After initial page calls and about a minute of waiting, polling receives 429 for roughly another three to four minutes; successful payment/grant can remain shown Waiting. Timer continues generating rejected calls.

Fix: (1) Track/reserve token uses centrally in BillingTokenClient/AboClient, including concurrent summary/history calls; rotate before 60 local sends, with existing mint coalescing. (2) Bound polling to one in-flight refresh and back off on rate limits; on an unexpected 429 invalidate this token and retry a GET once using a newly minted token, with no infinite retry and no mutation replay unless its stable key/payload is retained. (3) Retain expiry renewal and version-error handling. Completion: a multi-minute waiting checkout continues receiving state under the 60-use cap without a long blind interval or a mint storm.

## CU-4 — P2: token and hourly limits are read-then-write races

`rate.ts:37–60` reads hits then separately inserts/increments. At hits=59, overlapping requests all pass and update beyond 60; simultaneous first uses can throw a unique-key error. `checkouts.ts:207–225,549–550` checks hourly count separately from creation; at nine recent rows multiple distinct-key checkouts all pass ten. These are actual specified 60/token and 10/org/hour bounds, not merely performance observations. R1 explicitly handed token race to R3.

Fix: (1) Replace token read/write with one conditional upsert increment (`ON CONFLICT(jti) DO UPDATE SET hits=hits+1 WHERE hits<60 RETURNING hits`), returning 429 on no row; keep org bound to authenticated claims. (2) Enforce the hourly cap in the durable checkout reservation transaction from CU-2, using a serialized insert-time constraint/trigger against authoritative creation timestamps. Do not count asynchronously written export facts as admission authority. (3) Replays of an existing matching key reuse the reservation without consuming another hourly slot. Completion: overlapping last-slot requests permit exactly one, normal first-use overlaps do not 500, and expired-window creations no longer count.

## CU-5 — P2: sold terms and accepted terms can be different versions

`offers.ts:108–118` serves each offer's terms_version; `checkouts.ts:558–560` requires global MAX terms_version, but `:626` records `offer.terms_version`, not the accepted request value. Publishing a newer terms version without replacing every sellable offer makes legitimate old-offer UI loop terms_not_accepted forever. A direct request accepting latest version passes but stores the older version in its immutable checkout, losing proof of the accepted text.

Fix: (1) Retain the current-global-terms contract in 04 §2.3: serve current terms text/version for every sellable offer, independent of its historical offer_version row. (2) During creation validate the same current terms selection and snapshot the validated `parsed.terms_version`; do not copy the historical offer terms pointer over it. (3) Keep the terms record immutable; a newer version arriving between display and POST returns the existing 409 and refreshes terms. Completion: an unchanged offer remains purchasable after global terms publication, and checkout terms_version exactly identifies the text the admin accepted.

## CU-6 — P2: offer-change recovery silently changes version without reviewing its content

`checkout_screen.dart:269–280` refetches an updated offer but retains only price and version; `:195–200` submits that override with original offer id and original accepted terms. UI does not show updated duration/allowance/copy/terms or require a fresh selection. The fallback to a different offer's version at `:276` is combined with the original id. A same-id replacement with new allowance/duration and unchanged global terms can therefore be sold without displaying its changed package. `offers_screen.dart:147` likewise changes terms text without clearing acceptance.

Fix: (1) Remove version override/fallback behavior; route offer_unavailable back to OffersScreen using a dedicated parent callback and clear old selection/acceptance/request id. (2) Show a fresh complete offer and require explicit selection and terms acceptance before a new checkout intent. (3) Reset acceptance whenever selected offer/terms identity changes, including reload. (4) Keep a frozen id/version/terms payload for network retries; changing commercial intent creates a fresh request id. Completion: no subsequent POST uses a package whose complete displayed details were not selected.

## Additional concrete seams for consolidation

Same-key/different-payload checkout requests (`checkouts.ts:540–546`) and contacts (`billing-contact.ts:111–120`) return original values with no comparison. Returning the original result can be a valid first-write-wins idempotency policy, so this alone is not asserted as an independent contract violation. However desktop contact retains `_saveRequestId` across edits after errors (`billing_contact_form.dart:88–97`): lost success followed by editing and retry silently advances with old contact. Implement request fingerprint comparison/conflict as part of CU-2; for contact freeze retry payload or create a fresh key when edited, and catch unique collisions by rereading matching original payload. Concurrent distinct contact saves compute the same MAX+1 (`billing-contact.ts:123–151`) and one fails unique org/version; allocate version at atomic insertion or retry that collision.

Money is displayed as raw integer minor units with currency (`offers_screen.dart:222`, `checkout_screen.dart:399`) although 03/04 define minor-unit wire fields: for EGP 10000 shows as 10000 EGP instead of 100.00 EGP. Coordinator can include P2 display correction: shared currency-aware major-unit formatter, retaining integer wire values, used on both selection and checkout.

Existing checkout replay also reconstructs starts solely from nonnull coverage_through (`checkouts.ts:460–475`), while initial decision requires state active (`:292–317`); expired/grace snapshots with a historical through therefore change starts from now to after_current on retry. Persist the actual decision/projected_start in the durable checkout creation snapshot and reuse it verbatim. No grant-authority impact claimed; paid term placement remains R4.

091:1 reference-based resume intentionally lacks checkout id/redirect. The actual resume polls reference through open list; submit is a no-op without offer/terms/created response (`checkout_screen.dart:174–187`). It cannot reopen an unpaid provider page after closing the browser. Frozen contract does not expose a resume redirect; record this as a product/contract recovery limit unless coordinator establishes a stronger requirement, rather than inventing a new endpoint here.
