## Established trace and failure map

`beginTransfer` verifies Access and HP then writes source retirement, destination installation/live binding and transfer authorization in one D1 batch. Only afterwards it opens destination `awaiting_transfer`. Existing-operation replay returns the transfer row without initialization recovery. Out/in run using that persisted transfer; D1 step records short-circuit retries only after the local DO response has been received and copied. DO owner established that local out/in have no durable step replay: losing the response before the D1 step write corrupts recovery. The canonical local findings belong to that owner.

Deletion selects the live org binding, inspects DO terms, marks installation deleted, then holds/freezes or retires the binding, and finally purges operational data. Inspection failure is treated as empty coverage. Held replay returns before freeze/purge recovery. Commercial rows and DO state survive purge; operational request/envelope/usage rows do not. The lead owns delayed callback erasure after successful purge.

Reversal validates the exact signed body, key activity and signature before business effects. Partial input must be boolean; partial true writes nothing. Full reversal finds an installation through the asynchronously shipped grant ledger; matching completed reversal returns original `receipt.result=applied` under outer `already_applied`. No ledger produces a nil-org/nil-installation receipt with empty term list/sequence zero, D1 tombstone, then R2 void object. Operator void uses the exact ledger installation binding, whereas reversal and held release incorrectly require an active org binding.

## Findings

### R6-PT1 — P1: reversal routing treats lagging copies and active bindings as authoritative

**High confidence; source defect; implementation-ready after R4-PG1.** `vendor/entrypoint.ts:4008–4025` selects a single grant-ledger row by applied time/origin; `4085–4108` uses that installation and the *current active org* epoch. `548–560` excludes held bindings. `1708–1754` repeats those choices for replay. Without a ledger row, `4115–4143` reports applied and creates only a tombstone. Grant checks tombstones before dispatch (`3650–3657`), then asynchronously calls the DO (`3673–3690`). Actual DO grant value creates a local ledger outbox (`quota-do/coverage.ts:1837–1849`); a later shipment inserts D1 (`2715–2736`). There is therefore a normal interval where the grant exists but the ledger does not. A refund during it is acknowledged as applied while the paid coverage survives. A request already past its pre-DO tombstone check can likewise apply after the tombstone. DO owner independently confirms `applyGrantRPC:1575–1654` performs no serialized tombstone check.

After transfer, destination ledger shipment can lag the import. The query may then route the refund to an ended source term. DO owner confirms `findTermForGrant:634–637` follows origin locally, but void on an ended/transferred term has effect none; it neither fences the supplied epoch nor checks the newer destination. This yields an applied void receipt while moved value remains usable. With deletion, a held binding exists but `readActiveTenantBinding` is null, so automatic full refunds cannot remove held value. These are financial correctness failures under ordinary shipping delays/authorized lifecycle changes, distinct from PG1's duplicate-grant creation root.

The tombstone crash variant is bounded but also concrete: D1 commits before R2 (`4127–4143`), then R2 fails; replay sees the row but no receipt and returns `coverage_unknown` (`4057–4065`) permanently. `findStoredReversalVoid:1757–1775` scans all voids and reads R2 to recover reversal identity because D1 lacks it. Fold repair into the same durable command rather than retaining that scan.

**Fix steps**

1. Extend PG1's platform global claim/routing migration with immutable full-reversal commands keyed globally by `reversal_id`, unique terminal void per original grant identity, the signed request digest/body and original signed receipt/export payload. Preserve original grant receipts. Add a `live_value_route` (installation, epoch, generation, state=`stable`/`moving`/`retired`) for each original grant lineage, including imported terms and adjustments. Backfill from authoritative DO grants/transfer facts; ambiguous routes fail closed for operator adjudication, never infer no value from a missing D1 ledger row.
2. Make `voidForReversal` claim/read that command atomically with the PG1 grant claim. Different grant/reason/evidence/partial for a used reversal is conflict. A genuinely unclaimed grant may become terminally tombstoned in the same transaction that reserves its identity, so later grant claims cannot dispatch it. Existing/pending grant routes require serialized DO void/no-effect proof on their exact installation/epoch/generation before the command can complete. A grant request already dispatched must encounter the durable local tombstone/seal, or be voided if it committed first. Reuse PG1's route seal; do not implement a second unlocked D1-before-DO check.
3. In begin/out/in, mark each lineage route moving before export; while moving, reversal stays transient and its command remains due. Serialize void against export at the source DO: if void wins, exported value excludes it; if export wins, source returns transferred/transient rather than successful no-effect. After durable import, CAS the exact old route generation to destination and publish stable. A late old-route void cannot return applied for a transferred term. This must compose with PT2 and DO local step replay.
4. Route full reversal through the claim, accepting `active` or `held_for_transfer` on its exact installation. Send that route's epoch, never another installation's current epoch. DO rejects mismatched org/installation/epoch/generation before mutation. For terminal replay return the original receipt without requiring a currently active binding. Keep `releaseHeld` fail-closed for deleted/transfer-pending installations: restoring service there requires transfer; only void/replay needs the held-route exception.
5. Commit terminal receipt and immutable R2 export obligation with command completion; retry R2 shipment idempotently from that payload. Never sign a replacement receipt after a crash. Remove all-void R2 scanning from request handling. Retain command/route/export facts in R9 rebuilds. Completion: refund before/after DO apply and before/after shipment leaves no live refunded value; during transfer it retries then removes destination value once; held deletion can be voided; changed replay conflicts; R2 failure returns the original receipt on retry and eventually ships its object.

### R6-PT2 — P1: transfer publishes its destination before the destination admission fence exists

**High confidence; implementation-ready with PG1/PG3 and DO step replay.** `coverage/transfer.ts:254–293` retires source and publishes the active destination. Only `295–300` initializes its awaiting-transfer flag; failure does not roll back publication. New paid grants resolve that live destination and can apply before its hot row is opened, violating 03 §5.4's requirement that moved coverage precede new purchases. A normal token/grant request racing this network await suffices. DO owner confirms open only sets the flag on existing state, so initialization cannot retroactively reorder the already-applied purchase. Retrying begin via `entrypoint.ts:3737–3747` merely returns the existing transfer row and never repairs missing initialization. A second authorized transfer or deletion can also target this prematurely live, still-empty destination. This is a core transfer ordering defect; local step replay/value arithmetic remain separate DO findings.

**Fix steps**

1. Add persisted preparation phases to the transfer authorization and a unique open preparation per source org/epoch, using PG3's durable accepted-command transaction (assertion, actor, audit, immutable source id/epoch/reason). Allocate and persist destination id/next epoch before external calls, but do not publish its live binding or retire source. The next epoch is reserved under the same per-org uniqueness boundary; a stale source CAS must abort without mutating a newer live binding.
2. Initialize destination `awaiting_transfer` with exact transfer id/org/epoch using an idempotent DO command; matching replay returns initialized, differing identity conflicts, and it refuses initialization over an unrelated existing grant/import. Persist acknowledgement. Then freeze source with a serialized transfer-preparation command carrying the same transfer/source epoch; both admission and apply-grant must honor that fence. Existing reservations remain attributable and must drain/settle according to R5 and the DO owner's conservation fix before export; never discard them.
3. Only after both acknowledgements CAS the source binding at its reserved installation/epoch/status to retired and insert destination's active binding in one D1 transaction. Until then the original binding remains live/held and new value-changing dispatch reports transfer pending. All grant routes already dispatched to the old source remain protected by PG1 seals and the source fence. Publish no destination binding on unknown acknowledgement.
4. Existing `beginTransfer` operation replay resumes these persisted phases before returning successful authorization; a bounded scheduled dispatcher resumes accepted preparation after caller loss. Out/in require the same prepared transfer and generation, use the DO owner's original package/receipt replay, and persist D1 steps with compare-or-return matching immutable payload semantics rather than overwriting concurrent results. A successor transfer/deletion must wait for preparation/import to finish or an explicit persisted no-effect cancellation; it cannot treat an awaiting destination as empty.
5. Completion: grants/tokens at every preparation boundary cannot place a new term ahead of moved value; failure before/after either acknowledgement and D1 publication resumes one transfer/destination; stale source/epoch cannot retire or import over its successor. PG3 supplies durable authorization and the lead owns ABO work handoff after successful begin.

### R6-PT3 — P1: deletion can retire unknown coverage and reports incomplete deletion as complete

**High confidence; implementation-ready.** `inspectInstallationTerms:580–594` converts unavailable/malformed DO response to `[]`. Consequently `652–687` retires the binding as if no coverage exists, allowing recreation while value remains on the deleted DO. `retireHeldBindingIfEmpty:729–748` has the same failure. With known coverage, deletion changes D1 status before calling `set_transfer_pending`, ignores that response (`658–676`) and still succeeds. Existing source admissions can therefore continue during an unavailable freeze, and no retry repairs it. `641–648` returns immediately for deleted+held before freeze/alert/purge. A failure after marking held but before or during `purgeByInstallationId` leaves request payloads indefinitely; every repeated deletion reports ok. Supporting `retention/index.ts:287–390` deletes R2 envelopes before its D1 batch, so interruption is credible and repeatable. An empty-coverage deletion retires the only live binding, making subsequent `readLiveOrgBinding` return null and preventing completion there too.

**Fix steps**

1. Add a durable deletion command keyed by accepted operation digest, storing immutable target installation/epoch, actor/reason, phase, freeze acknowledgement, retained term ids and completion detail. Use PG3 acceptance/audit and pin the target at acceptance; subsequent retries never dynamically target a successor org binding. Reuse PT2's per-org lifecycle exclusivity so deletion and transfer cannot independently mutate the same source/epoch.
2. Replace array-only inspection with a discriminated successful snapshot versus unavailable result. Both delete and `retireHeldBindingIfEmpty` must refuse retirement on unavailable/malformed responses. Obtain a serialized DO deletion-preparation acknowledgement that freezes new admission/grant application and returns the stable open-term/reservation inventory in one command. Set a terminal/no-new-value fence even when inventory is empty; compose with PG1 seal rules for requests already dispatched. Unknown acknowledgement leaves command due and binding held/live.
3. After acknowledgement, batch installation deleted plus binding held when any open value remains, or retired only with proved empty/no-pending-value state, with exact target epoch CAS. Preserve the acknowledged open term ids when purging usage. Persist an AL-18 delivery obligation once for held deletion; retries do not generate another logical alert. Never publish completion merely from installation/binding statuses.
4. Resume idempotent R2 envelope purge then D1 purge and audit from the pinned command even after its binding is retired. Persist purge completion before returning ok; retain the command's original detail for repeats. A failed purge remains due for bounded recovery without another touch. Follow the lead's separate delayed-callback erasure recipe so later work cannot recreate purged payloads.
5. Completion: failed inspection/freeze cannot retire live coverage; a stopped Worker at every phase resumes the same target, finishes purge and alert once, and cannot delete a newer epoch. Retiring the last held grant likewise requires authoritative successful empty inspection. Existing reservation identities survive the freeze until settled/released; no source/destination double allowance is introduced.
