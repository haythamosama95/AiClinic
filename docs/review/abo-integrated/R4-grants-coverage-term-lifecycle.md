## Established end-to-end trace

An eligible payment has authenticated bound success, matched amount/currency, disposition grant (or explicit release), a payment fact hash, and queued work. R3-C5/C6 still own the upstream marker-before-payment and suppression of a second captured success; those unfixed roots are not counted again. The paid producer copies frozen checkout plan/month duration/allowance/grace into a deterministic grant, includes the prescribed operation-object approval and signs its canonical bytes with the current ABO key. Retries reuse the original stored envelope/version/hash. Withheld payments need explicit HP release; reversed-before-grant normally emits no grant work. R2-P1 local HP target binding remains inherited.

Platform verification checks exact signed payload and key validity, current plan/source/duration/allowance/grace bounds, binding and tombstone before the DO. Complimentary grants require actual platform HP checks; R2-P2 still owns the second override binding defect. Published plan content is snapshotted into the term and later activation does not reread mutable registry policy. Same-content republish does not unretire a plan; new retired-plan application is refused. PG1 specifies the authenticated original-receipt replay exception.

The DO serializes an installation's mutations, applies placement and signs org/installation/grant/hash/term IDs with ledger_seq equal to that grant_applied event's clinic_seq. Matching local replay returns the exact original receipt with signed result=applied, even when the outer result says already_applied. D1 ledger/events/mirror and R2 NDJSON are asynchronous copies, not the dedupe authority. Normally an outbox row remains until its D1/R2 shipment finishes; source failures below break atomic grant linkage and wake-up guarantees. ABO success drives checkout Active and reversal term attribution. Subscription status reads live coverage with stored fallback, so an outcome is not coverage authority.

These arithmetic/selection reads do not constitute the full R5 accounting audit.

## Receipt-to-state linkage and crash windows

| Boundary | Durable effect / receipt relationship | Recovery result at T |
| --- | --- | --- |
| Before paid platform dispatch | Stored request and hash, no coverage receipt | Same immutable bytes can be re-signed with current active key |
| Value writes→await signature | Terms/hot/seq can precede grant+receipt | A retry can create another term/addition (D1) |

## R4-PG1 — P1: grant identity is lost when the live installation changes

**High confidence; implementation-ready.** Invariant: a deterministic grant id plus content identifies one commercial grant, with its original receipt, across transfer/recreation (04 §§1.2–1.4; NFR-02/03). Paid `grant` resolves the **current** binding (`ai-platform/src/vendor/entrypoint.ts:3621–3648`); complimentary replay also resolves the current binding (`1452–1517`). The actual dedupe is only the selected DO's `grant` table (`quota-do/coverage.ts:1603–1619`; schema `quota-do/index.ts:1960–1971`). Transfer imports retain origin lineage but create distinct transfer grant ids (`coverage.ts:3157–3160,3178,3227–3250`). Therefore: original grant applies; its reply is lost; a same-org transfer completes; original grant retries and is absent from the destination's grant table, so another full term is created alongside moved value. A changed envelope with that original id also escapes cross-installation conflict detection. Normal transport retry and authorized transfer suffice; no key compromise is required.

The global D1 PK is only applied later with `INSERT OR IGNORE` (`coverage.ts:2715–2734`), so it silently retains the earlier ledger copy while the second DO has already created coverage. R2 objects are keyed by grant id and similarly preserve an earlier copy (`2736–2753`). The problem is not solved by querying that eventual mirror before dispatch. The optional paid `installation_id` override (`entrypoint.ts:3626–3641`) additionally accepts a historical binding without an active-status predicate and must not become a route around global ownership.

**Related replay conflict, included in this root:** published-plan checks precede all replay (`3271–3273,3553–3555`), so a successful lost reply followed by retirement becomes `plan_not_published` rather than returning its receipt. The contract's unconditional validation-order wording conflicts with its original-receipt/idempotency promise. Resolve by making that order apply to **new application**, while authenticated exact replay returns the original completed fact. Never newly apply a retired plan.

**Fix steps**

1. Add a forward platform D1 migration for `grant_claim`, globally keyed by `grant_id`, containing immutable org/source/canonical envelope/hash, current route installation/epoch/generation and optional completed receipt. Preserve the DO as coverage authority: this row is routing/idempotency metadata. Before enabling new dispatch, backfill from retained DO grants and their ledger copies; fail closed and alert on differing identities/receipts instead of choosing a winner or recreating value. Include these rows in R9 rebuild/retention.
2. In `VendorEntrypoint.grant` and `tryComplimentaryGrantIdempotency`, authenticate the paid caller/current signature or human Access, validate/hash the supplied envelope, then atomically insert/read the claim before any DO application. Existing different org/hash is `conflict`; matching completed claim returns its **original** receipt before mutable plan/policy/live-binding checks. Matching pending claim dispatches only to its stored route. New claims require the normal current plan/policy/authorization checks. Remove client-controlled `installation_id` routing; internal replay uses the claim. Current signing-key auth still applies, so old envelopes can be re-signed by a rotated active ABO key.
3. In `applyGrantRPC`, check a local matching completed grant before `awaiting_transfer`/`transferred_out` rejection; this is read-only replay. Add a serialized `seal_grant_route` DO RPC and local persistent seal table keyed by grant id/hash/generation: if the original grant exists, return its receipt; otherwise record a no-effect seal atomically before replying. Every later old-route apply of that id must honor the seal. Wire/schema this in `quota-do/index.ts`, `quota-do/coverage.ts` and Worker RPC dispatch. A transfer flag alone is insufficient for deletion with no remaining coverage (`coverage/transfer.ts:679–687` leaves no DO terminal flag).
4. A pending claim whose installation is retired may move only after that old DO has returned a persisted seal/no-existing-grant proof. CAS the claim's exact old route/generation to the current live binding and increment generation; dispatch the new route only after winning/reloading that CAS. Source outage/unknown outcome means retry/alert, never reroute. A late old request is rejected by its durable seal; an earlier committed request returns its original receipt and prevents moving. This also covers a claimed request that had not applied when transfer began.
5. After DO success, require returned org/grant/hash/installation to match the claim route, then persist the original receipt; a crash before this D1 write is recovered by reading the same DO fact. Keep ledger/R2 asynchronous, but compare existing identity/receipt on collision and retain/alert discrepancies rather than silently discarding them. Transfer-generated grant ids must enter the same global namespace; origin lineage remains separate.
6. Completion: lost receipt before/after transfer, deletion/recreation, and plan retirement returns one original grant/receipt; changed content conflicts globally; concurrent new claims create one route; crashes on either side of sealing/CAS never let two DOs apply; an original no-effect pending claim eventually applies once on the new live identity. Deploy receiver/schema/seal support before enabling the new dispatcher. Amend 04's validation-order/replay exception together with source; no new service or queue is required.

## R4-D1 — P1: Grant value changes can commit before their receipt/idempotency record

High confidence; source defect; implementation-ready. `coverage.ts:1739–1808` inserts a queued term or mutates active/grace/sequence before awaiting `signReceipt`; the grant row is only inserted at `1820–1831`. Complimentary placement (`1398–1453`) and adjustment (`1553–1559`) similarly mutate before `finalizeGrantApply` awaits signing at `1248–1258`, then inserts grant at `1260–1271`. The wrapper uses blockConcurrencyWhile, with no SQLite transaction/rollback around these writes. Synchronous SQLite writes before an asynchronous signing suspension do not form an all-or-nothing application with later writes. Interruption/signing failure can leave usable or queued value without its grant row. A same-envelope retry sees no grant (`1606–1619`) and appends a second term; adjustment retry can add allowance/days twice. This violates 04 §1.4's atomic application and immutable receipt linkage. No runtime fault injection was performed.

**Fix steps**
1. In `coverage.ts`, refactor `applyGrantRPC`, `applyComplimentaryTermGrant`, `applyTermAdjustmentGrant` and `finalizeGrantApply` to prepare a pure mutation plan: term IDs, old→new term/hot values, ordered event payloads, grant_applied sequence and ledger row. Do not execute term/hot/outbox SQL while preparing or signing. Retain the installation concurrency block across prepare/sign/commit.
2. Sign the fully determined receipt before any grant-value write. Then use the SQLite storage's synchronous transaction API to commit **all** planned term changes, hot sequence/usage, grant+receipt and outbox rows together; recheck grant ID/hash in the transaction. Share the commit helper across paid, complimentary and adjustment paths. Wire their existing GatewayObject caller through the same helper; no caller may bypass it.
3. Keep alarm/remote I/O outside this transaction and apply D4's durable wake-up recipe. Add an integrity guard for one created term per term-grant ID; existing duplicate/orphan rows must be surfaced for reconciliation, never silently deleted or credited.
4. Completion: interruption before commit leaves no term/allowance/sequence/event effect; interruption after commit leaves exactly one complete grant+receipt+ordered outbox. Same-envelope retry returns those exact IDs/bytes; differing-envelope retry conflicts; adjustment retry changes neither allowance nor end a second time.

The same mutation-before-final-plan construction emits paid event snapshots from intermediate states (`coverage.ts:1757–1781`) although 03 §6.7 requires final post-grant state on each event. In fix steps1–2, generate every event snapshot from the fully planned final term/hot state and assign each its own clinic_seq, retaining term_ended→term_activated→grant_applied order. R7 must carry that invariant through paginated consumption; this is included in the one D1 staging/commit root, not a second severity count.

## R4-A1 — P1: a parked rejection makes successful retry unrecordable

Stale workers produce no outcome/fact; matching existing terminal receipt completes current work idempotently. Add a random lease/attempt token on acquisition if using it as the unique attempt identity.
3. Preserve old journal replay in `rebuild.replayLedger`: original `grant_outcome` facts replay to legacy/events idempotently; new event facts replay by attempt id, then the view supplies current state. Existing receivers keep querying the one-row compatibility view: `checkouts.shownStateForPaidCheckout`, `reversal.grantOutcomeApplied`, sweep grant joins, `ops.handleGetClinic` grant join, reconciliation payment/receipt checks and rebuild outcome existence. Completion: rejected→operator retry→applied/already_applied leaves both immutable attempts, one effective successful receipt and done work; repeated same success leaves one terminal receipt; expired-lease completion adds no row; voided remains done without creating value. ## R4-D4 — P1: Applied-grant replay does not recover a missing shipment/lifecycle alarm

High confidence; implementation-ready; depends on D1's atomic commit. Paid apply inserts grant/outbox (`1820–1859`) and then awaits a D1 paid-velocity read (`1869–1872`), before scheduling its first alarm (`1887–1889`). D1 failure there leaves a complete grant and pending outbox without a scheduled alarm. **Fix steps**

3. Move paid velocity observation to durable outbox processing (or make its failure retryable without abandoning the already scheduled wake-up). Keep the original grant receipt immutable and return already_applied only after pending outbox/boundary work has a durable wake-up. Apply shared scheduling behavior to complimentary/adjustment finalize paths.
4. Completion: a D1 outage after grant commit, lost setAlarm reply, process reset and same-grant replay all leave the complete grant plus an eventual shipment/boundary wake-up; no extra value or receipt appears. R9 must retain this requirement in alarm/rebuild recovery.

## R4-D3 — P1: Grant placement uses stale lifecycle state after a delayed alarm

## R4-D5 — P2: The per-org 90-day complimentary ceiling resets with its installation
