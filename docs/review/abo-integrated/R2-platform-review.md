## Established boundaries

The named service binding is the machine perimeter. `VendorEntrypoint` is exported by the Worker; no public HTTP route dispatches its methods (`worker.ts:2343–2513`). `abo/wrangler.toml:127–130` names that entrypoint. Service-binding authorization and Access application provisioning remain deployment facts. Both Workers disable workers.dev and preview URLs in checked configuration.

Version negotiation precedes Access verification on inspected public methods. Ordinary HP operations verify an active/due credential, WebAuthn assertion over the canonical operation, same-call Access actor, five-minute issuance window, exact arguments, and the replay table (`entrypoint.ts:1124–1305`). The replay table's primary key prevents two successful pre-mutation claims; an unhandled unique-key loser is an availability/error-envelope limitation, not proof of duplicate value. Pending credentials promote only after their stored activation deadline (`834–864`); bootstrap inserts pending plus 24 hours (`1874–1928`). Credential ownership is recorded but not compared to Access email. The amended contract requires operation actor = Access email, not credential-owner equality; no independent ownership finding is asserted.

## R2-PF1 — P1: second ceiling assertion is not bound to the granted operation

**High confidence, implementation-ready.** The required separate touch for a ceiling override must authorize the exact operation and be at most five minutes old (02 §3.3; 04 §1.5). `verifyCeilingOverrideAssertion` selects caller-supplied `ceiling_override_operation` at `entrypoint.ts:1369–1377`; its validation checks only the generic operation shape and `op` (`1379–1381`). It verifies that supplied operation's signature (`1393–1399`) and actor (`1445–1449`), but never compares its params, envelope, version, or freshness with the current call. Its unused digest is the only replay condition (`1383–1385`). A compromised relay with a captured, unused override assertion can pair it with a fresh first grant assertion for a different tenant/amount/envelope, even long after the override ceremony. The first real touch remains required, but the separately approved exception is substituted. The relay forwards the explicit override object unchanged (`abo/src/ops/index.ts:2685–2686`). Successful verification sets `skipCeilingCheck` (`entrypoint.ts:3346–3363`), forwarded at `3460`; the DO then bypasses complimentary and adjustment ceilings (`quota-do/coverage.ts:1354–1368,1512–1526`). This is unauthorized ceiling exception, not a forged WebAuthn signature or unlimited machine-only grant.

**Fix steps**

1. In `entrypoint.ts.verifyCeilingOverrideAssertion`, construct the expected operation from the current negotiated version, verified Access JWT/email, current envelope with only `ceiling_override` omitted, and the explicit override operation's validated nonce. Require explicit override `op`, top-level version, actor and canonical params equality with that expected context. Permit its own `issued_at` and nonce so the two ceremonies can occur sequentially; require the existing five-minute freshness helper.
2. Retain compatibility when the explicit object is absent only by deriving the exact expected operation from the current grant metadata. Remove the timestamp-search fallback (`1400–1442`): a verifier must validate the operation it was sent/derived, not search for an alternative authorization. Decode malformed client data defensively into `assertion_invalid`.
3. Check replay against the **actually verified** override operation hash and require that hash differs from the first assertion. Claim both hashes together in one D1 atomic batch before dispatch, avoiding a main-claim-only partial failure. Keep the same active signer requirement and separate AL-12 behavior.
4. Completion: a correctly bound second assertion succeeds; old, different-envelope/org/version/actor assertions fail before any coverage dispatch; replay of either challenge fails or returns an already-completed exact result. No timestamp-search path can skip these checks.

## R2-PF2 — P1: bootstrap emptiness is checked outside its credential insertion

**High confidence, implementation-ready.** Only the first credential may be registered without an approving assertion (04 §1.3). `registerOperatorCredential` reads count at `1947`, then calls `bootstrapRegister` at `1962`; after further awaits, bootstrap performs an unconditional insert at `1903–1910`. Two concurrent requests with distinct IDs can both observe zero and both insert without approval. `20261003120000_operator_credential_and_platform_alert.sql:3–12` constrains only credential ID, so neither insert conflicts. A valid Access identity is required; this does not let an internet outsider bootstrap. During first setup, a stolen Access session can race legitimate initial registration and leave additional independently active credentials after 24 hours without the required HP approval. The delay and AL-13 still apply and reduce immediacy; they do not enforce the one-row exception.

**Fix steps**

1. Replace bootstrap's plain insert with a single D1 statement `INSERT INTO operator_credential (...) SELECT ... WHERE NOT EXISTS (SELECT 1 FROM operator_credential)`. Use its `meta.changes` as the decision; D1 serializes the statement's predicate and write. Keep the early count only as an optional fast refusal.
2. On zero changes return `assertion_required` without success alert; only the inserted winner receives bootstrap audit and AL-13. Preserve pending state, 24-hour activation and no hard-deletion path. Do not count only active credentials: pending or revoked rows still permanently close bootstrap.
3. Keep the existing normal HP same-ID/same-key idempotency semantics. Completion: concurrent distinct no-assertion registrations produce exactly one row; after any registry row exists every subsequent new credential requires HP approval, including after revoke and while all rows are pending.

## R2-PF3 — P2: exact argument binding incorrectly depends on JSON property order

**High confidence, implementation-ready.** `stableJson` is `JSON.stringify` (`entrypoint.ts:914–916`); `operationParamsMatch` builds its expected object in implementation insertion order (`938–997`) and compares strings (`999`). Reordering keys in `operation.params`, including nested attestation/envelope fields, leaves the canonical challenge and actual method arguments unchanged but rejects a valid assertion. In particular, a client that serializes canonical params puts `access_jwt` before `contract_version`, whereas the expected object inserts the reverse order. Supported callers using canonical JSON fail all normal HP methods despite signing the correct operation. This is a concrete interoperability defect, not an authentication bypass.

**Fix steps**

1. Replace the comparison in `operationParamsMatch` with byte equality of `canonicalize(params)` and `canonicalize(expected)`, using the existing helper. Catch canonicalization rejection as a failed match. Retain complete expected-field comparison so missing, extra or modified bound arguments still fail.
2. Use this same comparison for PF1's override binding. Completion: permutations of object member order, including nested members, accept the same valid signed operation; changed values and additional bound params still reject.

## Version handoff to R2 synthesis

DO dispatch negotiates before `ensureCoverageDoTables` and routes all successful results through an echoed `contract_version` (`worker.ts:1719–2013`). Accepted-request errors omit it (`1809–1813,2014–2022`). HTTP wrapping adds the header only (`vendor/contract-version.ts:38–49`); the coverage JSON at `coverage-read/index.ts:139–145` omits the body version. More significantly, actual DO consumers cast HTTP-200 JSON without checking its version: `entrypoint.callCoverageDo:603–625`, `coverage/transfer.callCoverageDo:92–114`, `coverage-read.callReadCoverage:42–65`, `credit.invokeCreditRpc:105–109`, `credit.invokeSettleFallback:143–146`, `admission.callAdmissionDo:313–318`, and rebuild/refresh transport at `quota-do/coverage.ts:4140,4311`. The coverage reader even treats the DO's HTTP-200 version refusal as successful coverage and emits only `subscription_ref` with absent snapshot fields (`coverage-read:124–145`). Admission recognizes a rejection, but not an unknown response version. Coordinator owns the common cross-channel P2 recipe: validate response version before interpreting payload, consistently map refusal/unknown version to coverage_unknown, and echo accepted versions in required headers/body/errors. This report does not duplicate that finding ID.

## Replay and durability handoffs

- `beginTransfer` mutates via `executeBeginTransfer` before `finishHpAssertion` (`entrypoint:3773–3789`). Its D1 batch is atomic and the single-live-org index constrains concurrent duplicates (`coverage/transfer:231–309`; tenant migration partial unique index). Two simultaneous identical starts cannot both create live bindings through that batch. A lost DO-open response can leave a durable transfer before the replay claim; R6 owns recovery of the awaiting-transfer initialization and existing-assertion shortcut.
- `deleteInstallation` similarly executes before the replay claim (`entrypoint:3908–3922`). Its helper chooses the current live binding dynamically (`coverage/transfer:617–722`), not a binding fixed in the signed params. Two already-verified requests straddling a new binding could target different epochs before either inserts replay. No ordinary interleaving creating that new binding was established here; R6 must resolve target pinning plus transfer/deletion concurrency. This is an explicit open seam, not an asserted duplicate mutation.
- `releaseHeld`/`voidGrant` mutate before the D1 replay record, but the DO serializes and stores a receipt under the challenge (`coverage:2320–2337,2430–2445`). The replay-only peek returns that original receipt. R6 retains business-state correctness and target provenance.
- Complimentary grant consumes its challenge before dispatch (`entrypoint:3365–3372` vs `3426–3468`); no-apply storage failure then makes the same request fail `assertion_used`. The actual ABO relay is inline and stores rejected outcomes rather than retrying a stored HP operation (`ops:2646–2721,2219–2330`). R4/R8 should decide whether an accepted durable intent is required for resumability; no automatic-retry defect is claimed in this slice.
