## Established traces and limits

`GatewayObject.fetch` passes the real `ctx.blockConcurrencyWhile` into apply/read/inspect; apply serializes each installation's grant hash lookup and value mutation. Local replay compares `grant_id` plus canonical envelope hash and returns the original signed receipt. A differing hash conflicts. It does not establish global grant uniqueness across installation DOs: the platform reviewer owns that canonical finding. Imported terms use new transfer grant IDs, so the destination has no original paid ID to deduplicate.

Paid placement appends behind active/queued terms, activates when none exist, and replaces grace with a calendar anchored at the previous end. Sequence/events for paid renewal follow term_ended → term_activated → grant_applied; the signed receipt uses the grant_applied clinic sequence, explicit org/installation/grant/envelope hash and created term IDs. Queued terms have no dates. `loadTerms` sorts ascending position; both date-boundary succession and exhaustion select the lowest queued position. A delayed boundary loop can consume multiple already-expired successors in order. Month arithmetic clamps in UTC, leap years follow Date's UTC calendar, days are exact 24-hour multiples, and staging replaces unit lengths rather than compressing a computed interval.

The admission seam distinguishes reservation exhaustion from date expiry: exhaustion is final, has no grace, and activates the next queued term immediately. Date expiry without a successor starts grace; its budget is min(unused allowance, ceil(allowance × grace-days / unscaled term-days)). Grace usage stays on its original term. Full accounting, fallback, transfer/reversal and rebuild audits remain later-phase work.

Normal shipment reads outbox sequence order. Coverage events use immutable unique event IDs, then update the mirror only when the snapshot is newer; grant ledger uses grant_id uniqueness and writes D1 before its distinct R2 `grant-ledger/<id>.ndjson` object. A D1/R2 failure before outbox deletion retains the row for idempotent retry. This is eventual multi-store propagation, not an atomic D1/R2 commit. Missing/mismatched copies and global identity claims require coordinator/platform/R9 handling. An already-existing R2 key is trusted by `head`, not compared here; no live bucket-lock configuration was verified.

## R4-D1 — P1: Grant value changes can commit before their receipt/idempotency record

High confidence; source defect; implementation-ready. `coverage.ts:1739–1808` inserts a queued term or mutates active/grace/sequence before awaiting `signReceipt`; the grant row is only inserted at `1820–1831`. Complimentary placement (`1398–1453`) and adjustment (`1553–1559`) similarly mutate before `finalizeGrantApply` awaits signing at `1248–1258`, then inserts grant at `1260–1271`. The wrapper uses blockConcurrencyWhile, with no SQLite transaction/rollback around these writes. Synchronous SQLite writes before an asynchronous signing suspension do not form an all-or-nothing application with later writes. Interruption/signing failure can leave usable or queued value without its grant row. A same-envelope retry sees no grant (`1606–1619`) and appends a second term; adjustment retry can add allowance/days twice. This violates 04 §1.4's atomic application and immutable receipt linkage. No runtime fault injection was performed.

**Fix steps**
1. In `coverage.ts`, refactor `applyGrantRPC`, `applyComplimentaryTermGrant`, `applyTermAdjustmentGrant` and `finalizeGrantApply` to prepare a pure mutation plan: term IDs, old→new term/hot values, ordered event payloads, grant_applied sequence and ledger row. Do not execute term/hot/outbox SQL while preparing or signing. Retain the installation concurrency block across prepare/sign/commit.
2. Sign the fully determined receipt before any grant-value write. Then use the SQLite storage's synchronous transaction API to commit **all** planned term changes, hot sequence/usage, grant+receipt and outbox rows together; recheck grant ID/hash in the transaction. Share the commit helper across paid, complimentary and adjustment paths. Wire their existing GatewayObject caller through the same helper; no caller may bypass it.
3. Keep alarm/remote I/O outside this transaction and apply D4's durable wake-up recipe. Add an integrity guard for one created term per term-grant ID; existing duplicate/orphan rows must be surfaced for reconciliation, never silently deleted or credited.
4. Completion: interruption before commit leaves no term/allowance/sequence/event effect; interruption after commit leaves exactly one complete grant+receipt+ordered outbox. Same-envelope retry returns those exact IDs/bytes; differing-envelope retry conflicts; adjustment retry changes neither allowance nor end a second time.

## R4-D2 — P1: Complimentary grants during grace can become permanently stranded

High confidence; implementation-ready. `applyComplimentaryTermGrant:1370–1386` treats grace as a reason to queue. Both 03 §5.3 and §6.1 require every term grant during grace to renew with the old end as calendar anchor. Once that grace ends, `applyDueBoundaries:887–910` clears active_term_id without activating queued terms; `index.ts:1353–1368` then returns lapsed. There is no remaining active boundary to activate the complimentary grant, and later paid grants see hasQueued and queue too. A valid 14-day goodwill grant applied during grace can therefore provide no service indefinitely.

**Fix steps**
1. Replace the independent complimentary placement decision in `coverage.ts:1370–1451` with the same placement planner used by paid grants: a current grace term ends renewed, the new term becomes active, and its calendar anchor/end derive from that grace term's ends_at. Preserve the old term's used_final and clear grace_base_used.
2. Emit term_ended → term_activated → grant_applied with consistent post-transition snapshots and the grant_applied sequence in the receipt, using D1's atomic commit helper. Active coverage still queues complimentary terms; no-coverage trials activate now; held terms remain held.
3. Repair existing no-active/grace + unheld-queued orphan state through an explicit recovery action that activates the oldest stranded term at recovery time with full value and audit, then leaves successors in position order. Do not backdate this repair over the period when the grant was inaccessible.
4. Completion: complimentary during grace becomes active in that call; expiry/exhaustion advances successors; an affected clinic's later paid grant cannot remain behind an inert queue. A paid grant following an active trial still queues normally.

## R4-D3 — P1: Grant placement uses stale lifecycle state after a delayed alarm

High confidence; implementation-ready. `applyGrantRPC:1653–1713` reads stored active/grace states without `applyDueBoundaries`; the complimentary and adjustment branches are dispatched even earlier (`1629–1650`). Only admission (`index.ts:1319`) and shipment (`coverage.ts:2675`) apply due boundaries. After a platform interruption or delayed alarm, a purchase made after old coverage and grace have expired can see stale grace and backdate its new month to the old ends_at; stale active instead queues it behind a term already over. Catch-up then starts the new term in the past. A 1 May payment after a 1 March expiry can produce an already-expired renewal rather than the 1 May→1 June term required by 03 §6.8 / FM-04.

**Fix steps**
1. Before deciding a **new** grant's placement/adjustment target in `applyGrantRPC`, calculate all boundaries due at request.nowIso under the same concurrency block and include them in D1's pure mutation plan. An identical existing grant must replay its original receipt without creating new grant effects.
2. Use the caught-up state for paid and complimentary placement and adjustment eligibility. After old grace is over, a new purchase with no remaining active/unheld queue starts at now; a genuinely current grace renewal keeps the previous end anchor; valid prepaid successors continue from predecessor ends and catch up in order.
3. Commit boundary events and grant events in sequence with the resulting hot/term state atomically. Preserve distinct expired/exhausted reasons and never introduce grace after exhaustion. All existing `applyDueBoundaries` consumers must reuse the same transition logic.
4. Completion: a first post-outage grant after a full lapse receives its full new duration from now; a grant within live grace backdates only as specified; multiple prepaid successors and an adjustment against an expired target resolve from current state rather than stale stored flags.

## R4-D4 — P1: Applied-grant replay does not recover a missing shipment/lifecycle alarm

High confidence; implementation-ready; depends on D1's atomic commit. Paid apply inserts grant/outbox (`1820–1859`) and then awaits a D1 paid-velocity read (`1869–1872`), before scheduling its first alarm (`1887–1889`). D1 failure there leaves a complete grant and pending outbox without a scheduled alarm. On retry, local idempotency returns immediately (`1611–1616`), so neither shipment nor the term boundary is rearmed. Separate `syncAlarm:1011–1020` trusts hot.next_alarm_at rather than actual alarm presence, and callers write that field before awaiting setAlarm, creating another unrepaired scheduling gap. The clinic can have a valid applied receipt but no D1/feed/R2 record or automatic lifecycle progression until an unrelated operation repairs it.

**Fix steps**
1. Before committing a new grant, await a durable near-term wake-up alarm; only after successful prearming commit D1's grant transaction. A crash after prearm but before commit may cause a harmless empty wake-up. Do not put the D1 velocity read between commit and this wake-up guarantee.
2. Change `scheduleCoverageAlarm`/`syncAlarm` and both successful/replay exits of `applyGrantRPC` to reconcile desired time against `storage.getAlarm()`, and set/rearm whenever actual alarm is absent or later than needed. hot.next_alarm_at is a cache of desired state, not evidence that setAlarm succeeded.
3. Move paid velocity observation to durable outbox processing (or make its failure retryable without abandoning the already scheduled wake-up). Keep the original grant receipt immutable and return already_applied only after pending outbox/boundary work has a durable wake-up. Apply shared scheduling behavior to complimentary/adjustment finalize paths.
4. Completion: a D1 outage after grant commit, lost setAlarm reply, process reset and same-grant replay all leave the complete grant plus an eventual shipment/boundary wake-up; no extra value or receipt appears. R9 must retain this requirement in alarm/rebuild recovery.

## R4-D5 — P2: The per-org 90-day complimentary ceiling resets with its installation

High confidence; source defect; implementation-ready with the platform global routing/claim remedy as a prerequisite. `windowGrantRows:1087–1100` reads only the current installation DO's grant table, while 070:1 / 03 §3.2 requires all qualifying grants for the org. Supporting transfer code creates destination grant rows only as source_kind transfer (`3160,3229–3237`) and retains no historical complimentary/adjustment contributions; `contributionFromGrantRow:1109–1138` ignores those transfer rows. A same-org transfer or identity recreation therefore resets the history used by the next complimentary grant, even while the original grant remains inside 90 days. Two 31-day grants followed by transfer can admit a further 31-day grant without the separately approved override. HP authorization is still needed, so this is a bounded policy bypass, not unauthenticated minting. Full transfer lifecycle review remains R6.

**Fix steps**
1. After the platform reviewer's permanent grant→org/installation claim/routing fix, add a forward D1 migration for durable per-org complimentary ceiling claims keyed by grant_id and bound to envelope_sha256. Store org_id, original plan/version and its immutable allowance denominator, day/allowance contributions, claim status (pending/applied/sealed_no_effect), signed apply/no-effect receipt and actual applied_at. Preserve claims across installation epochs; backfill existing contributions from authoritative DO grant envelopes and verified receipts, and fail closed for an org whose 90-day history cannot yet be established. R9 export/rebuild must retain this history before enabling grants on rebuilt state.
2. In `vendor/entrypoint.ts` complimentary/adjustment grant authorization, atomically reserve the claim with the per-org ceiling sum in D1 using a transaction/trigger-backed conditional insert. Count applied claims whose actual applied_at is in `(now-window, now]`, plus **all pending claims regardless of reservation age**. An identical grant/hash reuses one reservation; a differing hash conflicts. Do not replace the sums with a stale asynchronous grant_ledger read. Retain existing per-grant validation and the R2-corrected second-approval override path.
3. Pass the exact immutable claim identity/contributions to `applyGrantRPC`; require the bound original installation and commit it with D1's grant transaction. Finalize the D1 claim as applied only from a verified matching signed receipt, using receipt.applied_at rather than reservation time. Until that finalization, leave the full amount pending/reserved so a lost reply, long outage or transfer cannot age it out or create a second budget slot. A later retry must validate the reservation against its actual application window before the local commit; the existing pending contribution remains counted once.
4. Release a pending reservation only after the originally bound DO atomically writes a durable terminal no-effect seal for that grant/hash and returns its signed seal; every future delayed apply must reject that seal. Update D1 to sealed_no_effect only after verifying that exact receipt. A local timeout or missing reply is never sufficient to release value. This uses the same grant routing/fencing authority as global replay and prevents cancellation racing delayed application.
5. Remove installation-local history as the authoritative window check in `grantExceedsCeiling` while keeping its pure per-grant arithmetic. Transfer/recreation consumers preserve org claim identity; imported transfer grants contribute zero additional complimentary value and never erase original claims. Completion: 31+31 days then transfer/recreation still rejects a further day without override; a failed pending claim remains reserved past 90 days until signed resolution; lost replies/retries count once; a sealed no-effect call can never apply later. Allowance months use each original plan's denominator, so changing plan versions does not reinterpret prior claims.
