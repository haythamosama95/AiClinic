## Finding for consolidation: P2 accepted billing refusals omit negotiated version

The final `auth_internal.issue_billing_token(integer)` override in `backend/supabase/migrations/20261014170000_canonical_billing_jwt_json.sql:107,112,123,139,149,158,243` calls `public.rpc_error` without its third argument. The actual final helper in `20261007180000_issuer_key_custody.sql:210–221` defaults that argument to **NULL**. A doctor calling the public billing mint with accepted version 1 (or 0) therefore receives `FORBIDDEN_ROLE` with `contract_version=NULL`; missing branch, unavailable key and session failures likewise lose the accepted version. The public gate at `issuer_key_custody.sql:1311–1333` correctly admits 0/1 and passes the version onward, so it does not repair the response. Success and rate-limit branches correctly pass the argument.

This violates the response-version agreement for the backend RPC channel (04 §§3.1,7), including the ordinary forbidden-role refusal. It does not issue an unauthorized token. `BillingTokenClient._callMint` (`frontend/lib/features/ai/billing/billing_token_client.dart:75–112`) parses this response through `RpcResult`, whose parser (`frontend/lib/core/rpc/rpc_result.dart:1–39`) discards `contract_version`, so the present UI does not catch the protocol loss. Consolidate with other negotiated-refusal echo defects found by the phase coordinator.

**Fix:** add a forward migration overriding the final billing issuer and pass `p_contract_version` to every listed `rpc_error`, including the session exception branch; retain all canonicalization, authorization, signing and throttle behavior. Keep unsupported requests refused by the public gate before internal authentication. Acceptance criteria: each permitted version 0/1 is preserved on success, forbidden-role, inactive/missing staff, missing branch, missing key, rate limit and expired session; missing/outside-pair version returns the existing current-version unsupported envelope. No historical migration edit alone suffices.

## R1-C1 propagation, no duplicate finding

`validateTokenClaims` checks canonical JWT header `{alg,kid,typ:"JWT"}`, canonical payload, Ed25519 signature, issuer, `ver="2"`, audience-specific allowlists, UUID JTI and finite lifetime limits, but never the current time. The two production callers are `abo/src/clinic-api/auth.ts:261–277` and `ai-platform/src/worker.ts:2234–2245`; both accept helper success without a time comparison. R1-C1 remains canonical. Its required clock/skew arguments must reach both sites; billing's later signature-only fallback returns refusal and must remain refusal. This is an implementation handoff, not a second P1.

The final SQL billing and feed overrides use the restricted ASCII-key/safe-integer canonical encoder (`canonical_billing_jwt_json.sql:5–73`; billing claim construction 184–203; `canonical_feed_jwt_json.sql:1–76`). Those claims fit its restrictions and match the shared verifier's strict profile. AI's final issuer still signs PostgreSQL `jsonb::text` (`issuer_key_custody.sql:1060–1084`), which includes spaces/order unlike JCS. Its actual custom verifier (`ai-platform/src/identity/index.ts:395–510`) verifies the original signed segments without requiring canonical byte equality. Do **not** replace that path with the strict shared helper during C1 remediation: it would reject legitimate SQL AI tokens.

Custom AI verification accepts exact `now=exp+skew` (`identity/index.ts:444–447`); R1's proposed strict `exp > now-skew` refuses that equality. This one-second boundary discrepancy is bounded and requires an authentic token; normalize deliberately if sharing a time helper. The AI parser also permits unknown keys and omits JWT `typ` enforcement, unlike strict billing/feed. The fixed SQL producer emits the expected fields, no caller-controlled signing surface was established, and no independent authority bypass is asserted from this profile difference.

Supporting actual calls at platform `entrypoint.ts:1203–1210,1393–1400,1430–1437` and ABO `ops/index.ts:498–505` were read; common ceremony authority is owned by the platform/ABO phase siblings. Access verifies RS256 signature, issuer, audience, expiry and email; both actual callers supply their configured team issuer/audience and clock. No untrusted cert URL is derived from the token.
- `validateReceipt` only models grant/reversal, whereas actual transfer receipt producer `quota-do/coverage.ts:3045–3074` uses `transfer_id` per amended 04 §1.6. No production call of `validateReceipt`/`validateResultEnvelope` was found (only their internal package composition), and `verifyReceiptSignature` accepts transfer signed bytes. Therefore no currently failing transfer consumer is established. R6 must avoid introducing the incomplete shape validator as a transfer gate without extending it.
- `ulid` encodes 128-bit bytes using trailing base32 padding rather than ULID's leading two bits. Production callers treat resulting IDs as opaque strings; no production standards-based ULID decoder/rejecting consumer was found, so this formal discrepancy is not promoted to a finding. Subscription-ref hash/base32 prefix agrees with SQL's separate implementation (`read_time_status_notices.sql:398–417`).
- Package root exports production modules only; testkit is a separate subpath. Package has no runtime dependencies. Loose integer/sign/string checks in shape validators are not independently sufficient findings where downstream policy validates values; R4/R6 retain grant amounts/durations/ceiling and lineage review.
