## R3-PR2 — P1: callback-less inquiry cannot discover the paid transaction

High confidence in missing source mechanism; remedy **not fully implementation-ready** until provider inquiry response/discovery contract is resolved. `client.ts:47–52,175–194` retains only order id/amount/currency from order inquiry. `adapter.ts:730–739` then selects a callback transaction id, stored `paymob_txn`, or the hardcoded transaction `99001`. It never derives a transaction id from the current order response and returns at most one transaction (`767`). For an ordinary paid checkout whose callbacks never arrived, neither callback evidence nor paymob_txn exists: every sweep retrieves transaction 99001 rather than that checkout's successful transaction. Missing/unrelated 99001 gives retry or unbound; the paid checkout remains unconfirmed. This violates the FM-02 blocked-callback recovery path and impairs FM-01 crash recovery before durable intake. Merely deleting the magic fallback cannot restore recovery. Multiple successes are also undiscoverable from one callback; coordinator owns the related paid-state early-exit finding.

Fix steps:

If no validated callback/stored transaction identity exists, return an explicit discovery-unavailable retry outcome, leave confirmation/sweep work durable and due, and raise an operator-visible recovery alert once per checkout; never synthesize a failed or empty-complete payment result. This contains false inquiry without claiming to restore callback-less discovery.
2. **Decision owner: maintainer/provider integration owner, with frontier reviewer validation.** Resolve the existing R-2 question: specify the authoritative order-scoped API response that enumerates transaction identities and its pagination/completeness semantics. Source review does not authorize live research or invent a response shape. Stop before implementing guessed fields.
3. Once resolved, extend the client response decoder to retain validated transaction identities and map every relevant transaction for the persisted order; use callback hints only to select/prioritize a known transaction, never as the sole discovery source.
4. A temporarily unavailable/incomplete response must remain retryable, distinguishable from a complete order with no transactions.
5. Apply stored-order binding to each returned transaction, return all successes/reversals required by the port, and reconcile payment_id queries to the exact requested parent payment instead of whichever callback is latest.
6. Coordinate runner/sweep consumers to process the complete set with payment-id idempotency (including another successful charge on an already-paid checkout). Completion: paid checkout with zero callbacks is discoverable; an order with two success IDs preserves both facts; unrelated transaction/order is refused. ## R3-PR3 — P1: cap 2 is bypassed, raced and consumed by unrelated work

Escalation 080:3 requires one shared per-minute cap of 2 and confirmation/grant priority. Current accounting occurs only after operations and uses each scheduler's stale local `spent` (`inquiry-budget.ts:39–67,148–176,202–215`). Concurrent inline/cron runs can both read remaining capacity and both inquire; first-row creation also races a plain INSERT. The production inline callback path runs `runConfirmForWorkId` **before** any budget check (`intake.ts:466–472`). A burst of distinct valid callbacks thus bypasses the cap entirely.

Even a single scheduler miscounts: `sweep.ts:288,361` inquires then runs a confirm that inquires again; runner's no-notification branch `864,885–897` inquires then calls `confirmSuccessBatch` whose inquiry is at `535`. Both count as one boolean result. All actual HTTP request counts also exceed logical inquiry count because each adapter inquiry performs order and transaction requests (plus optional auth); the established escalation states provider inquiries, not an independently specified per-HTTP cap.

Reuse a completed authoritative inquiry within sweep-to-confirm and no-notification confirmation via a typed internal confirmation function; do not repeat HTTP calls merely to enter the payment commit path. Remove unused `runDueConfirmWork` bypass or ensure its inquiries use the shared boundary too.
4. Serve confirmation rows first, grant work independently (no fabricated provider spend), then reversal/sweep inquiries. Keep deferred work open/due. Preserve the existing meaning of one logical provider inquiry reservation; if external provider rate is per HTTP request, maintainer must explicitly amend the cost contract and configure the cap accordingly rather than silently infer it.

Completion: simultaneous inline/cron/rebuild calls admit at most two logical inquiries per minute; process failure cannot unspend an attempt; nested confirmation does not double-inquire; grants do not consume Paymob quota; two reversal retries cannot displace pending confirmation; overflow work remains due.

## R3-PR4 — P2: notify cap counts UTF-16 characters after reading the entire body

High confidence; implementation-ready. Intake `329–332` uses `request.text()` then `body.length > 1_048_576`. Contract 078:1 is a byte cap. A JSON payload containing multibyte UTF-8 text can exceed 1 MiB while remaining below 1,048,576 UTF-16 units and proceed into R2/D1 intake. The entire unbounded body is also allocated before refusal. This is a bounded ingress/resource and explicit contract defect; no payment forgery follows from it.

Fix steps:
1. Replace the text-first body read with a streaming byte reader that stops/cancels after MAX_NOTIFY_BODY_BYTES+1 bytes; Content-Length may fast-refuse but cannot be authority.
2. Return the existing empty 413 before rate/evidence/work writes on overflow; decode UTF-8 once only after bounded reading succeeds and preserve exact valid body bytes for its evidence hash.
3. Completion: exactly 1 MiB accepted for parsing; one extra byte refused for ASCII or multibyte UTF-8; oversized body enqueues/stores nothing.
