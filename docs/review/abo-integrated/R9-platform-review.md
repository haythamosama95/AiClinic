## R9-PDO1 — P1: rebuild can erase newer authoritative coverage and leave a partial replacement live

**High-confidence source defect; forward recipe implementation-ready, historical repair requires adjudication.** `ai-platform/src/quota-do/coverage.ts:3847–3889` chooses the latest *shipped* event, unconditionally wipes existing DO state (`3298–3302`), hydrates it, then awaits D1/R2 reads. There is no empty-DO precondition, recovery generation/fence or atomic replacement transaction. If a grant has committed locally after that event but its outbox has not shipped, this H call erases its term, grant receipt and only pending outbox. Retrying its original grant can add value again; an interrupted R2 read can instead leave the old snapshot active with an incomplete grant dedupe table. `blockConcurrencyWhile` serializes concurrent calls; it does not roll back already committed writes across remote awaits. Successful rebuild also sets `next_alarm_at=NULL` (`3497`) without scheduling a boundary/outbox alarm before returning (`3975–3986`). Mirror comparison happens after installation (`4137–4145`) and mismatch only creates an alert row. This violates 03 §1 DO authority and 05 §5.2's reconstruction into an **empty** DO.

**Fix steps**

1. In `rebuildClinicDoRPC`, refuse replacement if any authoritative hot/term/grant/outbox state exists, except an explicitly persisted continuation of this same recovery generation. Preserve a damaged nonempty DO for maintainer/frontier evidence adjudication; never offer a generic force-wipe H flag. Recover a separate verified candidate before choosing how to repair it.
2. For an actually empty target, persist `recovery_state(generation, installation, org, epoch, anchor, status)` in a forward DO schema change (`quota-do/index.ts`); reject admissions/value mutations while this marker is building or blocked. Read every needed D1/R2 object and validate coherent identity/epoch, receipts, grants/voids and usage into a candidate before modifying hot/term/grant/outbox. Preserve historical `suspend`/`resume` aliases and original signed versions/bytes.
3. Prearm a durable wake-up using R4-D4's actual-alarm reconciliation. Install the complete candidate and its recovery completion marker in one synchronous SQLite transaction; include replay/seal/accepted-command state from canonical R4/R6 repairs. Errors leave the empty fenced target or the previous complete generation, never partial usable coverage. Apply due boundaries and arm the earliest boundary/outbox wake-up before lifting the fence.
4. Compare the candidate against durable witnesses before activation; a mismatch or unresolved old/new epoch stops recovery and alerts. Completion: an unshipped grant on a nonempty DO is preserved/refused, failures during every external read expose no partial candidate, retry is generation-idempotent, and a recovered idle term still advances by alarm. Missing original receipts/history is a maintainer/frontier stop, not permission to mint replacement value.

## R9-PUS1 — P1: wall-clock replay can charge usage already included in the anchor snapshot

**High confidence; implementation-ready for new facts; historical ordering is not inferable.** `reapplyUsageEventsAfterSnapshot` queries `usage_event.recorded_at >= anchor.at` (`coverage.ts:3573–3586`) and only tries to subtract snapshot usage when timestamps are exactly equal (`3596–3605`). The snapshot's counter includes DO settlement, but Worker takes the journal timestamp **after** `creditUsage` returns (`worker.ts:779–809`). A concurrent grant/suspension/snapshot can capture that settled counter before the reply/journal timestamp is taken. On rebuild the later-stamped row is added again. Conversely a delayed journal and older event timestamp do not establish whether the snapshot contains the charge. `normalizeCoverageSnapshotForMirrorCompare` deliberately deletes used/used_final/band (`4057–4081`), so the command can report clean with the wrong remaining allowance. This is independent of R5's original-term settlement defects.

**Fix steps**

1. Add monotonic per-installation `accounting_seq` to DO hot state and immutable settlement facts, committing each authoritative charge/release and its stable request/term identity plus outbox intent atomically under the R4/R5 transaction remedies. Include the committed accounting watermark in each event snapshot. Give fallback draining the same final authoritative accounting identity; do not use journal arrival order.
2. Add compatible D1 usage fields for origin request identity and accounting sequence, uniqueness on `(installation_id, accounting_seq)` and stable origin request identity. Update DO usage-adjustment shipment, `journal.persistPostResponseDetail`, credit/Worker settlement replies and stored-version decoders together: the journal enriches the same accounting fact rather than introducing a second charge.
3. Rebuild counters from the snapshot watermark plus only authoritative accounting facts with a greater sequence, once each, by their original term. Remove timestamp-equality subtraction. Detect sequence gaps and conflicting identity/weight before activation; preserve uncharged/released outcomes explicitly so R5-J1 cannot manufacture charges.
4. Completion: settle → intervening snapshot → delayed reply/journal restores the original used value, equal-millisecond requests remain separate, late original-term settlements remain on that term, and replaying the same candidate adds nothing twice. Old rows without a provable watermark need maintainer/frontier reconciliation from retained receipts/intents; stop the affected recovery rather than guessing from dates or totals.

## R9-PRET1 — P1: journal expiry destroys retained usage identity and rebuild collapses multiple charges

**High confidence; forward recipe implementation-ready.** `retention/index.ts:210–236` nulls usage request IDs before deleting 90-day journal rows; the FK also uses `ON DELETE SET NULL` (`migrations/20261006120000_usage_term.sql:5–16`). For a still-active annual term whose last coverage event predates those requests, only its first aged usage row is restored; paid allowance is recreated. The journal uniqueness index also ceases protecting these rows. The seven-year usage purge (`retention:242–245`) has no unended-term exception despite 03 §8; long-held/repeatedly extended histories must not rely on age alone. Installation purge preserves selected unended usage rows (`314–374`) but cascades their request joins away too. The retained request linkage is operational identity, not payment data.

**Fix steps**

1. Before enabling purge, deploy PUS1's stable accounting/origin identity fields independent of the erasable journal FK. Backfill non-NULL origin IDs from existing rows. For already-NULL rows retain their distinct `usage_event_id`; do not synthesize a shared empty identity or infer request identity. Do not deduplicate NULL IDs during recovery; with the current unique request index each usage row is already a distinct durable fact, and `usage_event_id` is the safe row key.
2. Change `runRetentionPurge`/`purgeByInstallationId` so journal erasure can remove the FK without erasing accounting identity. Rebuild uses accounting sequence/usage event identity and never nullable request_id as its Set key. Ship D1 schema first, all writers/readers second, then resume purge.
3. Add a durable term-retention checkpoint keyed by installation/term, updated from authoritative term-ended evidence. Purge usage only when older than the ledger horizon **and proven ended**; absent/unknown status preserves it. Held/queued/active/grace rows and pending accounting intents stay recoverable; final deletion must not remove global seals/claims.
4. Completion: multiple aged request rows on one unended term contribute separately and exactly once after journal deletion; installation contact/journal erasure preserves those counters; an unknown/held old term is not age-purged. Historical accounting ambiguity follows PUS1's adjudication stop; distinct existing usage IDs remain evidence.

Keep repeat scheduling/reopening distinct from one-shot event identity. 3. AL-13 retries must reuse stored original operation/actor/signer/version. Concurrent cron ticks do not own the same lease; a successfully sent one-shot is not resent by ordinary retry, and recurring conditions can become active again after resolution.
