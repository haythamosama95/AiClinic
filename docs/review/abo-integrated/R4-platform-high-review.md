## Source-established behavior

A paid request carries the immutable canonical ABO envelope and a current service-key signature. The platform checks the named key's active status and finite validity, verifies the exact JWS payload bytes, applies published plan/duration/allowance/grace restrictions, resolves a live tenant binding, checks a D1 void tombstone and dispatches to that installation's DO. Plan content is copied into `{plan_id, version, display_name, capabilities, max_cost_class, concurrency_limit}`; the DO stores the snapshot, rather than reading the plan again during later use. Republishing the same plan/version checks content without unretiring it; retirement changes only status.

Complimentary requests require Access plus a fresh main HP assertion. The existing completion shortcut hashes the envelope and scans grants in the **currently resolved** DO. Main assertion verification uses `args.signer_credential_id`, current credential state and the exact operation; consumption/audit occur before `apply_grant`. The envelope's evidence credential is a separate, unchecked input.

The DO signs an `applied` receipt with its grant id, org, installation, term ids, application time, grant event's clinic sequence and canonical envelope hash. Local matching retries return that original receipt (whose signed `result` remains `applied`). D1 grant ledger and R2 NDJSON are asynchronous copies; their global keys do not constrain the preceding DO mutation. ABO distinguishes transport exceptions/transient results (retry) from rejected/conflict (park), which makes the platform's failure classification consequential.

Inherited roots remain canonical: **R1-C2** covers atomic epoch-1 binding cap and all binding writers; **R2-P2** covers the second ceiling override's binding; **R2-C2/C3** cover negotiated metadata and strict decoders. R3-C5/C6 qualify exactly-once eligible payment production. They are not counted here.

## R4-PG1 — P1: grant identity is lost when the live installation changes

**High confidence; implementation-ready.** Invariant: a deterministic grant id plus content identifies one commercial grant, with its original receipt, across transfer/recreation (04 §§1.2–1.4; NFR-02/03). Paid `grant` resolves the **current** binding (`ai-platform/src/vendor/entrypoint.ts:3621–3648`); complimentary replay also resolves the current binding (`1452–1517`). The actual dedupe is only the selected DO's `grant` table (`quota-do/coverage.ts:1603–1619`; schema `quota-do/index.ts:1960–1971`). Transfer imports retain origin lineage but create distinct transfer grant ids (`coverage.ts:3157–3160,3178,3227–3250`). Therefore: original grant applies; its reply is lost; a same-org transfer completes; original grant retries and is absent from the destination's grant table, so another full term is created alongside moved value. A changed envelope with that original id also escapes cross-installation conflict detection. Normal transport retry and authorized transfer suffice; no key compromise is required.

The global D1 PK is only applied later with `INSERT OR IGNORE` (`coverage.ts:2715–2734`), so it silently retains the earlier ledger copy while the second DO has already created coverage. R2 objects are keyed by grant id and similarly preserve an earlier copy (`2736–2753`). The problem is not solved by querying that eventual mirror before dispatch. The optional paid `installation_id` override (`entrypoint.ts:3626–3641`) additionally accepts a historical binding without an active-status predicate and must not become a route around global ownership.

**Related replay conflict, included in this root:** published-plan checks precede all replay (`3271–3273,3553–3555`), so a successful lost reply followed by retirement becomes `plan_not_published` rather than returning its receipt. The contract's unconditional validation-order wording conflicts with its original-receipt/idempotency promise. Resolve by making that order apply to **new application**, while authenticated exact replay returns the original completed fact. Never newly apply a retired plan.

**Fix steps**

1. Add a forward platform D1 migration for `grant_claim`, globally keyed by `grant_id`, containing immutable org/source/canonical envelope/hash, current route installation/epoch/generation and optional completed receipt. Preserve the DO as coverage authority: this row is routing/idempotency metadata. Before enabling new dispatch, backfill from retained DO grants and their ledger copies; fail closed and alert on differing identities/receipts instead of choosing a winner or recreating value. Include these rows in R9 rebuild/retention.
2. In `VendorEntrypoint.grant` and `tryComplimentaryGrantIdempotency`, authenticate the paid caller/current signature or human Access, validate/hash the supplied envelope, then atomically insert/read the claim before any DO application. Existing different org/hash is `conflict`; matching completed claim returns its **original** receipt before mutable plan/policy/live-binding checks. Matching pending claim dispatches only to its stored route. New claims require the normal current plan/policy/authorization checks. Remove client-controlled `installation_id` routing; internal replay uses the claim. Current signing-key auth still applies, so old envelopes can be re-signed by a rotated active ABO key.
3. In `applyGrantRPC`, check a local matching completed grant before `awaiting_transfer`/`transferred_out` rejection; this is read-only replay. Add a serialized `seal_grant_route` DO RPC and local persistent seal table keyed by grant id/hash/generation: if the original grant exists, return its receipt; otherwise record a no-effect seal atomically before replying. Every later old-route apply of that id must honor the seal. Wire/schema this in `quota-do/index.ts`, `quota-do/coverage.ts` and Worker RPC dispatch. A transfer flag alone is insufficient for deletion with no remaining coverage (`coverage/transfer.ts:679–687` leaves no DO terminal flag).
4. A pending claim whose installation is retired may move only after that old DO has returned a persisted seal/no-existing-grant proof. CAS the claim's exact old route/generation to the current live binding and increment generation; dispatch the new route only after winning/reloading that CAS. Source outage/unknown outcome means retry/alert, never reroute. A late old request is rejected by its durable seal; an earlier committed request returns its original receipt and prevents moving. This also covers a claimed request that had not applied when transfer began.
5. After DO success, require returned org/grant/hash/installation to match the claim route, then persist the original receipt; a crash before this D1 write is recovered by reading the same DO fact. Keep ledger/R2 asynchronous, but compare existing identity/receipt on collision and retain/alert discrepancies rather than silently discarding them. Transfer-generated grant ids must enter the same global namespace; origin lineage remains separate.
6. Completion: lost receipt before/after transfer, deletion/recreation, and plan retirement returns one original grant/receipt; changed content conflicts globally; concurrent new claims create one route; crashes on either side of sealing/CAS never let two DOs apply; an original no-effect pending claim eventually applies once on the new live identity. Deploy receiver/schema/seal support before enabling the new dispatcher. Amend 04's validation-order/replay exception together with source; no new service or queue is required.

## R4-PG2 — P1: ordinary DO unavailability permanently parks paid grants

**High confidence; implementation-ready.** `callCoverageDo` returns null for fetch exceptions, non-success HTTP and JSON/transport failure (`entrypoint.ts:603–625`). Paid grant maps null to `rejected/coverage_unknown` (`3689–3690`), as does complimentary grant (`3464–3465`). ABO persists a rejected outcome and parks the paid work (`abo/src/work/grant.ts:886–919`), while only `transient`/thrown calls reach backoff (`767–775`). A brief single-clinic DO outage therefore converts a valid paid purchase into manual recovery, violating 04 §1.2 and FM-04. A lost DO reply may also hide an already applied grant; rejection does not prove no effect.

**Fix steps**

1. In both grant branches return `grantTransient(version, 'unavailable')` on null transport. After R2-C3's strict decoder integration, preserve this classification for transport-unavailable/unknown outcome; retain explicit version refusal and actual validation rejection as their documented outcomes.
2. Keep the exact immutable grant id/envelope on all retries. Recover possible prior application through PG1's claim/original-receipt path; do not generate a replacement grant id. For complimentary requests implement PG3's durable accepted command before relying on transient retry.
3. Completion: DO 5xx/timeout/disconnect before or after commit leaves paid work open with bounded backoff and AL-04, then completes once; a malformed authorization/plan and unsupported negotiated version still follow their intentional refusal paths. No `grant_outcome=rejected` is appended solely because transport failed.

## R4-PG3 — P1: a complimentary touch can be consumed without an accepted grant

**High confidence; implementation-ready after PG1 and R2-P2.** The completion shortcut returns only when a DO grant already exists (`1452–1517`). `finishHpAssertion` inserts the single-use marker and then writes audit (`1290–1303`); complimentary `grant` calls it before binding/tombstone checks and DO dispatch (`3365–3427`). A crash/audit failure after insertion, or DO unavailability before application, leaves a consumed assertion with no grant. Matching retries find no DO grant and fail `assertion_used` (`1253–1258`); after five minutes they fail freshness too. There is no durable accepted command that can resume without another operator touch. The inline ABO relay forwards once (`abo/src/ops/index.ts:2689`) and does not itself establish platform command acceptance. This is the R2 handoff's unclosed consume-without-apply window, distinct from R2-P2's second-assertion binding.

**Fix steps**

1. Extend PG1's claim with human authorization state: exact validated operation/envelope, verified actor/signer, main/override challenge hashes, validated plan snapshot and accepted contract version, plus due/lease/result fields. After full HP checks, atomically batch acceptance, both single-use claims (when overriding), and audit in platform D1. Reuse R2-P2's correctly bound second digest; a failed acceptance batch consumes neither challenge. Perform binding creation and DO dispatch only after durable acceptance.
2. On an exact accepted-command retry under current Access, resume stored authorization rather than checking the already consumed assertion's freshness again. Different envelope/org/hash conflicts. Missing/revoked authorization on a **new** command still fails. Do not silently rewrite accepted bytes/version, and do not treat accepted authorization as proof that coverage exists.
3. Add an indexed, bounded due-accepted-command dispatcher using D1 conditional lease tokens, invoked by the existing five-minute Worker scheduled path (`worker.ts:2584–2598`) and the immediate request. It calls the same PG1 route/replay path, retries unavailable/transfer-pending state, and stores verified original receipt or terminal business refusal. Current activation time is the actual DO apply time. Failed audit/response delivery cannot erase the durable accepted command; source outage never consumes a new touch.
4. Completion: crash after every acceptance/dispatch/reply boundary leaves either no consumed approval or a resumable accepted command; the original touch produces at most one grant even after five minutes; concurrent retries cannot authorize altered bytes or consume only the first of an override pair. Actual ceiling/plan failures before acceptance require corrected fresh authorization; a pending accepted command cannot bypass DO ceilings/tombstones.

## R4-PG4 — P1: grant containment is indexed under an unverified credential

**High confidence; implementation-ready.** The main HP verifier loads/verifies `args.signer_credential_id` and returns `check.signer` (`entrypoint.ts:1132–1134,1183–1209,1281–1286`). Yet the complimentary branch sends `operatorCredentialId` taken from `envelope.evidence.approvals[0].credential_id` (`3398–3405,3444`). Shared `validateApproval` merely checks that credential/assertion are strings (`packages/vendor-contracts/src/grant-envelope.ts:80–95`); it never verifies that element or compares it with the actual signer. The DO copies the supplied credential into its ledger outbox (`quota-do/coverage.ts:1273–1283`), and D1 persists it (`2717–2733`). Both `listGrants` and `listGrantsForVoid` filter this field (`entrypoint.ts:4615–4617,4416–4425`).

A compromised relay substituting the operation behind a legitimate touch, or a hijacked session plus stolen key/PIN, can put another/unknown credential in evidence and obtain coverage that is omitted from list-and-void for the actually leaked key. This defeats the explicit AD-8/AD-12/SR-25 containment, not the HP touch itself. Audit has the actual challenge but the required grant index is false.

**Fix steps**

1. In the complimentary/adjustment branch set `operatorCredentialId = check.signer.credential_id`; reject a supplied primary evidence credential that differs. Keep actual verified actor/challenge in accepted-command metadata and use the verified actor for operator attribution, rather than trusting an independent source email. Do not change paid operation-object approvals into passkey requirements.
2. Carry the verified credential unchanged through PG3's accepted-command dispatcher, DO ledger outbox, D1 grant ledger and R2 record; include that binding in replay/claim consistency checks. Override authorization keeps its separately verified digest/signer metadata per R2-P2.
3. For already stored discrepant rows, produce an explicit correction/containment index from platform audit/accepted authorization where linkage is provable; preserve immutable signed receipts and historical ledger/R2 objects. Ambiguous old entries must remain flagged for expanded incident lookup, never silently attributed to a guessed credential. No source-only review can establish whether affected deployed rows exist.
4. Completion: a valid assertion under credential A with evidence naming B cannot create a B-attributed grant; every newly accepted A grant appears in the credential/time-window containment query, including after retry or delayed dispatch. Paid automatic grants retain their intentionally empty credential attribution.
