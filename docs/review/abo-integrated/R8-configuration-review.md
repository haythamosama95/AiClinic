## R8-C1 — P1: losing publication can overwrite the winning routing document

**High confidence, implementation-ready.** `control/routing-policy.ts:155–169` derives a shared key from policy ID/version, checks D1 absence and writes R2 unconditionally. Only afterwards does the PK-protected D1 batch arbitrate (`171–189`). Two requests with different documents for an initially absent pair can both pass SELECT: A writes object A and wins D1; B writes object B and receives already_published. The successful row and audit still point to B's bytes. `config-cache/index.ts:185–203,367–412` loads those bytes without a content hash. On refresh an active winner can silently route with the rejected publisher's configuration, or fail router validation; audit attributes the effective bytes to the wrong accepted publication. This is a source-proved integrity/recovery defect, not a claimed runtime reproduction.

**Fix steps**
1. In `publishRoutingPolicyAction`, serialize validated content once, hash the exact bytes, and use a content-addressed immutable R2 key (include digest, with encoded identity or digest-only path). Store that exact pointer on the inserted D1 row; two different contents must never share an object key.
2. Retain insert+audit in one D1 batch. On a losing PK conflict do not replace/delete the winning row's object; orphan content may be cleaned separately after proving no reference. Compare stored digest/pointer if distinguishing exact retry from conflict.
3. In `loadRoutingPolicyDocument`, verify content hash/identity before returning a row; retain a compatibility branch for existing pointers until migrated or republished. Historical unknown winner content requires operator re-publication as a new version, not guessed repair.
4. Completion: concurrent different publications leave the winner's exact bytes and audit stable; rejected publication has no runtime effect; missing/tampered content fails closed with an explicit configuration error.

## R8-C2 — P1: accepted routing publication can activate an unusable document globally

**High confidence, implementation-ready.** Publication accepts `{policy_id,policy_version}` without schema/rules/overrides (`routing-policy.ts:140–149`) and warns rather than validates (`192–193`). `promoteRoutingPolicyAction:278–321` checks only status. Runtime router dereferences `document.rules` and `document.overrides` and validates schema/catch-all only at invocation (`router/index.ts:243–270,617–624`). A mistyped or incomplete authenticated publish followed by promotion returns success, supersedes working configuration and breaks every clinic using that policy. Existing H authority to intentionally stop service does not justify reporting a broken document as successfully deployable.

**Fix steps**
1. Add a shared pure parser/validator in the routing module and call it in `publishRoutingPolicyAction` before any R2/D1 write. Validate supported schema_version, identity, defaults, nonempty rules ending in catch-all, match/requires/targets field shapes, numeric bounds and overrides (including valid cost classes and string arrays). Return invalid_policy_document with no publication on failure.
2. Reuse that parser at runtime rather than relying on TypeScript casts; retain target feature validation when building runtime decisions. Export typed parsed document to avoid two competing shape definitions.
3. In canary/promote, load and validate selected stored bytes before changing serving status; this protects pre-existing malformed published rows. Missing R2 binding/object or invalid document leaves the old serving version unchanged.
4. Completion: identity-only, unsupported-schema, missing-rules/overrides and invalid target documents cannot become published/serving; a valid catch-all document preserves normal canary/promotion behavior. These are future acceptance criteria, not tests performed.

## R8-C3 — P2: rollback can activate a never-active canary instead of the actual predecessor

**High confidence, implementation-ready.** `active_from` is assigned at publication (`routing-policy.ts:154,177–178`) and never updated by promotion. Promotion marks both old active and every other canary superseded (`306–321`). Rollback then picks any superseded row ordered by original publication time (`378–384`). Publish A then B then C; promote A, canary C, promote B. A and never-active C become superseded; rollback B activates C. The action advertised as recovery deploys the unpromoted experiment and clears remaining canary membership. Repeated rollback can also toggle based on publication order rather than unwind actual activation history. Migration comment explicitly promises restoration of prior configuration.

**Fix steps**
1. Add a migration with a per-policy activation generation and durable promotion record containing target version and previous active version. Do not infer historical predecessor from publication timestamp; for existing active rows use explicit null/unknown until a new recorded transition.
2. Change promote to atomically compare expected active generation, update serving states, append the predecessor record and audit. A concurrent stale transition returns conflict without writes; transaction assertions/guarded SQL must make zero-change conflicts roll back the batch.
3. Rollback active selects that active generation's recorded predecessor, validates its bytes, then atomically switches to it and records the resulting generation. Keep canary rollback a scoped cancellation and ensure it cannot inadvertently promote another canary.
4. Completion: the A/B/C sequence restores A; publication order and unrelated canaries cannot affect recovery; concurrent promote/rollback yields one recorded order, and unknown historical predecessor returns explicit conflict requiring a chosen new promotion.

## R8-C4 — P2: configuration audit is incomplete and can be permanently lost after a successful mutation

**High confidence, implementation-ready.** Capability lifecycle commits then calls audit (`capability-lifecycle.ts:104–136,179–211`), kill switch does likewise (`kill-switch.ts:132–152,177–194`), rotation begin (`token-contract.ts:24–49`) and installation suspension (`installation-lifecycle.ts:26–32`) do too. A failure between these writes leaves effective configuration without an audit; retries either return early success or illegal transition and do not repair it. Separately, routing/cohort/token-retire inserts omit `actor`, although 03 §3.2 and 05 §3.2 require the Access email there; the nullable migration has no filling trigger. Cohort activation of new installation grants stores neither membership in before nor after (`cohort.ts:192–203`), so even its committed audit cannot identify affected installations. These defects weaken the explicit AD-11 H-action audit guarantee; no cryptographic authorization bypass is asserted.

**Fix steps**
1. Refactor `control/audit.ts` to construct a prepared audit statement with actor and operator_id both equal to verified Access email, explicit before/after values, and optional assertion hash; keep execution inside callers' batches.
2. In lifecycle/kill/rotation/installation handlers, put local D1 mutation and audit in the same batch, conditional on the actual transition. Preserve existing no-op behavior; failure must commit neither, and retry must produce one durable transition audit. Fence expected states where SELECT precedes UPDATE.
3. Update routing/cohort/token-retire batches to populate actor through that helper. Store cohort activation's full canonical selected installation list and each before/after version, including new grants; promote records must include newly created plan/installation scopes too.
4. Keep cross-store DO suspension and AL-19 recovery with the lead/R9 durable-command design; batching D1 alone must not be described as cross-store atomicity. Do not fabricate historical actors/memberships from current state; explicitly retain historical unknowns.
5. Completion: interruption/audit storage failure cannot leave a new local D1 transition unaudited; exact no-op retry does not duplicate transition audit; every new audit has Access actor and reconstructable target set. R9 owns alert/remote recovery after these atomic facts.
