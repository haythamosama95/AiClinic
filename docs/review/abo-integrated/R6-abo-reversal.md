## Traces and invariants

Notification intake stores raw R2 callback evidence and, for an existing payment, calls the reversal recorder before inquiry (`notify/intake.ts:365–429`). The recorder resolves a parent, forms `paymob:<parent>:reversal:<cumulative>`, hashes a deterministic reversal ID, selects an effect, and batches reversal plus fact_log (`reversal.ts:193–243,456–552`). It then closes payment sweeps, alerts, and for inquiry-origin full reversals creates work and calls the platform (`557–571`). Notification reversals instead wait for `processPendingNotificationReversals`: inquiry agreement creates reverse work and calls the same void producer (`625–700,868–900`). Pending/no-result inquiry remains discoverable; a non-reversal disagreement records a finding and is permanently skipped. This dismissal is explicitly described by amended 03 §5.5, so dismissal alone is not raised as a new defect; BR2 addresses continuing independent payment monitoring.

The void producer signs the exact version/grant/reversal/reason/evidence/partial=false body with the current ABO key (`703–746`). Reverse work uses a conditional 60-second lease; transient/missing success replies stay open and retry with one-minute exponential backoff capped at 15 minutes; explicit conflict/rejected or bad signatures park (`747–796,902–1004`). Signing-gate pause prevents taking work; invalid/missing local key leaves open retries. Platform owner confirms exact replay returns outer `already_applied` plus the original signed receipt whose result remains `applied`; tombstones use NIL org/installation, empty term IDs and seq 0. DO owner confirms it resolves actual grant/origin lineage and current state, so a stale ABO `remove_queued` reason after transfer does not select the DO mutation. Reason is immutable audit/replay input. Active/grace becomes ended and queued terms held; queued/held target is removed; ended/exhausted has no service effect.

For reversal-before-grant, intake routes a callback without a payment through confirmation. `runner.ts:652–731` writes a `reversed_before_grant` payment and completed confirm work, then records the reversal separately. Partial-first evidence retries without a payment (`653–661`). The final void/tombstone race and transfer route safety belong to the platform/DO owners and R4-PG1. No assumption that an ABO grant outcome proves the current term location is needed for DO effect selection.

Sweeps materialize checkout timing rows (+2/+5/+10/+20 minutes, rolling to expiry, then +1/+3/+7 days for expired/cancelled), call inquiry, and may invoke confirmation; reversal payment sweeps call the same recorder (`sweep.ts:118–192,253–445`). Payment populations are hourly (first seven days/unapplied), six-hour (live-funded terms), and daily one-seventh of older payments up to 180 days (`481–753`). The shared runner selects due work and enforces its flawed post-hoc cap; R3-C7 remains canonical for cap/priority/concurrency defects.

## BR1 — P1: child/callback evidence can authorize a full void of a partial refund

**High confidence; source defect. Ready containment and source changes; final provider cumulative completeness requires the existing R3-C4 provider decision.** Amended 080:2 / 03 §2.7 requires cumulative from authoritative inquiry, identity of the original payment parent, and `is_full = cumulative >= payment.amount_minor`. `adapter.ts:418–440` instead sets child fullness by comparing cumulative (defaulting to child amount) with the child's own amount; `reversal.ts:535–536` accepts that flag with OR, overriding the correct parent comparison. Example: a successful child refund of 20 against a paid 100, child amount/cumulative 20, is marked full and inquiry-origin processing immediately voids the entire paid grant. `txnKindFromAcceptance:445–455` also classifies a parent-flagged pending child as reversal before checking `pending`, so unsettled reversal evidence can reach that same path.

The callback path compounds this: `adapter.ts:535–547` reads unsigned `refunded_amount_cents`, guesses its parent using local checkout/order history (`471–520`), then intake records it before inquiry. `verifyNotificationReversal:684–690` compares the inquiry parent with the inquiry's own resolved parent, rather than the stored original payment parent; it only requires inquiry cumulative >= callback cumulative and retains the callback-derived effect. Changing an unsigned cumulative can therefore create false commercial facts, poison dedupe/sweep eligibility, or allow a partial inquiry to approve a callback-derived full effect. Correct signature verification of the eventual ABO/platform call does not repair its unsupported business claim.

**Fix steps**
1. In provider `port.ts`, adapter normalization, and intake, represent callback reversal data as an inquiry hint/evidence reference only. Preserve the signed callback transaction ID; do not construct final reversal amount/fullness/dedupe or guess its parent from the first local row. Enqueue durable inquiry work under the C5 atomic acceptance recipe.
2. In `inquireImpl`, bind the hinted child to the stored order, obtain its authenticated `parent_transaction.id`, then query that exact parent and bind it to the same order/payment. Payment-ID inquiry must select that original parent (R3-C4). Return `payment_pending` before reversal for pending results; do not treat a failed child merely having a parent as a completed refund. If authoritative terminal reversal/cumulative cannot be proved, return typed deferred/unknown and preserve due work, never fallback to child amount as cumulative.
3. In `recordReversalFromProviderTxn` and `verifyNotificationReversal`, require the authoritative parent/payment identity to match the durable payment and provider; require finite nonnegative safe-integer cumulative and matching currency. Derive fullness exclusively as cumulative >= original payment.amount_minor, remove the adapter `is_full` override, and construct the dedupe key from that exact parent and authoritative cumulative. Persist the actual `ProviderReversal.kind`. Verification must create/use the authoritative row/effect, rather than approve callback-derived effect by a lower-bound comparison.
4. Commit authoritative inquiry evidence/reference, reversal+fact, required reverse work and current work completion atomically using R3-C5 lease fencing. Preserve incomplete hints separately. Existing callback-derived or ambiguous rows need explicit evidence reconciliation; do not silently rewrite append-only facts or auto-void from historical guesses.
5. Completion: parent resend and child delivery of the same cumulative produce one reversal; 20/100 remains partial with no automatic void; later cumulative 100 creates the full reversal once; pending/failed/unknown data never ends coverage. Parent/payment mismatch cannot void a different payment. **Provider integration owner/frontier stop point:** establish exact terminal parent cumulative availability/completeness and missing-field semantics under R3-C4 before implementing any fallback that asserts money was fully reversed. Ready containment is to defer/alert unknown cases.

**Decision 2026-10-18 ([01 §3.8 D-3](../../architecture/ai-billing-orchestration/01-abo-design-decisions.md#38-decisions-from-the-integrated-review-r10)):** the step-5 stop is resolved. No fallback ever asserts full reversal. Fullness comes only from the authenticated original-parent cumulative, and anything missing or inconsistent takes `review_partial` with an alert, so steps 1–5 are implementation-ready as written. Paymob confirmation of parent `refunded_amount_cents` (01 R-2) affects only how often cases reach operator review, not correctness.

## BR2 — P1: one reversal permanently removes the payment from future discovery

**High confidence; implementation-ready after BR1/C7.** `reversal.ts:557–562` closes all open payment sweeps for any recorded reversal, including partial and unverified notification data. More decisively, `inquiry-budget.ts:101–105` excludes every payment having any reversal from **all** due payment sweeps; `sweep.ts:672–674` also excludes it from six-hour population. Hourly/daily materialization cannot rescue this because their new rows fail the central due predicate. A genuine partial refund followed later by a full refund/chargeback, with its callback lost, is never inquired again, so fully reversed money can retain live paid coverage indefinitely. Even a dismissed callback can disable future discovery.

Separately, `sweep.ts:681–709` uses `seenOrgs`, selecting only the earliest live payment per org from the ordered query. With one active payment and later queued/held prepaid payments older than seven days, the later payments receive at most weekly inquiries instead of six-hour monitoring. The schedule in 05 §1 requires every payment funding active/grace/queued/held coverage.

**Fix steps**
1. Remove the any-reversal anti-join from `dueOpenSweepWork` and six-hour population. A recorded partial/unverified/dismissed reversal must not suppress further authoritative inquiries. Stop closing all payment sweeps in the recorder; complete only the specific work attempt with its verified evidence/next-work batch (C5).
2. Keep daily monitoring to 180 days, even for payments with a recorded reversal; the existing state/cumulative dedupe makes unchanged evidence harmless. Select every live-funded payment in the six-hour pass; remove `seenOrgs` while retaining the per-org coverage-response cache. Missing old term IDs remain conservatively eligible; do not incorrectly infer ended status from the 12-term read limit.
3. Preserve per-payment/per-bucket work dedupe, and run every inquiry through C7's atomic cap reservation; overflow stays due. Removing per-org suppression must not bypass that cap or introduce a second budget.
4. Completion: a partial refund then full refund without another callback is discovered; a dismissed hint cannot disable monitoring; two paid live/queued terms in one org each get a six-hour row. Unchanged cumulative creates no second reversal or void; ended older payments retain weekly coverage through the stated horizon.

## BR3 — P2: provider voids are permanently recorded as refunds

**High confidence; implementation-ready with BR1.** Adapter emits `ProviderReversal.kind = void` (`adapter.ts:425–430,527–532`) and the port allows refund/void/chargeback/unknown, but `insertReversalRow` hardcodes `kind: refund` in the commercial fact and SQL (`reversal.ts:477,493`). Thus actual void evidence is misreported in immutable reversal history and exported fact data. The same loss would affect a future supported chargeback producer.

**Fix steps**
1. Add validated reversal kind to `insertReversalRow` input and pass the authoritative `txn.reversal.kind`; use the same value in SQL and fact_log canonical object. Unknown evidence stays unknown rather than being invented as refund.
2. Keep kind out of the existing state/cumulative dedupe key per 080:2. On same-identity conflicting kind, retain the original and raise an evidence discrepancy instead of appending an inconsistent fact.
3. Completion: authoritative void/refund/chargeback/unknown remains the same in D1, fact_log and payment-history output. Historic incorrect rows require an explicit correction/audit procedure under R9, not direct mutation of append-only facts.
