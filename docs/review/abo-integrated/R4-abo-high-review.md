## A1 — P1: a parked rejection makes successful retry unrecordable

`abo/migrations/0004_grant.sql:11–19,50–60` permits exactly one immutable outcome per grant. `work/grant.ts:886–919` inserts a rejected/conflict outcome before parking. The supported operator recovery (`ops/index.ts:1965–1986`) only reopens work. After the cause is repaired, the platform may apply the grant, but success insertion (`grant.ts:819–846`) violates the existing primary key; its batch rolls back and catch silently releases the lease. Every later already_applied repeats this failure. The checkout remains Paid (`checkouts.ts:804–815`), reconciliation still sees the original rejection, and grant work can loop forever. FM-05 explicitly promises inspect/fix/retry. Concrete ordinary triggers include transient DO loss misclassified as rejected (platform finding) or granting a plan before publication then publishing it. High confidence, major because the documented financial recovery path cannot complete.

The same completion block has a distinct crash/concurrency expression of this root: stale worker A inserts outcome even when its lease-conditioned final UPDATE changes zero rows; the lease check is outside the committed batch (`839–842`). New worker B then cannot insert that existing outcome. A manual retry is sufficient to establish the defect; no runtime claim about RPC duration is needed.

Copy legacy applied/already_applied rows as terminal events and legacy conflict/rejected rows as nonterminal historical events (their old code was not stored), preserving original rows/fact hashes and work state; do not rewrite locked exports. Provide a `grant_outcome` compatibility view selecting the first terminal event if one exists, otherwise the latest event by `outcome_seq`. This preserves one effective row per grant without erasing rejected attempts.
2. Update paid and complimentary outcome writers (`grant.ts` and `ops.recordComplimentaryGrantRows`) to append to the new event table and log its immutable event identity. In paid work, append only via `INSERT … SELECT` guarded by the exact work id and current lease/token; fact-log insertion and done/parked transition must share the same batch and the same predicate. Stale workers produce no outcome/fact; matching existing terminal receipt completes current work idempotently. Add a random lease/attempt token on acquisition if using it as the unique attempt identity.

## A2 — P2: complimentary relay can record a different tenant/grant than the authorized mutation

`ops.handlePostComplimentaryGrant:2665–2689` accepts URL org and action_id separately from the envelope and forwards the envelope unchanged. Platform grants the envelope org/id (`entrypoint.ts:3301–3304,3427–3444`). Only afterwards ABO derives its own grant id from action_id (`2711–2718`) and persists URL org and derived id with the returned receipt (`2249–2318`), without matching the envelope or checking its receipt signature. A valid HP operation for org B/grant B sent through org A/action A therefore applies B and creates an ABO request/outcome attributed to A/grant A. This is an audit/lineage defect, not a claim of bypassing platform authorization. `grant.ts:789–807` verifies paid receipt cryptography but also never checks that signed grant_id/org/hash/result belong to its request. `verifyReceiptSignature` checks authenticated bytes only (`receipt.ts:158–181`), not schema or request linkage. High confidence, bounded P2; no hypothetical forged platform key is needed for the complimentary mismatch.

**Fix steps (implementation-ready; coordinate global grant-claim recipe):**
1. Before dispatch in `handlePostComplimentaryGrant`, compute expected id=grantIdComp(action_id); require envelope.org_id=URL org, envelope.grant_id=expected, source.kind=complimentary and source.ref=action_id. Reject a mismatch before platform mutation or writing a canonical grant outcome. Retain platform exact HP operation binding.
2. Add one ABO production receipt validator reused by `processGrantWork` and complimentary relay. Require shared `validateReceipt`, configured-key signature verification, grant_id/ org_id / envelope_sha256 equal the durable request, stored contract version equal its envelope, receipt.result=applied, nonempty valid term IDs and positive ledger_seq. For already_applied, accept the original receipt.result=applied; never rewrite the signed receipt. Validate installation against the platform durable claim introduced by the global identity fix when that claim is available; do not compare it with a potentially newer live installation after transfer.
3. Persist the validated complimentary request before dispatch (matching existing request hash on retry), then write a successful outcome only for a matching verified receipt. Unverified/missing/mismatched success goes to explicit parked recovery/AL-07 and never becomes grant_outcome success; repeated request/fact insertion must be conditional on actual insertion, not unconditional fact_log duplication (`2277–2318`). Use A1 outcome events for rejected attempts and terminal success.
4. Completion: cross-org, cross-action and swapped valid receipts cannot create successful ABO lineage; an ordinary matching paid or complimentary first apply/lost-reply replay retains the original signed receipt exactly, including installation and signature. Reconciliation 085:1 becomes an independent divergence detector rather than the first identity check.
