## Established perimeter and authority

| ABO→platform RPC | Service binding named VendorEntrypoint, configured per environment. Relays send `CHANNEL_VERSIONS.vendorEntrypoint`; HP relays pass original operation/assertion and Access JWT to platform. |

Both ABO channels currently N=1, accept `[0,1]`, reject missing or other versions before token/Access parsing. Normal versioned helpers echo negotiated version; access failures have the P2 exception below. Version telemetry is intentionally a best-effort asynchronous write even on unsupported versions; no domain dispatch follows a rejected gate. Header numeric parsing uses Number plus integer validation, not lexical decimal-only validation; no extra lexical restriction was established by the contract.

| Authority class | Actual ABO consumer |
| --- | --- |
| M | listOperatorCredentials and other registry reads use service binding without Access. Active registry is fetched for each local HP request. |
| H | All console dispatch first verifies Access; local lookups and control actions inherit that gate. Configuration H relays forward verified JWT for platform re-verification. R8 owns individual local H mutations. |
| HP local | publish_offer, retire_offer, reinstate_offer, release_payment, manual_chargeback, erase_contact: Access → operation validation/name/version/email → ±5-minute issued_at check → replay precheck → active passkey signature → unique replay insert → audit → mutation. Target binding is defective below. |
| HP platform | Credential register/revoke and configuration relays forward JWT, operation, assertion, signer credential id and selected method arguments. Platform is the authoritative re-verifier; sibling platform review owns full method binding. |
| Bootstrap | ABO does not grant a local bypass: registration relay may omit assertion, but platform alone chooses empty-table bootstrap and inserts pending +24h. Platform sibling owns concurrency of its count/insert boundary. |

ABO checks the Access issuer from ACCESS_TEAM_DOMAIN, signature against fetched certs (or explicit environment cert override), configured audience and expiry; additionally requires a nonempty signed payload JTI for audit. Email in the signed operation must equal the verified Access email. Active credentials are selected by platform, promoting due pending credentials before listing; ABO matches signatures by trying each active key/algorithm. The registry list intentionally omits operator_email: possession of any active key plus the same-call Access actor is the specified authority, not a per-email ownership restriction. No unsupported extra binding requirement is inferred.

WebAuthn verifies operation hash, exact HTTPS console origin and RP ID hash, get type, UP+UV, ES256/EdDSA signature. The replay table primary key prevents *two completed local mutations* from concurrent use of the same challenge: both may pass SELECT, but only one plain INSERT succeeds and all mutations follow that INSERT. The loser throws rather than returning assertion_used; no replay bypass was established. Freshness is checked before asynchronous credential retrieval, and revocation is a per-request snapshot; this review does not assert atomic revocation of in-flight requests. Replay consume, audit and business mutation are separate commits: a crash may burn a challenge without applying the action. R8/R9 must assess action recovery and audit accuracy, rather than assume this sequence is transactional.

## R2-ABO-01 — P1: local HP actions do not bind the signed target to the URL

**High confidence; implementation-ready.** Contract 04 §1.5 requires params to be the exact method input. `verifyHpRequest` receives subject but only uses it for refusal/audit; accepted checks at `abo/src/ops/index.ts:656–746` compare action/version/actor and verify the provided operation, never compare params to subject. `handleHpPost:1372–1403` passes the independently selected URL subject into execution. Release route `3411–3421` supplies releaseMatch[1], and `handleHpReleasePayment:1079–1159` reads and releases that payment without inspecting signed payment_id. Chargeback `3424–3434` similarly reaches `1161–1294`; erase `3437–3447` reaches `1323–1370`. Catalogue routes `3366–3409` reach `882–1077`, using the URL offer even though only changed price/text/copy come from signed params.

A real actor's unused, fresh assertion authorizing release of payment A can be sent first to payment B's release URL, with the same Access session and unchanged signed operation. If B is withheld and not fully reversed, B is released and grant work is queued. Equivalent retargeting can charge back another payment, erase another org's billing contact/evidence bodies, or publish/retire/reinstate another offer. No forged passkey or replay is required. The concrete preconditions are a valid same-actor Access session (including a stolen session), a fresh unused assertion legitimately generated for that actor/action, and first-use URL substitution before that assertion is consumed. No second touch is assumed. No shipped browser producer was found, so this demonstrates a receiver authorization defect for a correctly formed client submission, rather than a reproduced existing UI journey. Even where a compromised ABO is an accepted broad threat, an uncompromised receiver must enforce exact operation authorization.

**Fix steps:**
1. Add one local HP parameter validator called by `verifyHpRequest` before replay/signature acceptance. Define exact maps: publish_offer `{offer_id, price_minor, terms_text, copy}`; retire_offer/reinstate_offer `{offer_id}`; release_payment/manual_chargeback `{payment_id}`; erase_contact `{org_id}`. Require the named ID to be a string exactly equal to the route subject and the method-specific key set; preserve the existing content validation and current response codes. Return assertion_invalid before challenge consumption for mismatch.
2. Keep all mutation values derived from this validated signed map; adopt these ID names as the explicit receiver schema (they are a chosen remedy, not a verified existing browser-producer map). Supporting production-source searches found no browser ceremony producer in abo/src, frontend/lib, ai-platform/src or package production source; the complete ops dispatch returns JSON and wrangler defines no asset binding. R8 must provide the missing console ceremony required by spec 082 FR-001 and make it include exactly these ID/content fields before obtaining its challenge. Do not inject or rewrite a missing ID after signing. No compatibility bypass accepting unbound operations.
3. Preserve primary-key replay reservation before mutations. Completion: unchanged assertion for A sent to B produces assertion_invalid with no B mutation and no replay consumption; correctly bound A succeeds once; actor/action/version mismatches still fail. Cover all six action names and retry/concurrent reuse.

## R2-ABO-02 — P2: Access refusals lose the accepted console version

**High confidence; implementation-ready.** `abo/src/ops/index.ts:262–296` hardcodes `contractVersion = 1`; `handleOps:3303–3313` does not pass its negotiated contractVersion to that helper. At current N=1, an accepted request version 0 without valid Access returns header/body version 1, violating 04 §7.2's accepted-request echo. Any future version bump leaves the same hardcoded behavior. Impact is bounded error compatibility, not an authentication bypass.

**Fix steps:**
1. Add contractVersion parameter to verifyOpsAccess, remove constant 1, pass handleOps's already-negotiated value at its sole call.
2. Keep unsupported-version handling before Access. Completion: for each accepted console version, missing/invalid/cert-fetch failure/JTI-missing Access refusals return 401 with that version in header and body; unsupported/missing versions still return 400/current version/reload before Access.

## R2-ABO-03 — P1: the browser passkey ceremony has no production entry point or producer

**High confidence in missing source path; remedy not implementation-ready pending the bootstrap contract decision below.** Spec 082 FR-001 requires the ABO console to run WebAuthn get and construct the canonical operation. Production-source searches over `abo/src`, `frontend/lib`, `ai-platform/src` and `packages/vendor-contracts/src` (excluding testkit) find no `navigator.credentials` or `credentials.get` invocation. `webauthn.get` appears only in the verifier (`packages/vendor-contracts/src/webauthn.ts:147`); `operationChallenge` is exported/implemented by the package and used by platform verification, without a browser caller. Full `abo/src/ops/index.ts:3303–3825` dispatch serves JSON handlers and ends in 404; `abo/src/worker.ts:193–206,294–359` admits only `/ops/` paths and applies a custom contract header before all ops dispatch. `abo/wrangler.toml` points to this worker and has no asset binding/page handler. The tracked ABO source inventory has no browser page/module. The only HTML search hit under ABO source is the provider return page, which has no ceremony. These observations establish a source-level absent producer, not merely an undiscovered form element.

A real operator has no shipped browser entry point through which to obtain the required per-action assertion. The backend can verify externally prepared assertions, but the stated operator approval workflow cannot be performed by the production console. This is a core human-approval flow gap; full console forms and method UX remain R8 scope. No finding is made about tests or the excluded viewer.

**Recommended fix and explicit stop point:**

1. **Maintainer/architecture decision required before routing changes:** approve an Access-gated `GET /ops` HTML shell bootstrap exception, with all `/ops/*` JSON APIs remaining version-gated exactly as today; alternatively supply an approved page bootstrap contract. Recommendation is the narrow shell exception because an initial browser navigation cannot supply `Abo-Contract-Version`. Document that exception in 04 §§2.3/7 and the relevant perimeter/082 contract. This report does not authorize silently bypassing the existing universal ops version rule. Stop before changing host/path/version routing until the maintainer resolves that choice. ABO-01 and ABO-02 remain independently implementation-ready.
2. After approval, add a browser shell and ceremony module (recommended exact new paths `abo/src/ops/browser/shell.ts`, `abo/src/ops/browser/ceremony.ts`) and an explicit `GET /ops` handler wired in worker fetch **after host validation and Access verification**, before the JSON custom-header gate only for that exact method/path. Ensure `GET /ops/` and every other API path retain explicitly documented behavior rather than accidental prefix exceptions. Use source-bundled JS or an explicitly configured asset route whose Access policy is specified with the approved shell contract; do not introduce an unauthenticated API exception.
3. Add versioned authenticated `GET /ops/ceremony-context` in `ops/index.ts` returning the verified Access email, configured RP ID/origin, accepted console version, and active `{credential_id, alg}` metadata only (alg is required by the existing assertion decoder; omit public-key bytes). Obtain that metadata through the existing registry call; do not expose stored signing material or trust a caller-supplied actor. Initial empty-registry credential enrollment must use a separate documented bootstrap UI flow into the existing platform registration relay; it cannot pretend an assertion can be obtained from an empty allow-list.
4. In ceremony.ts use the frozen local schema from ABO-01 for all six actions, construct `{op, params, actor_email, issued_at, nonce, contract_version}` with exact target/content, calculate the package operationChallenge, convert its base64url bytes to `publicKey.challenge`, set RP ID and `userVerification: 'required'`, and call `navigator.credentials.get`. Preserve the selected operation unchanged through submission. Serialize response authenticatorData/clientDataJSON/signature as base64url strings with `alg` matching the selected active credential, so existing `decodeAssertion` consumes the exact signed bytes. Include `Abo-Contract-Version` on every JSON request; handle unsupported/reload before retrying a ceremony.
5. Provide a reusable preparation/submission interface for platform HP actions that accepts an explicitly validated method-argument map, signer credential ID and the applicable vendor channel version; use the same canonical challenge and byte serialization. Have R8 action forms supply the exact platform-defined maps, including nested grant envelopes/overrides where applicable; do not automatically reuse a console-version operation for a vendor-version method or rewrite a signed operation in the relay. R8 owns those forms and action-specific policy. Completion: an authenticated browser can open the approved shell, prepare each of the six local actions, touch the passkey once and submit exact signed bytes/target through the actual versioned handler; cancel/no UV/inactive credential/expired Access fail without mutation, and initial HTML handling cannot bypass API version/auth gates.

**Decision owner:** maintainer/architecture reviewer. The new-path names and narrow exception are the recommended design, not existing source or an already approved contract. This finding remains not implementation-ready until step 1 is resolved; no routing or application changes were applied.
