## O1 — P1: accepted operator actions can lose their mutation or transfer runner

High confidence, implementation-ready. Local HP verification rejects a used challenge (`abo/src/ops/index.ts:709–718`), while `commitAcceptedHp:750–771` consumes it and records accepted audit before the action runs. Release calls this before its payment_release/work batch (`1113–1145`); manual chargeback before reversal/work (`1212–1258`); erase before contact update/R2 deletes (`1346–1355`). A crash or failed mutation leaves accepted authorization but no resumable command; replay requires another touch and partial erasure can remain incomplete. Separately, beginTransfer mutates platform state first (`2988–2997`), then awaits audit (`3012–3021`) before creating the only ABO transfer work (`3023–3043`). A crash/lost successful reply/audit failure in that gap leaves the org in a transfer with no runner. The due runner only queries existing work (`3273–3282`). This is the ABO acceptance/handoff root; R4-PG3 owns platform complimentary acceptance, and R3-C5 owns reversal/payment fact-next-work batching. R2-P1 target binding must be fixed first; this finding does not count that authorization defect again.

**Fix steps**
1. Add an ABO accepted-operation table keyed by exact challenge SHA256, containing canonical operation, verified actor/credential, target, accepted contract version, action_id, stage, due/lease/result. For release/manual/erase, atomically insert it, assertion_used and accepted operator_action/fact_log. Retry under current Access with identical bytes resumes the stored command before applying freshness/used checks; changed bytes conflict. New commands retain current credential checks.
2. Execute local D1 effects in a lease-fenced batch with stage advancement. Release atomically rechecks `NOT EXISTS(full reversal)` and inserts release+grant work; manual atomically inserts reversal+fact+reverse work. Existing exact facts are success/recovery signals, never reasons to abandon missing work. Make audit delivery an outbox stage rather than gating the business action.
3. Persist a begin-transfer intent before platform dispatch, keyed by its verified operation challenge. Platform begin replay must return the same row after a lost reply (platform begin repair is a prerequisite); store transfer_id and insert transfer_step work in one ABO batch. Retry the original accepted bytes/version, never synthesize new authorization or a new destination. A bounded existing cron dispatcher resumes pending local/remote stages.
4. Erasure records remaining object deletions and completion (O2); D1 acceptance is not completion. Preserve original results and immutable commercial facts. Completion: interruption at acceptance, mutation, platform reply, audit or work insertion leaves either no consumed touch or a discoverable resumable command; every accepted transfer has one durable runner; retries do not regrant/reverse a different target.

## O2 — P2: erasure does not fence late provider-body writes

High confidence, implementation-ready. Erasure blanks every current contact version and deletes a one-time set of R2 keys (`1287–1320,1348–1355`), while a later valid callback writes raw body unconditionally (`abo/src/notify/intake.ts:364–374`), even for an existing old checkout. It can therefore restore payer contact values in the raw evidence prefix after successful erasure, without new contact entry. R2 write before D1 linkage also permits an orphan key if its later insert fails, beyond erasure's D1-selected key set. Checkout correctly refuses a latest erased contact (`checkouts.ts:172–186`), but that does not control asynchronous old evidence. Scope is data-erasure correctness, not an asserted legal retention rule; deployment bucket retention/Time Travel remains external/R9.

**Fix steps**
1. Persist a per-org erasure generation/fence independently of mutable contact versions, with a per-evidence raw-body registry keyed by notification/inquiry id, org and generation. Resolve old checkout/payment ownership before raw retention. Unknown-owner bodies stay quarantined under separately tracked keys and must be reclassified/deleted when ownership becomes known.
2. For each producer, first atomically claim raw retention against the org generation; erasure advances generation and enumerates claims, including pending claims. A producer uploads only to its claimed deterministic key, then rechecks/finalizes generation. A pre-erasure in-flight claim or erased-generation old-checkout callback must delete the raw object and retain only hash/normalized commercial evidence. Use a bounded cleanup outbox for failed deletes. Avoid embedding raw payer fields in immutable facts/outbox records.
3. New contact creation may permit raw retention only for new checkouts bound to the new generation; it must not reopen old checkout bodies. Update `notify/intake.ts`, `work/runner.ts` inquiry writer and `deleteTenantEvidenceBodies` together. Completion: callbacks arriving before/during/after erasure, and R2-success/D1-failure windows, cannot leave untracked retained payer bodies; commercial identifiers, hashes, payment/reversal facts and locked ledger remain intact.
