## Design

Routing rows live in the platform D1. The launch check already reads the platform through the ABO
`GET /ops/launch-state`, which calls the platform `readLaunchState`. That read-only path was extended; no new
write privilege, route, binding or method was added.

## Discovered issues

- `ops/launch/launch-live.test.mjs` is not run by `ops/launch/run_campaigns.py` (only `launch-check.test.mjs`
  runs), so its tests are not executed in CI. FR06's new tests are in `launch-check.test.mjs` for that reason;
  `launch-live.test.mjs` was updated but is unvalidated by CI.
- Scope choice: canary rows are included in the gate with published and active ones, because canary rows are
  served to their cohort. Superseded rows are excluded.

## Operator checklist

- Before launch, run the RM33 procedure for every id the launch check reports: quarantine the legacy
  `policy_id@version` row and republish it as a new digested version (RM33.md, items 2-3). The check passes
  when none remain.
- Deploy order: the ai-platform worker (new `readLaunchState` field) before the ABO worker and the operator's
  updated `ops/launch`; an old platform returns no field, which the launch check treats as not readable (fails).
