# FR03 — Operator submission of additional captures (FV-M3)

## Findings implemented

- FV-M3 (Major), closing FV-P1 (RM10 R3-C6 partial): `handlePostSubmitTransactionId` no longer returns 409
  because a checkout has any `paymob_txn` row. It refuses only when the submitted `txn_id` is already known.
  No fix step was deferred.

## Changed files and symbols

- `abo/src/ops/index.ts`, `handlePostSubmitTransactionId`:
  - Step 1: the check is now `SELECT checkout_id FROM paymob_txn WHERE txn_id = ?`; a known id (any checkout)
    still returns 409 `conflict`. New ids on checkouts with captures proceed to the unchanged confirm path,
    whose order binding still refuses a transaction not bound to this checkout's order.
  - Step 2: the `operator_action` row, its `fact_log` row and the `work` insert are one `env.DB.batch`. The
    existing `operatorActionStatements` already returns the prepared statements (`insertOperatorAction` is a
    wrapper over it), so no new sibling was needed. Other callers of `insertOperatorAction` are unchanged.
  - Step 3: the action label string is unchanged.
  - Step 4: `abo/src/work/runner.ts` is untouched; the tests show it handles the second capture.

## Tests added

All in `abo/test/system/ops.cross-worker.test.ts` (new helpers `submitOperatorTransactionId`,
`operatorSubmissionCounts`, `operatorActionFactCount`, `opsCheckoutWithCallbackCapture`):

- FV-M3: operator submission records a second capture on a checkout that already has one (check 1: two
  payments classified `normal` and `likely_duplicate`, two `paymob_txn` rows, grant work for both payments).
- FV-M3: resubmitting a known capture returns 409 and adds no action or work (check 2, including an id known
  for another checkout).
- FV-M3: a submitted id bound to another order records no payment on a checkout with captures (check 3).
- FV-M3: a failed work insert leaves no operator_action row behind (check 4, uses `setD1BatchThrows`; also
  asserts no orphan fact and that a retry then succeeds exactly once).
