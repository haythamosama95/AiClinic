## Operator checklist

Corrected procedure for staging and production (replaces the held-row recovery in RM01.md):

1. Apply migrations through `20261014170450_fv_m2_membership_role_repair_mapping.sql` only. Do not apply
   `20261014170500` or later yet.
2. Run the RM01 read-only reconciliation query and keep its output with the deployment record:

   ```sql
   SELECT m.user_id, m.organization_id, m.role AS membership_role, sm.role AS staff_role,
     (SELECT count(*) FROM ai_internal.membership m2 WHERE m2.user_id = m.user_id) AS membership_count
   FROM ai_internal.membership m
   JOIN public.staff_members sm ON sm.auth_user_id = m.user_id
   WHERE m.role <> sm.role
   ORDER BY m.user_id, m.organization_id;
   ```

   Rows with `membership_count > 1` where both roles are non-administrator, or where the membership is the
   org's only active administrator, are the held rows the repair will not settle by itself.
3. For each held row, the clinic's administrator and the maintainer agree a role. Insert one row per
   `(user_id, organization_id)` into `ai_internal.membership_role_repair_mapping` (`approved_role` must not be
   `administrator`; `approved_by` is required).
4. Apply `20261014170500_r1_sql02_membership_role_repair.sql` and all later migrations. If it still aborts with
   `MEMBERSHIP_ROLE_REPAIR_HELD_ROWS`, the message lists the rows still lacking a mapping; add them and apply
   again. The abort rolls back only the repair, and the mapping rows persist because they were inserted
   earlier.
5. Rehearsal (completion check 3, not automated): on a scratch database restored from staging, or seeded with a
   multi-org user whose membership and staff roles are both non-administrator and different, apply through
   `170450`, insert the mapping row, apply `170500`, and confirm the membership role equals `approved_role` and
   the migration does not abort. Then repeat without the mapping row and confirm it aborts with
   `MEMBERSHIP_ROLE_REPAIR_HELD_ROWS`.
