### Claims made in each doc (key architectural/business decisions)

**Cross-cutting (repeated across multiple docs)**
- Single Supabase instance is the entire backend; no custom API server.
- All domain writes via `auth_internal` SECURITY DEFINER RPCs; direct PostgREST mutations blocked by RLS.
- AI is a separate LAN HTTP service; never touches Supabase; commands require human approval.
- Shared-schema multi-tenancy: `organization_id` + `branch_id` + JWT-scoped RLS.
- Windows desktop Flutter client; no mobile in V1/V2.
- Staff authenticate with username (stored in GoTrue `email` field without `@`).
- Soft delete only; audit columns on all tables.
- Three deployment tiers; Tier 1/2 self-hosted Docker on receptionist PC; Tier 3 Supabase Cloud.
- Spec-driven, sequential feature delivery; backend before frontend; AI after V1 stable.

**Per-doc unique claims**
- **00-index:** Selective doc loading is intentional; avoid loading full architecture set unless task is architectural.
- **01-principles:** "Offline-first operation" is a guiding principle (A6: Tier 2 backup-only, not real-time sync).
- **02-system-overview:** Backend cannot distinguish AI-originated vs manual RPC calls.
- **03-deployment-networking:** Tier 3 write queuing on connectivity loss is V2+; clients can view cached data when LAN lost but writes blocked.
- **04-backend:** Edge Functions supplementary only; system must work without them (Tier 1/2 proof).
- **05-database:** Appointments are branch-wide slot conflicts (not per-doctor); `soap_notes` table name (not `visit_clinical_notes`); visit RPCs still listed as planned.
- **06-ai:** Sequential one-request-at-a-time inference; stateless agents; Phi-3 mini recommended on 8GB RAM.
- **07-frontend:** Full clean architecture with use cases; `auth_session_provider` is an exception using repos directly; `activeBranchProvider` drives branch-scoped refresh.
- **08-automation:** Engine runs in Flutter service layer polling `workflow_event_queue` — not yet implemented.
- **09-security-rbac:** Defense in depth: Flutter permission checks are UX-only, not security boundary.
- **10-resilience-and-scale:** Subscription never hard-locks; expired + offline → read-only mode after grace.
- **11-spec-driven-development:** Agents must not redesign architecture or alter schemas unless spec is being revised.
- **12-roadmap-phases:** V1-5 Visits and V1-6 Billing marked Complete; authoritative specs are numbered (`005-appointment-management`, `007-billing`) not only `specs/operations/*`.
- **13-glossary:** "Phone confirmation" required before check-in in V1-4.

## Agent: Frontend (2026-07-02)

### State management
Riverpod: `NotifierProvider`/`AsyncNotifierProvider`/family providers. Global `authSessionProvider` holds JWT-derived `AuthSessionContext` (staff, org, branchIds, activeBranchId, permissions). No separate `activeBranchProvider`. Realtime via `StreamProvider` pattern in appointment queue.

### Navigation
GoRouter + `ShellRoute`/`AuthenticatedShell`. `AuthRouteGuard` permission redirects per feature. Many routes still `uiPendingPlaceholder` (settings admin, billing, shifts, appointment hub/book).

### API integration
Supabase RPC only via `AppRpcInvoker` mixin → `RpcResult` composite. Concrete repositories per feature. Storage for visit attachments. No custom REST client.

### Offline/caching
Deliberately online-only for clinical data. `EmptyLocalStorage` (no cross-restart auth). Encounter child mutations deferred in `VisitEncounterDraft` until save/submit. Workspace mode + idle timeout + web deployment profile cached in SharedPreferences.

### UI architecture
Feature-first presentation with shared `core/ui` components (`AppButton`, `AppStepper`, `AppCard`, tokens). Visits use phase canvases (`encounter_phase_*`), safety rail, expert/guided toggle, rich-text Quill editors, catalog autocomplete.

### Business workflows (visits UI)
Appointment → create visit → `/visits/:id/document` → 3 editable phases + Summary → submit via `complete_visit`. Completed visits view-only until explicit edit mode. Patient safety, vitals (BMI derived client-side), investigations, treatment plans, attachments under Plan phase. Permission: `visits.edit_soap` + branch scope.

`07-frontend.md` ends at V1-4; missing visits/encounter workspace, setup feature, application layer, placeholder strategy, ForUI theming, and correct provider paths (`app/providers` not `shared/providers`). Claims universal clean-arch use-case pattern; code uses direct repo access in visits/appointments. Sidebar diagram overstates implemented nav.
