## Isolation Principle (Target)

The AI service is designed to be a fully isolated layer:

```
┌──────────────┐      HTTP       ┌──────────────┐
│   Flutter     │◄──────────────►│  AI Service   │
│   Frontend    │  JSON request  │  (Ollama +    │
│               │  JSON response │   HTTP API)   │
└──────┬───────┘                 └──────────────┘
       │                                │
       │ Supabase SDK                   │ NEVER connects
       ▼                                │ to Supabase
┌──────────────┐                        │
│  Supabase    │◄───── no connection ───┘
│  Backend     │
└──────────────┘
```

- The AI service would have NO database credentials and NO Supabase URL/keys.
- The AI service would receive prompts and optional context from the Flutter app, and return structured JSON commands.
- The backend would see all requests as normal Supabase SDK calls from Flutter, with zero awareness of whether a human or an AI-approved command originated them (same RPC surface either way — see `docs/architecture/02-system-overview.md`).

## AI Service Architecture (Target)

### Runtime

- **Ollama** as the inference runtime (llama.cpp-based, CPU-only, GGUF model format).
- A thin **HTTP wrapper service** in front of Ollama would provide domain-specific system prompts, request routing, structured output parsing, and local file logging (no DB).

### Deployment (Target)

- Would run on the receptionist PC as a system service or Docker container, listening on a configurable LAN port (default `8090`, per `docs/architecture/03-deployment-networking.md`).

### Resource Constraints (Target)

| Constraint            | Specification                                                                         |
| --------------------- | --------------------------------------------------------------------------------------- |
| Max RAM for AI models | 3 GB (on 8GB systems), 4 GB (on 16GB systems)                                         |
| GPU                   | Not required. CPU inference only.                                                     |
| Context window        | Limited. No long-term memory, no cross-session context.                               |
| Model size            | 1B–7B parameter quantized models (Q4/Q5 GGUF)                                         |
| Concurrent requests   | Sequential processing. One request at a time per agent.                               |

### Recommended Models (Target, CPU, 8GB RAM)

| Use Case                           | Model Class                   | Approx RAM  |
| ---------------------------------- | ------------------------------ | ----------- |
| Intent parsing, command generation | Phi-3 mini (3.8B, Q4)          | ~2.5 GB     |
| Clinical-note summarization        | Phi-3 mini or Mistral 7B (Q4)  | ~2.5–4 GB   |
| Analytics query generation         | Phi-3 mini (3.8B, Q4)          | ~2.5 GB     |

## Internal Agent Model (Target)

| Agent                | Responsibility                                  | Output                                                                                                     |
| -------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **Scheduling Agent** | Appointment booking, rescheduling, cancellation | `create_appointment`, `reschedule_appointment`, `cancel_appointment`, `update_appointment_status` commands |
| **Billing Agent**    | Invoice generation, payment recording           | `create_invoice_from_visit`, `record_payment` commands                                                     |
| **Clinical Note Summarizer** | Draft clinical-note text from free-text description | Structured `visit_clinical_notes` JSON (complaint/history/examination/diagnosis/plan) — the target for this agent shifted when 013-visits replaced the SOAP model with the current five-field clinical note; do not design this agent around `subjective/objective/assessment/plan` field names |
| **Analytics Agent**  | Answer operational questions                    | Pre-defined analytics query identifier + parameters (analytics itself does not exist yet either — see `docs/architecture/12-roadmap-phases.md`) |
| **Shift Agent**      | Shift scheduling assistance                     | `create_shift`, `modify_shift_assignments` commands                                                        |

### Agent Routing (Target)

Two-step process: (1) intent classification (keyword/pattern router or lightweight model call) → (2) agent execution with a domain-specific system prompt.

## Structured Command Protocol (Target)

All AI outputs would follow a strict JSON schema. The AI service would never return free-text for actionable operations.

```json
{
  "command_type": "create_appointment",
  "confidence": 0.92,
  "params": {
    "patient_name": "Ahmed Hassan",
    "doctor_name": "Dr. Ali",
    "date": "2026-05-14",
    "time": "17:00",
    "type": "planned"
  },
  "display_summary": "Book Ahmed Hassan with Dr. Ali tomorrow at 5:00 PM",
  "requires_resolution": {
    "patient_id": "lookup_required",
    "doctor_id": "lookup_required"
  }
}
```

The Flutter app would: receive the command → resolve `lookup_required` fields → show a confirmation card → on approval, call the same `supabase.rpc()` used by manual UI actions → on rejection, discard.

## Context Strategy (Target)

AI agents would be stateless; context assembled per-request by Flutter:

| Context Type                        | Source                                  | Example                              |
| ------------------------------------ | ----------------------------------------- | --------------------------------------- |
| Current branch                      | Flutter app state (`activeBranchProvider`) | `branch_id`, `branch_name`           |
| Current date/time                   | System clock                            | `2026-05-14T17:00:00+02:00`          |
| Active patient (if in patient view) | Flutter UI state                        | `patient_name`, `patient_id`         |
| Doctor list (for the branch)        | Pre-fetched from Supabase, passed to AI | `[{"name": "Dr. Ali", "id": "..."}]` |
