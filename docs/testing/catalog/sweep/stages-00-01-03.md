### Finding SW-00-01 — S00-010 is a tautological test that exercises no code

- **Scenario:** S00-010 (CONFIG_CACHE_TTL_MS unset/empty/invalid → 30 000 ms default).
- **Test:** `ai-platform/test/e2e/stage-00-boot-bindings-routing.test.ts:376-402`.
- **Catalog expectation:** "All four variants resolve to `30_000`
  (`DEFAULT_CONFIG_CACHE_TTL_MS`): unset/empty short-circuit; `Number.parseInt("abc")`
  is `NaN`; negative parses are rejected by the `< 0` guard" — i.e. observe the value
  `configureIsolateConfigCache` installs, per variant.
- **Actual test assertion:** the loop asserts `expect(variant.expectedTtlMs).toBe(30_000)`
  — a constant equal to itself, mirroring the catalog table. The only code touch is
  `expect(typeof isolateConfigCache.getTtlMs()).toBe("number")`, which does not assert
  the value (the live pool isolate is booted with `"100"`, so `getTtlMs()` returns 100,
  not the 30 000 under test). The test passes even if `resolveConfigCacheTtlMs` is
  deleted or returns garbage.
- **VERDICT:** WEAK TEST (tautological). **SEVERITY:** med.
- **Evidence:** `stage-00-boot-bindings-routing.test.ts:391-401`;
  `ai-platform/src/config-cache/index.ts:31-40` (the unexercised resolver);
  `ai-platform/test/config-cache.test.ts:80-90` (a unit test already imports
  `resolveConfigCacheTtlMs` directly from src and covers exactly these variants).
- **Fix brief:** The harness-gap note ("`resolveConfigCacheTtlMs` not exported") is only
  about the frozen barrel — the barrel itself re-exports straight from
  `../../../src/...` (`harness/index.ts:152-153`), and the unit suite imports the
  resolver directly. Import `resolveConfigCacheTtlMs` from
  `../../../src/config-cache` in the e2e file and assert all four variants
  (`undefined`, `""`, `"abc"`, `"-50"`) return `30_000`. Also assert
  `isolateConfigCache.getTtlMs() === 100` to pin the pool's configured TTL. Delete the
  constant-equals-constant loop.

### Finding SW-00-02 — S00-032 third arm: catalog's expected error message is unreachable

- **Scenario:** S00-032 (build gate rejects malformed manifest), third example only.
- **Test:** `ai-platform/test/e2e/stage-00-auth-schema-cron-happy.test.ts:445-455`.
- **Catalog expectation:** adding a `Routing.provider` key throws "`Manifest must not
  name provider or model at manifest.Routing.provider`".
- **Actual test assertion:** `loadManifest(namesProvider)` throws
  `"Malformed manifest group: Routing"`.
- **Verification:** `validate()` runs per-group exact-key validation first —
  `assertExactKeys` throws `Malformed manifest group: Routing` for any extra key
  (`ai-platform/src/manifest/index.ts:223-227`, via `validateObjectGroup` :264-274);
  the provider/model naming ban runs afterwards over the whole tree
  (`assertNeverNamesProviderOrModel(json, "manifest")` at :584). So for a top-level
  `Routing.provider` key the naming-ban message is unreachable. The architecture pins
  the *rule* ("Routing must not name a `provider` or `model` directly",
  `implementation-references/01-band-a-implementation-reference.md:216`) but no message
  or ordering; the rejection still happens, so the code is compliant.
- **VERDICT:** CATALOG WRONG (test is correct). **SEVERITY:** low.
- **Note:** this deviation was a documented fixer note (`reports/stage-00.md` §5.4) but
  never landed in `stage-00-conflicts.md` and was not adjudicated in
  `implementation-audit-findings.md`; recorded here for the catalog text sweep.
- **Fix brief:** Edit the S00-032 catalog text: the `Routing.provider` example throws
  `Malformed manifest group: Routing` (exact-key validation precedes the naming ban).
  If the naming-ban message is worth pinning, change the fixture to smuggle the key
  inside an allowed nested object (e.g. under `Routing.requiredProviderFeatures`) so
  `assertNeverNamesProviderOrModel` is what fires. No code or test change needed.

### Finding SW-00-04 — S00-030/031 re-implement the build gate instead of running it

- **Scenarios:** S00-030, S00-031 (manifest-tree build gate).
- **Test:** `ai-platform/test/e2e/stage-00-auth-schema-cron-happy.test.ts:107-131`
  (stand-ins), `:385-428` (tests).
- **Catalog expectation:** "load every `manifests/published/*.json` through `load()`,
  compute `hashManifest` over each raw file, and assert each … entry against
  `published-registry.json` via `verifyManifestTree`."
- **Actual test assertion:** `loadManifest` is real, but the hash is a local
  canonical-stringify SHA-256 stand-in (`hashCanonical`) and the registry compare is a
  local re-implementation (`verifyPublishedRegistryEntry`). The real
  `verifyManifestTree` / `verifyPublishedRegistry` / `hashManifest`
  (`src/manifest/index.ts:630-698`) are never executed, so a regression inside them
  (path handling, error text, iteration) would not be caught. Risk is blunted because
  the stand-in hash is anchored to the committed registry hash (which the real
  `hashManifest` produced), so the canonicalization is pinned.
- **VERDICT:** WEAK TEST (stand-in for the unit under test; documented harness gap).
  **SEVERITY:** low.
- **Evidence:** `stage-00-auth-schema-cron-happy.test.ts:107-131`;
  `reports/stage-00.md` §6 (documented gap); `ai-platform/src/manifest/index.ts:630-698`.
- **Fix brief:** Re-export `verifyManifestTree` and `hashManifest` from
  `../../../src/manifest` through the harness barrel (same pattern as
  `harness/index.ts:152`), then call the real gate for the accept case. For S00-031,
  keep the in-memory tamper but compare via the real `hashManifest` and assert the
  real `verifyPublishedRegistry` throw. This turns a stand-in into a true gate test.
