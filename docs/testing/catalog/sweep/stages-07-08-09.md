#### 1.1.1 S07-052 — stale-after-entitle test re-seeds the cache it claims to observe

- **Test:** `ai-platform/test/e2e/stage-07-etag-cache.test.ts:558-571`
- **Catalog expectation:** "(a) HTTP 200, body `{"manifests":[]}` — entitle writes
  D1 and **does not bust the isolate cache**, so the stale pending entitlement still
  yields the empty list" (`stage-07-discovery.md` S07-052).
- **Actual assertion:** after the raw-`controlFetch` entitle, the test runs a retry
  loop (up to 8 attempts) that calls `isolateConfigCache.remember("entitlements", …,
  pendingRow)` to **re-insert the stale row itself** before each GET, breaking only
  when the GET returns empty.
- **VERDICT:** WEAK TEST. **SEVERITY:** MEDIUM.
- **Evidence:** loop + `remember` at
  `ai-platform/test/e2e/stage-07-etag-cache.test.ts:558-571`; the worker's entitle
  path contains no cache clear (no `isolateConfigCache`/`clear` reference anywhere
  under `ai-platform/src/control/`; isolate-cache consumers are only `worker.ts`,
  `discovery/index.ts`, `journal/index.ts`, `config-cache/index.ts`). Not recorded
  in `stage-07-conflicts.md` (only S07-051 is).
- **Fix brief:** The catalog's mechanism claim is true in code (entitle never
  touches `isolateConfigCache`), but the test cannot catch a regression: if entitle
  started clearing the cache, the loop's `remember()` would still force a pass.
  Drop the loop; warm once, entitle via raw `controlFetch`, then assert the very
  next GET is served stale **without** any test-side `remember()` (assert
  `isolateConfigCache.consult("entitlements", id)` still returns the pre-entitle
  row immediately after entitle — that is the actual catalog claim). Keep the
  post-`clearConfigCache()` listed assertion.

#### 3.1.1 S09-066 — admitted-replay test's core assertion is dead code; catalog text is pre-C-04 stale

- **Test:** `ai-platform/test/e2e/stage-09-admission-journal-compose.test.ts:340-390`
- **Catalog expectation:** "the worker maps both `admitted` and `completed` prior
  states to this synthetic completion" — replay of an in-flight (`admitted`) prior
  emits a synthetic `completed` terminal event (`stage-09-the-guard.md` S09-066).
- **Actual assertion:** `readSseUntil(secondResponse, (seen) => seen.some(e =>
  e.event === "accepted"))` **stops reading the moment `accepted` arrives**
  (helper at L223-251), so `events.find(e => e.event === "completed")` can never
  succeed and the subsequent `if (completed) assertSyntheticCompleted(…)` block is
  unreachable. The test pins nothing about what follows `accepted` on an
  in-flight replay.
- **VERDICT:** WEAK TEST (primary) + CATALOG WRONG (secondary). **SEVERITY:**
  HIGH (test) / LOW (catalog).
- **Evidence:** `ai-platform/src/worker.ts:809-812` — the `admitted` branch of
  `replayIdempotentTerminal` explicitly returns **without** fabricating a terminal
  event (leaves the stream open), i.e. remediation C-04 ("never fabricate
  completion for non-terminal prior states", `remediation-plan.md`) **is**
  implemented at HEAD (commit `4ce84128`, remediation wave 1). This also means the
  prior audit's BUG-02 premise ("C-04 NOT IMPLEMENTED, worker.ts:804 replays
  `admitted` as `completed`") is outdated at HEAD — flagged here as context, not
  re-litigated. Not recorded in `stage-09-conflicts.md`.
- **Fix brief:** Rewrite the test to keep reading past `accepted` for a bounded
  window (or until a short idle timeout) and assert that **no** terminal event
  arrives while the prior is `admitted` — that is the C-04 behavior the catalog
  should now describe. Update the catalog S09-066 text: replay of an `admitted`
  prior re-emits `accepted` and leaves the stream open; only `completed`/
  `failed` priors get the synthetic terminal. As written, the test would pass
  under both the buggy pre-C-04 behavior and the fixed behavior — it protects
  nothing.
