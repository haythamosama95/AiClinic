# Implementation Plan — Patients page (web-reference → Flutter port)

Spec target: port the **Patients** page at `web-reference/src/pages/app/patients/` into the Flutter `frontend/` feature layer, surfaced as the `/patients` route (V1-3). Scope per request: **everything except the patient detail page** (the `PatientDetailPage.tsx` opened when a user clicks a row). Split into **3 phases**.

This is a feature-page port (like `login-page-implementation-plan.md` / `settings-page-implementation-plan.md`), not a Dev components-showcase group — so there is **no** `component_registry.dart` / `component_section_builders.dart` work. All new widgets live under `frontend/lib/features/patients/presentation/` and wire to the existing patient domain/data backbone (search_patients / check_patient_duplicates / create_patient / archive_patient RPCs).

## 0. Ambiguities & Design Decisions (resolve before coding)

> ⚠️ **Set-specific runtime regressions.** This page embeds `AppSearchInput`, `AppDataTable` (Syncfusion grid), `AppDialog` overlays containing `AppTextInput`/`AppPhoneInput`/`AppSelect`/`AppDatePicker`/`AppTextarea`, `AppPopover`-backed popovers (select/date-picker/filter menu), `MenuAnchor`-based row context menu, debounced RPC search, and a motion enter/identity-preview `AnimatedSwitcher`. Before coding, confirm the group-specific regressions to avoid (consult `docs/ui/memory/ui-runtime-errors.md` only when explicitly instructed):
> - **#1 / #5** — `AppDialog` shells inputs inside a `DecoratedBox`; the input controls already wrap with `appWrapMaterialInput`/`appCenterInputField`. Do **not** re-shell them in another custom `DecoratedBox` without a `Material` ancestor (the identity-preview banner + branch banner are `DecoratedBox` shells that sit **above** the form fields — they are display-only, no `TextField`, so they are safe; just do not nest a bare `TextField` in them).
> - **#2 / #10 / #12 / #13** — the page rebuilds on every search keystroke and the Add Patient dialog rebuilds on every field change. `AppSelect`/`AppDatePicker`/`AppPopover` (filter menu) open overlays; the popover refresh/detach guards in `app_popover.dart` already cover rebuild-during-open. Do not bypass them by mutating overlay state synchronously from `didUpdateWidget`; route filter/search updates through the notifier (debounced) and let the overlay settle.
> - **#3** — `AppDatePicker` formats with explicit locale for AR. `ensureIntlDateFormattingInitialized()` must run at app startup (already wired — verify still called from `main.dart`).
> - **#4** — the Add Patient form uses a `FocusScope`/`onSubmit` for Enter-to-submit and `autoFocus` on the first field. Keep a `FocusNode` on the `TextField` only; never share a node between an ancestor `Focus` and the field. Dispose nodes in `dispose`.
> - **#8 / #30** — the patients page body sits in `AppShell` → scroll view → `Column`. Use `CrossAxisAlignment.start` (not `stretch`) and guard the `Column` with `mainAxisSize: min` + `LayoutBuilder` so the outgoing page does not crash during route transition when the shell passes unbounded height (memory #30 — `fillViewport`/`effectiveFillViewport`).
> - **#23** — the row context-menu trigger and the "Clear all"/"Clear filters" affordances live inside `AppDataTable`/`DecoratedBox` shells; wrap each actionable control in `Material(color: transparent)` (or drive hover with `MouseRegion`+`AnimatedContainer`). The `MenuAnchor` for the row context menu needs a `Material` ancestor.
> - **#11** — do not put `Tooltip`/`MenuAnchor` inside `AppSelect`/`AppDatePicker` popover children.
>
> Memory "Checklist for new input components" items 1, 4, 5, 6, 7, 8 apply to every Add Patient form field. Items 1, 4 of the shell/placeholder checklist (#28/#30) apply to the page column + transition.

Other decisions:

1. **forui vs native Material** — native Material only; `forui-wrappers.md` is superseded (same as the inputs-forms / settings plans). All controls reuse the shipped `App*` widgets; no `forui` import.
2. **File layout** — feature-page tree under `frontend/lib/features/patients/presentation/`:
   - `pages/patients_page.dart` — the `/patients` route widget (header + list controls + table + pagination + empty/no-results states; hosts the Add Patient dialog).
   - `widgets/patient_list_controls.dart` — the controls bar (search + sort dropdown + last-visit filter popover + active filter chips + clear-all).
   - `widgets/patient_active_filters_bar.dart` — the active-filter chip strip (web `ListControlBar` `activeFilters` region).
   - `widgets/patient_row_context_menu.dart` — `MenuAnchor`-based row actions menu (Open / Edit / Book appointment / Deactivate).
   - `widgets/patient_table.dart` — the `AppDataTable` wrapper with the supported columns + row click + row context menu.
   - `add_patient/add_patient_dialog.dart` — the registration dialog (web `AddPatientDialog` + `useAddPatientRegistration`).
   - `add_patient/add_patient_form_fields.dart` — the form body (web `AddPatientFormFields`).
   - `add_patient/duplicate_patient_dialog.dart` — the duplicate confirmation dialog (web `DuplicatePatientDialog`).
   - `providers/patient_registration_notifier.dart` — page-local Riverpod notifier mirroring web `useAddPatientRegistration` (values/errors/submitting/duplicate flow), driven by `checkDuplicates` + `createPatient` use case providers.
   - `providers/active_branch_name_provider.dart` — provider resolving the active branch display name (`listBranchesUseCaseProvider` → find `activeBranchId` → `name`) for the "Registering at <branch>" banner.
   - `models/patient_registration_form.dart` — the form values model + validation (`validateAddPatientForm` analog) reusing `PatientFieldValidation`.
3. **Per-request ignore rule** — the user instructed: *"If the web reference implements a label or a text field that is not supported by the patients feature, ignore it."* Drop web surface that the backbone (domain `PatientListItem` / `PatientListFilters` / `search_patients`) cannot populate:
   - **Table columns** — drop **email** (no `email` on `PatientListItem`) and **Status** (no `status` on `PatientListItem`); drop the **MRN** subtext in the Patient cell (no `mrn`). Keep: Patient (avatar + `fullName`), Phone, DOB, Last visit.
   - **Status filter** — the web `FilterMenuPanel` "Status" section (`all/active/inactive/archived`) has **no backbone filter** (`search_patients` has no status param). **Ignore it.** Instead, surface the backbone's supported `PatientLastVisitFilter` (`any/last30Days/last90Days/over90Days/never`) as the filter menu section ("Last visit") so the filter affordance is meaningful and wired.
   - **Sort** — drop `dob-asc`/`dob-desc` (no DOB sort field in `PatientSortField`). Keep the 4 supported: `name-asc`, `name-desc`, `lastVisit-desc`, `lastVisit-asc`.
   - Add Patient form fields (`fullName`, `phone`, `dateOfBirth`, `gender`, `maritalStatus`, `notes`) are **all** supported by `CreatePatientInput` → none ignored; reproduce verbatim.
4. **Pagination** — web slices the in-memory `filtered` array client-side with `page`/`pageSize`. The backbone paginates **server-side**: `patientListProvider` calls `searchPatients(limit: filters.pageSize, offset: filters.offset)` and returns a `PatientSearchPage` with `totalCount`. `AppPagination` binds to `PatientListUiState.totalCount` + `filters.page`/`pageSize`; changing page/pageSize calls `notifier.applyFilters(filters.copyWith(page: …))`. Default `pageSize = 10` (web) by seeding `PatientListFilters(pageSize: 10)` in the page; `AppPagination.pageSizeOptions: [10, 25, 50]`.
5. **Search debounce** — `AppSearchInput` already debounces `onValueChange` (300 ms, configurable `debounceMs`). The page wires `onValueChange` → local filter patch → `notifier.applyFilters`. Do not roll a second debounce layer.
6. **Initial filters** — the page reads `patientListProvider`'s `state.filters` as the single source of truth; local UI state patches a copy and calls `applyFilters` (which reloads from the RPC). The notifier already rebuilds on `authSessionProvider.activeBranchId` change, so branch switches refresh the list.
7. **Active branch name** — `authSessionProvider` exposes `activeBranchId` only (no name). Add `activeBranchNameProvider` (FutureProvider) using `listBranchesUseCaseProvider` to look up the `BranchListItem.name` for `activeBranchId`. Unresolved → fall back to "your active branch" (matches web fallback intent). Used in the Add Patient banner ("Registering at <branch>").
8. **Duplicate flow** — web `findPatientDuplicates` runs client-side over `MOCK_PATIENTS`; the backbone runs `checkDuplicates` over the DB via `check_patient_duplicates` RPC. The registration notifier calls `checkDuplicatesUseCaseProvider`; on candidates → open `DuplicatePatientDialog`; "Register anyway" sets `acknowledgeDuplicate: true` and re-calls `createPatient`. "Open" opens the existing patient (Phase 3 wires `AppNavigator.pushPatientDetail`).
9. **Toast on success** — web `toast({variant:'success', message})`; Flutter → `appToast(context, AppToastInput(variant: success, message: …))` (requires `AppToastHost` ancestor, mounted at app root — verify present).
10. **Reduced motion** — enter page animation + identity-preview `AnimatedSwitcher` + duplicate dialog all gate on `AppMotion.prefersReducedMotion(context)`.
11. **AR / i18n** — EN-only copy for this port (matches shipped auth/settings features). `AppDatePicker` already consumes locale for AR glyphs when the dev preview locale flips; the page itself is direction-agnostic via `Directionality.of(context)`. AR strings land with the future l10n milestone (§6).

## 3. Phasing

> Rationale: **Phase 1** = the read-only patients list a user can browse, search, sort, filter (last-visit), and paginate — wired to `patientListProvider` (server-backed) and the router; the table + controls + empty/no-results states all land. **Phase 2** = Add Patient registration: dialog form (all 6 fields), validation, identity preview, branch banner, toast — direct create via `createPatientUseCaseProvider` (the duplicate interception path is deferred to Phase 3; Phase 2 submits `acknowledgeDuplicate: false` and surfaces a returned duplicate warning as a generic `_form` error until the dialog lands). **Phase 3** = the duplicate detection flow (`checkDuplicates` + `DuplicatePatientDialog` + "Register anyway" + "Open existing patient") + the row context menu (Open/Edit/Book appointment/Deactivate → `archivePatientUseCaseProvider`) + reduced-motion animation polish. Each phase is independently shippable: after Phase 1 the list works; after Phase 2 a patient can be registered; after Phase 3 duplicates are caught and rows have actions.
