### 2.2 Reconciliation decisions

1. **P5 and P7.2 are one virtual-host transport work item, with a staged
   assertion.** P5 has repeated 404 evidence plus exact source causality.
   P7.2 has identical source construction but its helper omitted the status from
   the timeout. Implement the shared test-only authority-preserving transport,
   then require a focused P7.2 probe to prove the hypothesis. Do not claim the
   P7.2 archive alone proves 404.
2. **P7.3 is independent of the P5/P7.2 readiness diagnosis.** It registers an
   issuer before it reaches the ABO readiness check. The `access.test` DNS
   failure therefore blocks P7.3 first. It also explains the Flutter
   contract-matrix preparation failure. Fix or instrument that mock boundary
   before using P7.3 as virtual-host evidence.
3. **The P5 cleanup recommendation in the older plan is already superseded.**
   P5 current code has a rollback scope, child diagnostic tails, and restart
   cleanup. Do not rewrite it merely to repeat that work. P7.2 still needs the
   equivalent rollback and better readiness diagnostics.
4. **Frontend classification and fake failure are independent.** The live
   signed-out paths demonstrate a bad user-facing classification: appointment
   settings and patient search after `signOut()` both expect `FORBIDDEN` and
   actually receive `RPC_NOT_CONFIGURED` in both runs. The fake `auth` getter
   prevents three unit tests from reaching any mapper branch. The implementation
   must retain a way to test an authenticated `42501` as a configuration error
   while testing each signed-out path as `FORBIDDEN`.
5. **The ABO storage error and AI settlement failures are different classes.**
   The former includes an `SQLITE_IOERR`/isolated-storage teardown failure and
   passed in the comparison run. The latter has ordinary missing/null journal
   fields, no stored-error marker, and a direct fixed-delay race. Do not apply
   retries or storage cleanup changes as a substitute for semantic AI polling.

### 2.3 Guardrails

* Keep ABO production dispatch based on request authority. Do not make it trust
  an independently supplied `Host` header to accommodate local tests.
* Keep Supabase/PostgreSQL authorization authoritative. Do not add `anon`
  execute grants or turn an authenticated deployment/grant defect into
  `FORBIDDEN`.
* The plan introduces no service or architecture. It follows the constitution's
  layer boundaries and preserves backend authority, tenant isolation, and
  auditability.
* Keep test changes request-specific and bounded. A timeout must identify the
  request or startup phase that failed.
